# Governance and evaluation in production — explained

## The intuition
With a local model, behaviour can change with *no* code change: someone runs `ollama pull`, `fake-model:latest` points at new weights, answers shift silently. Governance puts model changes under the same discipline as code changes.

`governance.py` implements five. **Pin**: `models.lock.json` records each model's name *and digest*; `pin_check()` refuses to start on a mismatch. **Gate**: a candidate model is run through lesson 12's golden set (per-case regressions, not just pass rate) and lesson 16's red-team suite; `decide_upgrade()` — code, not a person or a model — computes ACCEPT/REJECT. **Drift**: without labels, a chi-square test compares the category mix of current traffic (or replayed outputs) with a reference, alarming at α = 0.01. **Audit**: every event is a row whose hash includes the previous row's hash, so editing any row breaks the chain. **Retention**: prompt *content* older than 30 days is deleted; the hash chain stays.

Analogy: a hashed lockfile, CI, monitoring and an append-only change log.
Where the analogy breaks: a model's behaviour is only *measured*, on the cases you included.

```
startup ─▶ pin_check(lock vs server digest) ─mismatch─▶ refuse
candidate ─▶ evaluate_candidate(): golden set (regressions?) · red team (all safe?) · replay drift
          ─▶ decide_upgrade() ─▶ ACCEPT / REJECT ─▶ fill_record() ─▶ upgrade-record.md
traffic ─▶ chi-square(category counts vs reference) ─▶ alarm?
events ─▶ audit(seq, …, prev_hash, hash)   retention: DELETE old content, keep audit rows
```

The one thing to remember: treat a model like a dependency — pinned by digest, upgraded only through a gate that code decides.

## Walkthrough: what actually happens when you run it
1. **You run** `python governance.py` (it starts its own L400 fake server so it can re-tag a model). I ran it on a copy of the lab folder because it rewrites the shipped `upgrade-record.md`; the regenerated file was byte-identical (same md5) to the shipped one.
   **What you see:**
   ```
   pin check at start   : OK
   pin check after pull : ['fake-model:latest: pinned 1f49242847a4, server has 52d1337ffaca']
   ```
   **What it means:** this is the failure lab. `server.retag` simulated a re-pull; the alias now points at v2. Without a digest pin nothing in the app's logs would show it — but t14 ("I need it immediately") silently changes from high to normal priority (`test_failure_lab_unpinned_alias_changes_answers`).

2. **Same run**, the upgrade evaluation.
   **What you see:**
   ```
   {"pinned": "fake-model", "candidate": "fake-model:v2", "passed": 19, "total": 20, "pass_rate": 0.95, "regressions": ["t14"], "gate_reasons": ["regressions vs baseline: ['t14']"], "redteam_safe": 8, "redteam_total": 8, "drift_chi2": 3.92, "drift_df": 1, "drift_alarm": false}
   decision: REJECT
   ```
   **What it means:** 95% meets a pass-rate bar, the red team is 8/8 safe, output drift (3.92 on 1 degree of freedom) is below the α = 0.01 critical value (about 6.63) — and the candidate is still rejected because one case that used to pass now fails.

3. **Same run**, input drift.
   **What you see:**
   ```
   input drift, same mix      (chi2, df, alarm): (0.0, 4, False)
   input drift, shipping surge (chi2, df, alarm): (45.71, 4, True)
   ```
   **What it means:** 5 categories → 4 degrees of freedom; 45.71 is far above the critical 13.277, so a shipping surge alarms. Drift says "traffic changed, re-evaluate" — it does not say whether answers are wrong.

## The decision
4. **Options and evidence.** Manual spot checks — rejected (lesson 12's broken prompt passed 3/3, and a re-tag is invisible without a pin). Pass-rate gate alone — rejected: try-it 1 below shows it ACCEPTs v2. Pin + regression gate + red team + drift + audit — chosen.
5. **Why ADR-0021.** Each brief constraint maps to one control: pin, gate, drift, audit + retention. Recorded cost: after 30 days investigations see who/what/when, not the prompt.
6. **Fitness function.** `test_fitness_governance.py` asserts: lock matches server; v2 REJECT and an equivalent candidate ACCEPT; surge alarms; audit verifies, then detects one edited row.
   ```
   test_controls_hold (test_fitness_governance.FitnessGovernance.test_controls_hold) ... ok
   test_gate_blocks_a_regression_that_the_pass_rate_hides (test_governance.Governance.test_gate_blocks_a_regression_that_the_pass_rate_hides) ... ok
   ```

7. **You run** `python agent_assist.py` (the model drafts the record's Context paragraph).
   **What you see:**
   ```
   unknown numbers: []
   tampered draft unknown numbers: ['100', '0']
   ```
   **What it means:** code checks that every number in the draft appears in the measured report; a draft claiming "100%" and "0 regressions" is caught. The Status line is computed by `decide_upgrade()`, never written by the model.

8. **You run** `python -m unittest -v test_try_it_21`.
   **What you see:**
   ```
   observed: pass rate 95% -> ACCEPT (t14 'immediately' is now normal priority)
   observed: verify() -> (False, 3)
   ```
   **What it means / what would look wrong:** a pass-rate-only gate ships the regression. Editing one audit row makes `verify()` fail and name the first broken row.

9. **Build task** (`retention.purge()`).
   **What you see:** shipped `AssertionError: Tuples differ: (30, (False, 32)) != (61, (True, None))`; solution `removed 30, audit rows 61, old content left 1, verify (True, None)`.
   **What it means:** the naive purge deleted audit rows and broke the chain; the fix deletes only old *content* (keeping one item a newer audit row still references).

Expected (not run here): with Ollama, `curl http://localhost:11434/api/tags` lists each model's `digest`; that value goes into `models.lock.json`, and `ollama pull` of the same tag can change it.

## Common confusions
**Q:** Pinning the tag (`qwen2.5:1.5b`) is enough. — **A:** Tags move; pin the digest. The failure lab changed `:latest` with no code change.

**Q:** No drift alarm means the model is fine. — **A:** v2's drift (3.92) did not alarm, yet t14 regressed.

**Q:** Retention breaks auditability. — **A:** Only content goes; `verify (True, None)`.
