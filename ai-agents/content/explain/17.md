# Multi-agent patterns: when one agent with tools is enough — explained

## The intuition
"Multi-agent" mechanically means more model calls and more hand-offs where information can be lost. A **router** gives one specialist fewer tools — cheap, but blind to cross-domain tasks. A **planner/executor** plans first — fewest calls, but cannot react to tool results. A **supervisor/worker** isolates sub-agents — small contexts, many calls, lossy hand-offs. A **single agent** sees everything and pays for every schema and result on every call.

`patterns.py` measures five designs on ten ops tasks graded by code, on a fake model with a 1,000-token window; the ADR picks from the numbers.

Analogy: a project manager plus specialists, or one senior engineer with access to everything.
Where the analogy breaks: an agent hand-off carries only the text you pass; tacit context is gone.

```
hybrid: estimate peak prompt ─ ≤ 90% window ─▶ single [agent + 6 tools] ⟲
                             └ > 90%         ─▶ supervisor ─▶ workers ─▶ merge
```

The one thing to remember: one agent with tools is the baseline every other topology must beat on *your* tasks, measured.

## Walkthrough: what actually happens when you run it
1. **You run** the L400 fake server with `--context-limit 1000`, then `python patterns.py`.
   **What happens inside:** each design runs the ten tasks against `ops_world.py` (six deterministic tools). The fake counts words as tokens and returns HTTP 400 `context_length_exceeded` when a prompt is larger than the window.
   **What you see:**
   ```
   single     9/10 passed  model calls  26  tokens   4753  failed ['t07']
   router     6/10 passed  model calls  33  tokens   2982  failed ['t05', 't06', 't07', 't09']
   planner    9/10 passed  model calls  20  tokens   1937  failed ['t09']
   supervisor 9/10 passed  model calls  52  tokens   3977  failed ['t09']
   hybrid     10/10 passed  model calls  30  tokens   4821  failed []
   ```
   **What it means:** no design wins every column. The planner is cheapest (1,937 tokens) but fails t09; the supervisor uses 2× the single agent's calls and also fails t09; only the hybrid passes all ten.

2. **You read the failures** from `patterns.jsonl`.
   **What you see (trimmed):**
   ```
   {'pattern': 'single', 'task': 't07', 'pass': False, 'model_calls': 4, 'tokens': 1395, 'error': 'context_length_exceeded: 1137 prompt tokens > context 1000'}
   {'pattern': 'router', 'task': 't05', 'pass': False, 'model_calls': 3, 'tokens': 148, 'error': None}
   {'pattern': 'planner', 'task': 't09', 'pass': False, 'model_calls': 2, 'tokens': 57, 'error': None}
   ```
   **What it means:** t07 is a *resource* failure (three log reads → 1,137 tokens). The others are *design* failures with `error: None` — wrong answers that look like successes: the router's specialist lacked a tool, the planner planned before seeing t09's metric, the supervisor's split hid it.

## The decision
3. **Options and evidence** (all numbers from step 1):
   - Router — 6/10; rejected because cross-domain tasks fail silently.
   - Planner/executor — 9/10 at 1,937 tokens; rejected *for this mix* because t09 is observation-dependent; revisit if that task type disappears.
   - Supervisor/worker — 9/10, 52 calls; too many calls and the hand-off loses facts.
   - Single — 9/10, 26 calls; fails only on context overflow.
   - Hybrid — 10/10, 30 calls, 4,821 tokens: single agent by default; escalate to supervisor/worker only when a code estimate (schemas + task + expected tool output) exceeds 90% of the window. For t07 the estimate is 1,178 > 900, so it escalates and passes in 8 calls.
4. **Why ADR-0017 chose the hybrid.** The only 10/10 design, costing nothing extra on the nine tasks that fit. Consequence recorded: the estimate is a keyword heuristic; new long-output tools must declare their size in `OUTPUT_WORDS`.
5. **How the fitness function keeps it true.** `test_fitness_patterns.py` asserts: hybrid 10/10; on every non-escalated task, hybrid tokens == single tokens; no task > 8 model calls.
   **What you see:**
   ```
   test_one_agent_default_holds (test_fitness_patterns.FitnessTopology.test_one_agent_default_holds) ... ok
   ```
   If someone makes escalation the default, the token equality breaks; if a new tool overflows unannounced, 10/10 breaks.

6. **Build task — the alternative fix** (`trim_results.py`: keep the fact line plus ≤ 60 words, say what was cut).
   **What you see:** shipped `AssertionError: 9 != 10` and `202 not less than or equal to 75`; solution:
   ```
   single+trim: 10/10, model calls 26, tokens 4168
   ```
   **What it means:** a tool-result budget lets *one* agent pass everything with fewer tokens than the hybrid. The ADR notes it may replace escalation if it holds on real models.

7. **You run** `python -m unittest -v test_try_it_17`.
   **What you see:**
   ```
   observed: context 2000 -> single 10/10, tokens 5925, failed []
   observed: 6 tools -> 5925 tokens; 18 tools -> 10293 tokens (+4368) for the same 26 model calls
   ```
   **What it means:** with a bigger window the single agent passes — the overflow, not the topology, was the problem. Twelve unused tools add 4,368 schema tokens to the same calls: the real case for routing at dozens of tools.

Expected (not run here): on Ollama, an over-long prompt is typically truncated rather than rejected with HTTP 400, so t07 would fail *quietly* with a wrong answer; and a real model may pick wrong tools, so pass rates would drop for every design.

## Common confusions
**Q:** More agents means better answers. — **A:** Supervisor: 52 calls, still 9/10. Each hand-off can drop the fact the next agent needs.

**Q:** The router is cheapest, so use it. — **A:** Its failures carry `error: None` — silent wrong answers.

**Q:** t07 proves one agent is insufficient. — **A:** Try-it 1 and the build task both make the single agent pass; the constraint was context size.
