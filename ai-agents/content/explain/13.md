# Tracing and observability — explained

## The intuition
"The agent is slow" is not a diagnosis. One agent run is a tree: a root operation containing several model calls and several tool calls, each with its own latency, tokens and status. A single log line with the total duration flattens that tree into one number, and you cannot tell which branch was slow.

A **trace** keeps the tree. `traced_agent.py` opens a **span** for the agent run (`invoke_agent support-agent`), one per model call (`chat fake-model`, kind CLIENT) and one per tool call (`execute_tool <name>`). Each span records its parent, start, duration, status and attributes, using the OpenTelemetry GenAI attribute names (`gen_ai.operation.name`, `gen_ai.usage.input_tokens`, …). Spans are written as JSON lines to `trace.jsonl`; `summarize()` groups them by name and ranks by time share.

Analogy: a flame graph instead of one access-log line.
Where the analogy breaks: a profiler samples automatically; here you choose where spans go, and anything you did not wrap is invisible.

```
invoke_agent support-agent ──────────────────────────────── 745 ms
 ├─ chat fake-model        ─ (×4, small)
 ├─ execute_tool calculator ·
 ├─ execute_tool get_weather ·
 └─ execute_tool search_docs ███████████████████ 600 ms  (cold index)
```

The one thing to remember: instrument the boundaries — every model call and every tool call — and the slow branch names itself.

## Walkthrough: what actually happens when you run it
### Failure lab: the cold index
1. **Inject.** `search_docs` loads its index on first use: `COLD_INDEX_S = 0.6`, a constant sleep. The model server is fast.
2. **Symptom.** **You run** `python untraced_run.py`.
   **What you see:**
   ```
   {"event": "agent_run", "duration_ms": 615.6, "answer_chars": 171}
   slowest below the root: None
   ```
   **What it means:** you know the run took ~616 ms; `diagnose()` has nothing below the root to rank, so it returns `None`.
3. **Diagnose.** **You run** `GENAI_PROVIDER=fake python traced_agent.py`.
   **What happens inside:** each `with tracer.span(...)` records start/end; the chat span copies `usage` from the response into `gen_ai.usage.*`; `summarize()` aggregates.
   **What you see:**
   ```
   invoke_agent support-agent   x1    745.0 ms  share 100%  tokens 0
   execute_tool search_docs     x1    600.1 ms  share 81%  tokens 0
   chat fake-model              x4     73.3 ms  share 10%  tokens 109
   execute_tool calculator      x1      0.1 ms  share 0%  tokens 0
   execute_tool get_weather     x1      0.1 ms  share 0%  tokens 0
   slowest below the root: execute_tool search_docs
   ```
   **What it means:** one tool is 81% of the run; four model calls are 10%. The README observed 643.6 ms and 93% — wall-clock numbers vary by machine and load (the chat spans took longer here); the 600 ms tool span is constant because it is a sleep.
4. **Look at the raw span.** The last line of `trace.jsonl` (the root, trimmed):
   ```
   {"trace_id": "cd18fc9fb6494384932af3bda6fe8102", "span_id": "c0fa7a26774e22af", "parent_span_id": null, "name": "invoke_agent support-agent", … "duration_ms": 745.0}
   ```
   A chat span carries `"gen_ai.usage.input_tokens": 31, "gen_ai.usage.output_tokens": 25` and `"server.port": 8765`. Ids are seeded, so `trace_id` matches the README.
5. **Fix.** Warm the index at process start (`warm_up()` calls `load_index()`) and add per-operation budgets checked from the trace (the build task).
6. **Proof.** `BUILD_TARGET=mine python -m unittest -v test_build_task` on the shipped file:
   ```
   + ['execute_tool search_docs: 600 ms > 200 ms']
   FAILED (failures=1)
   ```
   The solution passes (`Ran 1 test in 2.061s`, `OK`). The test swaps in a fake clock, so time advances only in the 600 ms sleep — a busy CI runner cannot flip it. `test_traced_agent` also passes both failure-lab tests (`…one_log_line_cannot_find_the_slow_tool`, `…trace_names_the_slow_tool`).

7. **You run** `python -m unittest -v test_try_it_13`.
   **What you see:**
   ```
   observed: [('invoke_agent support-agent', 1), ('chat fake-model', 4)] | slowest: chat fake-model
   observed: [('invoke_agent support-agent', 1), ('chat fake-model', 4)] | slowest: chat fake-model
   ```
   **What it means / what would look wrong:** with no cold index, the 4 model calls become the biggest cost. With the index still cold but every model call 250 ms slower, 4 × 250 ms beats one 600 ms tool. Same symptom ("slow"), two different causes — only the trace tells them apart.

Expected (not run here): through the OpenTelemetry SDK and Jaeger (`otel_sdk_equivalent.py --otlp`) you should see the same tree with `execute_tool search_docs` as the longest bar; with Ollama, real token counts and much longer chat spans on CPU.

## Common confusions
**Q:** Total duration is enough to detect regressions. — **A:** It detects them; it cannot locate them (`slowest below the root: None`).

**Q:** Tool-call turns cost no tokens. — **A:** The fake counts reply words, so tool-call turns show few; real servers report `completion_tokens` for tool calls too.

**Q:** Record prompts and outputs on every span. — **A:** They are opt-in and deliberately not recorded here: personal data and secrets would land in the trace store.

## Check your understanding
1. What makes a span a child of the root?
<details><summary>Answer</summary>Its `parent_span_id` equals the root's `span_id`, set by opening it inside the parent's `with` block.</details>

2. Why does the build-task test use a fake clock?
<details><summary>Answer</summary>So only the deterministic 600 ms sleep counts; machine speed cannot change the result.</details>

3. Try-it 2 shows `chat` as slowest. What would you change first?
<details><summary>Answer</summary>The model side — fewer calls, a faster/smaller model, or a warm server — not the index.</details>
