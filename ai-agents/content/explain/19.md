# Cost, latency and model choice — explained

## The intuition
Locally, cost is GPU time, memory and latency. Three levers move it: **model size** (1.5B is ~4–5× cheaper per token than 7B, less accurate); **prompt caching** (servers reuse a seen *prefix* — instructions first, ticket last); **memory sizing** (weights plus KV cache, which grows with context × parallel slots, must fit the GPU).

The routing question is: which tickets can the small model handle? A **cascade** tries small first and escalates to large when code *rejects* the answer (bad JSON, disallowed value). A **rule** sends recognisably hard tickets straight to large. `route_cost.py` measures four strategies on lesson 12's 20-case golden set, using a deterministic cost model (≈ 2 × parameters per token, cached prompt tokens at 10%) so the numbers are repeatable.

Analogy: juniors take every ticket; QA failures and "outage" tickets go to the senior.
Where the analogy breaks: QA (the validator) can check *form*, not *truth* — a junior's well-formatted wrong answer sails through.

```
ticket ─▶ rule: urgent|asap|immediately|down? ─yes─▶ large ─▶ answer
              │ no
              ▼
            small ─▶ validate(JSON, allowed values) ─ok─▶ answer
                               │ rejected
                               ▼
                             large ─▶ answer
prompt = [stable instructions … (cached prefix)] + [ticket (varies)]
```

The one thing to remember: a cheaper route is only cheaper if the golden set still passes — and validators cannot see valid-but-wrong answers.

## Walkthrough: what actually happens when you run it
1. **You run** `python route_cost.py` (L400 fake server; `fake-small` stands in for qwen2.5:1.5b, `fake-large` for 7b).
   **What you see:**
   ```
   {"strategy": "large-only", "passed": 20, "cases": 20, "cost": 7000.0, "p50_ms": 867.8, "p95_ms": 883.2, "escalated": 0, "cache_ratio": 0.76}
   {"strategy": "small-only", "passed": 13, "cases": 20, "cost": 1590.0, "p50_ms": 182.1, "p95_ms": 249.7, "escalated": 0, "cache_ratio": 0.76}
   {"strategy": "cascade", "passed": 19, "cases": 20, "cost": 3807.6, "p50_ms": 182.1, "p95_ms": 1132.9, "escalated": 6, "cache_ratio": 0.75}
   {"strategy": "rules+cascade", "passed": 20, "cases": 20, "cost": 3890.1, "p50_ms": 182.1, "p95_ms": 1123.6, "escalated": 4, "cache_ratio": 0.76}
   ```
   **What it means:** the latencies are *estimates* from `cost_model.py`, not stopwatch readings — that is why they match the README exactly. Small-only fails 7 of 20 (the fake's rule S: prose-wrapped JSON on long tickets, only "outage" counts as high priority). The cascade recovers 6 but misses t03. Rules + cascade passes all 20 at 3,890.1 — 56% of large-only. Note p95 rises to ~1.1 s: escalated tickets pay for both models.

2. **Same run**, prompt order and batching.
   **What you see:**
   ```
   prompt order instructions first: cached 76% of prompt tokens, cost 7000.0, p50 867.8 ms
   prompt order ticket first      : cached 3% of prompt tokens, cost 14056.0, p50 1082.8 ms
   batching: {"parallel": 1, "kv_gb": 0.23, "need_gb": 4.93, "wall_s_for_batch": 17.37}
   batching: {"parallel": 4, "kv_gb": 0.94, "need_gb": 5.64, "wall_s_for_batch": 4.34}
   ```
   **What it means:** moving the ticket to the front destroys the shared prefix and doubles cost — a free optimisation. Four parallel slots quadruple KV memory (0.23 → 0.94 GB) and cut batch wall time about 4×.

3. **You run** `python sizing.py`.
   **What you see (first lines):**
   ```
   qwen2.5:7b    weights 4.7 GB + KV 0.23 GB (57.3 kB per token, f16)
   Mac mini M6 16GB               qwen2.5:7b       4.93     10  GPU (Metal)        16
   ```
   **What it means:** both models fit a 16 GB Mac mini at 4k context. The tok/s column is an estimate (50% of the memory-bandwidth bound).

## The decision
4. **Options.** Large-only is the quality bar (20/20) but fails the cost constraint (≤ 60%). Small-only fails quality (13/20). Cascade alone: 19/20 — rejected because t03 is a *silent* miss: valid JSON, priority `normal` instead of `high`. Rules + cascade: 20/20, 56% cost, 76% cached.
5. **Why ADR-0019 chose rules + cascade.** It is the only option meeting every constraint. The rule (`urgent|asap|immediately|down` → large) was *learned from eval failures*; the ADR says it must be re-learned when the golden set or model changes. Instructions-first prompt order is part of the decision.
6. **Fitness function.** `test_fitness_cost.py` asserts rules+cascade passed == large passed, cost ≤ 0.6 × large, cache ratio ≥ 0.6.
   ```
   test_route_keeps_quality_and_saves (test_fitness_cost.FitnessCost.test_route_keeps_quality_and_saves) ... ok
   test_failure_lab_small_only_and_the_silent_miss (…) ... ok
   ```
   Reorder the prompt or weaken the rule and it fails.

7. **You run** `python -m unittest -v test_try_it_19`.
   **What you see:**
   ```
   observed: 14b at 32k x 4 needs 34.77 GB -> M6 24GB: does not fit; M5 Pro 48GB: GPU (Metal)
   observed: 19/20, cost 3711.9, failed ['t03']
   ```
   **What it means / what would look wrong:** long contexts × slots blow memory long before weights do. Dropping "urgent" and "down" from the rule saves a little cost and brings back the silent t03 miss.

8. **Build task** (`budget.fit()`: keep system + question + reply reserve first, then best docs, then newest history).
   **What you see:** shipped `AssertionError: Lists differ: ['deploy', 'deploy', …] != ['QUESTION:', 'why', 'is', 'checkout', 'slow?']`; solution `fit: 714 words; question kept True; docs ['RB-3', 'RB-7']`.
   **What it means:** budgeting by position truncated the *question*; budgeting by priority keeps it.

Expected (not run here): `real_model_probe.py qwen2.5:1.5b qwen2.5:7b` on Ollama should show cached prompt tokens > 0 on the second call and decode speeds below `sizing.py`'s estimate; `ollama ps` shows a CPU/GPU split if the model does not fit.

## Common confusions
**Q:** The cascade's validator guarantees correctness. — **A:** t03 passed validation and was wrong.

**Q:** Local models are free. — **A:** Cost is GPU-seconds and latency; ticket-first prompts doubled it (7000.0 → 14056.0).

**Q:** More parallel slots is free throughput. — **A:** KV memory scales with slots; 14b at 32k × 4 needs 34.77 GB.
