# Agents with several tools — explained

## The intuition
With one tool the model's only decision is "call it or not". With several, it must pick *which* tool and *which arguments*, and the only information it has is each tool's name, description and JSON Schema. So descriptions are routing logic, and schemas are contracts.

Treat every tool call as untrusted network input. `execute()` runs four gates: name in `REGISTRY`? arguments parse? `validate()` passes (enum, maximum, `additionalProperties: false`)? function succeeds? Any failure becomes a precise error string returned as the tool result, so the model can fix its call.

Analogy: an API gateway that answers bad requests with a field-level 400.
Where the analogy breaks: this "client" may resend the same bad request forever — `max_steps` is the backstop.

```
tool_call ─▶ registry? ─▶ json? ─▶ validate(schema)? ─▶ fn(**args)
               └──────────any failure──────────▶ "error: …" ─▶ model retries
```

The one thing to remember: validation errors are not failures of the agent — they are feedback the loop is built to absorb.

## Walkthrough: what actually happens when you run it
1. **You run** `python multi_tool_agent.py`.
   **What happens inside:** the task asks for three things with two deliberate mistakes (kelvin, top 50). The fake plans one call per turn and, like many real models, retries once without the offending argument when it sees an `invalid arguments` error.
   **What you see:**
   ```
   step 1: calculator({"expression": "12*7"}) -> 84
   step 2: get_weather({"city": "Paris", "unit": "kelvin"}) -> error: invalid arguments: $.unit: 'kelvin' is not one of ['celsius', 'fahrenheit']
   step 3: get_weather({"city": "Paris"}) -> 18 C
   step 4: search_docs({"query": "context window", "top_k": 50}) -> error: invalid arguments: $.top_k: 50 is greater than the maximum of 5
   step 5: search_docs({"query": "context window"}) -> The context window limits … | Embeddings turn text into vectors for similarity search.
   step 6: final -> Final answer: 12*7 = 84; get_weather(city=Paris) = 18 C; …
   ```
   **What it means:** 6 model calls for 3 tools — each schema error cost a round trip. Errors name the path (`$.unit`) and allowed values so a model can self-correct. Expected (not run here): `qwen2.5:1.5b` may never send `kelvin`, or may repeat a bad call until the budget ends.

2. **You run** `python agent_assist.py`.
   **What happens inside:** the model drafts a schema for a new `convert_temperature` tool; code parses it, forces `additionalProperties: false`, and runs 1 good and 4 bad example argument sets through `validate()`.
   **What you see:**
   ```
   accepted ['added additionalProperties: false']
   ```
   **What it means:** the model proposes, code decides. The draft was accepted only after code tightened it.

3. **You run** `python -m unittest -v test_try_it_08`.
   **What you see:**
   ```
   observed: step 2: get_weather({"city": "Paris", "unit": "fahrenheit"}) -> 64 F | steps: 5
   observed: The context window limits how many tokens one request can hold. | Embeddings turn text into vectors for similarity search. | Tool arguments must be validated in code before anything runs.
   ```
   **What it means / what would look wrong:** a valid unit saves a step (5 not 6). Raising the `top_k` maximum returns all 3 notes — with real data, the `maximum` is what stops a model pulling thousands of tokens into context. Note: the README says notes are joined by `' / '`; the code and this run use `' | '`.

## Common confusions
**Q:** The model will read the error and fix it. — **A:** Often, not always. The fake's retry rule is generous; real models can loop on the same mistake, which is why `max_steps=8` exists.

**Q:** Schema validation makes tools safe. — **A:** It makes *arguments* well-formed; risky effects still need approval (lesson 6) or idempotency (lesson 15).

**Q:** More tools make the agent more capable. — **A:** Similar descriptions make routing harder.
