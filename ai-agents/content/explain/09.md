# State and memory — explained

## The intuition
An agent has two kinds of memory. **Short-term state** is the `messages` list resent every call (lesson 2), bounded by the context window and cost, so it must be trimmed. **Long-term memory** is data stored outside the model — SQLite rows — brought back through tools.

`Chat.fit()` runs before every model call: over `budget` (60 words), it has the model summarise older turns into one line in the system message and keeps the last 2 messages. Summaries are lossy. Must-keep facts go through `save_memory` (a parameterised `INSERT`); `recall_memory` does a `LIKE` search.

Analogy: a whiteboard and a notebook. The whiteboard (messages) is erased and condensed when full; anything you need next week goes in the notebook (SQLite) deliberately.
Where the analogy breaks: the model decides what to "write in the notebook" only if asked — here the user says "Remember…"; nothing is saved automatically.

```
send(text) ─▶ messages += user
          ─▶ fit(): tokens > budget? ─yes─▶ summarise old turns ─▶ system += "Earlier: …"; keep last 2
          ─▶ model(messages, tools=[save_memory, recall_memory])
                 tool_call ─▶ MemoryStore.save/recall ─▶ notes table (memory_demo.db)
New Chat() ─▶ empty messages, same SQLite file ─▶ recall still works
```

The one thing to remember: the conversation is a cache you are allowed to lose; memory is a database you write on purpose.

## Walkthrough: what actually happens when you run it
1. **You run** `python memory_agent.py`, turn 1.
   **What happens inside:** the fake sees `save_memory` and "Remember" and calls the tool; `MemoryStore.save()` inserts row 1 and commits.
   **What you see:**
   ```
   > Remember that the staging database is on port 5433.
     Final answer: save_memory(note=the staging database is on port 5433) = saved note 1
     tokens=34 summaries=0
   ```
   **What it means:** 34 words already, because the turn holds user, tool-call, tool-result and final messages.

2. **Turns 2 and 3.**
   **What you see:**
   ```
     tokens=57 summaries=0
   > And one about penguins please, keep it short.
     …
     tokens=62 summaries=1
   system now: Earlier: Summary: Remember that the staging database is on port; Thanks. Now tell me a fun fact about
   ```
   **What it means:** before turn 3's model call the list exceeded 60, so `fit()` summarised once. The printed 62 is measured *after* the reply was appended — the budget is checked before each call, not enforced afterwards, so leave room for the reply. The fake's "summary" is a crude truncation: the port number 5433 was lost from short-term state.

3. **A new conversation.**
   **What you see:**
   ```
   > What do you remember about staging?
     Final answer: recall_memory(query=staging) = 1: the staging database is on port 5433
   [(1, 'the staging database is on port 5433')]
   ```
   **What it means:** `later` starts with empty messages; the fact came from the SQLite row (see the `SELECT`). Expected (not run here): a real model's fluent summary may or may not keep "5433".

4. **You run** `python -m unittest -v test_try_it_09`.
   **What you see:**
   ```
   observed: summaries = 0 | messages = 9 | tokens = 78
   observed: Final answer: recall_memory(query=staging) = no matching notes
   ```
   **What it means / what would look wrong:** with `budget=500` nothing is summarised and the list grows to 9 messages — fine for three turns, a cost and context-overflow problem for three hundred. With an in-memory store per conversation the second chat finds nothing: memory lives in the file.

## Common confusions
**Q:** A bigger context window removes the need for memory. — **A:** It delays trimming; try-it 1 shows the list only grows.

**Q:** The summary preserves important facts. — **A:** Step 2's summary dropped the port. Store must-keep facts explicitly.

**Q:** Word counts are token counts. — **A:** Only in the fake. Real tokenizers produce more tokens than words; calibrate the budget against `usage.prompt_tokens`.
