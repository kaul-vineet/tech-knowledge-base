# Safe tool execution — explained

## The intuition
Lesson 14 made retries safe for *reads*: asking the model again costs tokens, nothing more. A tool that *changes the world* — sends money, deletes a record, emails a customer — is different. When a request times out you do not know whether the server did the work. Retrying might do it twice.

Three ideas fix this, and `safe_tools.py` implements all three in `ToolGate`. **Idempotency key**: derive a key once per logical call (`sha256(run_id:call_id:tool)`), send it as an `Idempotency-Key` header, and retry only with the *same* key; the payments service stores the first result per key and replays it. **Approval queue**: the agent never calls the payment API; `request()` inserts a `pending` row in SQLite and tells the model "queued … nothing has been sent yet". A human `decide()`s; only `execute_approved()` sends. **Audit log**: every step (`queued`, `approved`, `timeout_retry`, `executed`) is an append-only row with the actor.

Analogy: a bank cheque with a unique number. Present it twice and the bank pays once; and a second signature is required above a limit.
Where the analogy breaks: the cheque number is printed once on paper; in code, a "new key per retry" bug is one line away (try-it 1).

```
model ─send_refund─▶ ToolGate.request(): key = sha256(run:call:tool) ─▶ approvals(pending) ─▶ "queued #1"
human ─decide(1, alice, yes)─▶ approved
execute_approved(): status=executing (commit) ─▶ _send(args, key) ─timeout─▶ retry SAME key
                    payments: key seen ─▶ replay stored result (Idempotent-Replayed: true)
                    status=done; audit every step
```

The one thing to remember: a timeout means "unknown", not "failed" — only a reused key makes the retry safe.

## Walkthrough: what actually happens when you run it
### Failure lab: the late reply
1. **Inject.** `payments_service.py` (`slow_first=True`) *commits* the first refund, then answers 0.6 s late. The client timeout is 0.3 s.
2. **Symptom.** **You run** `python safe_tools.py`; the first line is the naive tool (no key, retry on timeout).
   **What you see:**
   ```
   naive, 1 slow response : [{'id': 1, 'order_id': 'A-1001', 'amount': 25.0}, {'id': 2, 'order_id': 'A-1001', 'amount': 25.0}]
   ```
   **What it means:** the customer was refunded twice. The first request succeeded; the client just didn't hear about it in time.
3. **Diagnose.** The duplicate is not a payments bug: two independent POSTs with no shared identity look like two legitimate refunds.
4. **Fix — run the gated agent.**
   **What you see:**
   ```
   agent   : Final answer: send_refund(order_id=A-1001, amount=25.0) = queued for human approval as #1; nothing has been sent yet
   refunds before approval: []
   executed: [{'refund_id': 1, 'order_id': 'A-1001', 'amount': 25.0, 'replayed': True}]
   refunds after approval : [{'id': 1, 'order_id': 'A-1001', 'amount': 25.0}]
   ```
   **What it means:** zero refunds until Alice approved. Then the first attempt timed out (same fault), the retry carried the same key, and the service *replayed* refund 1 (`replayed: True`) instead of creating refund 2.
5. **Proof in the audit trail.**
   ```
   {"actor": "executor", "event": "timeout_retry", "attempt": 0, "key": "2f848eae73459b0ec30c1d92159fda06"}
   {"actor": "executor", "event": "executed", "approval": 1, "key": "2f848eae73459b0ec30c1d92159fda06", …}
   [(1, 'send_refund', 'done', 'alice')]
   ```
   Same key on the retry and the execution; the approval row records who approved. Tests: `test_failure_lab_naive_retry_refunds_twice` and `test_failure_lab_key_and_approval_refund_once` both `ok` (`Ran 8 tests in 24.516s`).

6. **You run** `python -m unittest -v test_try_it_15`.
   **What you see:**
   ```
   observed: [{'id': 1, 'order_id': 'A-1001', 'amount': 25.0}, {'id': 2, 'order_id': 'A-1001', 'amount': 25.0}]
   observed: Final answer: … = DRY RUN: would call send_refund with {"amount": 25.0, "order_id": "A-1001"} | approvals: 0 | refunds: []
   ```
   **What it means / what would look wrong:** a new key per attempt brings the double refund straight back. Dry-run mode previews the exact call and changes nothing.

7. **Build task** (resume after a crash between "sent" and "done").
   **What you see:** shipped file `AssertionError: Tuples differ: (2, False, 'done') != (1, True, 'done')`; solution `OK`.
   **What it means:** the shipped `resume()` re-sends stuck `executing` rows with a *new* key → 2 refunds; resuming with the stored key → 1 refund, replayed.

Expected (not run here): a real model might phrase the refund request differently or call `lookup_order` first; the gate behaves the same because it sits in code, not in the prompt.

## Common confusions
**Q:** Approval alone prevents duplicates. — **A:** No; step 4's retry happened *after* approval. Only the key made it safe.

**Q:** Any unique id works as a key. — **A:** It must be stable for the logical call and stored before the first attempt; `uuid4()` per attempt is try-it 1's bug.

**Q:** The model knows a refund happened. — **A:** It was told "queued … nothing has been sent yet" — honest status, not a claim of success.

1. Why commit `status='executing'` before calling `_send()`?
<details><summary>Answer</summary>A crash after that line leaves the row and its key, so a restart can resume with the same key.</details>

2. What does the service return if the same key arrives with a different amount?
<details><summary>Answer</summary>HTTP 422 — key reused with a different request; re-queue for approval.</details>

<details><summary>Answer</summary>Under a tested policy (e.g. small refunds) once golden-set and audit data justify it; the policy then becomes the control.</details>
