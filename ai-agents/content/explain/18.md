# Durable agent workflows: checkpoints, resume and exactly-once effects — explained

## The intuition
A *workflow* is longer than one tool call: look up, ask the model, wait days for a manager, pay, notify. A process will die mid-way. "Durable" means: after a restart it continues where it was, and every external effect happens exactly once.

`durable.py` gets there with three mechanisms. **Event history**: after each step, its result is committed to an SQLite `history` table in one transaction; on restart, `Engine.run()` *replays* recorded results instead of re-executing steps. **Idempotency keys derived from the workflow**: the refund carries `Idempotency-Key: wf-1:refund`, so a re-sent payment after a crash is replayed by the API, not repeated. **Outbox**: the customer notification is a row written in the *same* transaction as the `notify` checkpoint, so it exists if and only if the step completed. Waiting for a human is not a sleeping thread: `_approval()` returns `WAITING`, the process can exit, and an approval signal is just another history row.

Analogy: a lab notebook — write each result in ink before the next experiment; after a fire drill, read it and continue.
Where the analogy breaks: the gap between "the payment API did it" and "I wrote it down" cannot be closed by your notebook alone — the API's idempotency key closes it.

```
run(wf): status? ─▶ for step in [lookup, propose, approval, refund, notify]:
            in history? ─yes─▶ reuse result (replay)
            no ─▶ execute ─▶ BEGIN; INSERT history(step, result) [+ outbox row]; COMMIT
   crash points: before:/after:<step>, after_model:propose, after_effect:refund  (12 total)
   refund: POST /refunds  Idempotency-Key = "<wf>:refund"   (same on every attempt)
```

The one thing to remember: checkpoint every step, and derive effect keys from *workflow + step* — never from the attempt.

## Walkthrough: what actually happens when you run it
1. **You run** `python durable.py` (L400 fake server running).
   **What happens inside:** first the naive in-memory loop runs with a crash injected at `after_effect:refund` and restarts from scratch; then the durable engine runs with the same crash, restarts from the SQLite file, and continues.
   **What you see:**
   ```
   naive, crash after the refund : 2 -> 2 refunds
   durable, same crash          : done ['after_effect:refund'] -> 1 refund
   {"step": "approval", "event": "signal:approve", "by": "alice"}
   {"step": "refund", "event": "completed", "refund_id": 1, "replayed": true}
   {"step": "notify", "event": "completed", "order_id": "A-1001", "amount": 25.0}
   outbox: [('refund_done',)]
   ```
   **What it means:** the crash hit after money moved but before the checkpoint. On restart the durable engine re-ran `refund` (it had no checkpoint) with the same key, and the payments API answered `replayed: true` — refund 1, not refund 2.

## The decision
2. **Options measured.** I re-ran the crash sweep (`harness.sweep()`, every one of 12 crash points, restart, drive to the end) for all three variants:
   ```
   naive              duplicate refunds at 4/12 ['after:refund', 'before:notify', 'after:notify', 'after_effect:refund'] | model re-asked at 9/12
   checkpoint_no_key  duplicate refunds at 1/12 ['after_effect:refund'] | model re-asked at 1/12
   durable            duplicate refunds at 0/12 [] | model re-asked at 1/12
   ```
   **What it means:** checkpoints alone remove most duplicates and model re-asks, but leave exactly the "after the effect, before the checkpoint" gap. Only keys close it. The one remaining model re-ask (crash right after the model answered) costs tokens, not money.
3. **Why ADR-0018 chose SQLite history + keys + outbox.** 0 of 12 duplicates, no extra server, runs on one Mac mini or PC. Temporal gives the same guarantee as a service (recorded activity results, durable timers, a history UI) and is recorded as the next step when one SQLite writer becomes the limit; it was not run here (pending CI, `temporalio` not installed). Keys are needed either way.
4. **How the fitness function keeps it true.** `test_fitness_crash_sweep.py` kills the workflow at each of the 12 points and asserts status done, exactly 1 refund, exactly 1 `refund_done` row, ≤ 1 model call (2 only for `after_model:propose`).
   ```
   test_every_crash_point (test_fitness_crash_sweep.FitnessCrashSweep.test_every_crash_point) ... ok
   test_failure_lab_checkpoint_without_key_refunds_twice (…) ... ok
   test_failure_lab_durable_refunds_once (…) ... ok
   Ran 8 tests in 100.867s
   ```
   Anyone who changes the key to include an attempt counter, or moves the outbox write out of the checkpoint transaction, turns this red.

5. **Build task** (approval deadline: 48 h, late clicks ignored).
   **What you see:** shipped `AssertionError: Tuples differ: (['waiting', 'waiting', 'waiting', 'done'], 1, ['refund_done']) != (['waiting', 'waiting', 'escalated', 'escalated'], 0, ['approval_timeout'])`; solution `OK`.
   **What it means:** without a deadline a click days later still moved money; with it, the workflow escalates and writes an `approval_timeout` outbox row instead.

6. **You run** `python -m unittest -v test_try_it_18`.
   **What you see:**
   ```
   observed: done, crashes ['after_model:propose'], model calls 2, refunds 1
   observed: done, approve signals stored 1, refunds 1
   ```
   **What it means / what would look wrong:** a crash between the model's answer and its checkpoint asks the model twice — acceptable. A double-clicked approval is stored once (`UNIQUE (wf_id, step, event)`).

Expected (not run here): with a real model, the re-asked proposal could return a *different* amount; the engine caps it at the paid amount in code (`min(...)`), and the approval shows the recorded proposal, so the human approves what will actually be sent.

## Common confusions
**Q:** Checkpointing makes effects exactly-once. — **A:** `checkpoint_no_key` still duplicated at `after_effect:refund`. You need the API's cooperation (keys) for the last gap.

**Q:** Waiting for approval needs a long-running thread. — **A:** `_approval()` returns `WAITING`; the signal is a history row read on the next `run()`.

**Q:** Replaying means calling the model again. — **A:** Recorded results are reused; `test_replay_does_not_call_the_model_again` passes.

## Check your understanding
1. Why is the key `"<wf>:refund"` and not a random UUID?
<details><summary>Answer</summary>A restart must send the *same* key for the same logical effect so the API can replay it.</details>

2. Why write the outbox row in the checkpoint transaction?
<details><summary>Answer</summary>So the notification exists if and only if the step completed — no lost or duplicate notifications.</details>

3. What would trigger moving to Temporal?
<details><summary>Answer</summary>Several workers or hosts, many long timers, or `database is locked` from one SQLite writer.</details>
