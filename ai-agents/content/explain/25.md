# Foundations III: decision theory and planning — explained

## The big picture
Many L300–L400 choices were engineering judgement backed by measurement: how many retries in "Reliability: timeouts, retries, budgets and fallbacks", when to auto-approve vs escalate in "Deterministic core, LLM at the edge", the hybrid escalation rule in "Multi-agent patterns: when one agent with tools is enough", and the allow-lists in "Guardrails basics" and "Red-teaming prompt injection". This lesson gives those choices a theory: expected cost for retries, Bellman's equation for multi-step decisions, search algorithms for plans, and Rice's theorem for why "just analyse the program" cannot replace an allow-list. `decision_planning.py` checks each claim.

### T1 Expected cost of retries and when another attempt pays
**In plain words.** Retry while the chance the next attempt works, times what failure would cost you, exceeds the price of a call. With correlated failures that point comes quickly; with a stuck loop only a budget saves you.

**Why it is true (intuition).** Allowing one more attempt only matters in the world where all previous attempts failed. In that world you pay one more call, and with probability pᵢ you avoid the give-up cost.
1. The expected change from allowing attempt i+1 is P(reach it)·(c − pᵢ·C_fail).
2. So it pays exactly when pᵢ·C_fail ≥ c.
3. Constant p: every attempt pays or none does — budget 0 or unbounded.
4. Decreasing pᵢ (correlated failures): a finite optimal k*.
5. p = 0: unbounded cost without a budget; a budget k caps it at k·c.

**See it in numbers.** `python decision_planning.py check T1`:
```
p=0.70 k=3: E[attempts] formula 1.3900 sim 1.3926; P(all fail) formula 0.0270 sim 0.0267
correlated failures (p_i = 0.7 * 0.5^i): retry while p_i*20 >= 1 -> k*=4; cost k=1 7.0000, k*=4 4.5918, k=20 6.5160
saving from allowing attempt i = P(reach i) * (p_i*C_fail - c): 1:+13.0000, 2:+1.8000, 3:+0.4875, 4:+0.1207, 5:-0.0183, 6:-0.0790
```
The formula matches simulation. With correlated failures, the 5th attempt has a negative saving (−0.0183): k* = 4 costs 4.5918, while k = 20 costs 6.5160.

**Where it shows up.** Lesson 14's `retries=2` and its circuit breaker: correlated failures (an overloaded server) are exactly the decreasing-pᵢ case.

### T2 Bellman optimality: value iteration converges to the unique optimal value
**In plain words.** The value of a state is the best immediate reward plus the discounted value of where you end up; repeatedly applying that rule converges to the one right answer.

**Why it is true.** The Bellman update shrinks any disagreement between two value guesses by at least a factor γ.
1. For each action, the difference between TU and TW is a probability-weighted average of γ(U − W).
2. An average is no larger than the largest term; probabilities sum to 1.
3. Max over actions preserves this bound: ‖TU − TW‖ ≤ γ‖U − W‖.
4. A contraction (γ < 1) has a unique fixed point; iteration converges geometrically.
5. Acting greedily on V* is optimal.

**See it in numbers.** `check T2`:
```
value iteration (gamma 0.95, p_harm 0.05): V(open) = 4.9383, policy = auto, 16 iterations
contraction: max ||TU - TW|| / ||U - W|| over 1000 random pairs = 0.9500 <= gamma 0.95
p(wrong refund)=0.07: V(open) 4.0000 -> escalate
break-even p_harm where auto = escalate: (7 - 4*0.81)/60 = 0.0627
```
Auto-approval is worth 4.9383 > escalate's 4 at a 5% harm rate; above 6.27% escalation wins.

**Where it shows up.** "Deterministic core, LLM at the edge": `AUTO_LIMIT` is a policy threshold; this is how you would justify its value.

### T3 BFS and A* optimality; overestimating heuristics break it
**In plain words.** A* finds the cheapest plan if its guess of remaining cost never overestimates; overestimate and it can confidently return a worse plan.

**Why it is true.** With an admissible h, the optimal path always has a frontier node whose f = g + h is at most the optimal cost, so A* cannot finish a worse path first. An overestimate can inflate the good branch's f above a bad finished path.

**See it in numbers.** `check T3`:
```
grid: BFS shortest 15 steps (58 expanded); A* h=0 (Dijkstra) 15 (58 expanded); A* Manhattan 15 (26 expanded); A* 5x Manhattan 19 (21 expanded)
plan graph, h=overestimating: cost 8 via start -> lookup_order -> check_policy -> draft_reply (4 expanded)
```
Good heuristics save work (26 vs 58 expansions); an inflated one returns 19 instead of 15, and a cost-8 plan instead of 4.

**Where it shows up.** "Multi-agent patterns": the planner commits to a plan from estimates; a wrong estimate means a wrong plan.

### T4 Deciding whether an arbitrary tool program calls delete is impossible (Rice) — hence allow-lists
**In plain words.** No checker can always tell whether arbitrary code will eventually call `delete`; you must either run it with a budget (and sometimes say "unknown") or reject anything that *names* a forbidden tool.

**Why it is true.** If such a checker D existed, you could decide halting: build "run P; then call delete" and ask D. Halting is undecidable, so D cannot exist.

**See it in numbers.** `check T4`:
```
collatz_then_delete(27): halts after 111 steps; budget 10/100/1000 -> ['unknown (budget exhausted)', 'unknown (budget exhausted)', 'calls delete']
never_deletes: dynamic no delete; allow-list rejected ['delete_records'] (conservative)
```
The bounded checker answers "unknown" until its budget exceeds 111 steps; the allow-list rejects without running — and also rejects a safe program that merely mentions `delete_records`.

**Where it shows up.** Lessons 11 and 16: session allow-lists, not model-based "intent analysis".

## Worked problems
**l25-p1: tool succeeds with p = 0.6; budget 4.**
1. *Use the tail sum* (why: E[min(N, k)] = Σ P(N > i)): 1 + 0.4 + 0.16 + 0.064 = 1.624 calls.
2. *Give-up probability:* all four fail, 0.4⁴ = 0.0256.
3. *No budget:* E[N] = 1/0.6 = 1.6667 — finite only because p > 0; the budget protects against p = 0.

**l25-p3: auto-approve (+3 correct, −60 wrong, 4% wrong) vs review (3 − 2).**
1. *EU(auto)* = 0.96·3 + 0.04·(−60) = 0.48 (why: weight each outcome by its probability).
2. *EU(review)* = 1.
3. *Choose review* (why: higher expected utility).
4. *Break-even:* 3(1 − e) − 60e = 1 → e = 2/63 = 0.0317.
5. *Practice:* e is itself estimated — compare the upper end of its Wilson interval (lesson 24) with 0.0317.

## Common confusions
**Q:** More retries are always safer. — **A:** With correlated failures k = 20 costs more than k* = 4.

**Q:** A smarter checker could decide "will it delete?" — **A:** Not for arbitrary programs (T4); it must say "unknown" or be conservative.

**Q:** A* is always optimal. — **A:** Only with an admissible heuristic; 5× Manhattan returned 19 instead of 15.
