# Evaluating agents with a golden set — explained

## The intuition
Changing a prompt is changing code whose behaviour you cannot read off the diff. A one-line "cleanup" can silently break a category of inputs. The defence is the same as for ordinary code: a frozen test suite and a CI gate. For model behaviour the suite is a **golden set** — `golden.jsonl`, 20 tickets with labelled answers — and the gate is `eval_gate.py`, which exits 1 to block a merge.

Each case is scored by three kinds of check in `check()`: **structural** (is it JSON with exactly the expected keys and allowed values?), **exact** (does `category`/`priority` equal the label?) and **rubric** (a 3-point checklist on the free-text summary: ≤12 words, mentions a key term, no "sorry"; 2 of 3 points pass). `gate()` then applies two rules: overall pass rate ≥ 95%, *and* no case that passed in `baseline.json` may now fail.

Analogy: a regression test suite plus a coverage floor — the floor catches broad decay, the per-test comparison catches a specific break.
Where the analogy breaks: with a real model the "tests" are themselves noisy; the same prompt can score differently on reruns unless temperature and model tag are pinned.

```
prompts/vN.txt ─┐
golden.jsonl ───┼─▶ run_case() ×20 ─▶ check(): structural · exact · rubric ─▶ report
                │                                                         │
baseline.json ──┴──────────────────────────────▶ gate(): rate ≥ 95%? regressions? ─▶ exit 0 / 1
```

The one thing to remember: a prompt change is not done until the whole golden set passes the gate — examples you tried by hand prove nothing.

## Walkthrough: what actually happens when you run it
1. **You run** `python eval_gate.py` (prompt v1, against `fake_server_l300.py`).
   **What happens inside:** each ticket is substituted into `{{ticket}}` and sent at `temperature: 0`. The fake's rule T classifies by keywords, but only into categories *named in the prompt*.
   **What you see:**
   ```
   v1.txt: 20/20 passed (100%)
   GATE: PASS
   exit code: 0
   ```
   **What it means:** v1 matches the accepted baseline.

### Failure lab: the "cleanup" prompt
2. **Inject.** `prompts/v2.txt` differs from v1 by one line:
   ```
   < Categories: billing, technical, account, shipping, other.
   > Categories: billing, technical, shipping, other.
   ```
3. **Symptom — the spot check lies.** Trying the first three tickets by hand, as a reviewer would:
   **What you see:**
   ```
   spot check v2 (first 3 cases): 3 / 3
   ```
   All three are billing tickets; the change looks safe and would merge.
4. **Diagnose — run the full set.** `python eval_gate.py --prompt prompts/v2.txt`
   **What you see:**
   ```
   FAIL t07 (account): exact: category='other', expected 'account'
   FAIL t15 (account): exact: category='other', expected 'account'
   v2.txt: 18/20 passed (90%)
   GATE: BLOCK - pass rate 90% < 95% | regressions vs baseline: ['t07', 't15']
   exit code: 1
   ```
   **What it means:** both failures are *exact* checks in one category — the output is still valid JSON, so a structural-only check would have passed. With "account" no longer allowed, account tickets fall to `other`.
5. **Fix.** Run the whole set in CI and gate on both rules; restore "account" in the prompt.
6. **Proof.** `python -m unittest -v test_eval_gate`:
   ```
   test_failure_lab_gate_blocks_v2 (test_eval_gate.EvalGate.test_failure_lab_gate_blocks_v2) ... ok
   test_failure_lab_spot_check_misses_the_regression (…) ... ok
   Ran 5 tests in 32.833s
   ```

7. **You run** `python -m unittest -v test_try_it_12`.
   **What you see:**
   ```
   observed: ["regressions vs baseline: ['t07', 't15']"]
   observed: 18/18 []
   ```
   **What it means / what would look wrong:** lowering the bar to 85% still blocks — the per-case regression rule does not care about averages. Deleting the account cases turns the gate green: the gate is only as good as the set, so golden-set edits need review.

8. **Build task** (`category_gate.py`, per-category ≥ 80%).
   **What you see:** the shipped file fails `Lists differ: [] != ['account: 0/2 passed (0%) < 80%']`; the solution prints `Ran 1 test in 1.235s` … `OK`.
   **What it means:** a 2-case category at 0% hides inside a 90% average; a per-category floor catches it even without a baseline.

Expected (not run here): with `qwen2.5:1.5b`, write a baseline for that model first (`--write-baseline`); a fake-server baseline means nothing for a real model, and its scores will differ.

## Common confusions
**Q:** 90% is close to 95%, so v2 is nearly fine. — **A:** The 10% is *all* account tickets. Look at which cases failed, not the average.

**Q:** Valid JSON means the prompt works. — **A:** t07/t15 were valid JSON; only the exact check against labels caught them.

**Q:** Removing failing cases is a fix. — **A:** Try-it 2 shows 18/18 green with the bug still present.
