# Reliability: timeouts, retries, budgets and fallbacks — explained

## The intuition
A model server is a remote dependency that is sometimes overloaded (HTTP 503) and sometimes slow (a cold GPU), and an agent makes several calls per question. If code does not decide how long to wait, what to retry, how much to spend and what to say when it all fails, the defaults decide: wait forever, retry everything, spend without limit.

`Client._call()` puts a 0.5 s **timeout** on each request and **retries** only 5xx and timeouts (a 4xx is our bug) with **backoff plus jitter**, 3 attempts max. `Client.chat()` adds a **cache** and a **fallback chain** (primary, then a smaller model). `Budget` caps each question at 8 calls, 1,500 tokens, $0.01 — retries included. Any `BudgetExceeded` or `Unavailable` ends in an honest **canned answer**.

Analogy: a fuse (budget), a backup generator (fallback), and "we'll call you back" instead of an endless ring.
Where the analogy breaks: these thresholds are product decisions, not physics.

```
answer(q) ─▶ chat(): cache? ─▶ [fake-model, fake-small]
   _call(): timeout 0.5 s; 5xx/timeout → backoff·jitter → retry (≤3) → give_up → next endpoint
   BudgetExceeded / all Unavailable ─▶ CANNED
```

The one thing to remember: every wait, retry and token must have a limit set in code before the outage, not after.

## Walkthrough: what actually happens when you run it
### Failure lab: a flaky server
1. **Inject.** `compare.py` starts seeded fake servers (rule F, seed 7): 30% of requests get HTTP 503, 20% are delayed by 2 s. Same seed, same request order, same faults every run.
2. **Symptom and diagnosis.** **You run** `python compare.py`.
   **What you see:**
   ```
   naive     wall 20.5 s | slowest question 6.08 s | HTTP calls 44 | tokens 269 | canned 0 | flaky server saw {'requests': 44, '503': 17, 'slow': 10}
   hardened  wall  6.5 s | slowest question 1.74 s | HTTP calls 46 | tokens 132 | canned 1 | flaky server saw {'requests': 43, '503': 17, 'slow': 10}
   hardened events: {'retry': 24, 'call': 19, 'give_up': 3, 'fallback': 3, 'cache_hit': 2, 'canned': 1}
   ```
   **What it means:** both loops met the *same* 17 errors and 10 stalls. The naive loop waited out every 2 s stall and let one runaway question burn most of its 269 tokens. The hardened loop cut stalls at 0.5 s (20.5 s → 6.5 s wall) and spent 132 tokens, with slightly *more* HTTP calls (46 vs 44) — retries are cheap, waiting is expensive. Wall times vary (README: 20.3 s, 6.7 s); tokens, faults and events are deterministic.
3. **Read the event log.** First lines of `reliability.jsonl`, then one of each recovery event:
   ```
   {"event": "retry", "model": "fake-model", "attempt": 0, "error": "timeout", "ms": 502, "sleep_s": 0.033}
   {"event": "retry", "model": "fake-model", "attempt": 1, "error": "http_503", "ms": 3, "sleep_s": 0.058}
   {"event": "call", "model": "fake-model", "attempt": 2, "ms": 2, "tokens": 3}
   {"event": "fallback", "reason": "fake-model: http_503 after 3 attempts"}
   {"event": "cache_hit", "key": "02affd35dcfe"}
   {"event": "canned", "reason": "calls 8 >= 8"}
   ```
   **What it means:** `ms: 502` is the timeout firing on a stall; `sleep_s` grows per attempt (backoff), randomised (jitter). The canned answer came from the call budget.
4. **Fix and proof.** The fix is the hardened client itself; `FailureLab.test_naive_hangs_and_overspends_hardened_stays_bounded` asserts naive max > 4 s and > 250 tokens, hardened max < 3 s and < 150 tokens.

5. **You run** `python -m unittest -v test_try_it_14`.
   **What you see:**
   ```
   observed: canned 1, fallbacks 13, HTTP calls 33
   observed: canned 3, fallbacks 3, HTTP calls 40
   ```
   **What it means / what would look wrong:** with no retries, 13 steps went to the smaller model — retries buy primary-model quality. With no fallback endpoint, 3 users get the canned reply instead of 1.

6. **Build task** (circuit breaker: after 2 consecutive give-ups, skip the endpoint for 5 chats).
   **What you see:** shipped file `AssertionError: Tuples differ: (24, 24) != (24, 9)`; solution `OK`.
   **What it means:** without a breaker the client keeps hammering a dead endpoint (24 calls); with one, it stops paying for doomed retries (9).

Expected (not run here): on Ollama the first request can take seconds while the model loads; warm it, and set timeouts per call type.

## Common confusions
**Q:** Retries make things slower. — **A:** Here a 0.5 s timeout plus retry beat waiting out 2 s stalls.

**Q:** Retry every error. — **A:** A 4xx means our request is wrong; retrying repeats the bug. `_call()` retries only 5xx and timeouts.

**Q:** A budget is only about money. — **A:** It also bounds latency and runaway loops.

## Check your understanding
1. Why does `Budget.before_call()` run inside the retry loop?
<details><summary>Answer</summary>So retries spend the same budget as steps; otherwise a flaky server could cause unbounded calls.</details>

2. What is jitter for?
<details><summary>Answer</summary>Randomising the backoff so many clients do not retry at the same instant and re-overload the server.</details>

3. When is a fallback model acceptable?
<details><summary>Answer</summary>When it passes the golden set for the task (lesson 12); otherwise you trade an outage for wrong answers.</details>
