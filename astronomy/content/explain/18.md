# Time-domain alerts: difference detection, alert schema and broker filters — explained

## The intuition
Subtract a deep reference from tonight's image: constant stars cancel, and what remains — a supernova, a variable, an asteroid — is a candidate. Each becomes a schema-checked alert packet, and a broker classifies and filters the stream so followers get a few real events.

Subtraction works only if the images look alike. Tonight's seeing blurs and thin cloud dims, so plain new − reference leaves a residual at every star. The reference must first be blurred to tonight's seeing and scaled to tonight's transparency.

**Analogy:** a diff of two log files with different timestamps: unless you normalise the format first, every line differs.
Where the analogy breaks: the normalisation is fitted from the data and can fail in ways that look like real signals.

```
reference (sigma 1.2 px) --blur to sqrt(s_new^2 - s_ref^2)--> --fit new = a*ref + b--> matched ref
new - matched ref --> 5-sigma residuals --> packets (schema.py: type, required, enum, min/max)
broker classify(): sharpness, sign, known-variable xmatch 1.5 px, motion a->b
option A: every residual | B: drop bogus | C: B + one alert per object per night + history
```

The one thing to remember: match the images before you subtract them, and let code — not a model — decide the class.

## Walkthrough: what actually happens when you run it
### Step 1 — the shipped stream
**You run** `python alerts.py`

**What happens inside** Eight seeded nights, two exposures each, seeing σ 1.5–2.1 px and transparency 0.75–1.0 against a σ 1.2 px reference. Every packet is validated by `schema.py`.

**What you see**
```
{"option": "A", "alerts_per_night": 192.4, "real_fraction": 0.027, "classes": {"bogus": 944, "moving": 155, "transient": 440}, "schema_errors": 0}
{"option": "C", "alerts_per_night": 58.2, "real_fraction": 0.045, "classes": {"moving": 155, "transient": 311}, "schema_errors": 0}
```

**What it means / what would look wrong** Schema-valid, yet 95 % of option C's alerts are not real.

### Failure lab 1/4 — inject and symptom
**You run** the shipped `difference()`: `new - reference`.

**What happens inside** Each constant star leaves a residual of hundreds of electrons.

**What you see**
```
{"night": 7, "exposure": "a", "objectId": "AKB036007", "class": "transient", "flux": -980.9, "n_prv": 5}
```

**What it means / what would look wrong** A constant star sold as a transient, with five previous detections — the history makes it look more credible, not less.

### Failure lab 2/4 — diagnose
**You run** `BUILD_TARGET=mine python -m unittest test_build_task test_fitness`

**What happens inside** One test images the same stars with worse seeing and 20 % less transparency and no noise; the difference must be about zero.

**What you see**
```
AssertionError: 1965.0921745653166 not less than 20.113176951249866
AssertionError: 58.2 not less than or equal to 6
FAILED (failures=2)
```

**What it means / what would look wrong** A noiseless test isolates the subtraction from the classifier.

### Failure lab 3/4 — fix
**You run** `python solution/alerts.py`

**What happens inside** The reference is blurred with one Gaussian kernel (a simplified Alard & Lupton 1998) and fitted to new = a·ref + b by least squares.

**What you see**
```
{"option": "B", "alerts_per_night": 4.2, "real_fraction": 0.882, "classes": {"known_variable": 3, "moving": 18, "transient": 13}, "schema_errors": 0}
{"option": "C", "alerts_per_night": 3.5, "real_fraction": 0.857, "classes": {"known_variable": 2, "moving": 18, "transient": 8}, "schema_errors": 0}
```

**What it means / what would look wrong** C's volume falls 17-fold (58.2 → 3.5) and the real fraction rises from 4.5 % to 85.7 %.

### Failure lab 4/4 — proof
**You run** `python -m unittest test_build_task test_fitness -v`

**What happens inside** The same tests on the solution.

**What you see**
```
Ran 6 tests in 4.723s
OK
```

**What it means / what would look wrong** `TestFailureLab` in test_alerts.py keeps the fault reproducible.

### Step 2 — agent explains, code decides
**You run** `python agent_assist.py`

**What happens inside** One alert per class goes to the fake model as a facts block; code publishes text only if it names code's class and every number is a fact.

**What you see**
```
{"candid": 23, "code_class": "known_variable", "class_ok": false, "unverified": ["2.5"], "publish": false}
{"candid": 33, "code_class": "moving", "class_ok": true, "unverified": ["2.5"], "publish": false}
```

**What it means / what would look wrong** The model mislabels V1 and invents "2.5"; nothing is published, and the classes are unchanged.

### The decision
**You run** `python try_it.py` and read decisions/0001-alert-broker-design.md.

**What happens inside** The brief: ≤ 6 alerts/night, ≥ 80 % real, the supernova every night from night 3, V1 never a transient, 0 schema errors, classes by code only.

**What you see**
```
1. PSF matched, flux not, option A: 43.8 alerts/night, classes {'bogus': 320, 'known_variable': 2, 'moving': 18, 'transient': 10}
2. no known-variable catalogue: V1 alerts classified as ['transient', 'transient']
```

**What it means / what would look wrong** Both matching steps matter, and the broker depends on the cross-match service. A (9.8/night, 46.2 % real) fails the volume rule; B is purest (88.2 %); C (3.5/night, 85.7 %) adds per-object deduplication and history. The ADR chose C, accepting that an asteroid moving 4 px gets a new objectId each exposure. My numbers match the ADR exactly. `test_fitness.py` replays the 8 nights through C and fails on any rule of the brief.

## Common confusions
- **Q:** "Schema-valid means correct." — **A:** the shipped stream had 0 schema errors and 4.5 % real alerts.
- **Q:** "Blur the new image to match the reference." — **A:** blur the sharper one (the reference), or rings remain.
- **Q:** "History (n_prv) proves an object is real." — **A:** the fake transient AKB036007 had n_prv 5.
