# Survey pipeline architecture: ingest, calibrate, detect, catalogue - throughput measured — explained

## The intuition
A survey pipeline turns each frame into catalogue rows: ingest, calibrate (bias, flat), estimate the sky, detect stars above a threshold. The architecture question is how to split the work — frame by frame, a process pool, or vectorised batches; the science question is whether the detections are right.

Throughput is measured (frames/s, best of 3); correctness is scored against the simulator's truth: completeness (real stars found) and purity (detections that are real). A catalogue hash proves every option produces the same rows.

The trap: the science failure is quiet. One sky level per frame cannot follow a moonlight gradient, so the threshold rises and most stars vanish — while purity stays 1.0.

**Analogy:** an ETL job whose every output row is valid while it silently drops 80 % of the input.
Where the analogy breaks: here only a simulation with known truth says how many stars there were.

```
sim.night() --> 48 raw frames (bytes) + bias + flat + truth
option A: 1 frame/unit, in process | B: spawn Pool(2), 1 frame/task | C: 16-frame batches, vectorised
process(): ingest --> (raw - bias)/flat --> background() --> detect() --> rows
rows --sorted--> catalogue_sha ; score(rows, truth) --> completeness, purity
```

The one thing to remember: measure correctness against truth and speed against a budget; neither alone tells you the pipeline works.

## Walkthrough: what actually happens when you run it
### Step 1 — the shipped pipeline
**You run** `python survey.py`

**What happens inside** `main()` runs each option (A and C best of 3), scores it and hashes the sorted rows.

**What you see**
```
{"option": "A", "frames_per_s": 272.7, "detections": 172, "completeness": 0.1745, "purity": 1.0, "catalogue_sha": "cb7b9698de2d"}
{"option": "B", "frames_per_s": 3.9, "detections": 172, "completeness": 0.1745, "purity": 1.0, "catalogue_sha": "cb7b9698de2d"}
{"option": "C", "frames_per_s": 244.2, "detections": 172, "completeness": 0.1745, "purity": 1.0, "catalogue_sha": "cb7b9698de2d"}
```

**What it means / what would look wrong** All three options agree byte for byte — and all find only 17 % of the stars.

### Step 2 — where the time goes
**You run** `head -3 pipeline_metrics.jsonl`

**What happens inside** `process()` times each stage with `perf_counter()`.

**What you see**
```
{"option": "A", "unit": 0, "frames": 1, "ingest_s": 6e-05, "calibrate_s": 0.0001, "detect_s": 0.0596}
```

**What it means / what would look wrong** Detection dominates; optimising ingest would be wasted effort.

### Failure lab 1/4 — inject and symptom
**You run** the shipped `background()`: `np.median(cal, axis=(1, 2))`, one level per frame.

**What happens inside** The sky rises 300 → 900 e⁻ across the frame; the residual's robust rms includes the gradient, so the 5σ threshold climbs far above the real noise.

**What you see**
```
{"option": "C", "frames_per_s": 244.2, "detections": 172, "completeness": 0.1745, "purity": 1.0, "catalogue_sha": "cb7b9698de2d"}
```

**What it means / what would look wrong** Purity 1.0 looks excellent; only completeness reveals the loss.

### Failure lab 2/4 — diagnose
**You run** `BUILD_TARGET=mine python -m unittest test_build_task test_fitness`

**What happens inside** One test compares the background with the simulator's true sky.

**What you see**
```
AssertionError: 0.9687442122207449 not less than 0.02
AssertionError: 0.1745 not greater than or equal to 0.95
FAILED (failures=3)
```

**What it means / what would look wrong** The background is wrong by up to 97 % of the sky somewhere — the cause, not just the symptom.

### Failure lab 3/4 — fix
**You run** `python solution/survey.py`

**What happens inside** A SExtractor-style mesh: 32 × 32 box medians, bilinear interpolation between box centres, one extrapolated virtual box beyond each edge.

**What you see**
```
{"option": "C", "frames_per_s": 117.4, "detections": 1808, "completeness": 0.9729, "purity": 0.984, "catalogue_sha": "b51fb7f42583"}
```

**What it means / what would look wrong** Ten times more stars; A and B print the same hash.

### Failure lab 4/4 — proof
**You run** `python -m unittest test_build_task test_fitness -v`

**What happens inside** The same tests, plus the fitness function, on the solution.

**What you see**
```
Ran 5 tests in 21.801s
OK
```

**What it means / what would look wrong** `TestFailureLab` in test_survey.py keeps the shipped fault reproducible.

### The decision
**You run** `python try_it.py` and read decisions/0001-survey-pipeline-execution.md.

**What happens inside** The ADR compared A (sequential), B (spawn pool, 2 workers) and C (16-frame batches) against: completeness ≥ 0.95, purity ≥ 0.98, identical catalogues, ≥ 50 frames/s on one core.

**What you see**
```
1. 3 sigma, 32 px mesh: 2597 detections, completeness 0.9739, purity 0.7624
2. 5 sigma, 64 px mesh: 1799 detections, completeness 0.9729, purity 0.98
```

**What it means / what would look wrong** 3σ buys no completeness and wrecks purity; 64 px boxes still pass on a linear gradient. The ADR chose C plus the mesh: one code path for a (B, H, W) stack, no pool until a multi-core host shows a speed-up. My timings differ from the ADR's: A beat C in both runs (C 244.2 and 117.4 frames/s) and B managed 1.9–3.9 (ADR: 10–19). On this noisy shared CPU "C fastest" is not reproduced, but C clears the 50 frames/s budget and B is clearly worst. The fitness function `test_fitness.py` replays the night and fails the build if completeness, purity, identical catalogues or C's throughput fall below the brief.

## Common confusions
- **Q:** "Purity 1.0 means the pipeline is fine." — **A:** completeness 0.1745 shows 83 % of stars missing.
- **Q:** "A process pool is always faster." — **A:** B ran at 1.9–3.9 frames/s: start-up and pickling dominate 128 × 128 frames.
- **Q:** "Throughput numbers are reproducible." — **A:** hashes are; timings vary (C: 244.2, then 117.4).
