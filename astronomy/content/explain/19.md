# Big catalogues: sky indexing, cone-search performance and TAP/ADQL — explained

## The intuition
A cone search returns every source within r of (RA, Dec). Brute force tests a million rows; a zone index tests dozens: declination zones, each sorted by RA, visiting only the zones and RA window the cone can reach, then an exact dot-product test — the brute-force answer, if the window is right.

The RA window is where intuition fails: RA lines converge towards the poles, so a cone spans more than r of RA off the equator (all RA at a pole), and near RA = 0 it wraps to 359.x. Searching RA ± r silently misses rows.

**Analogy:** a database index on (zone, RA): the query planner must turn "within r of a point" into correct key ranges, or rows silently drop out.
Where the analogy breaks: on a sphere the key range depends on declination and can split in two.

```
1M sources (uniform sphere) --Zones(h)--> zones by Dec, each sorted by RA
query(ra, dec, r): zones dec-r..dec+r --ra_windows()--> RA intervals --searchsorted--> candidates
candidates --dot product >= cos r--> result ;  compare with Brute --> wrong_cones
```

The one thing to remember: an index is only correct if its candidate set always contains the exact answer; test it against brute force near poles and across RA = 0.

## Walkthrough: what actually happens when you run it
### Step 1 — the shipped index
**You run** `python catalog.py`

**What happens inside** `make_catalogue(seed=19)` draws a million positions; 600 seeded cones (50 near the poles, 50 across RA = 0) are run through Brute, Zones(h=0.1) and CoarseZones(h=1.0).

**What you see**
```
{"option": "A brute force", "build_s": 0.64, "ms_per_query": 12.3663, "wrong_cones": 0, "sources_found": 16738, "tested_per_query": 1000000}
{"option": "B zones h=0.1", "build_s": 0.94, "ms_per_query": 0.2379, "wrong_cones": 374, "sources_found": 12765, "tested_per_query": 27}
{"option": "C zones h=1.0", "build_s": 0.87, "ms_per_query": 0.0716, "wrong_cones": 374, "sources_found": 12765, "tested_per_query": 43}
```

**What it means / what would look wrong** The index is 50–170× faster and wrong on 374 of 600 cones.

### Failure lab 1/4 — inject and symptom
**You run** the shipped `Zones.ra_windows()`: `[ra - r, ra + r]`.

**What happens inside** No 1/cos Dec widening, no pole case, no wrap; the exact test then only removes candidates, never adds them.

**What you see**
```
{"option": "B zones h=0.1", "build_s": 0.94, "ms_per_query": 0.2379, "wrong_cones": 374, "sources_found": 12765, "tested_per_query": 27}
```

**What it means / what would look wrong** 12765 instead of 16738: every error is a missing source. Nothing crashes.

### Failure lab 2/4 — diagnose
**You run** `BUILD_TARGET=mine python -m unittest test_build_task test_fitness`

**What happens inside** Sub-tests run cones near the poles and across RA = 0 against brute force.

**What you see**
```
FAIL: test_high_declination_and_poles (test_build_task.TestExactConeSearch.test_high_declination_and_poles) (cone=(33.0, 89.6, 0.5))
 ACTUAL: array([], dtype=int64)
FAIL: test_ra_wrap (test_build_task.TestExactConeSearch.test_ra_wrap) (cone=(359.9, -20.0, 0.6))
AssertionError: 374 != 0
```

**What it means / what would look wrong** The pole cone finds nothing; the RA 359.9 cone finds half. The failing cases name the cause.

### Failure lab 3/4 — fix
**You run** `python solution/catalog.py`

**What happens inside** α = atan(sin r / √|cos(δ−r) cos(δ+r)|), the whole zone if |δ| + r ≥ 90, and two windows across 0/360.

**What you see**
```
{"option": "B zones h=0.1", "build_s": 0.74, "ms_per_query": 0.3439, "wrong_cones": 0, "sources_found": 16738, "tested_per_query": 39}
{"option": "C zones h=1.0", "build_s": 0.75, "ms_per_query": 0.0765, "wrong_cones": 0, "sources_found": 16738, "tested_per_query": 62}
```

**What it means / what would look wrong** Exact answers; the candidate count rises a little (27 → 39, 43 → 62) because the windows are now honest.

### Failure lab 4/4 — proof
**You run** `python -m unittest test_build_task test_fitness -v`

**What happens inside** Same tests, solution file.

**What you see**
```
Ran 5 tests in 10.769s
OK
```

**What it means / what would look wrong** `TestFailureLab` in test_catalog.py keeps the fault reproducible.

### The decision
**You run** `python try_it.py` and read decisions/0001-catalogue-index.md.

**What happens inside** The brief: exactly the brute-force answer on every cone, build < 10 s, ≥ 10× faster than brute force, plus an ADQL query for a TAP service.

**What you see**
```
1. zones h=0.01: 2.006 ms/query (brute 14.88), wrong cones 0
1. zones h=1.0: 0.042 ms/query (brute 14.88), wrong cones 0
2. radius 5 deg: brute 6.69 ms, zones h=1.0 0.95 ms -> 7x, wrong 0
```

**What it means / what would look wrong** Finer zones are slower: per-zone Python overhead beats candidate count. So the ADR chose C (h = 1.0, about the typical query radius). Here, C ran at 0.0765 ms vs brute 12.4148 ms, about 160×. One difference from the ADR: big 5° cones gave only 7× here (ADR: 17–31×), a warning that large cones need a batched join instead. The fitness function `test_fitness.py` builds C on the million-row catalogue and fails on any wrong cone, a slow build or less than 10× speed-up (best of 3). The same question for Gaia goes to TAP as `1 = CONTAINS(POINT('ICRS', ra, dec), CIRCLE('ICRS', 83.82, -5.39, 0.05))`. Expected (not run here): pyvo_query.py sends it to the Gaia archive, and healpix_check.py compares HEALPix candidates (CI, macOS/Linux only). Gaia data are CC BY-NC 3.0 IGO, which matters when results are republished (lesson 21).

## Common confusions
- **Q:** "Finer zones are always faster." — **A:** h = 0.01 took 2.006 ms vs 0.042 ms at h = 1.0.
- **Q:** "If no query errors, the index works." — **A:** 374 wrong cones raised nothing.
- **Q:** "RA ± r is fine away from the poles." — **A:** at Dec 60 a cone spans about 2r of RA.
