# Catalogues and cross-matching: angular separation and a k-d tree — explained

## The intuition
Two surveys observe the same sky and each writes a table of positions. Cross-matching asks which row in B is the same star as a row in A: "the nearest one, if close enough". But "near" on a sphere is tricky, and comparing every pair is slow.

One idea fixes both: turn each (RA, Dec) into a 3-D unit vector. The straight-line distance between vectors (the chord) grows with the angle, so the nearest vector is the nearest star, the RA 0/360 wrap disappears, and an ordinary k-d tree can prune most of the search. Blends remain: two B sources may claim the same A source, which the build task resolves.

**Analogy:** a map app's spatial index: it does not measure the distance to every café in the country.
Where the analogy breaks: the sky is a sphere; flat (RA, Dec) distances fail near RA 0 and the poles, so the tree works on 3-D vectors.

```
cat A --unit_vectors()--> xyz --KDTree()--> tree
cat B --unit_vectors()--> q --tree.nearest(q)--> (j, chord)
chord <= 2 sin(r/2) ? match j : -1  --match_one_to_one()--> closest claim wins
```

The one thing to remember: compare positions as unit vectors, never as raw RA differences.

## Walkthrough: what actually happens when you run it
### Step 1 — build and match
**You run** `python crossmatch.py`

**What happens inside** `make_catalogues(seed=7)` puts 2000 A sources around RA 0.5, Dec +28; B is 90 % of A with 0.2 arcsec jitter, plus 200 unrelated and 30 blended sources. `match()` queries the tree for each B vector and accepts chords up to `2*sin(radius/2)`.

**What you see**
```
A 2000 sources, B 2042 sources (1812 true counterparts); the field wraps: 549 sources at RA 359.x deg
matched 1842 within 1 arcsec; correct 1812/1812; median sep 0.233 arcsec
```

**What it means / what would look wrong** Every true pair is found, even across the wrap. A median separation near 1 arcsec would mean you are matching noise.

### Step 2 — work saved, blends, the wrap
**You run** the same command (last lines).

**What happens inside** `KDTree._search()` visits the far child only if the splitting plane is closer than the best distance so far, and counts every distance it computes.

**What you see**
```
k-d tree distance evaluations: 38,999 vs brute force 4,084,000
A sources claimed by more than one B source (blends): 25
RA 359.9999 vs 0.0001 at Dec 28: naive |dRA| = 359.9998 deg, true separation = 0.6357 arcsec
```

**What it means / what would look wrong** About 105× less work, counted identically on every machine. 25 A sources are claimed twice (30 blends were injected). A count near brute force means the pruning test is wrong.

### Step 3 — the build task: one-to-one
**You run** `BUILD_TARGET=mine python -m unittest test_build_task -v`, then `python solution/crossmatch.py`.

**What happens inside** The shipped `match_one_to_one()` returns `match()` unchanged; the solution sorts claims by separation and lets the closest claim own each A source.

**What you see**
```
AssertionError: 1842 != 1817
FAILED (failures=1)
one-to-one: 1817 matches, true counterparts kept 1807/1812, duplicates left 0
```

**What it means / what would look wrong** 25 duplicates are gone; five true pairs lose to a closer blend — the honest cost of the rule. Suite: `Ran 10 tests ... OK (skipped=1)`.

## Common confusions
- **Q:** "Compare |ΔRA| and |ΔDec| with 1 arcsec." — **A:** ΔRA needs cos Dec, and the wrap gives 359.9998 deg; use `angular_sep()` or vectors.
- **Q:** "More matches is better." — **A:** 1842 includes blends; one-to-one gives 1817 with 0 duplicates.
- **Q:** "The tree is approximate." — **A:** pruning only skips branches that cannot hold a closer point; `correct 1812/1812`.
