# Reproducible data pipelines: provenance, caching and versioned inputs — explained

## The intuition
A pipeline caches step results; the cache key decides when an old answer may be reused. Key on something that stays the same while the data change — a file name — and you get yesterday's answer for today's data.

The fix is content addressing: key each result by what went in (a hash of the upstream data), how (a hash of the step's source code) and with what (parameters). Change any of them and the key changes. A provenance log (one JSON line per step, W3C PROV style) records those hashes, so you can later prove which input produced which output.

**Analogy:** a build system: `make` that compares timestamps can be fooled; Bazel-style content hashes cannot.
Where the analogy breaks: science pipelines also have hidden inputs — module constants, environment, library versions — that no function signature shows.

```
data/lightcurve.csv --load--> detrend(window) --> best_period()
each step: key = cache_key(step, ...) --> work/<key> exists? hit : run + store
prov.jsonl: activity, used entity + sha256, upstream_sha256, params, code_sha256, generated_sha256, cache
```

The one thing to remember: a cache key must hash the data and code, not name them.

## Walkthrough: what actually happens when you run it
### Step 1 — the demo
**You run** `python pipeline.py`

**What happens inside** `demo()` wipes work/, runs v1 twice, then replaces lightcurve.csv with the corrected v2 release (telescope B's JD/MJD half-day offset fixed) under the same name and runs again.

**What you see**
```
v1 input        : {'period_d': 0.43049, 'power': 0.5201}
v1 re-run       : {'period_d': 0.43049, 'power': 0.5201}
v2 (corrected)  : {'period_d': 0.43049, 'power': 0.5201}   <- true period 0.3011 d
```

**What it means / what would look wrong** v1 gives an alias caused by the offset — expected. v2 should differ and does not.

### Failure lab 1/4 — inject and symptom
**You run** the shipped `cache_key()`: sha256 of step name, input file name and params.

**What happens inside** v2 has the same name and params, so both keys match v1's and both steps hit.

**What you see**
```
{"activity": "detrend", "used": {"entity": "lightcurve.csv", "sha256": "6141395bece9"}, "upstream_sha256": "5a283c0d0f18", "params": {"window_nights": 5}, "code_sha256": "6d5af32b5516", "generated_sha256": "d3c83e662e46", "cache": "hit"}
```

**What it means / what would look wrong** The log shows a new input hash beside the old output hash and "hit": visible only if you read provenance.

### Failure lab 2/4 — diagnose
**You run** `BUILD_TARGET=mine python -m unittest test_build_task`

**What happens inside** One test swaps in v2; another changes `window_nights` and checks the downstream step.

**What you see**
```
AssertionError: 0.43049 != 0.30112
AssertionError: Lists differ: ['miss', 'miss', 'miss', 'hit'] != ['miss', 'miss', 'miss', 'miss']
```

**What it means / what would look wrong** Two faults: new data are ignored, and an upstream parameter change never reaches the next step.

### Failure lab 3/4 — fix
**You run** `python solution/pipeline.py`

**What happens inside** The key becomes sha256(step, step source code, upstream data, params).

**What you see**
```
v2 (corrected)  : {'period_d': 0.30112, 'power': 0.882}   <- true period 0.3011 d
{"activity": "best_period", "used": {"entity": "lightcurve.csv", "sha256": "6141395bece9"}, "upstream_sha256": "8dbcf371c9c4", "params": {}, "code_sha256": "eaac370b4f42", "generated_sha256": "85c5f7d18979", "cache": "miss"}
```

**What it means / what would look wrong** v2 misses on both steps and finds the true period; the identical v1 rerun still hits.

### Failure lab 4/4 — proof
**You run** `python -m unittest test_build_task -v` and `python -m unittest -v`

**What happens inside** The solution passes; `TestFailureLab` keeps the fault reproducible.

**What you see**
```
Ran 3 tests in 77.841s
OK
Ran 9 tests in 99.782s
OK (skipped=1)
```

**What it means / what would look wrong** The skip is joblib (pending-ci). Expected (not run here): joblib's path-keyed cache goes stale the same way; its data-keyed cache does not.

### Step 2 — hidden inputs and lineage
**You run** `python try_it.py`, then `python solution/lineage.py`

**What happens inside** try_it changes the module constant FREQ, which no key includes; lineage.py walks prov.jsonl back from the result to the input file.

**What you see**
```
2. fixed, FREQ changed: before {'period_d': 0.30112, 'power': 0.882}; after {'period_d': 0.30112, 'power': 0.882}; cache ['miss', 'miss', 'hit', 'hit']
{"activity": "best_period", "params": {}, "code_sha256": "eaac370b4f42", "input_file_sha256": "6141395bece9"}
```

**What it means / what would look wrong** Even the fixed key misses a global it cannot see: make such constants parameters.

## Common confusions
- **Q:** "Hashing the input file is enough." — **A:** downstream steps must hash their upstream result, or `['miss', 'miss', 'miss', 'hit']` happens.
- **Q:** "A cache hit proves nothing changed." — **A:** prov.jsonl shows a new input hash next to a hit.
- **Q:** "Hashing source code covers all code changes." — **A:** not module constants (FREQ).
