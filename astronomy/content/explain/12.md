# Observation planning: airmass, twilight, Moon distance and a scheduler under constraints — explained

## The intuition
A night is a scarce resource with rules: the Sun at least 18° below the horizon, the target's airmass (path through air relative to straight up) at most 2.0 — about 30° altitude — and at least 30° from the Moon. The scheduler walks the night in 10-minute steps and, whenever the telescope is free, starts the valid one-hour block with the lowest airmass.

A scheduler is only as safe as its scoring function. The shipped airmass is the textbook 1/sin(altitude): negative below the horizon, so "lowest airmass wins" prefers stars under the ground.

**Analogy:** a job scheduler that ranks jobs by estimated cost and silently reads an error code of −1 as the cheapest job.
Where the analogy breaks: here a correct formula is used outside its domain; nothing crashes.

```
NIGHT, SITE --grid()--> 10-min steps: Sun alt, Moon RA/Dec (ephem.py)
for each free step k: for each target: observable() at start/middle/end
    sun_alt <= -18  and  airmass(alt) <= 2.0  and  moon_sep >= 30
    best = lowest mean airmass --> 60-min block ; k += 6
```

The one thing to remember: no constraint may be satisfiable by an out-of-domain value.

## Walkthrough: what actually happens when you run it
### Step 1 — the night and the shipped plan
**You run** `python plan.py --check`

**What happens inside** `dark_window()` finds the first and last steps with Sun altitude ≤ −18°. `schedule()` calls `observable()` at block start, middle and end; all three must pass.

**What you see**
```
Gurgaon, India 2026-11-24: astronomical darkness 18:50-05:20 local (10-min grid)
{"target": "Sirius", "start": "18:50", "alt_deg": -34.6, "airmass": -1.76, "moon_sep_deg": 59.5}
unscheduled: ['Aldebaran', 'Capella']
blocks below 30 deg altitude: ['Sirius', 'Vega', 'Fomalhaut', 'Altair']
```

**What it means / what would look wrong** The full Moon sits near Aldebaran, so Aldebaran and Capella never pass the Moon rule — correct. But Sirius is scheduled 34.6° below the ground.

### Failure lab 1/4 — inject and symptom
**You run** the shipped file as is: the fault is its `airmass()`.

**What happens inside** `airmass(-34.6)` = 1/sin(−34.6°) = −1.76, and −1.76 ≤ 2.0 passes; −1.76 also beats every real airmass.

**What you see**
```
{"target": "Altair", "start": "01:10", "alt_deg": -35.0, "airmass": -1.74, "moon_sep_deg": 115.9}
```

**What it means / what would look wrong** Four of six blocks are below the horizon, yet the plan looks complete and plausible.

### Failure lab 2/4 — diagnose
**You run** `BUILD_TARGET=mine python -m unittest test_build_task`

**What happens inside** The test recomputes altitude at start, middle and end of every block with ephem.py, independent of the file under test.

**What you see**
```
AssertionError: -34.57441377066762 not greater than or equal to 29.9
FAILED (failures=15)
```

**What it means / what would look wrong** An independent check, not the planner's own numbers, exposes the fault.

### Failure lab 3/4 — fix
**You run** `python solution/plan.py --check`

**What happens inside** The fixed `airmass()` returns infinity at or below the horizon and Kasten & Young (1989) above it, clamped at 1.

**What you see**
```
{"target": "Deneb", "start": "18:50", "alt_deg": 60.8, "airmass": 1.14, "moon_sep_deg": 83.7}
{"target": "Sirius", "start": "00:10", "alt_deg": 30.2, "airmass": 1.98, "moon_sep_deg": 57.5}
blocks below 30 deg altitude: []
```

**What it means / what would look wrong** Three blocks, all real; Sirius waits until it has risen.

### Failure lab 4/4 — proof
**You run** `python -m unittest test_build_task -v` (default target: the solution), then `python -m unittest -v`.

**What happens inside** The same tests run on `solution/plan.py`; `TestFailureLab` in test_plan.py keeps the shipped fault reproducible.

**What you see**
```
Ran 3 tests in 0.302s
OK
Ran 14 tests in 0.547s
OK (skipped=1)
```

**What it means / what would look wrong** The skip is astroplan. Expected (not run here): astroplan's SequentialScheduler with the same constraints, and Sun/Moon altitudes within 0.1° and 0.5° of ephem.py (pending-ci).

### Step 2 — a different greedy rule
**You run** `python solution/urgent.py`

**What happens inside** Instead of lowest airmass, it starts the valid target that will set soonest.

**What you see**
```
{"target": "Altair", "start": "18:50", "alt_deg": 45.3, "airmass": 1.41, "moon_sep_deg": 112.7}
unscheduled: ['Aldebaran', 'Capella', 'Fomalhaut', 'Vega']
```

**What it means / what would look wrong** Four blocks, not three: greedy-by-airmass is safe, not optimal.

## Common confusions
- **Q:** "1/sin(alt) is wrong." — **A:** it is fine high up; the fault is using it below 0°.
- **Q:** "Checking start and end is enough." — **A:** the middle is checked too, so a target cannot dip out and back.
- **Q:** "Unscheduled means a bug." — **A:** Aldebaran and Capella fail the Moon rule all night.
