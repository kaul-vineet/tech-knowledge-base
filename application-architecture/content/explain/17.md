# Strangler-fig decomposition: facade, branch by abstraction, parallel run, cut-over — explained

## The intuition
You want to move the fines rule out of the Library Loans monolith into its own service. The rule has quirks nobody fully documented (2 grace days, students pay half, a 10.00 cap, cents rounded half-up). Rewriting it is easy; proving the rewrite charges every member the same fine is the hard part.

The strangler fig grows around a tree until the tree can be removed. In code that is four moves, each reversible:
1. **Branch by abstraction:** callers depend on `FinesPort`; only the `LegacyFines` adapter imports `legacy_monolith`. Now there is a seam.
2. **Facade:** one router decides per request: `legacy`, `shadow`, `canary %`, or `service`.
3. **Parallel run (shadow):** call both, *return the legacy answer*, log every difference. Members are protected while you collect evidence.
4. **Cut-over:** only when the evidence meets a written gate, then a sticky canary, then delete the old code.

**Analogy:** a new bridge built beside the old one; traffic stays on the old bridge while engineers run test loads over the new one.
Where the analogy breaks: a shadow run only compares the requests that happened to arrive, so you need a minimum count (1,000) before trusting "0 mismatches".

```
caller ─> FinesPort ─> Facade(mode)
             legacy : LegacyFines.calculate_fine
             shadow : legacy (returned) + HTTP fines_service (compared) ─> out/mismatches.jsonl
             canary : hash(member) % 100 < pct ? service : legacy        (sticky per member)
             service: fines_service only
cutover_decision(): comparisons ≥ 1000 AND mismatch rate ≤ 0.1 % AND candidate errors = 0
fitness_legacy.py : importers of legacy_monolith ⊆ legacy_callers.json (ratchet, may only shrink)
```

**The one thing to remember:** never switch on belief; shadow first, cut over when a measured gate opens, and ratchet the old dependency down.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py`.
   **What happens inside:** `traffic.py` generates 2,000 seeded fine requests (30 % students). In shadow mode the facade calls the monolith in-process and the extracted service over HTTP, compares the two `Decimal` strings, and writes each difference as a JSON line.
   **What you see:**
   ```
   shadow : {'comparisons': 2000, 'mismatches': 108, 'candidate_errors': 0} in 23.9 s over HTTP
   cutover: {'ready': False, 'mismatch_rate': 0.054, 'reasons': ['mismatch rate 5.40% > 0.10%']}
   ```
   **What it means:** the gate is closed for a stated reason. The 23.9 s is the price of shadowing over HTTP on this slow host (the lesson reports 3.0–26.6 s).

2. **You read** `head -2 out/mismatches.jsonl`:
   ```
   {"candidate": "0.62", "control": "0.63", "days_late": 7, "member_type": "student"}
   {"candidate": "0.12", "control": "0.13", "days_late": 3, "member_type": "student"}
   ```
   **What it means:** every mismatch is a student, one cent low. Python's `round()` rounds half to *even*; the monolith rounds half *up*.

3. **Option A, big bang — measured.** `python failure_lab.py`:
   ```
   base    : big-bang would charge 108 of 2000 wrong; shadow found 108 mismatches, members saw 0; cutover ready False ['mismatch rate 5.40% > 0.10%']
   mismatching (type, days late), first 6: [('student', 3), ('student', 7), ('student', 11), ('student', 15), ('student', 19), ('student', 23)]
   ```
   Same 108 differences either way — the difference is *who finds them*: in a big bang, 108 members; in shadow, you, with 0 members affected. The pattern (3, 7, 11 … every 4 days) points at the half-cent case. Option C (branch by abstraction in-process only) gives the same comparison without a network, but no independent deploy, which was the goal — so it is kept as the first step, not the end state.

4. **Fix and re-measure.** `solution/fines_service.py` uses `Decimal` with `ROUND_HALF_UP`. `python app.py --solution`:
   ```
   shadow : {'comparisons': 2000, 'mismatches': 0, 'candidate_errors': 0} in 2.9 s over HTTP
   cutover: {'ready': True, 'mismatch_rate': 0.0, 'reasons': []}
   canary 10%: routed {'legacy': 466, 'service': 34}
   canary 50%: routed {'legacy': 255, 'service': 245}
   ```
   **What it means:** the gate opens. 10 % canary routed 34 of 500, not 50, because buckets are per *member* (sticky), not per request — a member never flips between two fine engines mid-day. Build task: `CHECK_MINE=1` on the base `FAILED (failures=2)` (`test_half_cent_rounds_up_like_the_monolith`, `test_parallel_run_allows_cutover`); solution `Ran 3 tests` … `OK`.

5. **Why the ADR chose option B.** ADR 0001 records the constraint (0 members charged differently), the evidence (108 / 2,000 for big bang; same 108 caught with 0 member impact in shadow), and the costs it accepts: shadow doubles fine work, transitional code must be deleted later, and only read-only operations are safe to compare this way.

6. **How it stays true.** `python fitness_legacy.py; echo exit=$?`:
   ```
   {"budget": "<= 2 known callers, no new ones", "gate": "no-new-legacy-callers", "ok": true, "value": {"callers": 2, "migrated": [], "new": []}}
   exit=0
   ```
   `try_it.py` adds `new_feature.py` importing the monolith: `'ok': False, 'value': {'new': ['new_feature.py'], … 'callers': 3}`. And a fixed service with only 300 shadow requests stays closed: `['only 300 comparisons (< 1000)']`. Suite: `Ran 12 tests in 14.835s` … `OK`.

## Common confusions
**Q:** 0 mismatches means safe to cut over. — **A:** Not with 300 comparisons (try_it [2]); the gate needs ≥ 1,000.

**Q:** Canary 10 % routes exactly 10 % of requests. — **A:** It routes 10 % of *member buckets*: 34 of 500 requests here.

**Q:** The ratchet is about code style. — **A:** It makes "strangling" monotonic: a new importer fails CI, so the monolith cannot regain callers.

## Check your understanding
1. What does the shadow return to the member?
<details><summary>Answer</summary>The legacy answer, always; the candidate's answer is only compared and logged.</details>

2. Why every 4 days late for students?
<details><summary>Answer</summary>Students pay 0.125 per chargeable day (after 2 grace days), so odd day counts end in a half-cent. For 1, 5, 9 … chargeable days (0.125, 0.625 …) the cent digit is even, so half-even rounds down and half-up rounds up; for 3, 7 … (0.375) both round up.</details>

3. What must happen after cut-over?
<details><summary>Answer</summary>Delete the facade, adapter and legacy fine code, and shrink `legacy_callers.json`.</details>
