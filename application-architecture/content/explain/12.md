# CQRS and read models: projections that survive crashes — explained

## The intuition
CQRS splits one model into two. The **write side** (`write_model.py`) takes commands, enforces rules in the aggregate and appends events to an event store. The **read side** (`projector.py`) reads those events and maintains tables shaped for one screen: `member_loans` (how many active loans per member) and `book_status` (who has each book). Queries hit only the read side, so they are cheap.

The price is a gap: the projector polls every 20 ms, so right after a command the view may lag — the *consistency window*. The projector also keeps a **checkpoint** (last `seq` handled) to resume after a restart. If checkpoint and view change are saved separately, a crash between them silently skips or double-counts an event. That is the failure lab.

**Analogy:** a bank statement printed from the ledger: the ledger is truth, the statement a slightly late copy.
Where the analogy breaks: a projector updates incrementally, and an increment applied twice or never is invisible until you compare with the ledger (`drift()`).

```
command ─> LoanCommands ─> EventStore (seq 1..33)  ← truth
                                 │ read_after(checkpoint)
                                 ▼
            Projector.run_once: [checkpoint := seq] … crash? … [apply(event)]   ← base: 2 transactions
            solution:          BEGIN apply(event); checkpoint := seq COMMIT      ← 1 transaction
                                 ▼
            LoansView (member_loans, book_status) ── drift(store, view) == [] ?
```

**The one thing to remember:** the view and its checkpoint must commit together, and handlers must be safe to apply twice; the read model can always be rebuilt from the events.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py`.
   **What happens inside:** a seeded workload sends 40 commands; the aggregate rejects 7. A projector thread polls every 20 ms and logs `lag_ms` (now minus the event's `recorded_at`) for each event. A reader queries right after each command. Finally `rebuild()` deletes the view, replays from seq 0 and compares.
   **What you see:**
   ```
   write side : 40 commands -> 33 events, 7 rejected by the aggregate
   read side  : consistency window from the projector log: p50 16.3 ms, p95 57.9 ms, max 58.1 ms (poll every 20 ms)
   stale reads: 28 of 33 reads straight after the command did not see it yet
   view       : {'m1': 2, 'm2': 3, 'm3': 2}
   rebuild    : replayed 33 events, view identical: True, drift: []
   ```
   **What it means:** most reads straight after a write are stale — normal eventual consistency. The lesson says p50 "about 10 ms"; I measured 16.3 ms on this slow mount. A max far above the poll interval would point at a stuck projector.

2. **You run** `wc -l out/projector.jsonl` → `33 out/projector.jsonl`; first line `{"evt": "projected", "lag_ms": 20.3, … "seq": 1, "type": "LoanCreated"}` — one structured line per event.

## Failure lab: crash the projector
- **Inject:** `python failure_lab.py`. `random.Random(12)` picks seq 31; the base projector saves checkpoint 31, then raises `SimulatedCrash` before applying event 31. A new `Projector` restarts on the same read database.
- **Symptom:**
  ```
  base     projector.py: projector died at seq 31; restarted at position 33 of 33; drift: 2 row(s)
      member_loans[m3]: view 1, events say 2
      book_status[b6]: view None, events say 'm3'
  ```
  No exception after the restart; position 33 of 33 looks healthy.
- **Diagnose:** the checkpoint said 31 was done, so `read_after(31)` started at 32 and event 31 (m3 borrows b6) was never applied. `drift()` finds it by recomputing the view from the event store.
- **Fix:** `solution/projector.py` puts `apply` and the checkpoint in one `with self.db:` and recounts `active` from `book_status` instead of `active + 1`. For a view that is already wrong, `rebuild()`: `recovery: rebuild() -> drift []`.
- **Proof:** `solution projector.py: … drift: 0 row(s)`. With `CHECK_MINE=1` the build-task tests run on the base file: `Ran 3 tests` … `FAILED (failures=3)`; on the solution: `Ran 3 tests` … `OK`. The 11 lab tests pass (`Ran 11 tests in 0.342s`).

**Try it** (`python try_it.py`): a 200 ms poll raised p50 from 13.1 ms to 123.3 ms; and the "half fix" (apply first, checkpoint second, still two transactions) fails the other way: `drift: ['member_loans[m3]: view 3, events say 2']` — event 31 was applied twice.

## Common confusions
**Q:** Stale reads mean the projector is broken. — **A:** 28 of 33 stale reads with `drift: []` is the designed window; drift, not staleness, is the bug.

**Q:** Moving the checkpoint after apply fixes it. — **A:** try_it [2]: it turns a skip into a double count (`view 3`).

**Q:** A wrong view needs a data-repair script. — **A:** `rebuild()` replays the log; the read model is disposable.
