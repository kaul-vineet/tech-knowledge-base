# SLOs and error budgets: burn-rate alerts from request logs — explained

## The intuition
An SLI is a ratio counted from logs (good / all requests); an SLO is its target ("99.9 % over 30 days"). The **error budget** is the remainder: 0.1 % of requests may fail. The **burn rate** is how fast you spend it: burn 1 lasts exactly 30 days; burn 14.4 spends 2 % in one hour — page-worthy.

Two windows (1 h *and* 5 min) answer "is it serious?" and "is it still happening?". And the SLI must *count* bad requests: a mean lets many fast requests drown a few very slow ones.

**Analogy:** a monthly mobile-data allowance. The budget is the allowance; the burn rate is "at today's pace I run out on day 3".
Where the analogy breaks: for latency you must first *define* a bad request (over 300 ms); using a mean silently changes the question.

```
out/requests.jsonl ─> parse() ─> window(now-1h) ─> bad_ratio(sli) ─> burn = bad_ratio / (1 - SLO)
     availability: bad = status 5xx            SLO 0.999
     latency     : bad = POST /loans > 300 ms  SLO 0.99   (solution)
alerts(): page if burn(1h) > 14.4 AND burn(5m) > 14.4 ; page 6h/30m > 6 ; ticket 3d/6h > 1
```

**The one thing to remember:** count bad events against a budget and alert on how fast it burns — never alert on a mean.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py`.
   **What happens inside:** `traffic.py` (seed 15) writes 3 days of requests to `out/requests.jsonl`; `slo.py` computes availability, burn rates per window and last-hour percentiles; `mean check` compares the mean with 200 ms.
   **What you see:**
   ```
   log        : out/requests.jsonl, 25920 requests, 2026-10-25T12:00:00Z .. 2026-10-28T11:59:50Z
   availability: SLI 3d 99.9884% vs SLO 99.9%; budget used in 3d: 1.2% of 30 days; burn rates {'5m': 0.0, '1h': 0.0, '6h': 0.0, '3d': 0.1}
   latency 1h : {'mean': 147.9, 'p50': 42.9, 'p95': 94.3, 'p99': 2846.3, 'requests': 360}
   mean check : OK
   alerts     : none
   ```
   **What it means:** 25920 = 3 days × 8640 ten-second slots. Availability is healthy, but p99 is 19 times the mean while "mean check: OK" — that contradiction is the failure lab.

## Failure lab: a slow tail the mean cannot see
- **Inject:** the seeded traffic already contains it: from 10:30 UTC, 20 % of `POST /loans` take 2.4–3.0 s. Run `python failure_lab.py`.
- **Symptom:**
  ```
  last hour  : mean 147.9 ms, p95 94.3 ms, p99 2846.3 ms
  base     slo.py (mean <= 200 ms): latency problems none; alerts none
  ```
- **Diagnose:** POST /loans is a minority of the 360 requests, so even p95 stays at 94.3 ms. A mean ≤ 200 ms rule is blind to "1 in 5 borrows takes 3 seconds".
- **Fix:** `solution/slo.py` adds a latency SLI: bad = `POST /loans` over `LATENCY_THRESHOLD_MS = 300`, SLO 0.99, with the same multi-window burn-rate table.
- **Proof:**
  ```
  solution slo.py (latency SLI): latency problems ['latency page: burn 19.7 over 1h/5m']; alerts [{… 'burn_long': 19.7, 'burn_short': 33.3, 'threshold': 14.4}]
  ```
  Burn 19.7 means about 19.7 % of POST /loans in the last hour were bad (0.197 / 0.01). Build task with `CHECK_MINE=1` on the base file: `FAILED (failures=1, errors=1)` — the lesson says "2 of 3 fail"; here one is an error (`KeyError: 'latency'`, no latency SLO exists) and one a failure (`[] != [('latency', 'page', '1h/5m')]`). On the solution: `Ran 3 tests` … `OK`. Full suite: `Ran 17 tests in 20.972s` … `OK`.

**Try it** (`python try_it.py`): replaying the day, the page fires at 11:27 UTC, 57 min after the incident starts (`burn_long 16.4`) — detection time is a design parameter, not free. With 5 % slow instead of 20 %: `'1h': 1.4 … alerts none` — a real but slow burn that only a ticket window would catch.

**Agent assist** (`python agent_assist.py`): code computes the facts; draft 1 is `REJECTED` (`p99 is 2846.3, the draft says 147.9`), attempt 2 `OK`; a human posts it. Prometheus recording rules for the same SLI — Expected (not run here).

## Common confusions
**Q:** p95 is enough. — **A:** p95 was 94.3 ms during the incident; the bad requests were under 5 % of all traffic.

**Q:** Burn rate 19.7 means 19.7 % of the budget is gone. — **A:** It is a *speed*: at this rate a 30-day budget lasts about 1.5 days. The last hour used 2.7 % of it (agent facts).

**Q:** Alert on the 5-minute window alone. — **A:** It flaps on noise; the long window confirms significance.
