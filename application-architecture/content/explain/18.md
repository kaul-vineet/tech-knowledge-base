# Multi-tenancy: shared schema vs schema per tenant vs database per tenant — explained

## The intuition
Fifty small libraries will share one hosted Library Loans. Every library (tenant) must see only its own rows, the codebase must stay one codebase, and a big library's bulk import should not freeze the small ones. There are three classic ways to lay out the data:

- **Shared schema:** one `loans` table with a `tenant_id` column. Cheapest to run and migrate; isolation depends on every query remembering `WHERE tenant_id = ?`.
- **Schema per tenant:** one table per tenant in the same database. Names separate tenants; migrations fan out per tenant; writes still share one database (in SQLite, one writer per file).
- **Database per tenant:** one SQLite file each. The connection *is* the boundary, and writes are isolated; migrations fan out per file.

None is "the secure one": each trades a different risk, so the choice is made on measurements. Then, because the chosen layout relies on discipline, two guards make the discipline checkable.

**Analogy:** an office building: open-plan floor (shared), separate rooms on one floor (schema), separate buildings (database).
Where the analogy breaks: in an open-plan office you can see the neighbour; in a shared schema you see *nothing* wrong — a missing filter returns other libraries' rows silently, with a normal-looking result.

```
TenantSession(lib00) ─> repository.overdue_report(conn, tenant)
                          SQL ─> TenantGuard(trace callback): statement carries 'lib00'? else violation
fitness_tenant.py (CI): ast over string constants: SQL on a tenant table without "tenant_id = ?" → fail
layouts measured by app.py: isolation (rows, leaked) · noisy_neighbour (writes blocked) · migration (DDL, files, ms)
```

**The one thing to remember:** pick the cheapest layout that meets the constraints, then make tenant scoping a CI gate and a runtime check, not a code-review hope.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py` (each layout gets 50 libraries × 40 loans and the same faulty overdue query).
   **What you see:**
   ```
   {"layout": "shared-schema", "isolation": {"rows": 700, "leaked": 686, "guard_violations": 1}, "noisy_neighbour": {"attempts": 20, "blocked": 20}, "migration": {"ddl_statements": 1, "files": 1, "ms": 36.6}}
   {"layout": "schema-per-tenant", "isolation": {"rows": 14, "leaked": 0, "guard_violations": 1}, "noisy_neighbour": {"attempts": 20, "blocked": 20}, "migration": {"ddl_statements": 50, "files": 1, "ms": 372.1}}
   {"layout": "db-per-tenant", "isolation": {"rows": 14, "leaked": 0, "guard_violations": 1}, "noisy_neighbour": {"attempts": 20, "blocked": 0}, "migration": {"ddl_statements": 50, "files": 50, "ms": 812.1}}
   ```
   **What happens inside / what it means:** *isolation* runs lib00's overdue report: 700 rows in shared, 686 of them other libraries' (only 14 are lib00's). Per-tenant layouts return 14 — but the guard still counts 1 violation, because the *query* is still unscoped; the layout merely hid the bug. *noisy_neighbour* holds `BEGIN IMMEDIATE` for one tenant while a second tenant tries 20 writes with `timeout=0`: blocked 20 wherever tenants share a file, 0 with a file each. *migration* adds a column: 1 statement vs 50 (my times 36.6 ms vs 812.1 ms; the lesson saw 9–54 ms vs 0.45–4.5 s — same order).

2. **Options against constraints.** Schema per tenant pays the 50-migration cost *and* still blocks neighbours, and `try_it.py` adds a scaling limit: `[1] attached 10 tenant files, then: too many attached databases - max 10`. It is dominated: rejected. Database per tenant wins isolation and writes but multiplies operations. Shared schema is cheapest and meets "one schema change, one migration" — if the leak can be made impossible.

3. **The failure that decides the guards:** `python failure_lab.py`:
   ```
   base    : lib00 overdue report returns 700 rows, 686 from other libraries; guard violations 1; static gate ok=False
       guard saw: SELECT id, member_id, book_id, due FROM loans WHERE due < '2026-10-28' ORDER BY id
   solution: lib00 overdue report returns 14 rows, 0 from other libraries; guard violations 0; static gate ok=True
   ```
   The fix is one clause: `WHERE tenant_id = ? AND due < ?`. Build task: `CHECK_MINE=1` on the base `FAILED (failures=3)`; solution `Ran 3 tests` … `OK`.

4. **Why ADR 0002 chose shared schema + two guards.** Default tier: shared schema, `tenant_id` first in every index. Isolation is enforced twice — statically and at runtime — because "one missed filter would leak everything". Libraries that need write isolation or their own restore move to a database-per-tenant premium tier; the same repository code runs there because every statement is already scoped. Bulk imports in the shared file must be chunked into short transactions.

5. **How it stays true.** `python fitness_tenant.py; echo exit=$?` on the base code:
   ```
   {"gate": "tenant-scoped-queries", "ok": false, "value": ["repository.py:8 SELECT id, member_id, book_id, due FROM {table} WHERE due < ? ORDER BY id"], "budget": 0}
   exit=1
   ```
   The static gate reads string constants with `ast`, so it catches the query before it runs. The runtime guard catches what static analysis misses, e.g. a correctly-shaped query with the wrong tenant: `[2] session lib00 queries tenant_id='lib01' -> 6 rows; guard violations ["SELECT id FROM loans WHERE tenant_id = 'lib01'"]`. Suite: `Ran 9 tests in 2.719s` … `OK`.

## Common confusions
**Q:** Database per tenant makes the bug go away. — **A:** It hides it: rows 14, but `guard_violations 1`; the query would leak the day the tenant moves to the shared tier.

**Q:** The static gate is enough. — **A:** try_it [2] passes it (`tenant_id = ...` is present) yet reads lib01; the runtime guard checks the *value*.

**Q:** Shared schema cannot isolate writes. — **A:** Correct in SQLite (one writer per file, 20 of 20 blocked); hence chunked imports or the premium tier.

## Check your understanding
1. Why does schema-per-tenant still block 20 of 20 writes?
<details><summary>Answer</summary>All tenants' tables live in one SQLite file, and SQLite allows one writer per file.</details>

2. What does `TenantGuard` check that `fitness_tenant.py` cannot?
<details><summary>Answer</summary>That each executed statement carries the *current session's* tenant id.</details>

3. What would PostgreSQL add?
<details><summary>Answer</summary>Row-level security as a third guard inside the database (the ADR's consequence).</details>
