# Testing pyramid: unit, integration, end-to-end – measured — explained

## The intuition
A unit test calls `LoanService` with an in-memory store: no I/O. An integration test runs the real SQLite store against a file: it catches mapping bugs (types, ordering, persistence) a fake hides. An end-to-end test calls the HTTP server over a socket: it catches wiring bugs (status codes, JSON) and costs most.

The pyramid says: many cheap tests at the bottom, few expensive ones on top, because each layer catches a *different kind* of bug at a very different price. `pyramid.py` measures that instead of asserting it.

**Analogy:** checking a car: test each part on the bench (unit), test the engine on a stand (integration), then one test drive (e2e).
Where the analogy breaks: in software the "test drive" is not proportionally richer — try_it [2] shows each bug was caught by exactly one layer, not by the e2e test alone.

```
              /\        e2e (1)          http_api + sqlite + socket   ~seconds
             /  \       integration (4)  SqliteLoanStore + file       ~100 ms – s
            /____\      unit (8)         LoanService + memory store   ~0.03–0.3 ms
pyramid.py: run_layer(pattern) ─> TimingResult.durations ─> mean ms ─> shape_problems()
```

**The one thing to remember:** put each test at the lowest layer that can catch the bug, and measure the cost instead of guessing it.

## Walkthrough: what actually happens when you run it
1. **You run** `python pyramid.py`.
   **What happens inside:** for each `(layer, pattern)` in `LAYERS`, `run_layer` discovers matching files and runs them with a `TimingResult` whose `startTest`/`stopTest` record `perf_counter()` deltas. `shape_problems` checks counts unit ≥ integration ≥ e2e ≥ 1.
   **What you see:**
   ```
   layer        tests  skipped  failed  total ms  mean ms
   unit             8        0       0       2.9     0.34
   integration      4        3       0   16819.8  4204.89
   e2e              1        0       0    7061.0  7060.92
   one e2e test costs about as much as 20,630 unit tests (about 10^4)
   pyramid OK
   ```
   **What it means:** the 3 skipped are the PostgreSQL tests (no container here). My integration mean (4204.89 ms) is far above the README's 87.60 ms because this sandbox's storage is very slow for SQLite writes; the README itself reports 82–201 ms across its runs. The *order* of layers held, and that is the claim being tested.

2. **You run** `python try_it.py`.
   **What happens inside:** [1] re-runs `pyramid.py` and extracts the means; [2] plants one bug at a time in a scratch copy and counts failures per layer.
   **What you see:**
   ```
   [1] mean ms: unit 0.03, integration 119.06, e2e 15394.64 -> one e2e test = 481,818 unit tests (10^6)
   [2] sqlite_store.py: bool(row[3]) -> row[3]      failed tests -> unit 0, integration 1, e2e 0
   [2] http_api.py: BookAlreadyOnLoan 409 -> 422    failed tests -> unit 0, integration 0, e2e 1
   ```
   **What it means:** the ratio moved from 10^4 to 10^6 between two runs minutes apart: timing is noisy, so the lab budgets orders of magnitude, not exact values. The store bug (returning `0` instead of `False`) is invisible to units because they use the memory store; the status-code bug is invisible to everything but e2e. Deleting either layer would ship one of these bugs.

3. **You run** `python -m unittest -v` → `Ran 20 tests in 18.604s` … `OK (skipped=3)`.

4. **Real PostgreSQL (CI):** with `LOANS_TESTCONTAINERS=1` and a container engine, the 3 skipped contract tests run against `postgres:16-alpine` — Expected (not run here): they pass (pending-ci per the lesson).

## Common confusions
**Q:** More e2e tests make the suite safer. — **A:** try_it [2]: e2e caught 0 of the store bug. Each layer has a blind spot.

**Q:** The numbers in the README are what I should see. — **A:** Mine differed by 50×; read the layer order and the order of magnitude.

**Q:** Skipped tests are failures. — **A:** The 3 skips are opt-in (`LOANS_TESTCONTAINERS=1`), not a red build.
