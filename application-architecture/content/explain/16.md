# Performance and architecture fitness functions in CI — explained

## The intuition
A fitness function is a test for an architectural property rather than a feature: "the domain imports no adapters", "the overdue report uses at most 2 SQL statements", "p95 under 200 ms". `fitness.py` runs four such gates and exits 1 if any fails, so CI blocks the merge.

The interesting lesson is *which* gate catches a performance bug. Timing gates are noisy and depend on the machine; the lab's local SQLite is so fast that even a terrible query pattern stays inside the 200 ms budget. A **query-count** gate is deterministic: same data, same count, on every machine. The N+1 pattern — one query for the list, then one or two more per row — shows up as a count that grows with the data, long before it shows up as latency in production, where every statement is a network round trip.

**Analogy:** a building inspector who counts fire exits per floor instead of timing one evacuation drill on a quiet day.
Where the analogy breaks: an exit count is a proxy; a single slow JOIN would pass the query-count gate, which is why the timing gates stay too.

```
fitness.py main()
  gate_import_boundaries()  ast: domain.py imports no sqlite3/http          → ok
  gate_query_count(repo)    QueryCounter(set_trace_callback) at 10 and 500 loans; max ≤ 2
  gate_microbenchmark()     timeit best of 5×5 ≤ 50 ms
  gate_response_time()      start http_api, run_load(4 users × 10) p95 ≤ 200 ms, errors 0
  → one JSON line per gate → "fitness: FAILED …" → exit 1
```

**The one thing to remember:** gate on what is deterministic (counts, imports) and keep timing gates loose; a count that grows with data is the early warning.

## Walkthrough: what actually happens when you run it
1. **You run** `python fitness.py; echo exit=$?`.
   **What happens inside:** `QueryCounter` uses `conn.set_trace_callback` to record every executed statement while `overdue_report` runs.
   **What you see:**
   ```
   {"budget": 2, "gate": "query-count", "ok": false, "value": {"10": 11, "500": 337}}
   {"budget": 50, "gate": "micro-benchmark", "ok": true, "value": 2.33}
   {"budget": 200, "gate": "response-time-p95", "ok": true, "value": {"errors": 0, "max_ms": 84.0, "p50_ms": 23.8, "p95_ms": 80.1, "requests": 40}}
   fitness: FAILED query-count
   exit=1
   ```
   **What it means:** 11 statements for 10 loans, 337 for 500: 1 + 2 per overdue loan (168 overdue → 1 + 336). Both timing gates pass comfortably.

## Failure lab: an N+1 "readability" refactor
- **Inject:** the base `loans_repo.overdue_report()` loads loans, then selects the member and the book per overdue loan. Run `python failure_lab.py`.
- **Symptom:**
  ```
  same report rows (unit-test view): True, 168 overdue loans
  base     (after refactor): query-count {10: 11, 500: 337} -> FAIL; p95 52.4 ms -> PASS; with 0.5 ms round trips: 209.8 ms per report
  ```
  Same rows, green unit tests, green p95.
- **Diagnose:** the trace shows the shape: `SELECT id, member_id, book_id, due FROM loans …`, then `SELECT name FROM members WHERE id = 15`, `SELECT title FROM books WHERE id = 229`, repeated. `with_round_trips` sleeps 0.5 ms per statement to imitate a networked database: 337 × 0.5 = 168.5 ms minimum; sleep overshoot made it 209.8 ms here (the lesson says about 340 ms — sleep accuracy differs per OS).
- **Fix:** one JOIN with the overdue filter in SQL (`solution/loans_repo.py`).
- **Proof:**
  ```
  solution (one JOIN)     : query-count {10: 1, 500: 1} -> PASS; p95 34.8 ms -> PASS; with 0.5 ms round trips: 1.4 ms per report
  ```
  `python fitness.py --solution` → `fitness: all gates passed`, `exit=0`. Build task: `CHECK_MINE=1` on the base `FAILED (failures=2)` (`test_query_count_does_not_grow_with_the_data`, `test_all_fitness_gates_pass`); solution `Ran 3 tests` … `OK`. Suite: `Ran 10 tests in 3.301s` … `OK`.

**Load test by hand:** `python http_api.py 18016`, then `python load_test.py http://127.0.0.1:18016/reports/overdue` → `{"requests": 80, "errors": 0, "p50_ms": 22.4, "p95_ms": 81.9, "max_ms": 84.4}`. The lesson step says 40 requests; the CLI default is 8 users × 10, while the CI gate uses 4 × 10 = 40. k6 with `p(95)<200` thresholds — Expected (not run here): exit 0 when both thresholds hold.

**Try it** (`python try_it.py`): in-process, `{'N+1': 3.4, 'JOIN': 0.41}` ms — an 8× gap that no 50 ms budget would notice; and adding `import sqlite3` to `domain.py` flips `import-boundaries` to `ok: False`.

## Common confusions
**Q:** p95 passed, so performance is fine. — **A:** p95 52.4 ms passed while 337 statements per report waited for a networked database.

**Q:** Tight timing budgets catch regressions. — **A:** They flake across machines; the query count was identical everywhere and failed first.

**Q:** N+1 is an ORM problem. — **A:** This lab has no ORM; it is plain SQL in a loop.
