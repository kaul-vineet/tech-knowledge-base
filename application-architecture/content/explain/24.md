# Foundations II: quality attributes and trade-off analysis – ISO/IEC 25010, ATAM and availability maths — explained

## The big picture
Several labs used availability numbers as if they were obvious. "SLOs and error budgets: burn-rate alerts from request logs" turned 99.9 % into a budget of minutes. "Resilience patterns: timeouts, circuit breaker, bulkhead, fallback" added redundancy and isolation. "Cost and capacity planning: Little's law, benchmarks, headroom, cost per request" added an N+1 spare. "Multi-tenancy: shared schema vs schema per tenant vs database per tenant" picked a layout by weighing criteria. This lesson supplies the maths: how availabilities combine, what a "nine" buys, why repair time matters, and when a weighted decision flips. ISO/IEC 25010 names the qualities; ATAM's utility tree ranks them; `check_quality.py` checks each formula by enumeration and simulation.

### T24.1 Series composition and its bounds
**In plain words:** if a request needs every component, multiply their availabilities (when failures are independent). Without independence you still know the answer lies between "unavailabilities add up" and "the weakest component".

**Why it is true (intuition):** the request is up only when *all* parts are up; independent events multiply. It is never more available than its weakest part, and never loses more than the sum of what each part loses.

Proof skeleton:
1. "Service up" is the intersection of "component i up".
2. Independence: P(∩Uᵢ) = ∏Aᵢ.
3. The intersection is inside each Uⱼ, so A ≤ min Aᵢ.
4. Boole's inequality on the complements gives A ≥ 1 − Σ(1 − Aᵢ).

**See it in numbers:**
```
  [OK] one API instance: series 99.3409%; union bound 99.3400% <= A <= min 99.50%
```
LB 99.99 % × API 99.5 % × DB 99.9 % × IdP 99.95 % = 99.3409 %. The union bound (99.3400 %) is almost equal because unavailabilities are small — the "they roughly add" rule.

**Where it shows up in practice:** every hop in lesson 13's borrow path multiplies in.

### T24.2 Parallel redundancy and k-of-n
**In plain words:** with independent replicas where any one suffices, the tier is down only if *all* are down: A = 1 − ∏(1 − Aᵢ). If you need at least k of n, count with the binomial distribution.

**Why it is true (intuition):** "all down" is one event; independent "down" probabilities multiply; take the complement. The number of replicas up is a sum of coin flips.

Proof skeleton:
1. Parallel tier down ⇔ every replica down.
2. Independence: P = ∏(1 − Aᵢ); complement gives A.
3. X = replicas up ~ Binomial(n, a); P(X ≥ k) = Σ C(n, j) aʲ(1 − a)ⁿ⁻ʲ.
4. k = 1 reduces to the parallel formula.

**See it in numbers:**
```
  [OK] Library Loans (LB, 2 API replicas, DB, IdP): formula 99.837569% = enumeration of 32 states 99.837569% (|diff| 1.1e-16)
  [OK] Monte Carlo 400,000 trials: 99.8363% within 4 sigma (0.0255%) of the formula
      adding the 2nd API replica: 99.3409% -> 99.8376%; a 3rd: 99.8401% (the database is now the limit: 99.90%)
  [OK] 2-of-3 replicas at 99%: binomial 99.970200% = enumeration 99.970200%
```
The formula matches brute-force enumeration of all 2⁵ = 32 up/down states exactly, and simulation within noise. A 2nd replica gains half a percent; a 3rd gains 0.0025 % because T24.1's upper bound now binds on the database.

**Where it shows up in practice:** lesson 21's N+1 spare is a 2-of-3 argument for capacity, not just uptime.

### T24.3 Nines, downtime and steady-state availability
**In plain words:** each extra nine divides allowed downtime by 10. Over the long run, the fraction of time up is MTTF / (MTTF + MTTR), whatever the shape of the failure and repair times.

**Why it is true (intuition):** downtime is (1 − A) × period, and one nine divides (1 − A) by 10. For the second part, every "up then repair" cycle is a fresh, independent copy of the same story, so the long-run share of up time is the average up time over the average cycle.

Proof skeleton:
1. Downtime = (1 − A)·T by definition.
2. One more nine: (1 − A) → (1 − A)/10.
3. Up+repair cycles are i.i.d. renewal cycles.
4. Renewal-reward theorem: long-run up share = E[up] / E[cycle] = MTTF / (MTTF + MTTR).

**See it in numbers:**
```
       99.900%          43.20     8.760
       99.950%          21.60     4.380
  [OK] MTTF 720 h, MTTR 1 h, exponential repair: simulated up fraction 99.86079% vs formula 99.86130%
  [OK] MTTF 720 h, MTTR 1 h, uniform repair: simulated up fraction 99.86142% vs formula 99.86130%
```
43.20 minutes per 30 days is lesson 15's 99.9 % budget. Two very different repair distributions give the same answer, as the theorem promises.

**Where it shows up in practice:** lesson 15's burn rate is spending exactly this budget.

### T24.4 Break-even weight between two options
**In plain words:** when two options are scored on two criteria with weights w and 1 − w, the preferred option can flip at most once as w moves from 0 to 1, at w* = d₂ / (d₂ − d₁).

**Why it is true (intuition):** the score difference is a straight line in w. A straight line crosses zero at most once, and only if its two ends have opposite signs.

Proof skeleton:
1. Δ(w) = w·d₁ + (1 − w)·d₂ = d₂ + w(d₁ − d₂): affine.
2. Δ(0) = d₂, Δ(1) = d₁.
3. A root in (0, 1) exists iff d₁, d₂ have opposite signs; it is w* = d₂ / (d₂ − d₁).

**See it in numbers:**
```
  [OK] SQLite (0.4, 0.9) vs replicated PostgreSQL (0.95, 0.5): w* = 0.4211; sweep flips at [0.4211]
  [OK] 2,000 random option pairs: sign changes match the formula (0 mismatches)
```
If stakeholders weight availability above 0.4211, PostgreSQL wins. In ATAM terms that weight is a *sensitivity point*, and storage is a *trade-off point*.

**Where it shows up in practice:** lesson 18's ADR chose a layout; recording the weights makes such a choice auditable.

## Worked problems
**P24-5 — common cause.** Two 99.5 % API replicas share one flag store (99.9 %).
1. Naive: 1 − 0.005² = 0.999975. *Why:* T24.2 assuming independence.
2. Model the truth: the tier works iff the flag store is up **and** at least one replica is up. *Why:* the shared store is in series with the parallel pair.
3. 0.999 × 0.999975 = 0.998975 → 99.8975 % vs 99.9975 % assumed (`OK  P24-5` in `l500_checks.py`).
4. Unavailability 0.001025 vs 0.000025: about 41 times larger. *Why it matters:* redundancy cannot beat a shared dependency (T24.1 upper bound).

**P24-7 — break-even.** SQLite (0.40, 0.90), PostgreSQL (0.95, 0.50).
1. d = SQLite − PostgreSQL = (−0.55, 0.40). *Why:* T24.4 works on differences.
2. Opposite signs → a flip exists. w* = 0.40 / (0.40 + 0.55) = 0.421.
3. At w = 0.6: SQLite 0.6·0.40 + 0.4·0.90 = 0.600; PostgreSQL 0.6·0.95 + 0.4·0.50 = 0.770 (`OK  P24-7`).
4. *Why it matters:* the "answer" is a weight someone chose; write it in the ADR.

## Common confusions
**Q:** Two replicas always add a nine. — **A:** Only if independent; P24-5 loses most of it to one shared store.

**Q:** Raising MTTF is the way to more nines. — **A:** MTTR counts equally; P24-6 needs MTTR ≤ 0.360 h for 99.95 %.

**Q:** Weighted scoring gives an objective answer. — **A:** It flips at w* = 0.4211; the weight is a judgement.
