# Cost and capacity planning: Little's law, benchmarks, headroom, cost per request — explained

## The intuition
Capacity planning answers "how many instances?" with arithmetic you can show. Four ideas carry the whole lab:

- **Demand from real logs.** `load_model()` reads lesson 15's request log (0.1 req/s per library), scales it to 400 libraries and multiplies by a peak factor of 3: average 40, peak 120 req/s. You size for the **peak**, not the average.
- **Little's law:** requests in flight = arrival rate × time in system (L = λ × W). At 120 req/s and 45.2 ms that is 5.4 — it tells you how many workers or connections must exist at once.
- **Benchmarked capacity, not theoretical.** One instance has 4 workers; at 100 % busy it could do c / S = 4 / 0.0452 s ≈ 88.5 req/s, but long before that queues explode. `benchmark()` simulates arrivals and finds the highest rate whose p99 still meets the 300 ms SLO: 75 req/s.
- **Headroom and N+1.** Plan to use at most 80 % of that capacity at peak, then add one spare so the SLO holds with an instance down or mid-deploy.

**Analogy:** a supermarket staffing checkouts for Saturday afternoon, not the weekly average, plus one spare.
Where the analogy breaks: shoppers leave long queues; requests do not, so above 100 % utilization p99 grows without bound — 58 seconds in the failure lab.

```
lesson 15 log ─> load_model(): avg 40, peak 120 req/s, mean service 45.2 ms
Little: 120 × 0.0452 = 5.4 in flight            emails: rate × 150 ms ⇒ 3.6 ⇒ 5 sender slots
benchmark(): simulate(rate, 4 workers) ─> highest rate with p99 ≤ 300 ms = 75 req/s
instances_needed(): ceil(peak / (75 × 0.8)) + 1 = ceil(2.5) + 1 = 3
cost_per_million(): instances × 0.10 USD/h ÷ (avg req/s × 3600) × 10^6
```

**The one thing to remember:** size from the peak, against benchmarked SLO-safe capacity, with headroom and a spare — then compare options by cost per request.

2. **The failure lab — average sizing:** `python failure_lab.py`:
   ```

   base    : 1 instance(s) -> at peak 120 req/s each, utilization 1.35, p99 58210.3 ms; one instance down: p99 58210.3 ms (SLO 300 ms)

   ```
   **Diagnose:** the base `instances_needed()` divides the *average* by the *100 %-busy* rate: 40 / 88.5 → 1 instance. Wrong demand and wrong capacity compound: utilization 1.35 (120 / 88.5) means work arrives faster than it can ever be served. **Fix:** peak, benchmarked capacity, headroom, +1. 3. **Why ADR 0005 chose async email, 3 instances.** It meets both SLO constraints (102.4 ms at peak, 130.4 ms one down) at the lowest cost. The cache is *deferred*, not rejected: `try_it.py` at 800 libraries shows `async email: 5 instances, 1.74 USD` vs `async email + cache: 4 instances, 1.39 USD` — the decision has a trigger point. ## Common confusions
**Q:** 88.5 req/s per instance is the capacity. — **A:** That is 100 % busy; the SLO-safe benchmark is 75.

**Q:** A cache always saves money. — **A:** Same 3 instances and 2.08 USD at 400 libraries; it pays off around 800.

**Q:** The price is a vendor quote. — **A:** `cost_per_million` states a hypothetical 0.10 USD per instance-hour; compare options, not invoices.
