# Aggregates and invariants (DDD) — explained

## The intuition
An invariant is a rule that must be true after every change: "a member has at most 3 active loans", "a member never has the same book twice". If any code can append to a list of loans, the rule lives in every caller and will eventually be forgotten. An aggregate fixes that by drawing a boundary: `Member` and its `Loan`s change together, and only through the root's methods. `member.loans` returns a tuple of frozen `Loan`s, so there is no back door.

Two rules do *not* fit inside one aggregate. Two requests saving the same member at once is a concurrency problem: the repository's `version` check (optimistic locking) handles it. "One book, one borrower" spans many `Member`s: a partial unique index handles it.

**Analogy:** a bank teller checks your balance; you never edit the ledger yourself.
Where the analogy breaks: two tellers serving one account at once can overwrite each other; the version check, not the teller, stops it.

```
caller ─> repo.get("m1") ─> Member(version=1)
          member.borrow("b4", today)     # invariants checked here, before state changes
          repo.save(member)
             UPDATE members SET version=version+1 WHERE member_id=? AND version=1
                rowcount 0 -> ConcurrencyConflict
             INSERT loans ... -> UNIQUE(book_id WHERE returned_on IS NULL) -> BookAlreadyOnLoan
```

**The one thing to remember:** rules inside one aggregate live in the root; rules across aggregates or across time need the database (unique index, version check).

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py`.
   **What happens inside:** each line loads `Member`, calls `borrow`/`give_back`, saves. `borrow` raises before touching `_loans`, so a rejected call leaves nothing half-done. `save` bumps `version`.
   **What you see:**
   ```
   m1 borrows b1          -> ok, 1/3 active, version 1
   m1 borrows b1 again    -> AlreadyBorrowed: member m1 already has b1
   m1 borrows b4          -> LoanLimitReached: member m1 already has 3 loans
   m2 borrows b1          -> BookAlreadyOnLoan: another member has that book on loan (UNIQUE constraint failed: loans.book_id)
   m1 returns b1          -> ok, 2/3 active, version 4
   m2 borrows b1          -> ok, 1/3 active, version 1
   ```
   **What it means:** the first two errors come from Python in `member.py`; the third comes from SQLite — m2's aggregate had no way to know m1 holds b1.

2. **You run** `python -m unittest -v` → `Ran 13 tests in 9.723s` … `OK`.

3. **You run** `python -m unittest -v test_aggregate.MemberRepositoryTest.test_stale_copy_is_rejected` → `Ran 1 test` … `OK`. Two copies of m1 are loaded at version 1; the first save wins, the second gets `ConcurrencyConflict`.

4. **You run** `python try_it.py`.
   **What you see:**
   ```
   [1] with version check    -> ConcurrencyConflict: member m1 changed since version 1
   [1] without version check -> saved; stored loans: ['b1', 'b2', 'b4'] (limit 3)
   [2] no unique index: b1 is on loan to ['m1', 'm2'] at the same time
   ```
   **What it means:** [1] two tabs load m1 (2 loans); tab A adds b3, tab B adds b4, each valid alone. Without the version check, `save` (delete-and-reinsert of the member's rows) lets tab B overwrite tab A: b3, already confirmed to a user, is gone — a lost update. [2] without the index the cross-aggregate rule fails silently.

## Common confusions
**Q:** The aggregate alone makes concurrent saves safe. — **A:** It guards one in-memory copy; try_it [1] loses `b3` without `version`.

**Q:** Put the "book on loan once" rule in `Member`. — **A:** A member cannot see other members' loans; it needs the unique index (step 1, last error).

**Q:** Frozen `Loan` is just style. — **A:** It removes the back door: outside code cannot set `returned_on` without `give_back`.
