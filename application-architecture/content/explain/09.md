# Event-driven integration: outbox, bus and AsyncAPI — explained

## The intuition
When a loan is created, notifications and a projection want to know. "Save, then publish" spans two systems: die in between and you lose the event or announce a rolled-back loan. The transactional outbox writes the event *as a row* in the same SQLite transaction as the loan; a relay later publishes unpublished rows in order and marks them sent.

If the relay crashes after publishing but before marking, the event goes out twice: at-least-once delivery. So consumers must be idempotent (remember `eventId`s). AsyncAPI is the event payloads' contract, as OpenAPI was in lesson 4.

**Analogy:** a shop writes the receipt and the delivery note on one carbon form; a courier collects delivery notes later and ticks them off.
Where the analogy breaks: a courier who forgets to tick a note delivers the parcel twice — the customer (consumer) has to notice it already has it.

```
borrow() ── BEGIN ── INSERT loans ── INSERT outbox(seq, payload) ── COMMIT
Relay.publish_pending():  SELECT … WHERE published_at IS NULL ORDER BY seq
    bus.publish(event) ──> NotificationConsumer (seen eventIds)
                      └──> ActiveLoansProjection (seen eventIds)
    _mark_published(seq)   ← crash here ⇒ event sent again
```

**The one thing to remember:** the outbox makes "state change + event" atomic; idempotent consumers make the resulting duplicates harmless.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py`.
   **What happens inside:** `borrow` opens `with self.db:` and inserts both rows; the second borrow raises inside the block, so SQLite rolls back and no outbox row exists. `give_back` adds a second row. The relay publishes rows by `seq`.
   **What you see:**
   ```
   borrow b1 by m1 -> outbox pending: 1
   borrow b1 by m2 -> BookAlreadyOnLoan; outbox pending: 1 (rolled back, no event)
   return loan 1   -> outbox pending: 2
   relay run 1     -> published 2: [('loanCreated', 'LoanCreated'), ('loanReturned', 'LoanReturned')]
   relay run 2     -> published 0 (nothing pending)
   projection      -> active loans per member {'m1': 0}
   asyncapi.json   -> 2 events checked, problems: []
   ```
   **What it means:** pending stays 1 after the failed borrow — no phantom event; pending 2 there would mean loan and event do not share a transaction. Run 2 publishes 0: both rows have `published_at`.

2. **You run** `python asyncapi_check.py` → `asyncapi.json: AsyncAPI 3.1.0, 2 channels, 2 operations: OK`. The official AsyncAPI CLI validator runs in CI (not run here).

3. **You run** `python -m unittest -v` → `Ran 20 tests in 2.011s` … `OK`.

4. **You run** `python try_it.py`.
   **What happens inside:** [1] a relay subclass raises after publishing the first event but before `_mark_published`; run 2 publishes it again to a naive and an idempotent consumer.
   **What you see:**
   ```
   [1] relay run 1 -> relay process killed; outbox pending: 1
   [1] relay run 2 -> naive consumer sent 2 mails, idempotent consumer sent 1 (ignored 1 duplicate)
   [2] bookId -> book: ["payload: missing required field 'bookId'", "payload: unexpected field 'book'"]
   ```
   **What it means:** the duplicate is by design; the naive consumer mails twice. [2] a rename breaks every subscriber; the checker names both sides.

5. **You run** `python agent_assist.py` (fake model proposes a `LoanOverdue` event).
   **What you see:** `attempt 1: REJECTED` with 4 problems (e.g. `action must be 'send' or 'receive' (AsyncAPI 3), got 'publish'`), `attempt 2: OK`, and `asyncapi.json unchanged: True`.

## Common confusions
**Q:** Publishing inside the transaction is simpler. — **A:** A broker send cannot be rolled back; the comment in `_record` says why the event is stored, not sent.

**Q:** At-least-once means my relay is buggy. — **A:** try_it [1] shows it is inherent; fix duplicates in the consumer.

**Q:** Keeping `seen` in memory is enough. — **A:** It is lost on restart; `consumers.py` notes real systems keep an inbox table.
