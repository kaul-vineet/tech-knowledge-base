# Evolutionary architecture: expand/contract migrations, API versions, flags, fitness over time — explained

## The intuition
`members.name` must become `given_name` + `family_name`. On a laptop that is one `ALTER TABLE` and one deploy. In production four instances are replaced one at a time, so for minutes old and new code run *at the same time* against *one* database. Every intermediate state — schema plus every running version — must work.

Expand/contract makes the change in steps where each step is compatible with whatever is still running:
1. **Expand:** add the new columns (old code ignores them).
2. **Deploy v2:** writes both shapes (dual write), still reads `name`.
3. **Backfill** existing rows in batches.
4. **Flip a release flag** so reads use the new columns.
5. **Deploy v3:** uses only the new columns.
6. **Contract:** drop `name` — only when nothing running still uses it.

The API follows the same idea: v1 keeps working, rebuilt from the new columns, with `Deprecation` and `Sunset` headers. Flags carry an owner and an expiry date. And a *fitness history* records every step so CI can judge the rollout as a whole, not just the end state.

**Analogy:** replacing a bridge lane by lane while traffic flows: open the new lane, move traffic, then close the old lane.
Where the analogy breaks: you can *see* cars on a bridge lane; a running instance still reading `name` is invisible unless the guard asks the fleet.

```
step:   expand → v2 dual-write → backfill → flag on → [contract?] → v3 → contract
fleet:  v1v1v1v1  v2v2v2v2     v2v2v2v2  v2v2v2v2               v3v3v3v3
can_contract(): base     → unbackfilled rows == 0                     ← wrong question
                solution → … AND no running version uses `name`       ← right question
each step ─> out/fitness.jsonl {errors, unbackfilled, columns, fleet, flags} ─> dashboard.py → exit 0/1
```

**The one thing to remember:** a migration step is safe only if it is compatible with every version still running; ask the fleet before you contract.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py` (two plans against a simulated fleet sending requests through each step).
   **What you see:**
   ```
   big_bang        : 36 failed requests of 100; first error: v1: no such column: name
   expand_contract : 62 failed requests of 700; first error: v2: table members has no column named name
   ```
   **What it means:** option A (big bang) breaks v1 instances the moment the schema changes under them. Option B — expand/contract with the naive guard — is better and still broken.

2. **You run** `python dashboard.py; echo exit=$?`:
   ```
   expand_contract / flag read_split_name on                          v2v2v2v2        0            0  id,name,given_name,family_name
   expand_contract / try contract: dropped name                       v2v2v2v2       50            0  id,given_name,family_name  <-- errors=50 > 0
   expand_contract / deploy v3 (new columns only)                     v3v3v3v3       12            0  id,given_name,family_name  <-- errors=12 > 0
   9 steps, 3 broke a fitness function
   exit=1
   ```
   **What it means:** read the row before the failure: unbackfilled 0, so the base `can_contract()` said yes — while the fleet column says `v2v2v2v2`, all still dual-writing `name`. 50 writes fail in that phase; 12 more while instances are replaced by v3.

3. **The failure lab:** `python failure_lab.py`:
   ```
   base    : try contract: dropped name with fleet v2v2v2v2 -> 62 failed requests of 700; first: v2: table members has no column named name
   solution: try contract: refused (instances on v2 still use members.name) with fleet v2v2v2v2 -> 0 failed requests of 700
   ```
   **Diagnose:** "is the data ready?" is necessary but not sufficient; "is the *code* ready?" was never asked. **Fix:** refuse while any running version uses the old column. Build task: `CHECK_MINE=1` on the base `FAILED (failures=2)`; solution `Ran 3 tests` … `OK`.

4. **Why ADR 0004 chose option C.** Measured: A 36 of 100 failed, B 62 of 700, C 0 of 700 — and only C meets "0 failed requests". It costs several deploys instead of one, plus transitional code (dual writes, the v1 representation) with a removal date. The guard needs to know running versions — here a fleet list, in production a deploy API or registry. The old column stays *nullable* so v3 can stop writing it.

5. **How it stays true.** `python app.py --solution`, then `python dashboard.py --plan expand_contract`:
   ```
   expand_contract / try contract: refused (instances on v2 still use members.name) v2v2v2v2        0            0  id,name,given_name,family_name
   expand_contract / contract: dropped name                           v3v3v3v3        0            0  id,given_name,family_name
   7 steps, 0 broke a fitness function
   exit=0
   ```
   The dashboard judges every step, so a rollout that ends well but hurt users mid-way still fails CI. `try_it.py` shows two more traps: keeping `name TEXT NOT NULL` gives `38 failed requests {'deploy v3 (new columns only)': 38}` (v3 cannot omit it), and on `today 2026-12-01` the flag gate fails: `{'gate': 'no-expired-flags', 'ok': False, 'value': ['read_split_name'], 'budget': 0}`. Suite: `Ran 10 tests in 0.158s` … `OK`.

## Common confusions
**Q:** Backfill complete means safe to drop. — **A:** The base guard said yes with unbackfilled 0 and fleet `v2v2v2v2`; 62 requests failed.

**Q:** Flags are free. — **A:** Each is a branch in production code; the expiry gate turns forgotten flags into a red build.

**Q:** v1 API needs the old column. — **A:** The ADR rebuilds v1 from the new columns and announces a `Sunset`.
