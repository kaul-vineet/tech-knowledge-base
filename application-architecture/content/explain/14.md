# Consumer-driven contract testing — explained

## The intuition
Two teams: loans-service (the **consumer**) calls catalogue-service (the **provider**) for `GET /books/{id}`. Each team has green unit tests, but each tests against its *own* idea of the other. The consumer uses a stub that returns `title`; the provider's unit test checks whatever field the provider returns. If the provider renames `title` to `name` and updates its own test, both suites stay green and production breaks.

A consumer-driven contract closes that gap. The consumer's test runs against a mock provider and, as a side effect, writes down exactly what it sent and what it relies on: `contracts/loans-service--catalogue-service.json`. The provider's CI then replays every interaction in that file against the real provider. The contract lists only what the consumer *reads*, with matchers like "`$.title` is a string" — so the provider stays free to add fields or change example values.

**Analogy:** a tenant hands the landlord a written list: "I need hot water and a working lock". The landlord can repaint freely but must re-check the list before every renovation.
Where the analogy breaks: the list is only as good as the check; a landlord who only checks "the door opens" (status code) passes a lock that no longer locks (missing field).

```
consumer test ─> ContractBuilder.mock_provider() ─> client code ─> write contracts/*.json
                                                                       │ (shared via repo / Pact Broker)
provider CI  ─> verify_provider(contract, real provider URL): replay each request
                  base:     compare status only
                  solution: status + body_problems(): required paths present, types match
```

**The one thing to remember:** the contract records what the consumer actually reads, and the provider must verify bodies, not just status codes.

## Walkthrough: what actually happens when you run it
1. **You run** `python -m unittest -v test_consumer`.
   **What happens inside:** `like(example)` marks values as type matchers; the mock serves the examples; `test_mock_fails_when_an_interaction_is_never_exercised` ensures no interaction is recorded that the client does not use.
   **What you see:** `Ran 3 tests in 1.092s` … `OK`; the file has `'consumerVersion': '1.4.0'` and 2 interactions, `a request for an existing book` and `a request for a missing book`. The first records `"matchingRules": {"$.available": "type", "$.title": "type"}`.
   **What it means:** `id` is an exact example; `title` only has to be a string.

2. **You run** `python -m unittest -v test_provider` → `Ran 2 tests in 7.251s` … `OK` (provider unit test + verification of every file in `contracts/`).

## Failure lab: the provider renames a field
- **Inject:** `python failure_lab.py` starts the provider with `title_field='name'`.
- **Symptom:**
  ```
  provider renames title -> name; base verifier (status only):
      provider unit test          PASS
      consumer unit test (stub)   PASS
      consumer in production      FAIL KeyError: 'title'
      contract verification       PASS
  ```
- **Diagnose:** the base `verify_provider` replays the request and compares only `status` (200 = 200). Every check the teams own is green; the only red line is the one you find out about from users.
- **Fix:** `solution/contract.py` adds `body_problems()`: every path in the contract's example must exist in the real body, and paths with a `type` matcher must have the same JSON type.
- **Proof:** the solution verifier reports `contract verification FAIL ['a request for an existing book: $.title: missing (the consumer reads it)']` — caught in the provider's CI, before deploy. Build task: `CHECK_MINE=1` on the base file `FAILED (failures=2)` (`test_renamed_field_fails`, `test_retyped_field_fails_and_extra_field_passes`); on the solution `Ran 3 tests` … `OK`. All 8 lab tests: `Ran 8 tests in 17.218s` … `OK`.

**Try it** (`python try_it.py`):
```
[1] consumer adds isbn to its expectations -> ['a request for an existing book: $.isbn: missing (the consumer reads it)']
[2] provider adds isbn and returns another title -> []
```
[1] a consumer cannot demand a field the provider never had — verification tells both teams before release. [2] additive changes and different values pass: matchers check type, not the example "Dune".

**Same flow with Pact** (pact-python 4.2.0, `LOANS_PACT=1`) — Expected (not run here): the consumer writes a V4 pact into `pact/pacts/` and the provider `Verifier` replays it; a Pact Broker would add "can I deploy?" checks across versions.

## Common confusions
**Q:** The provider writes the contract. — **A:** The consumer's test writes it (step 1); the provider only verifies.

**Q:** A 200 status means compatible. — **A:** Base verifier: `PASS` while production failed with `KeyError: 'title'`.

**Q:** The contract freezes the provider's whole response. — **A:** try_it [2]: extra `isbn` and a new title pass (`[]`).
