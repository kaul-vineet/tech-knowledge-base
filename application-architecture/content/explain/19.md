# Policy as code: RBAC vs ABAC, policy tests and decision logs — explained

## The intuition
Authorization rules start life as `if` statements scattered over handlers. That makes three questions hard to answer: *what are the rules?* (read every handler), *are they right?* (test every handler), and *why was this request allowed?* (nobody logged it). Policy as code moves the rules into one file, `policy/loans.rego`, evaluated by a decision point. Handlers become enforcement points: they build an input document (`subject`, `action`, `resource`), ask `authorize()`, and obey.

The model matters too. **RBAC** maps roles to actions: "librarian may view". **ABAC** decides on attributes of subject and resource: "a librarian may view loans *of the same library*", "a member may borrow if `active_loans < 5`", "anyone suspended is denied". Most real rules in this lab are attribute rules, so a role table alone cannot express them. Roles survive as one attribute among others.

**Analogy:** a club's written house rules at the door, with a doorman who checks them and a guest book that records every decision.
Where the analogy breaks: the doorman reads the rules literally; one rule that forgets "of this club" lets in members of every club, and the guest book will show it was "allowed" — correctly, by the rule as written.

```
handler (PEP) ─ input {subject, action, resource} ─> rego_lite / OPA (PDP) ─ policy/loans.rego
                                                     allowed := allow AND count(deny) == 0
             <─ {allowed, matched: ['allow@27', …], deny: [...]} ─ decision log (email erased)
fitness_policy.py: policy-tests (14 cases) · rule-coverage (every rule hit) · pep-coverage (every handler asks)
```

**The one thing to remember:** rules in one tested file, every handler forced to ask, every answer logged with *which rule* matched.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py`.
   **What happens inside:** the 14 requirement cases run through both the Rego policy and `rbac.py`'s role table; each policy decision is written to `out/decisions.jsonl`.
   **What you see:**
   ```
   policy policy/loans.rego (revision 58df760cbce4): 13/14 requirement cases
   RBAC role table            : 7/14 requirement cases
     WRONG: librarian of another library (expected allowed=False)
   in-process decision: 86 us (varies by host)
   ```
   **What it means:** option A (RBAC) is measured, not argued: 7 of 14 — it cannot say "own loan", "same library", "limit 5", "suspended" or "waiver above 20.00". The Rego policy gets 13 of 14; the one miss is the seeded failure. Decision cost here was 86 µs (the lesson saw 290–1,145 µs on a busier host) — cheap enough to call per request.

2. **You read** the first decision log line:
   ```
   {"decision_id": "58df760cbce4-000001", "deny": [], "erased": ["/input/subject/email"], … "matched": ["allow@12", "allowed@44"], … "result": true, "revision": "58df760cbce4", …}
   ```
   **What it means:** you can answer an auditor: which policy revision, which input (minus the e-mail, masked by design), which rule lines matched (`allow@12` = the rule on line 12).

3. **The failure:** `python failure_lab.py`:
   ```
   request: {'action': 'view', 'subject': {'id': 's9', 'tenant': 'lib01', 'roles': ['librarian']}, 'resource': {'tenant': 'lib00', 'member_id': 'm2', 'active_loans': 1}}
   base    : allowed=True matched=['allow@27', 'allowed@44']; policy tests failed: ['librarian of another library']
   solution: allowed=False matched=[]; policy tests failed: []
   ```
   **Diagnose:** `matched` points at line 27, the new rule R3: `"librarian" in input.subject.roles` and an action list — no `input.subject.tenant == input.resource.tenant`. No handler changed; the bug is entirely in the policy file, and the policy tests found it. **Fix:** add the tenant condition. Build task: `CHECK_MINE=1` on the base `FAILED (failures=2)`; solution `Ran 3 tests` … `OK`.

4. **Why ADR 0003 chose ABAC in a policy file.** Option A fails the "14 of 14" constraint by construction. Option B (Rego, in-process decision point, deny overrides allow, masked decision log) meets all five constraints once fixed. Option C — the same `.rego` on OPA 1.21.4 as library or sidecar — is the production equivalent: Expected (not run here): `opa test policy/` passes and `opa_parity.py` reports 0 differences on 14 cases (pending CI). `rego_lite.py` supports only a learning subset, which is why OPA is the path once rules grow.

5. **How it stays true.** `python fitness_policy.py; echo exit=$?`:
   ```
   {"gate": "policy-tests", "ok": false, "value": ["librarian of another library"], "budget": "14/14 pass"}
   {"gate": "rule-coverage", "ok": true, "value": [], "budget": "every allow/deny rule"}
   {"gate": "pep-coverage", "ok": true, "value": [], "budget": "0 handlers without authorize()"}
   exit=1
   ```
   Three gates for three ways to drift: wrong rules, untested rules, unenforced rules. `try_it.py` shows the last one: a new `renew()` handler without `authorize()` gives `'pep-coverage', 'ok': False, 'value': ['renew']`. And deny overrides allow: `suspended librarian borrows for m2 -> {'allowed': False, 'deny': ['account suspended'], 'matched': ['allow@27', 'deny@34']}`. Suite: `Ran 12 tests in 1.611s` … `OK`.

## Common confusions
**Q:** ABAC replaces roles. — **A:** Roles become an attribute; R3 still tests `"librarian" in input.subject.roles`.

**Q:** If every handler calls `authorize()`, we are safe. — **A:** The failure lab passed pep-coverage and still allowed a cross-library view; the policy itself must be tested.

**Q:** Decision logs should store the full input. — **A:** They store enough to explain the decision; `erased` shows the e-mail removed.
