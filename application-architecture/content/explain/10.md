# Authentication with OpenID Connect (code flow + PKCE) — explained

## The intuition
Your app (the Relying Party, RP) never sees the password. It sends the browser to an Identity Provider (IdP); after login the IdP redirects back with a one-time **code**, which the RP swaps for an **ID token** over a back-channel call, then checks.

Each value blocks one attack. `state` ties the callback to *this* login (CSRF). PKCE's `code_verifier` stays with the RP; the IdP saw only its SHA-256 hash (`code_challenge`), so a stolen code is useless. `nonce` ties the token to this login (replay). Claim checks (`iss`, `aud`, `exp`, `iat`, `sub`) ensure right issuer, this app, fresh.

**Analogy:** a cloakroom ticket: you get a numbered stub (code), and only the person holding the matching half (verifier) can collect the coat (token).
Where the analogy breaks: the token itself must be inspected too — a valid ticket for another venue (`aud=quiz-app`) is refused.

```
RP.start_login()  state, nonce, verifier ── challenge=S256(verifier) ─┐
browser ─GET /authorize?…challenge…──> IdP ─302 redirect?code&state──> RP
RP.finish_login(): state == ours? ── POST /token code+verifier ──> IdP.token():
                       pop(code) once · S256(verifier)==challenge? · sign(claims)
RP: verify(sig, alg) ── validate_claims(iss, aud, exp, iat, nonce, sub) ── logged in
```

**The one thing to remember:** the code is useless without the verifier, and the token is useless until every claim is checked.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py`.
   **What happens inside:** `start_login` makes three random values and the S256 challenge; `browser_follow` stands in for the browser and returns the `Location` header; `finish_login` compares `state` with `hmac.compare_digest`, posts the code, verifies the HS256 signature, then runs `validate_claims`. The app then replays the same code.
   **What you see:**
   ```
   1 authorize request -> ['client_id', 'code_challenge', 'code_challenge_method', 'nonce', 'redirect_uri', 'response_type', 'scope', 'state']
   2 redirect to RP    -> code of 43 chars, state matches: True
   3 ID token accepted -> sub=member-m1 aud=library-web nonce ok, valid 300 s
   4 same code again   -> LoginFailed: token endpoint 400: invalid_grant: code unknown or already used
   ```
   **What it means:** 43 chars is `token_urlsafe(32)` (32 bytes, base64url). Line 4 comes from `self.codes.pop(...)`: one use per code. The authorize request carries no secret.

2. **You run** `python -m unittest -v`.
   **What happens inside:** the suite attacks the RP: `alg: none`, a forged signature, wrong `aud`, expired `exp`, a stolen code, a wrong redirect, plus the RFC 7636 PKCE test vector.
   **What you see:** `Ran 19 tests in 5.591s` … `OK`.

3. **You run** `python try_it.py`.
   **What you see:**
   ```
   [1] stolen code, wrong verifier -> token endpoint 400: invalid_grant: PKCE verification failed
   [1] codes left at the IdP after the failed attempt -> 0
   [2] aud=quiz-app -> aud ['quiz-app'] does not contain 'library-web'
   ```
   **What it means:** [1] the attacker's attempt *consumed* the code (0 left), so even the real RP cannot use it now — a failed theft still fails safe. [2] a perfectly signed token for another app is refused by the `aud` check alone.

4. **Build task check** `python -m unittest test_build_task` → `Ran 5 tests in 0.798s` … `OK` (the `max_age`/`auth_time` rule, checked on the solution).

5. **Optional real provider:** Keycloak 26.8.1 with `keycloak_check.py` — Expected (not run here): `…/realms/master: OK (code flow, PKCE S256, RS256 ID tokens)`. A real IdP signs with RS256 and a published key; the mock's HS256 shared secret is for learning only.

## Common confusions
**Q:** The ID token is an access token for my API. — **A:** It proves who logged in to *this* RP (`aud=library-web`); APIs take access tokens.

**Q:** A valid signature means trust it. — **A:** try_it [2] has a valid signature and is still refused by `aud`.

**Q:** PKCE replaces `state`. — **A:** PKCE protects the code exchange; `state` protects the callback. `finish_login` checks `state` before it even posts the code.
