# Foundations III: formal reasoning about design – contracts, Liskov substitution, model checking and the evidence — explained

## The big picture
Tests show that some runs work; formal reasoning shows that *all* runs within a model work. This lesson takes three claims the labs relied on and proves them. "Aggregates and invariants (DDD)" claimed that routing every change through `Member` keeps the loan limit true forever. "Hexagonal architecture: ports and adapters" swapped adapters behind a port and expected callers not to notice — a substitution claim. "Event-driven integration: outbox, bus and AsyncAPI" and the capstone avoided races with an atomic conditional insert. `check_formal.py` runs each theorem against the real L200 code or a small model. The lesson ends with the evidence question: do these techniques measurably reduce defects? Its honest answer — associated, not proven causal — frames how much to claim.

### T25.1 Invariant induction for an aggregate
**In plain words:** if the rule holds for a new object, every allowed operation keeps it, and every rejected operation changes nothing, then the rule holds after *any* sequence of calls.

**Why it is true (intuition):** dominoes. The first one stands (construction); each call can only pass "rule holds" on to the next state. The hidden premise is that *only* those operations can change the state — encapsulation is part of the proof.

Proof skeleton:
1. Induct on the number n of public calls.
2. Base n = 0: Inv holds after construction.
3. Step, rejected call: state unchanged, Inv still holds.
4. Step, accepted call: its precondition held, so the operation's contract re-establishes Inv.
5. Hence Inv holds after every n — *provided* nothing else can mutate the state.

**See it in numbers:** `python check_formal.py`
```
  [OK] base case: a new Member satisfies Inv
      310,352 random calls on the real L200 #8 Member aggregate, 178,288 rejected by rules
  [OK] Inv broken after 0 calls
  [OK] rejected calls that changed state: 0
  [OK] loans is exposed as a read-only tuple (no append behind the root's back)
```
310,352 calls drive the real lesson 8 class; 178,288 were rejected, and none of those changed state (premise iii). The last line checks the encapsulation premise directly.

**Where it shows up in practice:** lesson 8's try_it showed what happens when the premise is false across two copies: the version check extends "only through the root" to concurrent saves.

### T25.2 Liskov substitution rule for a method
**In plain words:** a replacement is safe if it accepts at least everything the original accepted (weaker or equal precondition) and promises at least everything the original promised (stronger or equal postcondition).

**Why it is true (intuition):** a client written for T only ever sends inputs T allows and only relies on what T promises. If S accepts those inputs and its answers still satisfy T's promises, the client cannot tell.

Proof skeleton:
1. The client establishes pre_T before calling.
2. pre_T ⇒ pre_S, so S runs inside its own precondition and establishes post_S.
3. pre_T ∧ post_S ⇒ post_T, so what the client relies on still holds.
4. Contrapositive: a stronger precondition or weaker postcondition can break some correct client.

**See it in numbers:**
```
      StrictLimit        pre broken at  0 of 44 points, post broken at  0; supertype client (overdue 0 / 1) ends with: [2, 0]
      GenerousLimit      pre broken at  0 of 44 points, post broken at  8; supertype client (overdue 0 / 1) ends with: [5, 5]
      NoOverdueAccepted  pre broken at 33 of 44 points, post broken at  0; supertype client (overdue 0 / 1) ends with: [3, 'error: members with overdue loans are not accepted']
```
The domain is 11 values of `active` × 4 of `overdue` = 44 points. GenerousLimit returns True at active 3 and 4 for all 4 overdue values: 8 broken postcondition points — and the supertype client ends with 5 loans. NoOverdueAccepted refuses the 33 points with overdue > 0: the client gets an exception it never expected.

**Where it shows up in practice:** lesson 7's `StoreContract` is a postcondition test run against every adapter.

### T25.3 BFS model checking: complete and shortest counterexamples
**In plain words:** for a finite model, breadth-first search visits every reachable state, and the first bad state it finds comes with the shortest path to it.

**Why it is true (intuition):** BFS explores in rings — all states one step away, then two, and so on. It cannot miss a reachable state, and it meets the nearest bad state before any farther one.

Proof skeleton:
1. Each state is enqueued at most once → termination.
2. Induction on distance d: every state at distance d is enqueued while distance d − 1 is expanded → completeness.
3. States leave the queue in non-decreasing distance.
4. So the first unsafe state dequeued is a nearest one; parent pointers give a shortest trace.

**See it in numbers:**
```
      buggy check-then-act: violation after exploring 9 states; counterexample: ['A reads: book free', 'B reads: book free', 'A borrows', 'B borrows']
  [OK] BFS counterexample length 4 = brute-force minimum 4
  [OK] atomic conditional insert: 8 reachable states, no violation, 0 deadlocks
      state explosion, members -> (buggy, fixed) reachable states: {2: (9, 8), 3: (27, 20), 4: (81, 48), 5: (243, 112), 6: (729, 256)}
```
The 4-step trace is the classic race. Making "check and insert" one atomic step removes the bad state. The last line is the price: states grow exponentially.

**Where it shows up in practice:** lesson 8's partial unique index and the outbox `with self.db:` block are both "make check-then-act atomic".

## Worked problems
**P25-4.** An implementation returns `active < 4`.
1. Precondition: it accepts every input → pre broken at 0. *Why:* nothing is refused.
2. Postcondition `result ⇒ active < 3`: returns True at active = 3. *Why:* 3 < 4 but not < 3.
3. That happens for overdue 0, 1, 2, 3 → 4 points. *Why:* the 4 overdue values at active = 3.
4. Result: `OK  P25-4: post broken at 4 of 44 points, pre at 0` (`l500_checks.py`). Not a behavioural subtype.

**P25-6.** Reachable states with n members.
1. Buggy: each member is idle, checked or holding, and every combination is reachable → 3ⁿ. *Why:* no rule stops two holders.
2. Fixed, no holder: each member idle or checked → 2ⁿ.
3. Fixed, one holder: n choices × 2ⁿ⁻¹ for the others.
4. Total 2ⁿ + n·2ⁿ⁻¹ = (n + 2)·2ⁿ⁻¹; for n = 2..6: 8, 20, 48, 112, 256 vs 9, 27, 81, 243, 729 (`OK  P25-6`). *Why it matters:* even a correct design explodes; real model checkers need symmetry reduction.

## Common confusions
**Q:** A passing model check proves the service is safe. — **A:** It proves the *model* is; the link to code must be tested (lesson 8's unique index).

**Q:** A subtype may add stricter validation. — **A:** That strengthens the precondition: 33 of 44 points broken.

**Q:** 310,352 random calls prove the invariant. — **A:** They test it; the induction proves it, given encapsulation.
