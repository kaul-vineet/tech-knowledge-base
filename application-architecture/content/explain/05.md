# Configuration the 12-factor way — explained

## The intuition
The same build should run on your laptop, in test and in production; only the configuration differs. The 12-factor rule is to read per-deploy values (port, database path, log level, secrets) from environment variables, once, at startup. `load_settings()` reads them, validates all of them, and either returns a frozen `Settings` object or raises one `ConfigError` listing every problem. A bad deploy dies immediately with a readable message instead of failing on the first request.

**Analogy:** a hotel key card: the same door lock everywhere, a different card per guest, checked at the door.
Where the analogy breaks: a key card can be checked later; config is checked once and then frozen — changing it means restarting.

```
os.environ ─> load_settings() ─┬─ all valid ─> Settings(frozen, smtp_password repr=False) ─> app
                               └─ errors[]  ─> ConfigError("a; b") ─> stderr, exit 2
```

**The one thing to remember:** validate all config at startup, fail fast with every error at once, never print secrets.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py` with no `LOANS_*` variables.
   **What happens inside:** each `env.get(name, default)` falls back to the default; `smtp_password` is `None`.
   **What you see:**
   ```
   starting with Settings(port=8080, db_path='loans.db', max_active_loans=3, log_level='INFO')
   smtp password: not set
   ```

2. **You run** `LOANS_PORT=9000 LOANS_LOG_LEVEL=debug LOANS_SMTP_PASSWORD=example-only python app.py`.
   **What happens inside:** `.upper()` normalises `debug`; the password is stored but `field(repr=False)` drops it from the dataclass repr.
   **What you see:** `Settings(port=9000, … log_level='DEBUG')` and `smtp password: set` — the value never appears.

3. **You run** `LOANS_PORT=abc LOANS_LOG_LEVEL=LOUD python app.py; echo exit=$?`.
   **What happens inside:** `integer()` appends to `errors` instead of raising, so the log-level check still runs.
   **What you see:**
   ```
   invalid configuration: LOANS_PORT='abc' is not an integer; LOANS_LOG_LEVEL='LOUD' must be one of ['DEBUG', 'ERROR', 'INFO', 'WARNING']
   exit=2
   ```

4. **You run** `python -m unittest -v` → `Ran 9 tests in 10.359s` … `OK`.

5. **You run** `python try_it.py`.
   **What you see:**
   ```
   [1] LOANS_LOG_LEVEL=warn -> exit 2: invalid configuration: LOANS_LOG_LEVEL='WARN' must be one of ['DEBUG', 'ERROR', 'INFO', 'WARNING']
   [2] repr=True -> starting with Settings(port=8080, db_path='loans.db', max_active_loans=3, log_level='INFO', smtp_password='example-only')
   [2] python -m unittest -> exit 1; FAILED (failures=2)
   ```
   **What it means:** `WARN` is not `WARNING` — strict beats guessing. Flipping one flag leaks the secret into every log line, and two tests catch it.

## Common confusions
**Q:** A `.env` file in the repo is fine. — **A:** Not for secrets; `test_no_hardcoded_secret_assignments` exists for this reason.

**Q:** Stop at the first error. — **A:** Step 3 shows both errors in one message: one deploy, one fix.

**Q:** Hiding the value in `print` is enough. — **A:** Tracebacks and loggers use `repr`; try_it [2] shows the leak.
