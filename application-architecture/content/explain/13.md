# Resilience patterns: timeouts, circuit breaker, bulkhead, fallback — explained

## The intuition
A borrow needs two remote answers: *members* ("may m1 borrow?", required) and *catalogue* (the book title, nice to have). When a dependency is down, failing fast is easy. The dangerous case is a dependency that is **slow**: every call to it holds a thread while it waits, and threads are shared.

Four patterns divide the work. A **timeout** stops the caller waiting — but, as `Pool.call` says, "a call that already started keeps its thread until it returns". A **circuit breaker** counts recent failures and, above 50 %, stops calling for `open_s`, then lets one trial call through (half-open). A **fallback** answers `(title unavailable)` instead of failing a borrow over a cosmetic field. A **bulkhead** gives one dependency its own small pool and rejects the call that would exceed it, so a slow catalogue cannot starve members.

**Analogy:** a ship's hull divided into compartments: one flooded compartment does not sink the ship.
Where the analogy breaks: a ship's compartments are fixed; here you choose sizes (4 + 4), and a compartment too small rejects healthy traffic.

```
borrow ─> members_pool.call(check, timeout=0.1)                      required
       └> with_fallback( breaker.call( catalogue_pool.call(title, 0.1) ) ) → "(title unavailable)"
base:     members_pool IS catalogue_pool = Pool("shared", 8)   ← slow catalogue holds all 8
solution: Pool("members", 4)  +  Bulkhead("catalogue", 4) (5th call: BulkheadFull at once)
```

**The one thing to remember:** a timeout frees the caller, not the thread — isolate pools per dependency or one slow dependency takes everything down.

## Walkthrough: what actually happens when you run it
1. **You run** `python app.py`.
   **What happens inside:** `CircuitBreaker._record` keeps a window of results; after 6 calls at failure rate 0.5 it moves to open. While open, `call` raises `CircuitOpen` without calling the catalogue, and the fallback answers.
   **What you see:**
   ```
   {"calls": 6, "evt": "breaker", "failure_rate": 0.5, "from": "closed", "name": "catalogue", "to": "open"}
   # catalogue down: 8 borrows, 8 with fallback title, catalogue called 3x, breaker open
   {"evt": "breaker", "from": "half_open", "name": "catalogue", "to": "open", "trial": "failed"}
   …
   # transitions: closed -> open -> half_open -> open -> half_open -> closed
   ```
   **What it means:** 8 borrows, only 3 catalogue calls: the breaker saved 5 calls to a dead service. A failed half-open trial re-opens; a successful one closes. Constant calls while "open" would mean the breaker is bypassed.

## Failure lab: a slow catalogue
- **Inject:** `python failure_lab.py`. `Catalogue(mode='slow')` hangs 1 s per call; 3 waves of 8 concurrent borrows, 0.25 s apart.
- **Symptom:**
  ```
  base     (one shared pool of 8): 8/24 borrows ok, 8 with fallback title
      per wave: {1: {'ok': 8}, 2: {'TimeoutError': 8}, 3: {'TimeoutError': 8}}
      first failed request log: {… "error": "TimeoutError: shared: no answer within 0.1 s", … "pools": {"shared": "8/8"}, "wave": 2}
  ```
- **Diagnose:** wave 1's catalogue calls timed out after 0.1 s (fallback, so ok), but their 8 threads stayed busy for 1 s. Wave 2's *members* check — a healthy service — queued behind them and timed out. The log line `"shared": "8/8"` is the smoking gun: the pool was full when a healthy call failed. The breaker opened, but the threads were already taken.
- **Fix:** `solution/loans_service.py`: `Pool("members", 4)` and `Bulkhead("catalogue", 4)`; the 5th concurrent catalogue call gets `BulkheadFull` immediately and the fallback title.
- **Proof:** `solution (members 4 + catalogue bulkhead 4): 24/24 borrows ok, 24 with fallback title`. Build-task tests: with `CHECK_MINE=1` on the base file `FAILED (failures=2)` (`test_members_has_its_own_pool`, `test_every_borrow_succeeds_with_a_fallback_title`); on the solution `Ran 3 tests` … `OK`. Lab suite: `Ran 11 tests in 2.055s` … `OK`.

**Try it** (`python try_it.py`): raising the timeout to 2.0 s "fixes" the errors — `24/24 ok, 8 degraded, fastest 1004 ms, slowest 2402 ms` — by making every borrow wait a second or more. And a breaker alone: `breaker went closed -> open; still {… 2: {'TimeoutError': 8}, 3: {'TimeoutError': 8}}`.

## Common confusions
**Q:** A longer timeout is safer. — **A:** try_it [1]: success, but the slowest borrow took 2402 ms; you traded errors for latency and held threads longer.

**Q:** The circuit breaker protects my threads. — **A:** try_it [2]: it opened and waves 2–3 still failed; it stops *new* calls, not ones in flight.

**Q:** `future.cancel()` stops the slow call. — **A:** Only if it has not started; a running call keeps its worker (comment in `Pool.call`).
