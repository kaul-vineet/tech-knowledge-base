# Quantum and post-quantum: crypto inventory and migration plan — explained

## The intuition

Shor's algorithm would break RSA and elliptic-curve cryptography (key exchange and signatures) on a large fault-tolerant machine. Lesson 19 estimated that such a machine is far beyond today. So why migrate now? Because of **harvest now, decrypt later**: an attacker can record encrypted traffic today and decrypt it once the machine exists. Mosca's inequality turns that into a rule: if *secrecy lifetime X* + *migration time Y* > *time until a quantum computer Z*, you are already late.

Migration is mostly a software-engineering problem. First, **find** every public-key use and what it is for (key establishment, signature, or symmetric, which Shor does not break). Second, **prioritise** by data lifetime. Third, **replace** with the NIST post-quantum standards: ML-KEM (FIPS 203) for key establishment, ML-DSA (FIPS 204) for signatures, and keep AES-256. Fourth, make the next swap cheap: *crypto agility*, one interface with the algorithm chosen by configuration.

The lab's toy app hides the classic traps: RSA mentioned in a docstring, X25519 and ECDH that never contain the letters "RSA", and an aliased import of ECDSA.

**Analogy:** a dependency-vulnerability migration (think Log4Shell): inventory, triage by exposure, patch behind an abstraction, then block regressions in CI.
Where the analogy breaks: the "exploit" is retroactive: data captured before you patch stays vulnerable.

```text
toy_app/*.py, *.toml --scan (AST, imports, aliases)--> inventory: file, line, algorithm, usage
      + data_classification.json (secrecy years)
      --plan(): P1 if key-establishment and X + Y > Z (Y=3, Z=9)--> migration steps
code:  agility.establish(CONFIG["kem"])  ->  x25519 | ml-kem-768 | x25519+ml-kem-768 (hybrid)
CI:    ratchet vs migration_baseline.json (may only shrink); recall = precision = 1.0
```

The one thing to remember: an inventory you can test, prioritised by data lifetime, plus an agile interface, is the migration; the algorithm swap itself is the easy part.

The grep finds 5 "RSA" hits and zero P1 items. The KEM sizes are the real cost of PQC: about 1.1 kB more per handshake. Milliseconds are machine-dependent.

## Failure lab: an inventory by grep

1. **Inject:** the shipped `scan()` (regex `rsa` over `.py` and `.toml`).
2. **Symptom:** 5 findings, all `usage: unknown`; `auth.py:1` is a docstring; X25519, ECDH P-384 and ECDSA are missing.
3. **Diagnose:** the tests compare with a hand-checked ground truth:
   ```text
   AssertionError: None != 'ECDSA P-256'
   AssertionError: 'unknown' != 'key-establishment'
   AssertionError: Tuples differ: (0.0, 0.0) != (1.0, 1.0)
   FAILED (failures=6)
   ```
   Recall and precision are both 0.0: not one grep hit matches a real (file, line, algorithm, usage) entry.
4. **Fix:** `solution_scanner.py` parses the AST, resolves imports and aliases, classifies calls by purpose, and reads TLS config with comment-aware rules.
5. **Proof:** `python -m unittest test_build_task test_fitness` → `Ran 7 tests in 37.434s` … `OK`.

## Walkthrough: the decision

1. **The real inventory.** You run `python solution_scanner.py`.
   **What you see:**
   ```text
   {"scanner": "ast", "findings": 8}
   {"file": "toy_app/billing.py", "line": 7, "algorithm": "RSA-3072", "usage": "key-establishment", "secrecy_years": 10, "priority": "P1 now (harvest now, decrypt later)", …}
   {"file": "toy_app/sync.py", "line": 7, "algorithm": "ECDH P-384", "usage": "key-establishment", "secrecy_years": 7, "priority": "P1 now (harvest now, decrypt later)", …}
   {"file": "toy_app/auth.py", "line": 11, "algorithm": "ECDSA P-256", "usage": "signature", … "replacement": "ML-DSA-65 (FIPS 204)"}
   {"file": "toy_app/storage.py", "line": 10, "algorithm": "AES-GCM", "usage": "symmetric", "secrecy_years": 10, "priority": "none", …}
   ```
   **What it means:** 10 + 3 > 9 and 7 + 3 > 9, so both are P1. The P1 ECDH was invisible to grep. AES-GCM with 10-year data needs no change.

2. **Sensitivity.** `python try_it.py`:
   ```text
   longer_secrecy ['toy_app/api_client.py:11', 'toy_app/billing.py:7', 'toy_app/sync.py:7']
   old_receiver   receiver rejects envelope: unknown kem 'x25519+ml-kem-768'
   ```
   An 8-year secrecy requirement promotes the partner API to P1. A receiver that only knows X25519 fails loudly instead of silently downgrading: upgrade receivers before senders.

3. **Options.** A: replace at each call site (four key-establishment sites now, and again next time). B: an agile interface with the hybrid X25519+ML-KEM-768 (1216/1120 bytes; next swap is one config line). C: wait until 2030 (P1 data recorded today stays exposed). The ADR (`docs/adr/0001-crypto-agility.md`) chooses B; the hybrid stays secure if either component holds.

4. **The fitness function** `test_fitness.py`: inventory recall = precision = 1.0; a ratchet against `migration_baseline.json` (which may only shrink) catches any new quantum-vulnerable call; `CONFIG["kem"]` must be hybrid or post-quantum.

5. **Agent assist** (`python agent_assist.py --fake`): a drafted migration note is checked fact by fact against the inventory.
   ```text
   summarise REJECT  toy_app/storage.py:10 is symmetric (AES-GCM): keep it, do not replace; P1 item missing: toy_app/sync.py:7
   ```

## Common confusions

- **Q:** Quantum breaks AES too. — **A:** Shor does not; the plan keeps AES-GCM (`priority: none`).
- **Q:** No RSA in the code means safe. — **A:** ECDH P-384 in `sync.py` is P1 and contains no "RSA".
- **Q:** Migrate when a quantum computer appears. — **A:** Data recorded before then is already exposed (Mosca).
