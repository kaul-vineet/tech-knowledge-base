# Error-aware compilation: layout, routing and a depth budget — explained

## The intuition

Lesson 11's transpiler treated every connection as equal. Real devices are not: each coupler and readout has its own error rate from a daily calibration, and one coupler can drift badly overnight. An *error-aware* compiler uses that data to choose placement and routing.

Candidates are scored by **estimated success probability** (ESP): the product of `(1 − error)` over every gate and measurement. It ignores how errors interact but, as a density-matrix check confirms, ranks options like the real fidelity. Hard limits: CX count and depth (budget 22 layers).

The circuit is lesson 14's 5-node QAOA. Its graph contains a triangle, and the device is a ladder (two rows of four with rungs), which has no triangles. So every placement needs at least one SWAP: the question is where to pay it.

**Analogy:** route planning with live traffic: shortest distance is not fastest if one road is jammed today.
Where the analogy breaks: "traffic" here also degrades the cargo: a bad edge does not just slow the circuit, it corrupts the answer.

```text
calibration (CX 0.5-2 %, readout 1-4 %, drift: (1,2) = 15 %)
      |
choose_layout --> route (hops | most reliable path) --> cancel CX pairs
      |
metrics: ESP = prod(1 - err), cx, depth   -> must satisfy depth <= 22, ESP >= 0.75, cx <= 20
check:   noiseless TVD < 1e-9 vs logical ; density-matrix fidelity ranks like ESP
```

The one thing to remember: compile against today's calibration, and score candidates by expected fidelity under a depth budget, not by gate count alone.

## Walkthrough: what actually happens when you run it

1. **You run** `python compile_lab.py` (shipped options A and B).
   **What happens inside:** A maps logical `i` to physical `i` and routes by hop count. B picks a dense region by degree, routes by hops, and cancels back-to-back CX pairs. Both run on the calibrated and the drifted device.
   **What you see:**
   ```text
   {"device": "calibrated", "option": "A trivial + hop routing", "layout": [0, 1, 2, 3, 4], "esp": 0.5763, "cx": 27, "depth": 32, "within_depth_budget": false}
   {"device": "calibrated", "option": "B dense + hop routing + cancel", "layout": [1, 5, 2, 6, 3], "esp": 0.7315, "cx": 19, "depth": 24, "within_depth_budget": false}
   {"device": "drifted (1,2) = 15%", "option": "A trivial + hop routing", … "esp": 0.2084, "cx": 27, "depth": 32, …}
   {"device": "drifted (1,2) = 15%", "option": "B dense + hop routing + cancel", … "esp": 0.3059, "cx": 19, "depth": 24, …}
   logical circuit: {'esp': 1.0, 'cx': 12, 'depth': 17}
   ```
   **What it means:** routing more than doubles CX (12 → 27). Both layouts use the drifted coupler (1, 2), so drift collapses ESP. B's cancellation helps CX but not depth: still over 22.

## Failure lab: a compiler blind to drift

1. **Inject:** the shipped trivial `choose_layout()` and hop-count routing, with `DRIFT` setting coupler (1, 2) to 15%.
2. **Symptom:** ESP 0.2084, 27 CX, depth 32 (above).
3. **Diagnose:** run the build-task and fitness tests against the shipped module:
   ```text
   AssertionError: 0.5943 not greater than or equal to 0.75
   AssertionError: 38 not less than or equal to 22
   AssertionError: 50 not less than or equal to 22
   FAILED (failures=3)
   ```
   The layout never looks at errors, and the router happily walks through the bad edge.
4. **Fix:** `solution_layout.py`: brute-force all 6720 placements, route along the most reliable path (weighted shortest path), cancel pairs, keep the best ESP within the depth budget.
5. **Proof:** `python -m unittest test_build_task test_fitness` → `Ran 5 tests in 28.778s` … `OK`.

## Walkthrough: the decision

1. **Option C measured.** You run `python solution_layout.py`.
   **What you see:**
   ```text
   {"device": "calibrated", "option": "C noise-aware layout + reliable routing + cancel", "layout": [2, 3, 6, 1, 5], "esp": 0.7925, "cx": 13, "depth": 18, "within_depth_budget": true}
   {"device": "drifted (1,2) = 15%", "option": "C noise-aware layout + reliable routing + cancel", "layout": [5, 1, 6, 2, 3], "esp": 0.7835, "cx": 19, "depth": 21, "within_depth_budget": true}
   ```
   **What it means:** calibrated, C needs one extra CX; drifted, it pays more CX to avoid (1, 2) and keeps ESP near 0.78.

2. **Is ESP trustworthy?** You run the same comparison through the density-matrix check (`noisy_check.noisy_fidelity`).
   **What you see:**
   ```text
   [0, 1, 2, 3, 4] esp 0.2084 simulated fidelity 0.8959
   [5, 1, 6, 2, 3] esp 0.7835 simulated fidelity 0.9878
   ```
   **What it means:** the absolute numbers differ (ESP is pessimistic), but the ranking agrees, which is all a selector needs.

3. **Sensitivity.** `python try_it.py`:
   ```text
   other_drift  {'layout': [1, 2, 5, 0, 4], 'esp': 0.7503, 'cx': 13, 'depth': 18, 'uses_drifted_edge': False, 'noisy_fidelity': 0.9855}
   tight_budget {'esp': 0.7835, 'cx': 19, 'depth': 21, 'within_budget': False}
   ```
   Drift a different coupler and the layout moves away from it. Demand depth 17 and nothing fits: the triangle needs a SWAP.

4. **The ADR** (`docs/adr/0001-noise-aware-compile.md`) chooses C, recompiling when calibration changes. It records the scaling limit: 6720 candidates here grows factorially, so beyond about 10 qubits use VF2/SABRE-style heuristics (Qiskit level 3, Expected (not run here) in `compile_qiskit.py`).

5. **The fitness function** `test_fitness.py` requires depth ≤ 22, ESP ≥ 0.75, CX ≤ 20 and noiseless equivalence on *both* device states, so a regression to drift-blind compilation fails.

## Common confusions

- **Q:** Fewer CX always means better. — **A:** On the drifted device C uses 19 CX (same as B) yet ESP 0.7835 vs 0.3059.
- **Q:** ESP is the fidelity. — **A:** It is a proxy: 0.7835 vs simulated 0.9878; use it to rank.
- **Q:** A good compiler can meet any depth budget. — **A:** `tight_budget`: depth 17 is impossible on a ladder.
