# Hybrid quantum-classical architecture: orchestrator, job queue and backend adapter — explained

## The intuition

A variational algorithm (lessons 14–15) is a loop: propose angles, evaluate circuits, update. In production the backend is a shared device behind a queue: every *job* waits (modelled as 2 s), every circuit structure must be *transpiled* (0.5 s), and jobs sometimes fail transiently. The loop becomes a distributed system whose cost is overhead, not quantum execution.

The lab puts three components between the optimiser and the device. The **backend adapter** hides one provider's API behind `transpile()` and `run()`. The **orchestrator** decides how circuits become jobs and owns the transpile cache and the retry policy. A **FakeClock** models queue, transpile and classical time, so designs can be compared deterministically on a laptop.

Two design questions follow: how many circuits per job (one per circuit, one per optimiser step, or a reserved *session* that skips the queue but bills its whole window), and what is the cache key? All 240 circuits share one template, so one transpile should serve them all.

**Analogy:** calling a rate-limited cloud API from a training loop: batch requests, cache what does not change, retry idempotently.
Where the analogy breaks: a "session" bills wall-clock time, not requests, so idle classical time on your side costs device money.

```text
optimiser (SPSA, 4 starts) --circuits--> Orchestrator
     ^                                   | cache_key(template, target, opt_level) -> transpile once
     |                                   | mode: sync | batched | session
     |                                   | retry: 4 attempts, exponential backoff, seeded (idempotent)
     +------- counts <------------------ BackendAdapter.run(job)  [queue 2 s, transpile 0.5 s, FakeClock]
JSON line per design: wall_s, billed_s, jobs, transpiles, cache_hits, retries, best_ratio
```

The one thing to remember: in a hybrid service the queue and the compiler dominate cost, so the job granularity and the cache key are architecture decisions.

## Walkthrough: what actually happens when you run it

1. **You run** `python orchestrator.py` (the shipped code, with the naive cache key).
   **What happens inside:** each mode runs the same SPSA workload (4 starts × 30 iterations × 2 circuits, seed 2026) on a `FakeClock`; `compiled()` looks up `cache_key(template, params, …)`; the last run injects transient failures.
   **What you see:**
   ```text
   {"mode": "sync", "wall_s": 606.3, "billed_s": 4.8, "jobs": 240, … "transpiles": 240, "cache_hits": 0, … "best_ratio": 0.6922, …}
   {"mode": "batched", "wall_s": 186.3, "billed_s": 4.8, "jobs": 30, … "transpiles": 240, "cache_hits": 0, …}
   {"mode": "session", "wall_s": 131.2, "billed_s": 131.2, "jobs": 30, … "transpiles": 240, …}
   {"mode": "batched", "wall_s": 196.3, … "retries": 3, "best_ratio": 0.6922, …, "note": "seeded transient failures on attempts 3, 4, 17"}
   ```
   **What it means:** `best_ratio` is identical everywhere, even with 3 retries: retries are idempotent. But `transpiles = 240 = circuits`: 120 s of the batched 186.3 s is pointless compilation.

## Failure lab: a cache that never hits

1. **Inject:** the shipped `cache_key` includes `tuple(np.round(params, 12))`.
2. **Symptom:** `cache_hits: 0` and `transpiles: 240` on every line above.
3. **Diagnose:** the build-task test shows two calls with the same template and different angles produce different keys:

5. **Proof:** `python -m unittest test_build_task test_fitness` → `Ran 7 tests in 2.109s` … `OK`.

## Walkthrough: the decision

1. **You run** `python solution_cache_key.py` to measure the three options with the fixed cache.
   **What you see:**
   ```text
   {"mode": "sync", "wall_s": 486.8, "billed_s": 4.8, "jobs": 240, "circuits": 240, "transpiles": 1, "cache_hits": 239, …}
   {"mode": "batched", "wall_s": 66.8, "billed_s": 4.8, "jobs": 30, "circuits": 240, "transpiles": 1, "cache_hits": 239, …}
   {"mode": "session", "wall_s": 11.7, "billed_s": 11.7, "jobs": 30, "circuits": 240, "transpiles": 1, "cache_hits": 239, …}
   ```
   **What it means:** sync pays 240 queue waits. Batching sends one job per SPSA step (30 jobs): 66.8 s. A session is fastest (11.7 s) but bills the whole window, 2.4× more device time.

2. **You run** `python try_it.py` to stress the options.
   **What you see:**
   ```text
   busy_queue (wall_s, billed_s)         {'sync': (7206.8, 4.8), 'batched': (906.8, 4.8), 'session': (39.7, 39.7)}
   slow_classical_step (wall_s, billed_s) {'sync': (2585.3, 4.8), 'batched': (2165.3, 4.8), 'session': (2165.3, 2165.3)}
   ```
   **What it means:** with a 30 s queue a session wins clearly on wall time. With a 70 s classical step (longer than the 60 s interactive TTL) the session expires between jobs: same wall time as batched, 2165.3 s billed instead of 4.8 s.

3. **The ADR** (`docs/adr/0001-batched-jobs.md`) chooses batched as the default: within the 90 s wall budget, lowest billing, no dependency on session plans or TTLs. Sessions are opt-in for interactive work with short classical steps. Its consequences record the scaling limit (`max_circuits` per job) and the trigger to revisit (growing queues).

4. **The fitness function** `test_fitness.py` keeps the decision true: default mode is `batched`, jobs ≤ 30, transpiles == 1, wall ≤ 90 s, billed ≤ 5 s for the reference workload. The shipped naive key fails it (`240 != 1`, `186.3 not less than or equal to 90.0`), which is exactly the regression it exists to catch.

## Common confusions

- **Q:** Sessions are always faster, so use them. — **A:** `slow_classical_step`: session billed 2165.3 s for the same wall time as batched.
- **Q:** Caching on parameters is safer. — **A:** It turns a structural cache into a no-op: 240 transpiles.
- **Q:** Retries can change the answer. — **A:** Seeded per-circuit sampling keeps `best_ratio` 0.6922 with 3 retries.
