# A serial gateway to the PC — explained

## The intuition
USB serial looks like a clean text pipe and is not. It is a **byte stream**: no message boundaries, arbitrary chunks, boot noise, lines cut by a pulled cable, a flipped bit turning `20` into `22`. A gateway doing `line.split(",")` either crashes or forwards a wrong number.

The fix is **framing**: wrap each reading so the receiver can find where it starts, know how long it is, and verify it. The device sends `$LLL<payload>*CCCC\n` — a start marker, a 3-digit length, the payload, `*`, a CRC-16 in hex, a line end. The PC-side `Framer` buffers bytes and yields a payload only when all of these check out. Any mismatch drops **one byte** and searches for the next `$` (resync). Every decision bumps a published counter.

**Analogy:** a length-prefixed protobuf stream — never trust that `read()` returns one message. Where the analogy breaks: TCP gives you integrity; here the CRC is your only defence.

```
device: frame("1,20,100") → "$0081,20,100*1DA1\n" ─USB─► bytes in random chunks
PC:  Framer.feed(chunk): buf += chunk
       find "$" → skip garbage (skipped_bytes)
       "LLL" digits & ≤ MAX? else resync (bad_len)
       full frame? else wait
       "*" + line end? CRC ok? else resync (bad_len / bad_crc)
       yield payload → parse_payload (range check) → publish JSON {topic, qos, payload}
```

The one thing to remember: a stream needs framing, a length and a checksum before it can carry messages.

## Walkthrough: what actually happens when you run it
1. **You run** a peek: build one device frame, then feed the Framer boot garbage, that frame, a copy with `20` changed to `22`, a broken `$00` header and the frame again — all in one chunk.
   **What you see**
   ```
   device frame: $0081,20,100*1DA1
   input bytes: b'\x00boot!!$0081,20,100*1DA1\n$0081,22,100*1DA1\n$00$0081,20,100*1DA1\n'
   payloads: [b'1,20,100', b'1,20,100']
   metrics: {'frames_ok': 2, 'bad_len': 1, 'bad_crc': 1, 'bad_payload': 0, 'resyncs': 2, 'skipped_bytes': 25}
   ```
   **What it means** Length 008 is the 8 bytes of `1,20,100`. The altered `22` frame keeps the old CRC and is rejected (`bad_crc: 1`); `$00$` is not a 3-digit length (`bad_len: 1`). Both good frames get through; garbage is counted, not fatal.

### Failure lab: inject → symptom → diagnose → fix → proof
2. **Inject.** `samples/noisy.bin` (seeded, from `serial_link.py`) has boot garbage, 3 dropped bytes, 5 flipped bits and 2 cut lines across 200 frames. **You run** the naive gateway on the clean file, then the noisy one.
   **What you see**
   ```
   {"payload": {"light": 100, "seq": 1, "temp": 20}, "qos": 1, "topic": "microbit/mb1/telemetry"}
   200
   ValueError: not enough values to unpack (expected 3, got 1)
   ```
3. **Symptom.** 200 lines on clean input; on noisy input it dies on the first line (boot garbage) and forwards nothing. `test_fault` (`Ran 2 tests … OK`) also pins the silent case: a flipped digit forwarded as 22 instead of 20.
4. **Diagnose.** `parse_line()` slices `body[4:]` and splits on `*` without checking anything the frame offers.
5. **Fix.** `solution.py` reads bytes, uses `Framer`, range-checks the payload and publishes metrics.
6. **Proof.**
   **What you see**
   ```
   FAILED (errors=4)
   Ran 4 tests in 2.088s
   {"payload": {"bad_crc": 3, "bad_len": 6, "bad_payload": 0, "frames_ok": 190, "resyncs": 9, "skipped_bytes": 184}, "qos": 1, "topic": "microbit/gateway/metrics"}
   ```
   **What it means** The naive gateway errors on all 4 build tests; the solution passes, forwarding 190 frames whose values all equal what the device sent. 3 + 6 = 9 damaged frames, 9 resyncs.

7. **You run** `python3 agent_assist.py --fake`.
   **What you see**
   ```
   alarms (decided by code): LINK_NOISY=4.5, SEQ_GAP=9
   …
   check: PASS (numbers from the metrics; alarm names match the code's alarms)
   ```
   **What it means** 9 bad of 199 frames ≈ 4.5 %; code raises alarms, the model explains.

8. **You run** `python3 try_it.py`.
   **What you see**
   ```
   try 1: no CRC: forwarded 181, 2 WRONG, bad_crc 0, bad_payload 9 | with CRC: forwarded 179, 0 WRONG, bad_crc 13, bad_payload 0
   try 2: forwarded 190 readings, 0 wrong; metrics {'frames_ok': 190, 'bad_len': 6, 'bad_crc': 3, 'bad_payload': 0, 'resyncs': 9, 'skipped_bytes': 184}
   ```
   **What it means** Without the CRC, the range check catches 9 bad values but 2 plausible wrong ones slip through. Feeding one byte at a time gives identical metrics: the Framer does not depend on chunk boundaries.

Expected (not run here): with a real board, pyserial 3.5 reads the port.

## Common confusions
**Q:** `readline()` gives one message. — **A:** Cut lines and boot garbage break that; `ValueError` on line 1.

**Q:** A range check is enough. — **A:** Try 1: `2 WRONG` without CRC.

**Q:** Resync should drop the whole buffer. — **A:** Dropping one byte keeps the next good frame (the third `$` in step 1).
