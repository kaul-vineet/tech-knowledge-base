# Radio between two boards — explained

## The intuition
The micro:bit radio is a broadcast shout, not a connection. `radio.send("btn:1:A")` puts a short packet in the air; every board on the same **group** that is listening queues it; nobody acknowledges anything. No sender address, no delivery guarantee, no ordering.

That is why the lab invents a tiny protocol: `kind:seq:value`. The receiver trusts nothing: `decode()` insists on three fields, a known kind and an integer sequence number. The sequence number lets it drop replays (`seq <= last_rx`). The receive queue holds only 3 packets, so a slow loop silently loses the fourth.

**Analogy:** UDP multicast, with the group as the multicast address. Where the analogy breaks: packets are at most `length` bytes (32 by default) and longer ones are cut, not fragmented.

```
board A                             air (group 7)                 board B
button A ─► send(state,"btn","A") ─► b'\x01\x00\x01btn:2:A' ─► queue[3] ─► receive()
                                                                      ├─ ValueError → "?" → rx bad
                                                                      ├─ decode()==None → rx bad
                                                                      ├─ seq <= last_rx → drop silently
                                                                      └─ print "rx btn 2 A"
```

The one thing to remember: the radio gives you a lossy, bounded, unauthenticated broadcast — every guarantee is code you write.

## Walkthrough: what actually happens when you run it
1. **You run** a peek with two stub boards sharing one `Air`: press A on board A, step both.
   **What happens inside** `send()` bumps `seq` to 1; the air copies the packet into B's queue; B decodes it and `last_rx` becomes 1.
   **What you see**
   ```
   tx btn 1 A
   rx btn 1 A
   ```
   **What it means** One send, one receive.

2. **You run** three bad inputs into B: a replayed `btn:1:A`, the text `hello`, and raw bytes `b'\xff\x00raw'`.
   **What happens inside** the replay passes `decode()` but fails `seq <= last_rx` and returns silently. `hello` has one field → `decode()` is None. Raw bytes lack the header, so `radio.receive()` raises `ValueError`, caught and turned into `"?"`.
   **What you see**
   ```
   rx bad 1
   rx bad 2
   ```
   **What it means** Only two "bad" lines for three inputs: the duplicate is dropped without noise, by design.

3. **You run** four presses on A without letting B poll.
   **What you see**
   ```
   tx btn 2 A
   …
   tx btn 5 A
   B queue length: 3 dropped: 1
   A on-air bytes for seq 2: b'\x01\x00\x01btn:2:A'
   ```
   **What it means** The fourth packet found a full queue and vanished; the sender never knows. The `01 00 01` header is what `receive()` accepts as a string.

4. **You run** `python3 try_it.py`.
   **What you see**
   ```
   try 1: tx btn 1 A
   try 2: tx btn 1 A*40 | rx btn 1 A*23 | bytes on air: 32
   ```
   **What it means** Group 8 hears nothing. With `length=32`: 32 − 3 header − 6 for `btn:1:` leaves 23 A's — cut, not split. The stub follows the V1 truncation rule; V2 is pending the Playwright check.

5. **You run** `python3 -m unittest -v`, then the build-task check against `solution.py`.
   **What you see**
   ```
   Ran 13 tests in 0.622s
   Ran 2 tests in 0.138s
   ```
   **What it means** The build task adds `ack:<seq>:` replies; acks are sent even for duplicates because the first ack may have been lost.

Expected (not run here): in the simulator the Radio panel plays the other board; real boards add range and interference loss.

## Common confusions
**Q:** Different groups are encryption. — **A:** Group is a filter; anyone on group 7 hears `btn:2:A` in clear text.

**Q:** A long message arrives in pieces. — **A:** `rx btn 1 A*23`: it is truncated.

**Q:** If B is slow, messages wait. — **A:** Only 3 wait; `dropped: 1`.

## Check your understanding
1. Why does the replayed `btn:1:A` not print anything?
<details><summary>Answer</summary>Its seq 1 is not greater than `last_rx` (1), so it is dropped as a duplicate.</details>

2. What does a sender that restarts at seq 1 experience?
<details><summary>Answer</summary>The receiver ignores it until its seq passes the old `last_rx`.</details>

3. Why catch `ValueError` around `radio.receive()`?
<details><summary>Answer</summary>Raw bytes without the string header raise it; uncaught, one stray packet would crash the loop.</details>
