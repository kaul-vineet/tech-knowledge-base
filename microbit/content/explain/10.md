# An external sensor over I2C — explained

## The intuition
I2C is a two-wire shared bus (clock SCL on pin 19, data SDA on pin 20) where the micro:bit is the controller and each chip answers to a 7-bit **address**. Talking to a sensor is like reading a tiny memory-mapped device in two moves: **write** one byte to choose a register (the "pointer"), then **read** n bytes from it. Nothing is self-describing: you need the datasheet to know that register 0x00 is temperature and that its 12 bits are left-justified two's complement at 0.0625 °C per step.

If no chip answers at the address, the bus sees no acknowledge and MicroPython raises `OSError(19)` (ENODEV). The lab catches that instead of crashing, because "sensor unplugged" is a normal state for field hardware — and the browser simulator has no I2C devices at all.

**Analogy:** a key-value store where you first `SELECT` a key and then `GET` the value, with the bytes in a packed binary format. Where the analogy breaks: there is no schema or type; misread the bit layout and you get a plausible-looking wrong number, not an error.

```
step() ─► i2c.write(0x48, b'\x00')   "pointer = temperature"
       ─► i2c.read(0x48, 2) ─► b'\x15\x80'
              msb=0x15  lsb=0x80
              raw = (msb<<4) | (lsb>>4) = 344      (12 bits)
              if raw & 0x800: raw -= 4096           (sign)
              raw × 0.0625 = 21.5 °C
   no ACK ─► OSError 19 ─► "i2c: no device at 0x48 (errno 19)"
```

The one thing to remember: the bus moves bytes; the datasheet turns them into meaning.

## Walkthrough: what actually happens when you run it
1. **You run** a peek: `step()` with nothing attached, then attach the SIMULATED TMP102 (a Python model of the TI register map) and scan.
   **What happens inside** the stub bus finds no device at 0x48 and raises like the firmware.
   **What you see**
   ```
   i2c: no device at 0x48 (errno 19)
   scan: ['0x48']
   ```
   **What it means** This first line is also what the simulator should print, since it has no sensor.

2. **You run** `step()` with the sensor at 21.5 °C and print the bus transactions.
   **What you see**
   ```
   temp_c=21.50
   transactions: [('write', 72, b'\x00'), ('read', 72, b'\x15\x80')]
   raw = 344 -> 21.5 C
   ```
   **What it means** 72 is 0x48 in decimal. 0x15 shifted left 4 is 336, plus 0x80 shifted right 4 (8) gives 344; × 0.0625 = 21.5.

3. **You run** the sensor at −25 °C.
   **What happens inside** the chip stores −400 steps as the 12-bit pattern 0xE70.
   **What you see**
   ```
   temp_c=-25.00
   last read bytes: e700
   raw unsigned = 3696 = 0xe70 sign bit: True -> signed -400 -> -25.0 C; without sign fix 231.0
   ```
   **What it means** Bit 11 set means negative: 3696 − 4096 = −400. Forget that and you read 231 °C.

4. **You run** `python3 try_it.py`.
   **What you see**
   ```
   try 1: i2c: no device at 0x49 (errno 19)
   try 2: temp_c=231.00
   ```
   **What it means** A wrong address fails loudly; a wrong decode fails silently with a plausible number — the more dangerous bug.

5. **You run** the tests and the build-task check.
   **What you see**
   ```
   Ran 11 tests in 0.210s
   Ran 3 tests in 0.047s
   ```
   **What it means** The build task writes T_HIGH: one write of `bytes([0x03, msb, lsb])`, then reads it back to confirm.

Expected (not run here): on a real board with a TMP102 breakout, `scan: ['0x48']` and room temperature; the stub does not model conversion delay or the ALERT pin.

## Common confusions
**Q:** `i2c.read` knows which register I want. — **A:** Only the previous write sets the pointer; see the `('write', 72, b'\x00')` line.

**Q:** 0xE70 is a big positive number. — **A:** It is 12-bit two's complement: −400 steps.

**Q:** The simulator tests the sensor code. — **A:** It has no I2C devices; only the stub's simulated TMP102 does.
