# A reliable radio protocol — explained

## The intuition
Lesson 7's radio is a lossy broadcast: packets vanish, repeat, reorder or arrive damaged, and the sender never knows. "Reliable" means building, in about 60 lines, the three guarantees TCP gives you for free: **integrity** (CRC-16: damaged frames are dropped, not believed), **delivery** (ack each frame; retransmit until acked, with bounded tries), and **exactly-once, in-order** (the receiver ignores sequence numbers older than the one it expects).

The lab's version is **stop-and-wait ARQ**: one frame in flight at a time. `send()` only queues; `pump()` owns the radio, sends the head of the queue, waits for its ack, and on timeout resends with the wait doubled (100 → 200 → 400 → 800 ms cap). After `MAX_TRIES = 8` it gives up, counts `gave_up` and moves on — a protocol must never hang the device.

**Analogy:** registered mail: keep posting copies until a numbered receipt returns; the recipient bins duplicates. Where the analogy breaks: the receipt itself can be lost, so the receiver must re-ack every copy — even ones it already has.

```
A: send(r) → queue → pump(): inflight = D:seq:payload:CRC ──radio──► B: decode() (CRC ok?)
       ▲                       │ deadline passed → resend, timeout×2    │ seq < expected → dup++, still ack
       │                       │ tries ≥ 8 → gave_up++                  │ else deliver, expected = seq+1
       └── A:seq:CRC ◄────────────────────────────── ack every copy ─────┘
```

The one thing to remember: reliability is ack + retransmit + dedupe, and each piece covers a different fault.

## Walkthrough: what actually happens when you run it
1. **You run** a peek on `solution.py`'s frame code.
   **What happens inside** `encode()` appends a CRC-16/CCITT (init 0xFFFF, poly 0x1021) of the body; `decode()` recomputes it.
   **What you see**
   ```
   frame: D:3:23:F877 len 11
   check value crc16("123456789") = 0x29B1
   decode ok   : ('D', 3, '23')
   decode flip : None
   waits per try: [100, 200, 400, 800, 800, 800, 800, 800] total ms before give-up: 4700
   ```
   **What it means** 0x29B1 is the standard check value, so the CRC is the real algorithm. Changing `:3:` to `:2:` (a one-bit change in ASCII) is rejected. A dead link costs 4.7 s per frame, then the sender moves on.

### Failure lab: inject → symptom → diagnose → fix → proof
2. **Inject.** **You run** `python3 link_sim.py`. It loads two stub boards over `radio.Air(loss=0.2, dup=0.1, reorder=0.1, corrupt=0.05, seed=12)` and sends 20 readings, one every 50 ms.
   **What you see**
   ```
   main.py     faulty delivered 14/20, missing ['r2', 'r8', 'r11', 'r13', 'r14', 'r20'], duplicates 2, in order False
     air {'sent': 20, 'lost': 5, 'duplicated': 2, 'reordered': 2, 'corrupted': 1}
     A {"t":6000,"tx":20,"rx":0,"bad":0,"delivered":0}
     B {"t":6000,"tx":0,"rx":17,"bad":1,"delivered":16}
   ```
3. **Symptom.** The sender's JSON says `"tx":20` and nothing else: from A's side, all is well. Six readings are gone (5 lost plus 1 corrupted and correctly rejected as `bad`), and B delivered 16 = 14 unique + 2 duplicates.
4. **Diagnose.** The CRC is doing its job (`bad:1`); what is missing is feedback. `test_fault` pins the symptom: `Ran 1 test … OK`.
5. **Fix.** `solution.py` adds acks, timeout with ×2 backoff, `MAX_TRIES`, and `seq < expected` suppression.
6. **Proof.** **You run** the build-task test against both files.
   **What you see**
   ```
   KeyError: 'gave_up'
   KeyError: 'retx'
   FAILED (failures=2, errors=2)
   Ran 4 tests in 0.427s
   ```
   and from `link_sim.py`:
   ```
   solution.py faulty delivered 20/20, missing none, duplicates 0, in order True
     A {"t":6000,"tx":42,"retx":22,"acked":20,"gave_up":0,"rx":31,"bad":1,"dup":0,"gap":0,"delivered":0}
     B {"t":6000,"tx":0,"retx":0,"acked":0,"gave_up":0,"rx":40,"bad":1,"dup":19,"gap":0,"delivered":20}
   ```
   **What it means** Same seed, all 20 in order. The price is visible: 42 transmissions for 20 readings (22 resends), and B discarded 19 duplicate copies — each the result of a lost ack or an impatient timeout.

7. **You run** `python3 try_it.py`.
   **What you see**
   ```
   try 1: delivered 20/20, missing none, duplicates 19, in order False | sender retx 22 gave_up 0 | receiver gap -19
   try 2: delivered 20/20, missing none, duplicates 0, in order True | sender retx 13 gave_up 4 | receiver gap 0
   ```
   **What it means** Without dedupe, every retransmission becomes a duplicate reading. With `MAX_TRIES = 2` the sender gave up on 4 frames whose *acks* were lost — the data had actually arrived. "Gave up" means "unknown", not "lost".

Expected (not run here): two bridged simulators give a clean link, so only the happy path (`"acked":1`) shows there.

## Common confusions
**Q:** The CRC makes the link reliable. — **A:** It only turns corruption into loss (`bad:1`); acks recover loss.

**Q:** Only send an ack for new frames. — **A:** The previous ack may be lost; `dup:19` copies were all re-acked so A could move on.

**Q:** `gave_up 4` means 4 readings lost. — **A:** Try 2 delivered 20/20; only the acks were lost.

## Check your understanding
1. Why does `pump()`, not `send()`, touch the radio?
<details><summary>Answer</summary>Only one frame may be in flight; `send()` queues so the ARQ state machine controls timing.</details>

2. What does `"gap"` report?
<details><summary>Answer</summary>Sequence numbers skipped at the receiver because the sender gave up on them.</details>

3. When is fire-and-forget the right choice?
<details><summary>Answer</summary>When losing some readings is fine, e.g. a display that refreshes anyway.</details>
