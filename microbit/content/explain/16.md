# Close-sibling low-level code: a timer interrupt race in Rust — explained

## The intuition
An interrupt is a function the hardware calls *in the middle of your code*. TIMER1 fires every 100 µs and its handler adds 1 to a shared counter, `PENDING`. The main loop "takes" it: read, work, reset to 0. If the interrupt fires after the read but before the reset, the reset wipes its tick out. No crash, just a wrong number.

This is a **read-modify-write race**. `AtomicU32` does not help: load and store are each atomic, the *sequence* is not. The fix is to make the sequence indivisible with a **critical section** (`critical_section::with`): interrupts are masked while you read, work and write. An interrupt arriving meanwhile is held *pending* by the NVIC and runs after your write.

**Analogy:** two requests doing `x = get(); set(0)` on a shared row without a transaction — a lost update. Where the analogy breaks: the NVIC has only **one** pending bit per interrupt, so holding the "lock" too long merges ticks.

```
main: take()                        TIMER1 ISR
  n = PENDING.load()      ← 5
  delay(2_000)  ──────────────────► PENDING = 5 + 1 = 6
  PENDING.store(0)        ← wipes the 6th tick
  consumed += 5           → lost = 1

fixed: critical_section { load; delay; store }  ISR held (pending bit) → runs after store → PENDING = 1
```

The one thing to remember: atomic operations do not make a *sequence* atomic — protect read-work-write as one unit, and keep it short.

## Walkthrough: what actually happens when you run it
The Rust firmware targets the nRF52833; `cargo` and Renode are not installed here, so the race is shown on `host_sim.py`, a Python mirror with the same rules (ISR runs to completion, masking holds one pending bit).

### Failure lab: inject → symptom → diagnose → fix → proof
1. **Inject.** **You run** a peek: one `take()` with an IRQ placed exactly in the window, then a seeded soak (1000 takes, a tick between takes, an extra IRQ in the window with p = 0.3, seed 16).
   **What you see**
   ```
   racy  IRQ in window: isr 1 consumed 0 pending 0 lost 1
   racy  soak: irqs 1316 isr 1316 consumed 1000 pending 0 lost 316
   fixed IRQ in window: isr 1 consumed 0 pending 1 lost 0
   fixed soak: irqs 1316 isr 1316 consumed 1316 pending 0 lost 0
   ```
2. **Symptom.** The handler ran 1316 times but the main loop accounted for 1000: 316 ticks (24 %) vanished. `test_fault` pins it (`Ran 3 tests … OK`).
3. **Diagnose.** `lost = isr_total − consumed − pending`: in the window case the ISR ran once and the store erased it.
4. **Fix.** `solution_model.py` (mirroring `fixed.rs`) masks before the load and unmasks after the store. In the window case the tick is now `pending 1`, collected by the next take.
5. **Proof.** **You run** the build-task tests on both models.
   **What you see**
   ```
   AssertionError: 1 != 0 : ('window',)
   AssertionError: 280 != 0 : 1
   AssertionError: Tuples differ: (1316, 316) != (1316, 0)
   FAILED (failures=3)
   Ran 3 tests in 0.082s
   ```
   **What it means** The racy model fails every-interleaving, other-seeds (seed 1 loses 280) and soak; the fixed one passes all 3.

6. **You run** `python3 -m unittest test_main`.
   **What you see**
   ```
   Ran 6 tests in 5.908s
   ```
   **What it means** The TIMER1 (0x4000_9000) and UART0 (0x4000_2000) register offsets in `main.rs` are checked against the nRF52833 Product Specification, and `main.rs`/`fixed.rs` are checked to differ only in `take()`.

7. **You run** `python3 try_it.py`.
   **What you see**
   ```
   try 1: racy, short window: irqs 1039, isr runs 1039, consumed 1000, pending 0, lost 39
   try 2: fixed, long section: irqs 1632, isr runs 1316, consumed 1316, pending 0, lost 0
   ```
   **What it means** A 10× shorter window makes the bug 8× rarer (39 lost) — likelier to pass a quick test, still wrong. A critical section spanning two timer periods balances the books (`lost 0`) but 1632 − 1316 = 316 timer events merged in the single pending bit: those ticks never ran at all.

Expected (not run here): `cargo test` in `logic/` runs 4 tests; in Renode 1.17.0 the nRF52840 model (close sibling: same Cortex-M4F core and TIMER1/UART0 map, no micro:bit peripherals) prints `round=N … lost=…` on uart0, `lost=0` for the fixed build. Both are pending CI.

## Common confusions
**Q:** `AtomicU32` makes it safe. — **A:** Load and store are separate atomics; the soak still loses 316.

**Q:** Masking interrupts loses them. — **A:** `fixed … pending 1`: held, then run — unless masked for several periods (try 2).

**Q:** A rarer bug is smaller. — **A:** Try 1: only harder to catch.

## Check your understanding
1. Why is the update inside the ISR safe without a critical section?
<details><summary>Answer</summary>Main code cannot preempt an ISR, so its load-add-store runs uninterrupted.</details>

2. What does a long critical section cost?
<details><summary>Answer</summary>Interrupt latency and merged interrupts — ticks that never happen.</details>

3. When is `fetch_sub`/`swap` the better fix?
<details><summary>Answer</summary>For one counter on ARMv7-M (V2); `swap(0)` reads and resets in one instruction. ARMv6-M (V1) lacks it.</details>
