# Edge-to-cloud architecture: from sensor boards to a dashboard — explained

## The intuition
Six boards around a classroom need to get one reading per second each into a store on a PC, with at least 99 % stored, p95 latency under 2 s, and **one** USB cable. That last constraint decides the shape: the boards cannot all be wired, so readings must hop through the air to a **relay** board plugged into the PC, which prints lab 15 frames to a serial **gateway** that publishes MQTT-style JSON and stores each reading idempotently by `(device, seq)`.

The surprise is *why* the first relay design fails. One board is fine — lab 12's ARQ recovers loss. Six fail together because they are **identical**: same start time, same 100/200/400 ms retry deadlines. They transmit in lock-step, their frames reach the relay together, the relay's 3-frame receive queue overflows, the losses trigger retries… which also arrive together. The fix is not mainly a bigger queue but **desynchronisation**: a random sampling phase per board and jitter on every timeout.

**Analogy:** the thundering herd — clients retrying a failed service at identical backoff instants. Where the analogy breaks: the stub has no collisions, so real radios add a second herd effect the model cannot show.

```
sensor ×6 ──radio (ARQ, loss 5–15 %)──► relay board (queue 3→12, ack, dedupe)
                                              │ USB serial: lab 15 frames
                                              ▼
                                  gateway (Framer) ─► MQTT QoS 1 JSON ─► store (dev, seq) ─► dashboard
lock-step:   ▮     ▮     ▮      all 6 at t=0, 100, 300 …  → queue overflow
jittered:    ▮ ▮  ▮ ▮ ▮   ▮     spread out                  → fits
```

The one thing to remember: identical devices synchronise; add randomness before you add capacity.

## Walkthrough: what actually happens when you run it

### The decision: options and what each measurement showed
1. **You run** `python3 options.py` (seed 17, six boards, 30 s, per-link loss 5–15 %).
   **What you see**
   ```
   {"file": "solution.py", "sensors": 6, "sampled": 180, "stored": 180, "delivery_pct": 100.0, "p50_ms": 13, "p95_ms": 13, … "option": "A direct serial", "usb_cables": 6}
   {"file": "node.py", "sensors": 6, "sampled": 180, "stored": 160, "delivery_pct": 88.9, "p50_ms": 2128, "p95_ms": 9578, "max_ms": 10568, "tx": 549, "retx": 369, "gave_up": 56, "relay_queue_drops": 149, "sensor_queue_drops": 1027, … "option": "B radio relay (node.py)", "usb_cables": 1}
   {"file": "solution.py", "sensors": 6, "sampled": 180, "stored": 180, "delivery_pct": 100.0, "p50_ms": 13, "p95_ms": 153, "max_ms": 393, "tx": 210, "retx": 30, "gave_up": 0, … "option": "B radio relay (solution.py)", "usb_cables": 1}
   {"option": "C BLE", "measured": false, "why": "micro:bit MicroPython V2: only BLE flashing is implemented; no BLE API for user code"}
   ```
   **What it means**
   - **A, direct serial:** perfect (p95 13 ms) but 6 cables — fails a hard constraint.
   - **B as written:** 88.9 % stored, p95 9.6 s. The tell is `relay_queue_drops: 149` and 369 retransmissions for 180 readings: the relay is drowning in synchronised bursts.
   - **B fixed:** 100 %, p95 153 ms; 210 transmissions instead of 549.
   - **C, BLE:** not measurable: no BLE API for user code.

### Failure lab: inject → symptom → diagnose → fix → proof
2. **Inject / symptom.** `test_fault` pins `node.py`'s 160/180 (`Ran 1 test … OK`).
3. **Diagnose.** In `node.py`, `next_sample` starts at `start_ms` on every board and `first_timeout()` returns the constant `TIMEOUT_MS` ("identical on every board: retries stay in lock-step"), with `QUEUE = 3`.
4. **Fix.** `solution.py` adds `phase = random.randint(…) * 10`, timeout jitter, `QUEUE = 12` and `LENGTH = 64`.
5. **Proof.** **You run** the build task against `node.py` (`BUILD_TARGET=mine`), then `solution.py`.
   **What you see**
   ```
   AssertionError: 8.8 not greater than or equal to 99.0
   AssertionError: 38 not less than or equal to 32
   AssertionError: 88.9 not greater than or equal to 99.0
   FAILED (failures=3)
   Ran 3 tests in 5.699s
   ```
   **What it means** At 24 boards `node.py` stores 8.8 %. After a school day the frame grows to 38 bytes, over the default 32-byte radio length — a slow-burning failure (lab 20 saw it after about 1,000 s). The solution passes all 3.

6. **You run** `python3 try_it.py` to separate the two fixes at 24 boards.
   **What you see**
   ```
   try 1: delivered 480/480 (100.0%), p95 165 ms, gave_up 0, relay drops 0, sensor drops 176
   try 2: delivered 151/480 (31.5%), p95 19031 ms, gave_up 216, relay drops 570, sensor drops 15787
   ```
   **What it means** Jitter with the old 3-frame queue: 100 %. A 12-frame queue *without* jitter: 31.5 %. Desynchronisation is the part that scales.

### Why the ADR chose B, and how it stays true
7. `adr/0017-radio-relay-to-one-serial-gateway.md` (Nygard format) records: one relay on USB; lab 12 ARQ; random phase; jittered timeouts; queue 12; length 64; gateway reuses lab 15's framer, MQTT QoS 1, idempotent `(dev, seq)` store. Consequences it admits: ~768 B of RAM per board for the queue, a single-point-of-failure relay, and no airtime/collision/CPU model.
8. **You run** `python3 -m unittest test_fitness`.
   **What you see**
   ```
   Ran 1 test in 13.615s
   ```
   **What it means** Seeds 1–5 must each give delivery ≥ 99 %, p95 ≤ 2,000 ms and `gave_up == 0`. Change the design so any seed breaks that and CI fails — fix it or write a new ADR.

Expected (not run here): the bridged-simulator test is pending CI; on real boards, collisions and relay CPU per frame are unmeasured scaling limits.

## Common confusions
**Q:** Bigger queues fix bursty loss. — **A:** Try 2: queue 12 without jitter stores 31.5 %.

**Q:** Option A lost because it is slow. — **A:** It was fastest (p95 13 ms); it failed the one-cable constraint.

**Q:** The fitness function is just a unit test. — **A:** It enforces the ADR's constraints over five seeds.
