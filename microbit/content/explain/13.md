# Non-blocking firmware structure — explained

## The intuition
`sleep(1000)` paces a loop simply, and blinds the board for a second at a time. A quick tap read with `is_pressed()` during the sleep is never seen; nothing crashes, the count is just wrong.

The fix is to stop *waiting* and start *asking what is due*. A **cooperative scheduler** keeps a list of tasks, each with a period and a next-due time: button every 20 ms, sensor every 1000 ms, display every 100 ms. The main loop never sleeps; `run_once()` walks the list and runs only what is due. Because one task can still hog the CPU, the scheduler **measures itself**: it logs `overrun` when a task exceeds its budget, `late` when a whole period was skipped, and after `MAX_ERRORS = 3` failures in a row it disables the task and enters a **safe state** (pin 0 low, `Image.NO`).

**Analogy:** a single-threaded event loop (Node.js) with timers instead of `Thread.sleep`. Where the analogy breaks: there is no OS to preempt a runaway task; the scheduler can only notice afterwards and report it.

```
blocking:   [poll|read|show|──── sleep 1000 ────][poll|read|show|── sleep ──]
                                 ↑ taps here are invisible

scheduler:  loop: for task in tasks:
                     if now >= due: run, time it → overrun? late? error?
                                    due += period
            button ▮ ▮ ▮ ▮ ▮ ▮ ▮ ▮ ▮ ▮ (20 ms)   display ▮    ▮ (100 ms)   sensor ▮ (1000 ms)
```

The one thing to remember: never sleep in the main loop — schedule, and make the schedule report on itself.

## Walkthrough: what actually happens when you run it

### Failure lab: inject → symptom → diagnose → fix → proof
1. **Inject.** **You run** `python3 tap_sim.py`. `taps(seed=13)` puts 8 presses of 150 ms on the stub's input timeline; `sleep()` fires them as the virtual clock passes.
   **What you see**
   ```
   taps at (ms): [932, 1680, 2630, 3695, 4645, 5655, 6689, 7744]
   main.py     (sleep 1000): counted 1 of 8
   solution.py (scheduler) : counted 8 of 8; stats {'runs': 610, 'overruns': 0, 'missed': 0, 'errors': 0}
   ```
2. **Symptom.** 1 of 8, silently. `test_fault` pins it (`Ran 1 test … OK`).
3. **Diagnose.** `main.py` samples the button only at t = 0, 1000, 2000 … ms. Only the tap at 932–1082 ms covers a sample instant (1000). Every other tap starts and ends inside a sleep.
4. **Fix.** `solution.py` turns the three jobs into tasks. 610 runs in 10 s is exactly 500 button + 10 sensor + 100 display runs — the periods are kept.
5. **Proof.** **You run** the build-task test before and after.
   **What you see**
   ```
   FAIL: test_every_quick_tap_counts (test_build_task.Scheduler.test_every_quick_tap_counts)
   AssertionError: 1 != 8
   FAILED (failures=1, errors=5)
   Ran 6 tests in 1.216s
   ```
   **What it means** On `main.py` five tests error because there is no `new_scheduler`; the sixth fails with the real symptom. On `solution.py` all 6 pass.

6. **You run** a peek that replaces the sensor task with one that always raises `OSError(19)`.
   **What happens inside** `run_once()` catches the exception, logs it, counts it; the third consecutive error disables the task and calls `safe_state()`.
   **What you see**
   ```
   {"t":0,"event":"error","task":"sensor","count":1}
   {"t":1000,"event":"error","task":"sensor","count":2}
   {"t":2000,"event":"error","task":"sensor","count":3}
   {"t":2000,"event":"safe_state","task":"sensor"}
   safe: True pin0: ('digital', 0) stats: {'runs': 124, 'overruns': 0, 'missed': 0, 'errors': 3}
   ```
   **What it means** A broken sensor does not crash the device; it fails once per period, visibly, and then the outputs go to a known-safe value.

7. **You run** `python3 try_it.py`.
   **What you see**
   ```
   try 1: counted 6 of 8 | stats {'runs': 160, 'overruns': 0, 'missed': 0, 'errors': 0} | events none
   try 2: counted 8 of 8 | stats {'runs': 440, 'overruns': 10, 'missed': 170, 'errors': 0} | events ['late', 'overrun']
   ```
   **What it means** Polling every 200 ms misses 2 taps of 150 ms — the poll period must be shorter than the shortest event. A 300 ms sleep inside the sensor task causes 10 overruns (one per sensor run) and 170 skipped periods of the button and display tasks; it happened not to swallow a tap this time, but the log names the culprit.

Expected (not run here): on a board the loop spins as fast as MicroPython runs (the stub advances 1 ms per pass), and `was_pressed()` would latch taps in the runtime — a different fix for this particular symptom.

## Common confusions
**Q:** The scheduler fixes slow tasks. — **A:** It detects them; try 2 still shows `missed: 170`.

**Q:** `sleep(100)` would be fine. — **A:** Any sleep longer than a tap loses taps; try 1 loses 2 at 200 ms.

**Q:** Errors should stop the program. — **A:** The safe-state line shows one task stopped, contained and reported.

## Check your understanding
1. Why was exactly one tap counted by `main.py`?
<details><summary>Answer</summary>Only the 932–1082 ms tap overlapped a sample instant (t = 1000).</details>

2. What does `late` with `missed` mean?
<details><summary>Answer</summary>A task ran a whole period or more after its due time; `missed` counts the skipped periods.</details>

3. Why reset a task's error count after a success?
<details><summary>Answer</summary>So only consecutive failures trip the safe state, not occasional glitches.</details>
