# Capstone: classroom environmental monitor network — explained

## The intuition
Each L400 lab solved one problem alone. The capstone asks whether the solutions **compose**: run all at once on one seeded classroom and check every constraint together.

Follow one reading. A board samples, tags the frame with SipHash and a counter (lab 19), and sends it with desynchronised ARQ (labs 12/17). A **keyless** relay acks, dedupes and prints lab 15 frames over USB. On the PC, the framer checks length and CRC, then the verifier checks device, MAC and replay window. That verifier is the **single trust boundary**: everything behind it — MQTT, the SQLite store keyed by `(dev, seq)`, the twin, the alarms, the model — trusts only verified readings. 

**Analogy:** microservices that keep their contract tests, plus one end-to-end scorecard. Where the analogy breaks: the whole environment is a deterministic simulation, so passing proves composed logic, not deployment.

```
boards n1..n6 (lab 19 tags + lab 17 ARQ + firmware TEMP_HIGH) ──radio──► relay (keyless)
Eve (replay + forge) ─────────────────────────────────────────────────┘     │ USB serial
PC: framer (15) → verifier (19, trust boundary) → MQTT QoS 1 → SQLite (dev, seq)
        → twin CUSUM (20) → alarm rules + freeze (21) → local model: text only
        → fleet controller (18) ⇄ boards ;  exports: dashboard.csv, metrics.txt → Superset / Grafana
```

The one thing to remember: one trust boundary, one source of truth per decision, and a scorecard that tests all of them on the same run.

## Walkthrough: what actually happens when you run it
1. **You run** `python3 build_firmware.py`.
   **What happens inside** it concatenates lab 19's `frame_auth.py` with lab 17's `solution.py` and applies `firmware_patches.json`; each patch must match exactly once, or the build stops (ADR 0022).
   **What you see**
   ```
   wrote build/classroom_node.py 255 lines
   ```

2. **You run** `python3 run_capstone.py` (600 simulated seconds, seed 22).
   **What you see**
   ```
   {"milestone": "M1", "criterion": "delivery", "value": 99.97, "threshold": ">= 99.0 %", "pass": true}
   {"milestone": "M1", "criterion": "p95 latency ms", "value": 324, "threshold": "<= 2000", "pass": true}
   {"milestone": "M2", "criterion": "attacks seen and rejected", "value": {"mac": 9, "replay": 8}, …}
   {"milestone": "M3", "criterion": "unacked config ticks / canary blast radius", "value": [0, 1], …}
   {"milestone": "M4", "criterion": "n5 link drift found (window)", "value": 14, "threshold": "<= 19 (drift from window 10)", "pass": true}
   {"milestone": "M4", "criterion": "other drift alarms", "value": ["n6 DRIFT_LAT"], "threshold": "<= 1 entry", "pass": true}
   {"milestone": "M5", "criterion": "TEMP_HIGH n4 by gateway and firmware", "value": [true, true], …}
   {"milestone": "M5", "criterion": "model cannot change alarms", "value": true, …}
   {"milestone": "M6", "criterion": "dashboard exports match the store", "value": [3599, 3599, 3599], …}
   {"scorecard": "PASS", "passed": 10, "total": 10, …}
   ```
   **What it means, decision by decision**
   - **M1 (ADR 0017):** 3,599 of 3,600 stored; p95 324 ms — higher than lab 17's 153 ms, still under 2 s.
   - **M2 (ADR 0023):** of Eve's 10 replays and 10 forgeries, 9 failed the MAC, 8 the window, the rest were lost on air; none stored.
   - **M3 (ADR 0018):** 0 unacknowledged ticks; the bad v3 reached only the canary.
   - **M4 (ADR 0020):** n5's drift found at window 14 (budget 19). n4's `DRIFT_TEMP` (sun on that desk) fires as designed; one unexplained extra is allowed — here `n6 DRIFT_LAT`.
   - **M5 (ADR 0021):** `TEMP_HIGH` at n4 raised by both firmware and gateway; the injected reply rejected, digest unchanged.
   - **M6 (ADR 0024):** CSV rows, Prometheus counter sum and store all equal 3,599.

3. **You run** `wc -l out/dashboard.csv` and look at `out/metrics.txt`.
   **What you see**
   ```
   3600 out/dashboard.csv
   classroom_readings_total{dev="n1"} 600
   ```
   **What it means** 3,600 lines = header + 3,599 readings; n1 delivered all 600.

4. **You run** `python3 -m unittest -v`.
   **What you see**
   ```
   test_scorecard_passes_on_another_seed (test_fitness.Fitness.test_scorecard_passes_on_another_seed) ... ok
   …
   Ran 9 tests in 40.191s
   OK (skipped=1)
   ```
   **What it means** The fitness function reruns everything on seed 23, never used for tuning. The skip is the real-broker test.

Expected (not run here): Superset shows 3,599 rows and Grafana `sum(classroom_readings_total)` = 3,599; brokers, models and simulator are pending.

## Common confusions
**Q:** Passing every lab means the system passes. — **A:** p95 rose from 153 to 324 ms when composed.

**Q:** The relay should verify MACs too. — **A:** ADR 0023 keeps keys off the relay: one place to audit.

**Q:** Seed 22 passing proves robustness. — **A:** That is why `test_fitness` uses seed 23.
