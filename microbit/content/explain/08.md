# Data logging — explained

## The intuition
Logging is two pipelines fed by one sample. Each interval the lab reads a row `{"temp": …, "light": …}` and sends it two ways:
- to the V2 **`log` module**, which appends CSV to flash (`MY_DATA.HTM` on a real board) with its own `Time (seconds)` column;
- to **serial** as our own CSV (`time_ms,temp,light`), which is the export path you can copy from the simulator and clean with `export_csv.py`.

Two design rules hide in that. Labels are set **once**, before the first row, because the header is a schema. And flash is finite: when it is full, `log.add` raises `OSError(28)` (ENOSPC). The main lab lets that crash on purpose; the build task handles it.

**Analogy:** writing every event both to a local append-only file and to stdout for a log shipper. Where the analogy breaks: the "disk" is a few hundred kilobytes, and there is no rotation — full means full until you erase.

```
temperature(), read_light_level() ─► row dict
       ├─► log.add(row) ─► flash CSV: "0.00,21,120"   (OSError 28 when full)
       └─► print(to_csv(running_time(), row)) ─► serial: "0,21,120"
                                   └─► export_csv.py ─► readings.csv (keeps integer time rows only)
```

The one thing to remember: one sample, two formats — and the flash copy can run out.

## Walkthrough: what actually happens when you run it
1. **You run** a peek: `setup()`, then `step()` four times with injected values and `sleep(1000)` between, with the stub log capped at 60 bytes.
   **What happens inside** `set_labels(..., timestamp=log.SECONDS)` writes the header; each `log.add` writes a row; the third row would exceed the cap, so the stub raises like CODAL's MicroBitLog does.
   **What you see**
   ```
   time_ms,temp,light
   0,21,120
   1000,22,110
   OSError 28 after 2 rows
   MY_DATA csv:
   Time (seconds),temp,light
   0.00,21,120
   1.00,22,110
   ```
   **What it means** Same data, two clocks: `1000` ms on serial, `1.00` s in flash. The exception escapes `step()` before the serial print, so the third row is lost from both — exactly what the build task fixes.

2. **You run** `python3 try_it.py`.
   **What happens inside** try 1 adds `log.set_mirroring(True)`, so the log also prints its rows to serial; try 2 feeds that mixed transcript to `export_csv.extract()`.
   **What you see**
   ```
   try 1: time_ms,temp,light | Time (seconds),temp,light | 0.00,21,120 | 0,21,120 | 1.00,22,110 | 1000,22,110
   try 2: kept 2 rows [['0', '21', '120'], ['1000', '22', '110']]; skipped 3 (…: time_ms not an integer, …)
   ```
   **What it means** The exporter validates rows against our schema: mirrored rows have a float time and are skipped with a reason, not silently mixed in.

3. **You run** `python3 agent_assist.py --fake`.
   **What you see**
   ```
   code stats (authoritative): 6 rows over 5 s; temp 21..24 mean 22.5 (up); light 41..120 mean 89.8 (down)
   …
   check: PASS (every number matches the CSV or a computed stat; trends match)
   ```
   **What it means** Code computes min, max, mean and trend; the model may only repeat them.

4. **You run** `python3 -m unittest -v`.
   **What you see**
   ```
   Ran 15 tests in 15.860s
   ```
   **What it means** The slow time is the storage mount.

5. **The build task.** `solution.py` wraps `log.add` in `try/except OSError`, re-raises anything but 28, sets `state["logging"] = False` and prints `log full after N rows` once; serial CSV keeps going.

Expected (not run here): the simulator's Data logging panel shows a table with `Time (seconds)`; this format was not observed here (pending CI).

## Common confusions
**Q:** The serial CSV and MY_DATA are the same file. — **A:** Different time columns: `0,21,120` vs `0.00,21,120`.

**Q:** Labels can be added later. — **A:** The header is written once; set them in `setup()`.

**Q:** A full log just stops quietly. — **A:** `OSError 28 after 2 rows` — it raises.
