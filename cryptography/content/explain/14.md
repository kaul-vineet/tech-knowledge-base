# Signing the software supply chain — explained

## The intuition
Installing a release means running code someone else built. Signing answers two questions first: *who* produced it, and *is it exactly what they produced*? Real systems sign one **manifest** listing every file with its size and SHA-256 digest; one Ed25519 signature over the manifest bytes covers every file transitively.

The catch, and the point of this lab: a signature protects only what the installer *checks*. A valid signature proves the manifest is genuine. It says nothing about files on disk unless the installer recomputes each digest, and nothing about extra files unless it rejects anything unlisted. Attackers aim at that gap: they leave the signed manifest alone and change or add files around it. Trust in keys works the same way: the installer pins accepted signer key IDs and rotates them deliberately.

**Analogy:** a sealed packing list taped to a crate; the wax seal proves the list came from the shipper. Where the analogy breaks: a human notices an extra box; software copies the whole folder unless you write the line comparing disk against list.

```
build: files ─sha256/size─▶ MANIFEST.json ─Ed25519 sign─▶ MANIFEST.json.sig {kid, sig}
install(dist, target, trusted):
   kid in trusted? ─no─▶ Rejected("unknown signer …")
   verify(sig, raw bytes) ─bad─▶ Rejected("manifest signature invalid")
   listed files exist?            ← the naive installer stops checking here
   [fix] on-disk set == listed set? every size + digest matches? ─then─▶ copy
```

**The one thing to remember:** verify the signature, then verify the disk against the signed list — both directions — before copying anything.

## Walkthrough: what actually happens when you run it
1. **You run** `python release_sign.py`. **What happens inside:** `build_artifacts()` writes a seeded four-file release; `sign_release()` serialises the manifest with `sort_keys=True` and signs the exact bytes; `key_id()` is the first 16 hex characters of SHA-256 of the public key (lesson 7's scheme). **What you see:**
   ```
   manifest lists 4 files; signer eeaa4068b2dd254d
   clean release                installed 4 files
   installer pins another key   REJECTED: unknown signer eeaa4068b2dd254d
   ```
   The key ID is random per run (README: `4793bac0a5cc620b`). **What it means:** a validly signed release from an unpinned key is refused.
2. **You run** `python try_it.py`. **What you see:**
   ```
   1) both keys trusted  v1.0.0: 4 files                                  v2.0.0: 4 files
   1) old key removed    v1.0.0: REJECTED (unknown signer 34750f98bd59fcfc) v2.0.0: 4 files
   2) one hex digit changed in MANIFEST.json: manifest signature invalid
   ```
   **What it means:** rotation is "trust old + new, then drop old" — after the drop, old releases stop installing. An attacker cannot "fix" a digest: the signature covers it.

### Failure lab: the installer that trusts the folder
- **Inject:** `tamper(dist, seed=14)` overwrites `README.txt` and adds `app/zz_extra.pth` — a file Python executes at start-up — keeping the old manifest and signature.
- **Symptom:**
  ```
  fault: attacker swapped README.txt and added app/zz_extra.pth; manifest + signature unchanged
  tampered release             installed 5 files
  ```
- **Diagnose:** `verified_manifest()` passed, correctly. `install()` then only checked that listed files *exist* and copied everything in `files_in(dist)`.
- **Fix:** `solution_strict.py` compares listed and on-disk sets both ways and every size and digest (`hmac.compare_digest`), copying only after all checks pass. **You run** `python solution_strict.py`. **What you see:**
  ```
  clean release:    4 files installed
  tampered release: REJECTED: unknown file(s): ['app/zz_extra.pth']
  ```
- **Proof:** against the unfixed file, `BUILD_IMPL=release_sign python -m unittest -v test_build_task` prints three `FAIL:` lines (`test_seeded_attack_rejected`, `test_swapped_file_rejected`, `test_unknown_file_rejected`) and `FAILED (failures=3)`. Against the solution: `Ran 4 tests in 0.018s`, `OK`. Full suite: `Ran 9 tests in 0.038s`, `OK (skipped=1)`.
3. **The skipped test:** `test_sign_verify_and_detect_edit … skipped 'minisign not installed'`. Expected (not run here): per the minisign release notes, `minisign -V -p ms.pub -m MANIFEST.json` verifies the clean manifest and fails after one hex digit changes — try_it 2's verdict. Sigstore cosign `sign-blob`/`verify-blob` does the same and also records signatures in a public transparency log.

## Common confusions
- **Q:** "The signature verified, so the release is safe." — **A:** `tampered release installed 5 files` happened *after* a valid signature check.
- **Q:** "Changing a README is harmless." — **A:** The check must be uniform, and the added `.pth` file runs on every interpreter start.
- **Q:** "Removing the old key only affects new builds." — **A:** try_it 1: v1.0.0 is `REJECTED` once its key is gone.
