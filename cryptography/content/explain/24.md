# Foundations II: probability for cryptography — explained

## The big picture
Many rules you followed in L100–L400 are really probability statements in disguise. "Use a fresh random 96-bit nonce per AES-GCM message, at most 2³² messages per key" is a birthday bound. "Use `secrets`, not `random`" and "a password is weaker than its length suggests" are statements about entropy. "Secure" in a security proof means an attacker's chance is *negligible*. This lesson proves those four statements and runs them as code. The labs they explain: **Authenticated encryption: AES-256-GCM and ChaCha20-Poly1305** (the nonce budget), **Secure randomness: secrets vs random** (uniform sources), **Misuse you can test: Wycheproof vectors, timing and nonce reuse** (what a repeated nonce costs), and **Password storage: Argon2id (and scrypt fallback)** (why min-entropy, not length, measures guessability). The lab code is `prob_tools.py`; `theorem_checks.py` tests each theorem numerically.

### Birthday upper bound (union bound)
**In plain words.** Draw q random values from N possibilities. The chance that any two match is at most q(q−1)/(2N) — roughly q²/2N.

**Why it is true (intuition).** Count pairs, not people. A collision means *some* pair matched; there are q(q−1)/2 pairs, each matching with probability 1/N, and the probability of "at least one" is at most the sum. Skeleton: (1) define the event C_ij "draw i equals draw j"; (2) Pr[C_ij] = 1/N whatever draw i was; (3) collision = union of all C_ij; (4) union bound: Pr[∪] ≤ Σ Pr = q(q−1)/(2N).

**See it in numbers.** `python theorem_checks.py`:
```
exact <= bound in 20/20 (N, q) cases; N = 365, q = 23: exact 0.507297, bound 0.693151
96-bit nonces, q = 2^32: bound = 2^-33.00
```
For birthdays the bound overestimates (0.69 vs 0.51) because at that size pair-events overlap a lot. For nonces q²/N is tiny, the overlap negligible, and the bound is essentially exact.

**Where it shows up in practice.** AES-GCM in **Authenticated encryption: AES-256-GCM and ChaCha20-Poly1305** uses `os.urandom(12)`; this is why its key must be rotated before 2³² messages.

### Birthday lower bound and the 50 % threshold
**In plain words.** Collisions are not just *possibly* likely — they are *guaranteed* likely once q passes about 1.18·√N.

**Why it is true (intuition).** Compute the chance of *no* collision one draw at a time, then bound each factor by an exponential. Skeleton: (1) draw i+1 avoids the first i (distinct) values with probability 1 − i/N; (2) multiply all factors (independence); (3) use 1 − x ≤ e^(−x) on each; (4) the product becomes exp(−q(q−1)/2N); (5) set it to 1/2 and solve: q ≈ √(2 ln 2 · N).

**See it in numbers.**
```
N = 365: first q with P >= 1/2 is 23 (formula 22.49)
N = 2^32: first q with P >= 1/2 is 77164 (formula 77163)
simulation N = 2^24, q = 4096, 2000 trials: observed 0.400, predicted 0.393
```
The formula is off by under one; the seeded simulation lands within 0.007. 77164 is the alarming number: 32-bit random IDs collide with even odds after ~77 thousand draws.

**Where it shows up in practice.** It is why 32-bit random request IDs or truncated hashes break at small scale, and why lesson 15's tag truncation matters.

### Nonce budget for random 96-bit nonces (corollary)
**In plain words.** With random 96-bit nonces, 2³² messages under one key give a repeat chance of about 2⁻³³; the risk reaches 2⁻³² at about 6 billion messages.

**Why it is true (intuition).** Plug N = 2⁹⁶ into the upper bound. Skeleton: (1) q(q−1)/2N ≤ q²/2⁹⁷; (2) q = 2³² gives 2⁶⁴/2⁹⁷ = 2⁻³³; (3) solving q²/2⁹⁷ = 2⁻³² gives q = 2³²·⁵; (4) the lower bound agrees closely, so the budget is tight, not pessimistic.

**See it in numbers.**
```
P[collision] after 2^32 messages = 1.1642e-10 = 2^-33.00
messages for risk 2^-32 = 6.0740e+09 = 2^32.50; risk 1/2 at 2^48.24
collisions among 2^20 os.urandom(12) nonces: 0 | pyca AES-GCM: 96-bit nonce, 16-byte tag
```
and from `python prob_tools.py`: `at 1,000,000 messages/s one key reaches 2^32 messages in 71.6 minutes`. A busy service exhausts a GCM key's budget in about an hour.

**Where it shows up in practice.** A repeat leaks the XOR of two plaintexts and lets an attacker forge GCM tags — exactly what `nonce_guard.py` demonstrated in **Misuse you can test: Wycheproof vectors, timing and nonce reuse**. Rotate keys (lesson 12) or use 192-bit XChaCha20 nonces.

### Entropy inequalities and negligible functions
**In plain words.** (a) Min-entropy ≤ Shannon entropy ≤ log₂ of the number of outcomes, with equality only for a uniform source. (b) A polynomial number of attempts, each with negligible success chance, still succeeds with only negligible chance.

**Why it is true (intuition).** (a) Min-entropy looks only at the single most likely outcome — the attacker's best first guess — so it can never exceed the average surprise; and no distribution on |S| outcomes is more surprising than uniform. (b) "Negligible" means smaller than every 1/poly, so multiplying by one polynomial leaves room under every other. Skeleton: (1) each −log₂ p(x) ≥ −log₂ p_max, average them; (2) Jensen on concave log₂ gives H ≤ log₂|S|; (3) for (b), absorb n^k into the exponent: ε(n) < n^(−c−k) ⇒ n^k·ε(n) < n^(−c).

**See it in numbers.**
```
random distributions satisfying both inequalities: 1000/1000
uniform 2^128: H = H_min = 128 bits | PIN with P('1234') = 0.1: H = 12.43, H_min = 3.32 bits
2^40 queries, 2^-128 per query: union bound 2^-88
```
The PIN looks like 12.43 bits "on average", but an attacker's first guess succeeds 10 % of the time — 3.32 bits. 2⁴⁰ queries against a 128-bit key leave 2⁻⁸⁸: negligible in practice.

**Where it shows up in practice.** `secrets.token_bytes` (lesson 3) is uniform, so H_min equals its length; human passwords (lesson 5) are not, which is why Argon2id must slow each guess.

## Worked problems
**24-P4 (10,000 messages per second, 96-bit random nonces).**
1. Budget: 2³² = 4,294,967,296 messages. *Why:* NIST SP 800-38D's limit for random IVs, which T24.3 shows keeps the risk ≤ 2⁻³³.
2. Seconds: 4,294,967,296 / 10,000 = 429,496.7 s. *Why:* rate × time = count.
3. Days: 429,496.7 / 86,400 = 4.97 days. *Why:* 86,400 s per day.
4. Conclusion: rotate the key within 4 days, or use counter nonces. *Why:* the bound is per key — every replica sharing it counts.

**24-P6 (PIN with P('1234') = 0.1, others uniform).**
1. Other PINs: 0.9 / 9,999 ≈ 9.0009·10⁻⁵ each. *Why:* the remaining mass is spread evenly.
2. Shannon: H = 0.1·log₂(10) + 0.9·log₂(9,999/0.9) = 0.332 + 0.9·13.440 = 12.43 bits. *Why:* H = Σ p·log₂(1/p), split into the one heavy PIN and 9,999 light ones.
3. Min-entropy: H∞ = −log₂(0.1) = 3.32 bits. *Why:* only the most likely outcome matters.
4. Which predicts one-guess success? Min-entropy: 2⁻³·³² = 0.1, exactly the attacker's chance by guessing '1234'. *Why:* Shannon averages over outcomes the attacker would never try first; matches `H = 12.43, H_min = 3.32 bits`.

## Common confusions
- **Q:** "96-bit nonces mean 2⁹⁶ messages are safe." — **A:** The birthday bound halves the exponent: `risk 1/2 at 2^48.24`.
- **Q:** "Entropy measures guessability." — **A:** Min-entropy does; the PIN has `H = 12.43` but `H_min = 3.32`.
- **Q:** "The union bound is too loose to use." — **A:** For nonces it is tight; it is only loose when q²/N is large (`exact 0.507297, bound 0.693151`).
