# Foundations III: security definitions, games and reductions — explained

## The big picture
"Is AES-GCM secure?" has no answer until you say *against what*. Cryptography answers with **games**: a challenger holds the key, an adversary asks questions (encrypt, decrypt, sign) and wins by doing what the definition forbids — telling which of two messages was encrypted (IND-CPA, IND-CCA) or forging a ciphertext (INT-CTXT) or signature (EUF-CMA). Secure means every efficient adversary's **advantage** is negligible (lesson 24). A **reduction** proves "winning game X would break assumption Y". This lesson turns rules from earlier labs into theorems: why **Authenticated encryption: AES-256-GCM and ChaCha20-Poly1305** forbids nonce reuse, why **Encoding vs hashing vs encryption** says ECB-style determinism leaks, why **Misuse you can test: Wycheproof vectors, timing and nonce reuse** cares about integrity, and what "hard" means for **Post-quantum cryptography in practice: ML-KEM, ML-DSA and hybrids**. `games.py` plays the games with real AES; `theorem_checks.py` checks each theorem.

### Perfect secrecy of the one-time pad, and Shannon's key-length bound
**In plain words.** XOR with a random, never-reused, message-length key reveals *nothing*; no scheme can do that with fewer keys than messages.

**Why it is true (intuition).** Every message maps to a given ciphertext under exactly one equally likely key. Skeleton: (1) Pr[C = c | M = m] = Pr[K = m ⊕ c] = 2^−ℓ for every m; (2) so C is independent of M; (3) Bayes: posterior = prior; (4) for (b): a fixed c decrypts to at most |K| messages; with |K| < |M| some possible message has posterior 0.

**See it in numbers.**
```
3-bit OTP, non-uniform prior: posterior = prior for 64/64 (m, c) pairs
2-bit key on 3-bit messages: 32 of 32 possible (m, c) pairs have posterior != prior; e.g. Pr[M=7 | C=7] = 4/13 vs prior 2/9
pad reused: c1 XOR c2 == m1 XOR m2: True
```
64 = 8 × 8 pairs unchanged; with 4 keys for 8 messages every pair leaks.

**Where it shows up in practice.** AES-GCM is a stream cipher plus a MAC; nonce reuse in lesson 15 is exactly pad reuse.

### No deterministic encryption scheme is IND-CPA secure
**In plain words.** If a message always encrypts the same way, an attacker identifies it by encrypting candidates.

**Why it is true (intuition).** Equality is information. Skeleton: (1) ask the encryption oracle for c* = Enc(m₀); (2) submit (m₀, m₁) and receive the challenge; (3) answer "0" if it equals c*; (4) determinism makes this right every time: advantage 1.

**See it in numbers.**
```
  AES-ECB (deterministic)      advantage 1.000 (1000 games)
  AES-GCM fixed nonce          advantage 1.000 (1000 games)
  Encrypt-and-MAC (tag on m)   advantage 1.000 (1000 games)
  AES-GCM random nonce         advantage 0.000 (1000 games)
```
Encrypt-and-MAC fails too: its deterministic tag on m is an equality test even if the ciphertext is randomised.

**Where it shows up in practice.** Every AEAD call in the labs takes a fresh nonce.

### Encrypt-then-MAC: integrity from MAC unforgeability (reduction sketch)
**In plain words.** MAC the *ciphertext*: forging a valid ciphertext then means forging the MAC; with IND-CPA this gives IND-CCA.

**Why it is true (intuition).** Build a MAC forger B that uses a ciphertext forger A as a subroutine. Skeleton: (1) B picks its own encryption key; (2) answers A's encryption queries using its MAC oracle for tags — A sees exactly the real game; (3) A outputs a new valid (c', t'); (4) t' = MAC(c') for a c' B never queried, so B outputs it as its forgery; (5) hence Adv(A) ≤ Adv(B).

**See it in numbers.**
```
1-byte tags, 2560 trials: A forges EtM 12 times, B (running A) forges the MAC 12 times; equal: True; expected about 2560/256 = 10
  IND-CCA bit-flip adversary vs AES-CTR (no MAC)   advantage 1.000
  IND-CCA bit-flip adversary vs AES-GCM            advantage 0.002
  IND-CCA bit-flip adversary vs Encrypt-then-MAC   advantage 0.015
```
Weak 1-byte tags make forgeries happen; every A success is a B success (12 = 12). Without a MAC a bit flip wins outright.

**Where it shows up in practice.** AES-GCM and ChaCha20-Poly1305 (lesson 4) are built this way; lesson 11's JWT signature plays the MAC's role for tokens.

### Generic discrete log in O(√q) (baby-step giant-step), and what hardness assumptions promise
**In plain words.** Any discrete log in a group of size q falls in about √q steps, so a 256-bit group gives at most 128-bit security.

**Why it is true (intuition).** Write x = i·m + j with m ≈ √q, tabulate all g^j, then step through h·g^(−im) until one hits the table. Skeleton: (1) m = ⌈√q⌉; (2) store m baby steps; (3) take at most m giant steps; (4) a match gives x = im + j; (5) total ≤ 2m operations.

**See it in numbers.**
```
  q ~ 2^24: recovered x: True, group ops 4461 <= 2*ceil(sqrt(q)) = 6688: True
  q ~ 2^28: recovered x: True, group ops 17007 <= 2*ceil(sqrt(q)) = 30720: True
  q = 3329, n = 16: error 0 -> elimination recovers s: True; error in [-2, 2] -> recovers s: False
  toy Regev, m = 32 samples: decryption errors 0/1000 bits with |e| <= 2, 122/1000 with |e| <= 300 (threshold q/4 = 832)
```
4 more bits of q means 4× the work: square-root scaling. In LWE, noise makes the problem hard but must stay small enough to decrypt. (This run and the stored check output both show 122/1000 errors at |e| ≤ 300.)

**Where it shows up in practice.** X25519's ~128-bit security level (lesson 8) and ML-KEM's noise parameters (lesson 18).

## Worked problems
**25-P2 (pad reused; m₁ = 'attack at dawn', c₁ ⊕ c₂ = 051112040d0f00151c454406161e).**
1. c₁ ⊕ c₂ = (m₁ ⊕ k) ⊕ (m₂ ⊕ k) = m₁ ⊕ m₂. *Why:* XOR is associative and k ⊕ k = 0 — the key cancels.
2. m₂ = m₁ ⊕ (c₁ ⊕ c₂). *Why:* XOR both sides with m₁.
3. First byte: 'a' (0x61) ⊕ 0x05 = 0x64 = 'd'. *Why:* byte by byte.
4. All 14 bytes give 'defend the gap'. *Why:* no cipher was broken — only the "one-time" rule.

**25-P6 (textbook RSA signatures, n = 3233, e = 17, d = 2753).**
1. (a) Pick σ = 100; compute m = 100¹⁷ mod 3233 = 1773. *Why:* verification checks σ^e = m, true by construction — a valid pair nobody signed.
2. (b) Obtain σ₆ = 2902 and σ₇ = 2667 from the oracle. *Why:* EUF-CMA allows signing queries.
3. σ₄₂ = 2902·2667 mod 3233 = 3065. *Why:* (6·7)^d = 6^d·7^d — RSA is multiplicative.
4. Verify: 3065¹⁷ mod 3233 = 42. *Why:* the forgery is on a message never queried, so textbook RSA is not EUF-CMA; the check prints `pyca RSA-PSS 2048: product of two signatures accepted: False` because PSS hashes and randomises first.

## Common confusions
- **Q:** "If no one can recover the plaintext, encryption is secure." — **A:** AES-ECB leaks equality: `advantage 1.000`.
- **Q:** "MAC-and-encrypt is as good as encrypt-then-MAC." — **A:** `Encrypt-and-MAC (tag on m) advantage 1.000`.
- **Q:** "A 256-bit group means 256-bit security." — **A:** BSGS needs ~2·√q operations: ~128 bits.
