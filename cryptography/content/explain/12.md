# Envelope encryption and key rotation — explained

## The intuition
If every record were encrypted with one master key, rotating it would mean re-encrypting every stored byte. Envelope encryption splits the job: each record gets a fresh **data encryption key (DEK)** used with AES-256-GCM, and the DEK is **wrapped** by a **key encryption key (KEK)** from a keyring (in production, a KMS or OpenBao). The record stores ciphertext, wrapped DEK and the KEK version that wrapped it (`kid`).

Rotation becomes cheap: add a KEK version, make it primary, and **rewrap** old records — unwrap each 32-byte DEK with the old version, wrap it with the new. The data ciphertext never changes. The dangerous step is deleting the old version: any record still naming it is unreadable forever. This lab injects exactly that.

**Analogy:** a block of flats with one lockbox per flat. Each flat key (DEK) sits in a lockbox opened by a master key (KEK). Changing the master means re-locking the lockboxes, not changing every door lock. Where the analogy breaks: melt the old master and every lockbox not yet moved is sealed for good — there is no locksmith for AES-GCM.

```
seal(record):  DEK = random 32 B ──AESGCM(DEK).encrypt(n, data, aad=ctx)──▶ ct
               DEK ──AESGCM(KEK[primary]).encrypt(n2, DEK, aad=kid)──▶ wdek
               store {kid, ctx, n, ct, wdek}
rotate():      KEK[v+1] = random, primary = v+1
rewrap_job():  for rec with kid != primary: unwrap(KEK[old]) → wrap(KEK[new]); ct untouched
retire(v):     delete KEK[v]   ← safe only if count_by_kid(store)[v] == 0
```

**The one thing to remember:** never delete a key version while `records_by_kid` still counts records under it.

## Walkthrough: what actually happens when you run it
1. **You run** `python envelope.py`. **What happens inside:** `seal()` makes six records; `wrap()` passes `kid` as AAD, tying header to wrapped DEK. **What you see:** `sealed 6 records with orders-kek:v1 | header: {'kid': 'orders-kek:v1', 'ctx': 'order-1'}`.
2. **Rotate and rewrap.** `rotate()` adds v2 (v1 stays in the ring); `rewrap_job()` moves each record, logging one JSON line. **What you see:**
   ```
   rotate -> orders-kek:v2 | old records still: 6/6 decrypt
   {"event": "rewrap", "id": "order-1", "from": "orders-kek:v1", "to": "orders-kek:v2"}
   …
   {"metric": "records_by_kid", "orders-kek:v2": 6}
   data ciphertext unchanged by rewrap: True
   retire v1 after a full rewrap: 6/6 decrypt
   ```
   **What it means:** the metric is the go/no-go signal: v1 at 0 records may retire.
3. **You run** `python try_it.py`. **What you see:**
   ```
   1) relabelled header: InvalidTag - the kid is bound to the wrapped DEK as AAD
   2) wrapped DEK = 60 B (12 nonce + 32 key + 16 tag); rewrapping 1000 x 4096 B records re-encrypts 32,000 key bytes instead of 4,096,000 data bytes
   ```
   **What it means:** a record cannot be pointed at another KEK; rotation cost scales with record count, not size (128× less here).

### Failure lab: crash mid-rewrap, then retire anyway
- **Inject:** the run continues with `rotate -> orders-kek:v3`; `rewrap_job(crash_after=N)` (N from `random.Random(12)`) dies; naive `retire()` deletes v2.
- **Symptom:**
  ```
  job: rewrap job crashed after 1 records | counts: {'orders-kek:v2': 5, 'orders-kek:v3': 1}
  after retire v2: 1/6 decrypt; LOST ['order-2', 'order-3', 'order-4', 'order-5', 'order-6'] ({'no KEK for orders-kek:v2'})
  ```
- **Diagnose:** the counts line already said five records still needed v2. `unwrap()` raises `UnknownKey` because the `kid` in their header no longer exists. Nothing is corrupted — the key is simply gone.
- **Fix:** `solution_retire.py` makes `retire()` call `count_by_kid` and raise `KeyInUse` if any record (or the primary) uses that version; `rewrap_then_retire` resumes the idempotent job first. **You run** `python solution_retire.py`. **What you see:**
  ```
  injected: rewrap job crashed after 2 records
  retire refused: orders-kek:v1 still wraps 2 record(s): finish the rewrap job first
  resumed job moved 2 record(s); 4/4 decrypt
  ```
- **Proof:** `BUILD_IMPL=envelope python -m unittest -v test_build_task` fails before the fix:
  ```
  FAIL: test_primary_cannot_be_retired (…)
  FAIL: test_retire_refused_while_records_use_the_version (…)
  Ran 3 tests in 0.043s
  FAILED (failures=2)
  ```
  Against the reference solution: `Ran 3 tests in 0.002s`, `OK`. The full suite: `Ran 11 tests in 0.003s`, `OK (skipped=1)` — the skip is the OpenBao test.
4. **OpenBao equivalent.** Expected (not run here): `openbao_transit.py` against a dev server shows `vault:v1:` ciphertext, `vault:v2:` after rotate + rewrap, and with `min_decryption_version=2` the old ciphertext refused (HTTP 4xx) — OpenBao archives versions instead of deleting them.

## Common confusions
- **Q:** "Rotation re-encrypts the data." — **A:** `data ciphertext unchanged by rewrap: True`; only the 60-byte wrapped DEK changes.
- **Q:** "After rotating, old records break until rewrapped." — **A:** `old records still: 6/6 decrypt` — old versions stay usable until retired.
- **Q:** "The crash corrupted the five records." — **A:** They are intact; the `no KEK for orders-kek:v2` error says the key was deleted, not that the data changed.
