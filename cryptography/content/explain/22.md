# Capstone: an encrypted document service — explained

## The intuition
The capstone wires the topic into one service: lesson 17's envelope with a fresh DEK; a separate KMS with lesson 12's versioned KEKs, reached only over mutual TLS (9–10); signatures from non-exportable token handles (19); a hash-chained, signed audit log; post-quantum shares (18); fitness functions (16, 17, 19, 21). Nothing is new — the lesson is how the pieces depend on each other.

**Analogy:** a law firm's records room: sealed folders (envelopes), a key office in another building that only staff with badges may call (KMS + mTLS), a signed visitor book (audit log), and courier pouches for clients (HPKE shares). Where the analogy breaks: the visitor book here proves its own integrity — edit or remove one line and verification points at that line.

```
user ─▶ doc_service.put/get/share ──mTLS (client cert CN = identity)──▶ kms.py wrap/unwrap/rewrap/rotate/retire
            │ envelope v2 (DEK, header=AAD)        │ token C_Sign (doc-signing, audit-log handles)
            ▼                                       ▼
        store {env, kek, wdek}             audit log: entry{seq, prev=SHA-256(prev)} + signature
            share ─HPKE ML-KEM-768+X25519─▶ recipient          audit.py rules decide ─▶ agent explains
```

**The one thing to remember:** each guarantee is owned by one component and proven by one milestone test — the scorecard is only as strong as its weakest milestone.

## Walkthrough: what actually happens when you run it
1. **You run** `python run_capstone.py`. **What happens inside:** a seeded scenario (SEED=22, fake clock) starts the KMS, stores six documents and prints one JSON line per milestone. **What you see (M1):**
   ```
   {"milestone": "M1 envelope + versioned KEK + rotation", "crash_after": 3, "records_by_kid_after_crash": {"docs-kek:v1": 3, "docs-kek:v2": 3}, "retire_refused_while_in_use": true, "resumed": 3, "retired": "docs-kek:v1", "readable": "6/6", "pass": true}
   ```
   **What it means:** lesson 12's failure lab, fixed: refuse, resume, then retire.
2. **M2 and M3.** **What you see:**
   ```
   {"milestone": "M2 mTLS between doc service and KMS", "doc_service_client": "ok", "no client cert": "refused (SSLEOFError)", "cert from another CA": "refused (SSLEOFError)", "pass": true}
   {"milestone": "M3 signed, hash-chained audit log", "entries": 50, "clean_log_anomalies": ["access_after_revoke", "unwrap_burst"], "tampered_at_seq": 10, "tampered_log_findings": ["access_after_revoke", "bad_signature", "chain_break", "seq_gap", "unwrap_burst"], "pass": true}
   ```
   **Differs from the README:** "no client cert" gave `SSLEOFError` here, `SSLError` there; both are an aborted handshake. **What it means:** editing entry 10 breaks its signature and the next `prev`; truncation leaves a gap. The two clean-log anomalies are seeded *behaviour* findings.
3. **M4–M6.** **What you see:**
   ```
   {"milestone": "M4 PQ-hybrid sharing (HPKE)", "kem": "HPKE-XWING", "pq": true, "recipient_opened": true, "wrapped_dek_bytes": 1168, "new_share_with_HPKE-X25519": "refused", "pass": true}
   {"milestone": "M5 fitness functions + threat model + secret handling", "agility_lint_violations": 0, "key_export_calls": 0, "token_keys_exportable": 0, "threat_model_problems": 0, "secrets_in_logs": 0, "pass": true}
   {"milestone": "M6 agent explains, code decides", "anomalies": 7, "accepted": 7, "rejected": ["A99"], "action": "page on-call (integrity)", "pass": true}
   {"scorecard": "capstone", "passed": 6, "total": 6, "decided_by": "code"}
   ```
   **What it means:** 1168 bytes matches lesson 18's HPKE; `python agent_explain.py` shows M6 in miniature: `A1` ACCEPTED, `A99` `REJECTED (no such anomaly)`.
4. **Tests:** `python -m unittest` → `Ran 19 tests in 30.858s`, `OK` (README: 37.749s). Expected (not run here): with Ollama, `run_capstone.py --real` changes only explanation wording; verdicts and actions still come from code.

## The decisions
- **ADR-0022-1 (KMS behind mTLS):** a separate KMS holding KEKs, identity from the client certificate CN, retirement decided by `records_by_kid`. Evidence: M1's `retire_refused_while_in_use: true` and M2's two refusals.
- **ADR-0022-2 (reuse lesson 17's envelope):** policy phase `classic`, because the soft token signs Ed25519 only — a deliberate gap until ML-DSA is available in the token. Evidence: `agility_lint_violations: 0`.
- **ADR-0022-3 (signed audit chain):** hash chain plus per-entry token signatures, rules as code, agent explains only. Evidence: M3's three integrity findings and M6's rejected `A99`.
- **ADR-0022-4 (PQ-hybrid sharing):** HPKE-XWING active, HPKE-X25519 deprecated. Evidence: `pq: true`, `refused`.

**How the fitness functions keep it true:** M5 reruns lessons 17, 19, 21 and 16's checks over the capstone folder with threshold 0 each, and `test_run_capstone.py` requires 6/6 — a refactor that hard-codes AESGCM or logs a token fails CI.

## Common confusions
- **Q:** "mTLS encrypts the documents." — **A:** It authenticates the doc service to the KMS; envelopes protect documents.
- **Q:** "Two anomalies on the clean log means the chain is broken." — **A:** `clean_log_anomalies` are behaviour rules; integrity findings appear only on the tampered copy.
- **Q:** "The agent decides whom to page." — **A:** `"decided_by": "code"`; the action comes from rule names.
