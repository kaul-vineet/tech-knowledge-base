# End-to-end encryption for groups: pairwise, sender keys and MLS-style epochs — explained

## The intuition
Two-party E2EE is lesson 8: one key exchange. Groups are harder because membership changes: a leaver must not read later messages, and after a stolen phone's owner updates, the thief must be locked out (**post-compromise security**). The relay must not read anything.

Three designs. **Pairwise**: encrypt each message to every member — 255 encryptions per message at n=256. **Sender keys**: one symmetric key per sender shared with all — one encryption per message, but a removal makes every remaining sender re-send to every other: quadratic. **MLS-style trees** (RFC 9420): members are leaves of a binary tree, each inner node's key pair is known only to leaves below it, and the root yields the **epoch secret**. A **Commit** refreshes one leaf-to-root path, encrypting each new secret to one node per level — about log₂(n).

**Analogy:** a master key cut from floor keys; to lock out a tenant, re-cut the keys on their floor's path and hand copies to whoever shares each floor. Where the analogy breaks: you must also discard every old floor key the tenant knew — miss one and they open the new master (the injected bug).

```
             root (epoch secret)                commit(committer, remove=dave):
            /                  \                  [fix] blank dave's leaf AND direct path (parents → root)
        n(a..d)              n(e..h)              fresh path secrets from committer's leaf up to root
        /     \              /     \              each encrypted (HPKE) to resolution(copath node)
    n(a,b)  n(c,d)       n(e,f)  n(g,h)           epoch += 1; app key = HKDF(epoch_secret, "app")
    a   b   c   d        e   f   g   h            BUG: n(c,d), n(a..d) keep keys dave knew → he decrypts
```

**The one thing to remember:** a removal is only real if every key the removed member knew is blanked before the new secrets are encrypted.

## Walkthrough: what actually happens when you run it
1. **You run** `python group_keys.py`. **What happens inside:** `Group(names)` builds an 8-leaf tree of X25519 node keys; `commit` HPKE-encrypts fresh path secrets; `_process` lets each member decrypt one and derive the rest to the root. **What you see:**
   ```
   1) group of 8 | epoch 0 | alice -> all: kick-off at 10
   2) carol updates her path: HPKE encryptions: 3 | epoch 1 | all in sync: True
   ```
   **What it means:** 3 = log₂(8), one per level of carol's copath.
2. **The fault.** **What you see:**
   ```
   --- fault: frank removes dave; the removed leaf's parent keys are not blanked
   commit HPKE encryptions: 3 | epoch 2 | can read post-removal message: {'alice': True, … 'dave': True, … 'heidi': True}
   ```
   **What happens inside:** `_remove` blanked only dave's leaf; frank encrypts to n(a..d), whose key dave still holds.
3. **You run** `python try_it.py`. **What you see:**
   ```
   1) attacker with carol's stolen state reads: before update True, after carol's update False
   2) unfixed remove leaks in 48 of 56 pairs; safe only when the committer is the removed member's sibling: [('alice', 'bob'), ('bob', 'alice'), ('carol', 'dave'), ('dave', 'carol')] ...
   ```
   **What it means:** line 1 is post-compromise security. Line 2: the bug is common — only a sibling's commit replaces every key the removed member knew.

## The decision
**Options measured** (`python compare_designs.py`; n=256 pairwise/sender-key rows are computed counts, `real_crypto: false`):
```
{"design": "pairwise", "n": 256, "encryptions_per_message": 255, "encryptions_per_removal": 0, …}
{"design": "sender keys", "n": 256, "encryptions_per_message": 1, "encryptions_per_removal": 64770, "bytes_per_removal": 5181600, …}
{"design": "MLS-style tree (toy)", "n": 256, "encryptions_per_message": 1, "encryptions_per_removal": 14, "bytes_per_removal": 1120, "removed_can_read": false, "commit_and_process_ms": 86.0, "real_crypto": true}
```
- **A, pairwise:** free removal, but n−1 encryptions per message.
- **B, sender keys:** removal costs 42, 3,906, 64,770 at n = 8, 64, 256 — (n−1)(n−2), quadratic.
- **C, tree:** 4, 10, 14 — within 2·log₂(256) = 16 — and `removed_can_read: false`.

ADR-0020 chose **C** (in production via a reviewed RFC 9420 library such as OpenMLS) plus regular empty Commits so PCS actually arrives. Timings differ from the README (n=64: 17.3 vs 71.8 ms); counts and bytes match.

### Failure lab: removal that does not exclude
- **Inject:** frank removes dave (both from `random.Random(20)`); `_remove` blanks only the leaf.
- **Symptom:** `'dave': True` in step 2.
- **Diagnose:** dave knew his leaf, n(c,d), n(a..d) and the root; the commit encrypted to n(a..d).
- **Fix:** blank the leaf and every node of `tree_math.direct_path(leaf)`; blanks make `resolution()` descend to children held only by members who stay. **You run** `python solution_remove.py`. **What you see:**
  ```
  frank removes dave: commit HPKE encryptions 4 | can read post-removal message: {'alice': True, 'bob': True, 'carol': True, 'dave': False, 'erin': True, 'frank': True, 'grace': True, 'heidi': True}
  ```
  4 vs 3 encryptions: blanked n(a..d) resolves to n(a,b) and carol's leaf.
- **Proof:** `BUILD_TARGET=mine python -m unittest -v test_build_task` before: `FAIL: test_every_committer_removed_pair`, `FAIL: test_seeded_removal_from_the_lab`, `FAILED (failures=2)`; the solution: `Ran 2 tests in 0.285s`, `OK`.

**Fitness function.** `test_fitness_removal.py` plays a seeded sequence of removals and updates in a 16-member group and requires 0 leaks and at most 2·log₂(16) = 8 HPKE encryptions per commit. Full suite: `Ran 9 tests in 0.302s`, `OK`. Expected (not run here): OpenMLS `cargo test -p openmls remove` passes; a removed member's group becomes inactive after the Commit merges.

## Common confusions
- **Q:** "Removing someone from the member list removes them." — **A:** `'dave': True`: he still derives the key.
- **Q:** "Sender keys are fine because messages are cheap." — **A:** They are (1 encryption), but removal at 256 costs 64,770.
- **Q:** "Post-compromise security is automatic." — **A:** Only after the victim commits: try_it 1 reads `before update True`.
