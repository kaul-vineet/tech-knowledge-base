# TLS on localhost — explained

## The intuition
Lessons 7–9 gave you the parts: key exchange, signatures, certificates. TLS assembles them on a live socket: the client names the host it wants (SNI), the server sends its certificate chain, both run an ephemeral key exchange, the server signs the handshake to prove it holds the private key, and every later record is sealed with an AEAD key derived from the shared secret.

What matters is where the *checks* happen: the client decides. `ssl.create_default_context(cafile=...)` turns on two: the chain must end at a CA you trust (`CERT_REQUIRED`), and `server_hostname` must appear in the certificate's SAN (`check_hostname`). If either fails, the handshake aborts before any application byte is sent.

**Analogy:** a courier at reception shows a badge (certificate) from a company you know (CA) with the expected name (SAN); you then agree a sealed-bag code (session keys) for this delivery only. Where the analogy breaks: the TLS badge check is automatic and binary — no receptionist judgement, and `verify=False` lets anyone in.

```
client: create_default_context(cafile=ca.pem)        server: SSLContext(PROTOCOL_TLS_SERVER)
        wrap_socket(server_hostname="localhost")              load_cert_chain(server.pem, server-key.pem)
   ClientHello(SNI, key share) ───────────────────────────▶
   ◀──────────── ServerHello(key share) + Certificate + CertificateVerify + Finished
   check chain → ca.pem?  check SAN ∋ "localhost"?  ──fail──▶ SSLCertVerificationError (no app data)
   Finished ─────────────────────────────────────────────▶  AEAD records: b"hello over TLS\n"
```

**The one thing to remember:** TLS is only as safe as the client's two checks — trusted chain and matching name — so never switch either off.

## Walkthrough: what actually happens when you run it
1. **You run** `python tls_localhost.py`. **What happens inside:** `make_pki()` reuses lesson 9 to write `ca.pem`, `server.pem`, `server-key.pem` to a temp folder; `server_context()` loads them with `minimum_version = TLSv1_2`. **What you see:** `Python ssl uses OpenSSL 3.3.7 7 Apr 2026`.
2. **Trusted connection.** `connect(port, ca.pem, "localhost")` completes the handshake and reads the echo. **What you see:**
   ```
   trusted CA       TLSv1.3 TLS_AES_256_GCM_SHA384 (256-bit) -> b'hello over TLS\n'
   ```
   **What it means:** TLS 1.3 was negotiated; records are protected with AES-256-GCM (lesson 4) and the key schedule uses SHA-384 (HKDF, lesson 8). A TLS 1.3 suite name no longer mentions the key exchange or signature — those are negotiated separately.
3. **Wrong name and wrong CA.** **What you see:**
   ```
   wrong hostname   REFUSED verify_code=62: Hostname mismatch, certificate is not valid for 'example.com'.
   untrusted CA     REFUSED verify_code=20: unable to get local issuer certificate
   ```
   **What happens inside:** code 62: chain fine, but `example.com` is not in the SAN; code 20: the client got another CA file. Both raise `ssl.SSLCertVerificationError` inside `wrap_socket`. **What would look wrong:** either line saying `TLSv1.3 …`.
4. **You run** `python try_it.py`. **What you see:**
   ```
   1) client max TLS 1.2 -> TLSv1.2 ECDHE-ECDSA-AES256-GCM-SHA384
   2) server_hostname='127.0.0.1' -> TLSv1.3 b'hello over TLS\n'
   ```
   **What it means:** a TLS 1.2 suite names everything: ECDHE, ECDSA (lesson 9's P-256 key), AES-256-GCM, SHA-384. The IP works because `127.0.0.1` is an IP SAN entry.
5. **You run** `python -m unittest -v`. **What you see:** `test_trusted_and_untrusted … skipped 'openssl CLI not installed'`, then `Ran 7 tests in 1.001s` and `OK (skipped=1)`. (README: 0.120s; slow storage here). Expected (not run here): with the OpenSSL CLI installed, `s_client -brief` reports `Verification: OK` for the lab CA.

## Common confusions
- **Q:** "The server checks the client's certificate too." — **A:** Only with mutual TLS (the build task: `CERT_REQUIRED` on the server context). In step 2 only the client verified.
- **Q:** "TLS_AES_256_GCM_SHA384 means SHA-384 signs the certificate." — **A:** In TLS 1.3 the hash is for the key schedule; the certificate signature is ECDSA, visible in step 4's TLS 1.2 name.
- **Q:** "Connecting by IP skips the name check." — **A:** It is still checked — against IP SAN entries; try_it 2 works only because `127.0.0.1` is listed.
