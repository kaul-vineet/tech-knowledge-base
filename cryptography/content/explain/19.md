# Keys in hardware-style storage: PKCS#11, non-exportable keys and key ceremonies — explained

## The intuition
In lesson 14 the release-signing key was a PEM file: whoever reads it once can sign releases forever, from anywhere. A **token** (smart card, HSM, here a software stand-in) changes the deal: the app gets a **handle** — an integer meaning "the key in slot 1" — and asks the token to sign. The private bytes never leave. An attacker on the host can still request signatures *while* there, but after clean-up has nothing to take away.

PKCS#11 is the standard API for tokens; its security lives in key **attributes**: `CKA_SENSITIVE` (value unreadable), `CKA_EXTRACTABLE` (cannot be wrapped out), and `CKA_ALWAYS_SENSITIVE` / `CKA_NEVER_EXTRACTABLE`, proving the key was *never* exposed. The lab's bug is classic: the app trusted the token's defaults, which allowed export. A **key ceremony** is a witnessed, recorded key creation, so everyone can trust which public key is real.

**Analogy:** a safe-deposit box versus cash in a desk drawer: a thief in your office gets nothing to keep. Where the analogy breaks: a thief *with your PIN* can still visit the bank — a token limits theft to misuse during the compromise.

```
app ─login(USER, PIN)──▶ Session ─generate_key_pair(CKM_EDDSA, label, template)──▶ handle 1
app ─sign(handle 1, CKM_EDDSA, data)──▶ token signs inside ──▶ 64-byte signature   (+ audit event)
attacker ─get_attribute_value(1, CKA_VALUE)──▶ BUG: bytes (defaults SENSITIVE=False, EXTRACTABLE=True)
                                              FIX: CKR_ATTRIBUTE_SENSITIVE (token enforces, template can't opt out)
```

**The one thing to remember:** the token, not the app's template, must make private keys non-exportable — provably, for their whole life.

## Walkthrough: what actually happens when you run it
1. **You run** `python soft_token.py`. **What happens inside:** `generate_key_pair` stores an Ed25519 key and returns handle 1; `sign()` signs inside and logs an audit event. **What you see:**
   ```
   1) wrong PIN: CKR_PIN_INCORRECT
   2) signed via handle 1 | sig bytes: 64 | public key DER bytes: 44
   ```
   **What it means:** the app holds an integer and a 44-byte public key (DER), never the private key.
2. **The fault.** **What you see:**
   ```
   --- fault: a compromised app asks the token for the private key
   attributes: {'CKA_SENSITIVE': False, 'CKA_VALUE': 48, 'CKA_EXTRACTABLE': True}
   after logout the stolen key still signs offline: True | audit events: 6
   ```
   **What happens inside:** with no template the defaults allow export, so `get_attribute_value(handle, "CKA_VALUE")` returns 48 bytes (PKCS#8 DER). Those bytes sign after logout, invisible to the token's audit log.
3. **You run** `python ceremony.py`. **What you see:**
   ```
   {"step": 3, "do": "export PUBLIC key and read fingerprint aloud", "sha256": "488b4454…94c2a1", "seen_by": ["witness-b", "witness-c"]}
   transcript verifies: True
   edited transcript verifies: False
   custodian as own witness: need 2 distinct witnesses who are not the custodian
   ```
   (Fingerprint random per run.) **What it means:** the new key signs the transcript, so edits break it; separation of duties is enforced in code.
4. **You run** `python try_it.py`. **What you see:**
   ```
   1) logins: ['CKR_PIN_INCORRECT', 'CKR_PIN_INCORRECT', 'CKR_PIN_INCORRECT', 'CKR_PIN_LOCKED']
   2) sign via handle 39.7 us vs raw key 33.9 us (overhead 1.17x, plus one audit event per call: 502 events)
   ```
   **What it means:** lockout after three wrong PINs; the handle costs ~6 µs per signature.

## The decision
**Options measured** (`python key_storage_options.py`):
```
{"option": "file key", "app_can_read_key": true, "sign_us": 34.4, "attacker_signs_after_cleanup": true}
{"option": "KMS-style remote signing (HTTP, 127.0.0.1)", "app_can_read_key": false, "sign_us": 587.5, "attacker_signs_after_cleanup": false}
{"option": "token handle (PKCS#11-shaped, non-exportable)", "app_can_read_key": false, "sign_us": 40.3, "attacker_signs_after_cleanup": false}
```
- **A, file:** fastest; the only `attacker_signs_after_cleanup: true`.
- **B, remote KMS:** safe after clean-up. **Differs from the docs:** 587.5 µs here versus ≈5,001.5 µs in the README/ADR (new TCP connection per call). On this run B met the 1 ms budget, so the ADR's latency argument against B is weaker than written — though B is still 15× the token.
- **C, token handle:** safe after clean-up, 40.3 µs, audited.

ADR-0019 chose **C** for the build host: token-enforced attributes, PIN lockout, 2-witness ceremonies, a KMS in front when many services sign. Accepted cost: no software backup.

### Failure lab: trusting the token's defaults
- **Inject:** keys created without a template; the attacker reads `CKA_VALUE` (attribute order from `random.Random(19)`).
- **Symptom:** step 2's `CKA_VALUE: 48` and `still signs offline: True`.
- **Diagnose:** the attributes say it (`CKA_SENSITIVE: False`, `CKA_EXTRACTABLE: True`); the audit events look normal.
- **Fix:** a `Session` subclass merges an `ENFORCED` dict *last* in `generate_key_pair` and rejects contrary templates. **You run** `python solution_nonexportable.py`. **What you see:**
  ```
  attributes: {'CKA_SENSITIVE': True, 'CKA_EXTRACTABLE': False, 'CKA_ALWAYS_SENSITIVE': True, 'CKA_NEVER_EXTRACTABLE': True}
  read CKA_VALUE: CKR_ATTRIBUTE_SENSITIVE
  wrap (export) the key: CKR_KEY_UNEXTRACTABLE
  flip CKA_EXTRACTABLE back on: CKR_ATTRIBUTE_READ_ONLY
  template asking extractable: CKR_TEMPLATE_INCONSISTENT
  signing via handle still works: 64 byte signature
  ```
- **Proof:** `BUILD_TARGET=mine python -m unittest -v test_build_task` fails all four tests before (`FAILED (failures=4)`); the solution passes (`Ran 4 tests in 0.002s`, `OK`).

**Fitness function.** `test_fitness_no_key_export.py` fails on any `private_bytes*`/`wrap_key` call outside the token module and on any inventory key without `ALWAYS_SENSITIVE` and `NEVER_EXTRACTABLE`. Full suite: `Ran 14 tests in 0.034s`, `OK (skipped=1)` (`PKCS11_MODULE not set`). Expected (not run here): with SoftHSM2 2.7.0 and python-pkcs11, `pkcs11_softhsm.py` generates a non-exportable P-256 key, signs via the handle, and fails to read the private value.

## Common confusions
- **Q:** "With an HSM, a host compromise is harmless." — **A:** The attacker signs *during* it; only `attacker_signs_after_cleanup` changes.
- **Q:** "Setting `CKA_EXTRACTABLE=False` in my template is enough." — **A:** Then one forgotten template leaks a key; the fix has the token enforce it and refuse `CKR_TEMPLATE_INCONSISTENT`.
- **Q:** "The audit log would catch the theft." — **A:** `audit events: 6` looked normal; offline signing leaves no event.
