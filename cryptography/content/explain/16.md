# Secrets handling in applications — explained

## The intuition
An API key is just a string, and strings go everywhere: `print()`, exception messages, debug logs, a dumped config dict, a base64 Kubernetes manifest. Encryption does not help once your own process writes the secret to a log shipped to five systems. Most real leaks are this boring.

The lab gives three layers. **Loading**: read from a mounted file (`NAME_FILE`), fall back to an env var, fail closed otherwise — never a default in code. **Holding**: a `Secret` type whose `repr` is `Secret('***')`, so you must call `reveal()` on purpose. **Emitting**: a logging filter masking sensitive keys, known values and token patterns, plus a deterministic `scan_log` that tests (and any AI assistant) are checked against.

**Analogy:** shop cash comes from the safe (file), stays in a closed till (`Secret`), and receipts never print the till (log filter). Where the analogy breaks: a banknote exists once, but Python copies strings silently — `wipe()` clears one buffer only.

```
ORDERS_API_KEY_FILE ──load_secret()──▶ Secret(bytearray)   repr → Secret('***')
handle_request(log, key, order, debug)
   headers = {"Authorization": "Bearer " + key.reveal()}
   debug? ─▶ log.debug(extra={"ctx": {headers}})   ← the leak (seeded by random.Random(16))
logging handler ─[fix: RedactFilter]─▶ JsonFormatter ─▶ one JSON line
scan_log(text, known=[key]) ─▶ [(line, BEARER|KNOWN_SECRET|SENSITIVE_KEY, detail)]  must be []
```

**The one thing to remember:** decide by a deterministic scanner over what was actually emitted, not by intentions in code review.

## Walkthrough: what actually happens when you run it
1. **You run** `python secrets_app.py`. **What happens inside:** a 40-character demo key (`sk_demo_` + 32 hex) is written to a file and loaded via `ORDERS_API_KEY_FILE`; six requests run, one taking the debug path. **What you see:**
   ```
   loaded from file: Secret('***') | length 40
   6 JSON log lines, e.g. {"headers": {"Accept": "application/json", "Authorization": …}, "level": "DEBUG", "msg": "upstream request", "order": 1}
   scanner findings:
     line 1: BEARER (pattern)
     line 1: KNOWN_SECRET (value of a configured secret)
     line 1: SENSITIVE_KEY (Authorization)
   ```
   (The `Authorization` value, the bearer token in clear, is trimmed here.) **What it means:** three detectors agree on line 1. The wrapper worked, but `reveal()` built a header and the header was logged.
2. **You run** `python try_it.py`. **What you see:**
   ```
   1) Secret    : {'service': 'orders', 'api_key': Secret('***')}
   2) scan with known=[key]:           []
   2) scan with known=[key, b64(key)]: [(1, 'KNOWN_SECRET', 'value of a configured secret')]
   ```
   The first line (the plain `str`) printed the whole key. **What it means:** base64 hides a secret from an exact-value scanner but not from anyone with CyberChef; scanners must know the encodings you use.

### Failure lab: the debug header dump
- **Inject:** `handle_request()` logs outgoing headers when `debug` is true; `random.Random(16)` picks which request.
- **Symptom:** the three findings on line 1 above.
- **Diagnose:** the value sits in `record.ctx["headers"]`, a nested dict from `extra=`; a filter on `record.msg` alone misses it.
- **Fix:** a `logging.Filter` on the *handler* that merges args (`record.getMessage()`, then `record.args = None`), deep-copies `record.ctx` and masks sensitive keys, known values and patterns. **You run** `python solution_redact.py`. **What you see:**
  ```
  {"headers": {"Accept": "application/json", "Authorization": "[REDACTED]"}, "level": "DEBUG", "msg": "upstream request", "order": 1}
  scanner findings after the fix: []
  ```
- **Proof:** `BUILD_IMPL=secrets_app python -m unittest -v test_build_task` before the fix: `FAIL: test_message_args_and_nested_fields`, `FAIL: test_seeded_request_mix_leaves_clean_logs`, `Ran 2 tests in 0.032s`, `FAILED (failures=2)`. Against the solution: `Ran 2 tests in 0.002s`, `OK`. Full suite: `Ran 11 tests in 1.064s`, `OK`.
3. **You run** `python agent_assist.py`. **What happens inside:** `review_me.log` is redacted, passed through a gate that refuses to send if any secret pattern remains, then the fake model labels lines; each label is checked against `scan_log`. **What you see:**
   ```
   line 2: MISSED by agent (scanner found it)
   line 3: CONFIRMED - agent explains: a credential appears to be logged here; remove it or log a
   line 4: REJECTED (scanner: no leak)
   line 6: MISSED by agent (scanner found it)
   LEAKS = [2, 3, 6] (decided by scan_log); the agent only proposes and explains.
   ```
   **What it means:** the keyword-matching fake model flagged `token_ttl_seconds: 3600` and missed two real leaks; the scanner decides. Expected (not run here): `gitleaks dir review_me.log -v` reports findings by rule and entropy; note which of lines 2, 3, 6 it catches.

## Common confusions
- **Q:** "Environment variables are the secure way to pass secrets." — **A:** Child processes inherit them; the lab prefers `NAME_FILE`.
- **Q:** "`Secret.wipe()` erases the key from memory." — **A:** It overwrites one `bytearray`; `reveal()` already created `str` copies Python will not wipe.
- **Q:** "If redaction works on the message, logs are clean." — **A:** The leak was in `extra={"ctx": …}`; `test_message_args_and_nested_fields` exists for that reason.
