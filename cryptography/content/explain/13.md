# Certificate lifecycle: short-lived certs, renewal and revocation — explained

## The intuition
Lesson 9 issued a certificate; this lesson is about time. Every certificate has a hard end (`notAfter`); once the clock passes it, every client refuses the handshake. Most certificate outages are not attacks but a renewal job that silently stopped. The answer is **short-lived** certificates renewed **automatically**, so renewal is a path exercised every few days, not a yearly ritual.

Revocation is the other half: if a key leaks, the CA publishes a signed **CRL** naming the serial. A CRL has its own freshness (`nextUpdate`); a stale one may miss recent revocations. Short lifetimes limit how long a leaked key stays useful. And because clocks disagree, CAs **backdate** `notBefore` a little.

**Analogy:** a gym card with an expiry date plus a "banned members" list at the desk. Where the analogy breaks: a clerk lets you in a day late; a TLS client refuses at hour 160 exactly, and an outdated banned list counts as unknown, not "probably fine".

```
simulate(Server, days=8): each simulated hour
   srv.tick(now)            ← bug: pass (never renews) | fix: renew at 60–72 % of lifetime
   metric {"cert_expires_in_hours": notAfter - now}
   handshake_ok(cert, ca, now) → local_ca.verify → ok | FAIL
check_revocation: CRL signature? → now ≤ nextUpdate? → serial listed?
```

**The one thing to remember:** an expiry you do not measure and renew automatically will eventually become an outage.

## Walkthrough: what actually happens when you run it
1. **You run** `python cert_lifecycle.py`. **What happens inside:** `simulate(Server, days=8)` issues one lab-9 certificate with `LIFETIME = 160 h`, backdated 1 h, and walks a simulated clock, logging a metric every 24 h. **What you see:**
   ```
   {"hour": 0, "metric": "cert_expires_in_hours", "value": 159.0, "handshake": "ok", "renewals": 0}
   …
   {"hour": 144, "metric": "cert_expires_in_hours", "value": 15.0, "handshake": "ok", "renewals": 0}
   {"hour": 160, "metric": "cert_expires_in_hours", "value": -1.0, "handshake": "FAIL", "renewals": 0}
   ```
   **What it means:** 159 at hour 0 because one hour was spent in the past (backdating). `renewals` stays 0: the warning was visible for six days.
2. **Revocation and skew.** **What you see:**
   ```
   CRL check now:         revoked (key_compromise)
   CRL check other cert:  good
   CRL check 25 h later:  stale CRL
   skew 5 min, notBefore = issue time: False
   skew 5 min, notBefore backdated 1 h: True
   ```
   **What happens inside:** `make_crl` sets `next_update = now + 24 h`; `check_revocation` checks signature, then freshness, then serial. **What would look wrong:** a stale CRL reported as `good`.
3. **You run** `python try_it.py`. **What you see:**
   ```
   1) distinct renewal hours for 100 servers: no jitter 1, jitter 20
   2) client clock 59 min slow: handshake ok
   2) client clock 61 min slow: handshake FAIL (not yet valid)
   ```
   **What it means:** without jitter 100 servers hit the CA in one hour; 1 h of backdating tolerates up to 1 h of skew.

### Failure lab: the server that never renews
- **Inject:** `Server.tick()` is `pass`; the build-task test also makes the CA unreachable for hours 90–124.
- **Symptom:** `static server: first failed handshake at hour 160, 32 failed hours of 192`.
- **Diagnose:** the metric falls monotonically and `renewals` is 0 on every line: nothing replaced `srv.cert`.
- **Fix:** `next_renewal(cert, rng)` = notBefore + `rng.uniform(0.60, 0.72)` × lifetime; `tick()` renews when due, retries hourly while the CA is down, keeps serving the still-valid cert, and logs `cert_expiry_soon` below 25 %. **You run** `python solution_renewal.py`. **What you see:**
  ```
  renewing server, 21 days: 0 failed handshakes, 4 renewals, 0 alerts
  CA down hours 90-124: 0 failed handshakes, 4 renewals, 6 alert lines
  first alert: {"alert": "cert_expiry_soon", "hours_left": 40.0}
  ```
  40 hours is 25 % of 160: the alert fires while there is time to fix the CA.
- **Proof:** before the fix, `BUILD_IMPL=cert_lifecycle python -m unittest -v test_build_task` gives `ERROR: test_jitter_spreads_a_fleet`, two `FAIL:` lines, `FAILED (failures=2, errors=1)`. After: `Ran 3 tests in 0.241s`, `OK`; full suite `Ran 8 tests in 0.275s`, `OK` (README: 0.889s).
4. **Independent tools.** `python tool_check.py` writes `ca.pem`, `leaf.pem`, `crl.pem`. Expected (not run here; step CLI and KeyStore Explorer not installed): `step certificate inspect` shows the 160-hour window; KeyStore Explorer lists the revoked serial in `crl.pem`.

## Common confusions
- **Q:** "Short-lived certs mean more outages." — **A:** Only without automation: `0 failed handshakes` over 21 days with 4 renewals.
- **Q:** "No CRL entry means the cert is fine." — **A:** Only if the CRL is fresh; at 25 h it is `stale CRL`.
- **Q:** "Backdating notBefore is a security hole." — **A:** It tolerates slow clocks (1 h); `notAfter` is still exact.
