# Password storage: Argon2id (and scrypt fallback) — explained

## The intuition
You never store passwords; you store something that lets you *check* a password. SHA-256 is too fast: after a leak, a GPU tries billions of guesses per second. A password hash is deliberately **slow and memory-hungry**, and a random **salt** makes identical passwords look different.

Argon2id stores algorithm, parameters, salt and hash in one self-describing **PHC string**, so costs can rise without breaking old logins.

**Analogy:** a lock that takes ten seconds to turn: harmless for the owner once a day, ruinous for a burglar trying a million keys. Where the analogy breaks: offline guessing on stolen data cannot be rate-limited — only cost helps.

```
hash_password(pw): salt=os.urandom(16) -> Argon2id(m=19456,t=2,p=1) -> "$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>"
verify_password(pw, stored): Argon2id.verify_phc_encoded(pw, stored)  # reads params+salt from stored
                             InvalidKey -> False
```

**The one thing to remember:** store salted, slow, parameterised hashes — and let the stored string carry its own parameters.

## Walkthrough: what actually happens when you run it
1. **You run** `python -c "from cryptography.hazmat.primitives.kdf.argon2 import Argon2id"`. **What you see:** no error (the lab prints `import ok`).
2. **You run** `python passwords.py`. **What happens inside:** first the RFC 9106 and RFC 7914 vectors with tiny test parameters. **What you see:**
   ```
   RFC 9106 Argon2id tag: 0d640df5…6b01e659
   RFC 7914 scrypt  dk  : fdbabe1c9d3472007856e7190d01e9fe ...
   ```
3. **Hash and verify.** `hash_password` draws a 16-byte salt and calls `derive_phc_encoded`. **What you see:**
   ```
   argon2id hash (0.074s): $argon2id$v=19$m=19456,t=2,p=1$g5ceMJLum61jNjwqIKSj/Q$BR6i…
   same password, new salt -> different hash: True
   verify right password: True
   verify wrong password: False
   ```
   **What it means:** m=19456 KiB (19 MiB), t=2 passes, p=1 lane, then salt, then hash.
4. **Scrypt fallback.** **What you see:** `scrypt fallback (1.303s): scrypt$131072$8$1$…` and `scrypt verify right/wrong: True False`. It needs 128 MiB.
5. **You run** `python try_it.py`. **What happens inside:** it doubles `memory_cost` and hashes again. **What you see:**
   ```
   1) new PHC prefix: $argon2id$v=19$m=38912,t=2,p=1$ | time 0.175s -> 0.329s (x1.9)
      old m=19456 hash still verifies: True
   2) verify 'hunter2 '  -> False
   ```
   **What it means:** cost doubled with memory, yet the old hash still verifies because its own parameters are in the string.
6. `python -m unittest` → `Ran 3 tests in 6.807s`, `OK` (slow by design).

## Common confusions
- **Q:** "SHA-256 with a salt is fine." — **A:** Salt defeats tables, not speed; compare 0.074 s per Argon2id guess with microseconds for SHA-256.
- **Q:** "I must store the salt separately." — **A:** It is the fourth `$` field of the PHC string.
- **Q:** "Raising parameters means a forced reset." — **A:** try_it line 1: old hashes verify; rehash on next login.
