# Key exchange and hybrid encryption (X25519 + HKDF + AEAD) — explained

## The intuition
AEAD (lesson 4) needs both sides to already share a key. How do you encrypt a message to Bob when all you have is his *public* key? **Key agreement**: you make a brand-new, throw-away (ephemeral) key pair, combine your ephemeral private key with Bob's public key using X25519, and get a 32-byte shared secret. Bob combines *his* private key with your ephemeral public key and gets the same secret. Observers cannot compute it.

**HKDF** turns that raw secret into an AEAD key bound to both public keys and a protocol label (`info`); ChaCha20-Poly1305 then encrypts. "Hybrid" = public-key math for the key, symmetric AEAD for the data. Same shape as age, HPKE and TLS 1.3.

**Analogy:** mixing paint. You and Bob each add a secret colour to a public base; exchanging the mixtures lets both reach the same final colour, while an observer cannot un-mix. Where the analogy breaks: a fresh ephemeral "colour" per message means even you cannot decrypt what you sent once the ephemeral key is discarded.

```
sender: eph = X25519PrivateKey.generate()
        shared = eph.exchange(bob_pub)
        key = HKDF(SHA256, salt=eph_pub||bob_pub, info=INFO).derive(shared)
        blob = eph_pub(32) || ChaCha20Poly1305(key).encrypt(ZERO_NONCE, msg, aad)  # ct || tag(16)
bob:    shared = bob.exchange(blob[:32]) → same key → decrypt → msg | InvalidTag
```

**The one thing to remember:** key agreement gives a shared secret, a KDF turns it into a labelled key, and AEAD does the actual encryption.

## Walkthrough: what actually happens when you run it
1. **You run** `python seal_box.py`. **What happens inside:** both `exchange` directions on RFC 7748 keys must equal the published `K`. **What you see:**
   ```
   RFC 7748 6.1 Alice public:   True
   RFC 7748 6.1 shared secret:  True
   ```
2. **Seal to Bob.** `seal` generates the ephemeral key, derives the key, encrypts with a zero nonce. **What you see:** `sealed 29 B -> 77 B (overhead 48 = 32 eph_pub + 16 tag)` and `bob opens:    b'db password rotation at 02:00'`. **What it means:** a zero nonce is safe *only* because every message gets a brand-new key; reuse the key and lesson 4's nonce-reuse leak returns.
3. **Fresh ephemeral key.** **What you see:** `same msg sealed twice -> different blobs: True`.
4. **Break it three ways.** **What you see:**
   ```
   eve opens:    InvalidTag (rejected)
   aad changed:  InvalidTag (rejected)
   eph swapped:  InvalidTag (rejected)
   ```
   **What it means:** Eve gets a different shared secret; a swapped ephemeral key changes DH output and HKDF salt.
5. **You run** `python try_it.py`. **What you see:**
   ```
   1) plaintext    0 B -> blob   48 B
   1) plaintext 4096 B -> blob 4144 B
   2) receiver uses info v2, sender used v1 -> InvalidTag (keys differ, domain separation works)
   ```
   **What it means:** overhead is a fixed 48 bytes; and one changed label byte produces an unrelated key — that is domain separation.
6. **You run** `python -m unittest -v`. **What you see:** `Ran 9 tests`, `OK (skipped=1)`. The skip is `test_age_cli.py`: the age CLI is not installed here. Expected (not run here): with age installed, `age -r age1… -o msg.age msg.txt` writes a file whose header starts `age-encryption.org/v1` with a `-> X25519` stanza — the same construction.

## Common confusions
- **Q:** "X25519 encrypts the message." — **A:** It only agrees a secret; ChaCha20-Poly1305 encrypts, in `seal()`'s last line.
- **Q:** "A zero nonce is always a bug." — **A:** It is a bug when a key is reused; here `eph` is new per call (step 3).
- **Q:** "I can use the shared secret as the AES key." — **A:** `_key` runs HKDF first and rejects an all-zero output from small-order points.
