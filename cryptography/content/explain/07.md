# Digital signatures with Ed25519 — explained

## The intuition
HMAC (lesson 2) proves "someone with the shared key made this". A **signature** splits that key in two: a private key that only the signer holds, and a public key anyone can have. Only the private key can *make* a signature; the public key can only *check* one. So a user with `app-1.0.tar.gz` and a 64-byte `.sig` can verify the release without being able to forge one.

Ed25519 is the modern default: 32-byte keys, 64-byte signatures, no parameters, and **deterministic** — the per-signature secret comes from key and message, not an RNG.

What a signature does *not* tell you is whether the public key you hold is the right one. Lessons 9 and 14 handle that.

**Analogy:** a handwritten signature compared against a specimen card at the bank. Where the analogy breaks: a digital signature covers every byte and cannot be copied onto another document.

```
signer:   Ed25519PrivateKey.generate()
          ├─ save_keys → release.key (PKCS#8 PEM, secret)   release.pub (SPKI PEM, publish)
          └─ sign_file(release) → key.sign(bytes) → app-1.0.tar.gz.sig (64 B)
verifier: load_public(release.pub) → pub.verify(sig, bytes) → True | InvalidSignature → False
```

**The one thing to remember:** the private key signs, the public key verifies, and the hard part is trusting the public key.

## Walkthrough: what actually happens when you run it
1. **You run** `python signatures.py`. **What happens inside:** the RFC 8032 TEST 1 secret is loaded; its public key and signature of the empty message are compared. **What you see:**
   ```
   RFC 8032 TEST 1 public key: True
   RFC 8032 TEST 1 signature:  True
   ```
   **What it means:** a signature can only match a published vector byte-for-byte because Ed25519 is deterministic.
2. **Key serialization.** `save_keys` writes PKCS#8 and SubjectPublicKeyInfo PEM files. **What you see:** `sizes: raw private 32 B, raw public 32 B, PEM private 119 B, PEM public 113 B`. **What it means:** the PEM files are the same 32 bytes wrapped in ASN.1 and base64, plus header lines.
3. **Sign and verify.** `sign_file` signs the whole file content and writes `<name>.sig`; the verifier loads *only* `release.pub`. **What you see:**
   ```
   signature file: app-1.0.tar.gz.sig 64 bytes
   verify original:        True
   verify with other key:  False
   verify after 1 change:  False
   ```
   **What it means:** the edit was `tarball` → `tarbaII` (capital i's — looks identical); one changed byte fails.
4. **You run** `python try_it.py`. **What you see:**
   ```
   1) same key + same message -> identical signatures: True | first 8 bytes: 8081583b8784835c
   2) raw 32 B | PEM 113 B | OpenSSH 80 B | PEM loads back to same key: True
      OpenSSH form: ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAINdam…
   ```
   **What it means:** the same key appears in three wrappers; your `~/.ssh/id_ed25519.pub` is this format.
5. **Build task.** Before you add `key_id()` and `verify_with_keyring()`, run `BUILD_IMPL=signatures python -m unittest test_build_task`. **What you see:** `Ran 2 tests` … `FAILED (errors=2)` — the functions do not exist yet. The reference (`solution_keyring.py`) hashes the raw public key to a 16-hex-char id and tries each key in the keyring, catching `InvalidSignature`.
6. **You run** `python -m unittest -v`. **What you see:** `Ran 6 tests in 0.031s`, `OK` (4 lab tests + 2 build-task tests against the solution).

## Common confusions
- **Q:** "Signing encrypts the file." — **A:** The file stays readable; the `.sig` is a separate 64-byte proof.
- **Q:** "If verify returns True, the release is safe." — **A:** It only proves who signed it, with *the key you loaded*; a swapped `release.pub` gives `True` for an attacker's file too.
- **Q:** "Signatures must vary like AES-GCM ciphertexts." — **A:** try_it line 1: identical by design.

## Check your understanding
1. Why can you publish `release.pub` but not `release.key`?
<details><summary>Answer</summary>The public key can only verify; the private key can sign anything as you.</details>
2. During key rotation, why does `verify_with_keyring` return a key id rather than `True`?
<details><summary>Answer</summary>So you can log which key signed and later refuse the old key once rotation completes.</details>
3. Why does the `.sig` stay 64 bytes for a 1 GB file?
<details><summary>Answer</summary>Ed25519 hashes the message (SHA-512) internally; the signature size is fixed.</details>
