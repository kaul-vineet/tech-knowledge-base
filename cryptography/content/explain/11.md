# Tokens done right: signed JWT-style tokens — explained

## The intuition
A token is a statement the issuer makes about a user — "alice may call orders-api until 12:05" — that an API can check without a database lookup. A JWT is three base64url segments: a header naming the algorithm, a payload of claims, and a signature over `header.payload`. Nothing is encrypted: anyone holding the token can read it.

Real bugs come from verification. The classic mistake lets the **token** choose the algorithm: an attacker writes `"alg":"none"`, or switches EdDSA to HS256 and computes an HMAC keyed with the *public* key. The fix is boring: the **verifier** decides — one allow-list, one key per algorithm, then `exp`, `nbf` and `aud`, only after the signature passes.

**Analogy:** a festival wristband: staff read the printed expiry (claims) and check the hologram (signature) with their own scanner. Where the analogy breaks: a wristband cannot tell staff which scanner to use — a naive JWT verifier lets the token do exactly that.

```
issuer: sign(claims, "EdDSA", private_key) → b64u(header).b64u(claims).b64u(sig)
API:    verify(token, keys={"EdDSA": pub}, audience="orders-api")
          alg from header ─ alg in keys? ─no─▶ TokenError("algorithm 'none' not allowed")
          signature over "h.p" with keys[alg] ─bad─▶ TokenError("bad signature")
          exp (+leeway 30 s) → nbf → aud ─fail─▶ TokenError(...)   else ─▶ claims
```

**The one thing to remember:** the server's configuration, never the token's header, chooses the algorithm and key.

## Walkthrough: what actually happens when you run it
1. **You run** `python tokens.py`. **What happens inside:** `sign()` JSON-encodes header and claims, base64url-encodes them and signs `h.p` with a fresh Ed25519 key; `verify(good, {"EdDSA": pub}, "orders-api")` returns the claims. **What you see:** `valid token: alice (211 chars)`.
2. **Five attacks, two verifiers** (`naive_verify` lets the header pick; `verify` uses the allow-list). **What you see:**
   ```
   alg none        naive ACCEPTS role=admin | safe rejects (algorithm 'none' not allowed)
   key confusion   naive ACCEPTS role=admin | safe rejects (algorithm 'HS256' not allowed)
   expired         naive ACCEPTS role=?     | safe rejects (expired or no exp)
   wrong audience  naive ACCEPTS role=?     | safe rejects (wrong audience)
   payload edited  naive rejects            | safe rejects (bad signature)
   ```
   **What happens inside:** in `naive.py` the `none` token skips both `if` branches; the key-confusion token is an HMAC keyed with `pub.public_bytes_raw()`, which naive code also uses. The safe `verify` stops both at `if alg not in keys`. Expired and wrong-audience tokens are correctly signed — only claim checks catch them. **What would look wrong:** any `safe ACCEPTS`. Note the naive verifier *does* catch the edited payload: the signature works; the policy around it fails.
3. **You run** `python try_it.py`. **What you see:**
   ```
   1) expired 20 s ago, leeway=30: accepted
   1) expired 20 s ago, leeway= 0: rejected (expired or no exp)
   2) payload read with NO key: {'sub': 'alice', 'email': 'alice@example.com', 'aud': 'orders-api', 'exp': 1800000060}
   ```
   **What it means:** leeway absorbs clock skew (`now > exp + leeway`); keep it to seconds. Line 2 decodes with `unb64u` alone — never put secrets in a JWT.
4. **You run** `python -m unittest`. **What you see:** `Ran 13 tests in 0.012s`, `OK` (README: 0.082s).
5. `python tool_check.py` writes tokens for an independent verifier. Expected (not run here): per the smallstep docs, `step crypto jwt verify --alg EdDSA --aud orders-api --subtle` prints the decoded token for `eddsa.jwt` and fails for `none.jwt`.

## Common confusions
- **Q:** "JWTs are encrypted, so the email is private." — **A:** try_it 2 reads the payload with no key.
- **Q:** "A valid signature means the token is acceptable." — **A:** The expired and wrong-audience tokens in step 2 are correctly signed; claim checks reject them.
- **Q:** "Using the public key as an HMAC key is harmless." — **A:** Anyone can compute that HMAC, so `key confusion` yields `role=admin`.
