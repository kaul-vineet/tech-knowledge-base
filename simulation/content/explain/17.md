# Digital twins with live data: state estimation, drift detection and recalibration — explained

## The intuition

A model calibrated once (lesson 13) goes stale: someone leaves a window ajar. A **digital twin** stays coupled to its system through a live feed and keeps three jobs apart:

1. **State estimation** — "what is the temperature *now*?" A Kalman filter blends prediction and noisy reading by their uncertainties. State [T, g]: temperature plus a heat gain g that soaks up small model error.
2. **Drift detection** — "has the plant changed?" Standardised innovations (reading minus prediction, over predicted sd) should be N(0, 1) noise. A tabular CUSUM sums them minus a slack k; persistent bias crosses threshold h.
3. **Recalibration** — "what changed?" After an alarm, refit (a, b) on fresh readings so the twin *explains* the change (heat loss up ~65%).

The feed is part of the model: messages arrive late, duplicated, null or wrong (an 85 C glitch). A twin never moves backwards in time and must not swallow an impossible reading.

Analogy: an SRE stack — ingestion, a smoothed health estimate, an anomaly detector, a postmortem that changes config.
Where the analogy breaks: a twin alerts on the *residual against physics*, so it tells "hot day" from "broken building".

```
sensor_feed.jsonl ─> read_feed(): drop late/dup, keep null
   └─> per reading: predict(x, P) ─> innovation nu, S
          ├─ |nu|/sqrt(S) > 5 ? ─> log "rejected", stop        (gate: the fix)
          ├─ Kalman update x, P ; history.append
          ├─ CUSUM s_hi/s_lo += z ∓ k ; > h ? ─> drift_alarm, refit_pending
          └─ 48 new readings after alarm ─> refit(a, b) ─> "recalibrated", reset CUSUM
```

The one thing to remember: a twin must separate "noise", "bad data" and "the system changed" — and it needs a gate so the second never looks like the third.

## Walkthrough: what actually happens when you run it

1. **You run** `python twin.py`.
   **What happens inside:** `run()` drives three variants and scores every 1-hour forecast against the plant's true temperature (the feed is synthetic).
   **What you see:**
   ```
     A open-loop model       0.167 |  6.316
     B Kalman filter only    1.480 |  0.194
     C KF + CUSUM + refit    1.789 |  0.151
   feed: 850 scored forecasts; skipped {'late_or_duplicate': 2, 'null_reading': 1}
   alarms before the drift (t < 2500 min): 5; first alarm after it: 2610 min
   ```
   **What it means:** RMSE before the drift | last day. A is fine until the plant changes. B and C are *worse than open-loop before the drift* — something misleads the filter.

## Failure lab: assimilating the glitch

1. **Inject.** Shipped `Twin.update()` assimilates every reading, including the 85.0 C glitch at t = 1250.
2. **Symptom.** Five false alarms and the before-drift error above.
3. **Diagnose.** **You run** `head -c 600 twin_log.jsonl`.
   **What you see:**
   ```
   {"t_min": 1250, "event": "drift_alarm", "s_hi": 405.13, "s_lo": 0.0}
   {"t_min": 1490, "event": "recalibrated", "a": 0.2, "b": 1.0}
   {"t_min": 1495, "event": "drift_alarm", "s_hi": 10.49, "s_lo": 0.0}
   ```
   **What it means:** one reading pushed the CUSUM to 405 (threshold 8). The refit, with the glitch in its 48-reading window, hit the clip limits a = 0.2, b = 1.0, and the bad model triggered the next alarm: a cascade.
4. **Fix.** In `update()`, if |nu|/sqrt(S) > GATE = 5, log `rejected` and return *before* the state, refit history or CUSUM move. `BUILD_TARGET=mine python -m unittest test_build_task test_fitness -v` on the shipped file reports `FAILED (failures=5)`.
5. **Proof.** **You run** `python solution/twin.py`.
   **What you see:**
   ```
     B Kalman filter only    0.189 |  0.194
     C KF + CUSUM + refit    0.189 |  0.127
      {"t_min": 1250, "event": "rejected", "zone_C": 85.0, "z": 404.5}
      {"t_min": 2525, "event": "drift_alarm", "s_hi": 0.0, "s_lo": 10.51}
      {"t_min": 2765, "event": "recalibrated", "a": 0.0331, "b": 0.267}
   ```
   **What it means:** the glitch is rejected at z = 404.5, the real drift is caught 25 min after it starts, and the refit finds a = 0.0331 against the plant's 0.035.

## The decision

ADR 0001 compares three options (solution numbers):

- **A, open-loop:** 0.167 / 6.316 C. Rejected — correct only while nothing changes.
- **B, Kalman filter only:** 0.189 / 0.194 C. Tracks, but a stays 0.020 — it cannot say *what* changed — and misses the 0.15 C requirement.
- **C, filter + CUSUM + refit + gate:** 0.189 / 0.127 C, 0 false alarms, alarm after 25 min, a = 0.0331. Chosen.

**The fitness function** `test_fitness.py` replays the committed feed and asserts the brief: 0 false alarms, delay ≤ 60 min, |a − 0.035|/0.035 < 15%, last-day RMSE ≤ 0.15 C *and* below option B. **You run** `python -m unittest test_fitness -v` → **What you see:** `Ran 4 tests in 0.897s` … `OK`. Retuning the gate or CUSUM must still pass all four.

6. **You run** `python try_it.py`.
   **What you see:**
   ```
   h=4.0: false alarms 2, detection delay 760 min, rejected 490, last-day RMSE 2.407 C
   gate=2.5: false alarms 0, detection delay None min, rejected 366, last-day RMSE 6.051 C
   ```
   **What it means:** a "more sensitive" h raises false alarms, refits on bad windows and ends up *slower*. A tight gate locks the twin out: after the drift every honest reading looks like an outlier — the ADR's follow-up is to treat bursts of rejections as drift.

## Common confusions

**Q:** The filter alone handles drift. — **A:** It tracks (0.194) but cannot explain; a stays at the commissioning value.

**Q:** A tighter gate is safer. — **A:** Gate 2.5: 366 rejected, no detection, RMSE 6.051 C.

**Q:** Dropping late messages loses data. — **A:** It keeps time monotonic; the null reading is kept and predicted through.
