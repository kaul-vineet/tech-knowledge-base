# Large-scale and parallel simulation: reproducible streams, checkpoints and result storage — explained

## The intuition

A long sweep on a worker pool will be interrupted — a laptop sleeps, a spot instance is reclaimed. You want to *resume*, and the result must be **bit-identical** to an uninterrupted run, or you cannot tell "the code changed" from "it crashed on Tuesday". That needs two properties; lesson 16's fix gives only one.

**Streams keyed on identity, not position.** Lesson 16 gave child i to task i of the list. After a crash the *pending* list is shorter, so a task gets a different child. `SeedSequence(ROOT, spawn_key=(s, r))` gives scenario s, replication r the same stream whatever is left, on any worker count.

**Results stored transactionally and idempotently.** A CSV line can be half-written when the process dies. SQLite batches are fully committed or rolled back; `PRIMARY KEY (scenario, rep)` with `INSERT OR IGNORE` makes re-running a finished task harmless; batches of 8 trade a little redone work for far less fsync time.

Analogy: idempotency keys — a retry with the same key cannot charge twice.
Where the analogy breaks: here the key must also fix the *random numbers*.

```
pending = all (s, r) − rows already in sweep.db
for each pending (s, r):  SeedSequence(ROOT, spawn_key=(s, r))   ← identity, not position
   spawn Pool ─> run_task ─> parent collects ─> every 8: BEGIN; INSERT OR IGNORE …; COMMIT
crash ─> torn batch rolls back ─> resume ─> same streams ─> same checksum
```

The one thing to remember: a resumed run must be indistinguishable from a clean one — key streams *and* rows on task identity.

## Walkthrough: what actually happens when you run it

1. **You run** `python sweep.py`.
   **What happens inside:** a clean 120-task sweep, then one that crashes after 48 committed results and resumes; both databases are hashed in a fixed order.
   **What you see:**
   ```
   clean run: 120 tasks on 2 spawn workers in 11.6 s (machine-dependent); checksum 5a2bd148609737c0
   interrupted run: crashed after 48 committed results; resuming...
   resumed run: +72 rows; checksum 8a6983e0e764e5cb -> DIFFERENT to the clean run
   ```
   **What it means:** no error, the right row count — and a different answer. Only the checksum tells you.

## Failure lab: streams by position

1. **Inject.** Shipped `seeded(pending)` uses `SeedSequence(20).spawn(len(pending))` and zips children with the pending list.
2. **Symptom.** The DIFFERENT checksum above.
3. **Diagnose.** Each stored row records its seed as entropy/[spawn_key]. **You run** `python try_it.py`.
   **What you see:**
   ```
   shipped: task (7, 2) seed column = 20/[14]
   fixed: task (7, 2) seed column = 20/[7, 2]
   ```
   **What it means:** the resumed task used stream 14, its position in the shortened pending list — already used by another task.
   `BUILD_TARGET=mine python -m unittest test_build_task -v` → **What you see:** `Ran 2 tests in 99.827s` … `FAILED (failures=2)` (resume on 1 and 2 workers).
4. **Fix.** `seeded()` returns `(s, r, SeedSequence(ROOT, spawn_key=(s, r)))`.
5. **Proof.** **You run** `python solution/sweep.py`.
   **What you see:**
   ```
   clean run: 120 tasks on 2 spawn workers in 14.7 s (machine-dependent); checksum 38975a17ffb143cd
   resumed run: +72 rows; checksum 38975a17ffb143cd -> IDENTICAL to the clean run
   ```
   **What it means:** try_it also prints `identical = True` for crashes after 9 and 33 resumed on 1 worker.

## The decision

2. **You run** `python storage_options.py`.
   **What you see:**
   ```
     CSV append + flush per row    0.098 s
     SQLite, commit every row     28.286 s
     SQLite, commit every 8 rows   7.528 s
     SQLite, one commit            0.068 s
   crash mid-write, CSV: 1 malformed of 2 lines - the torn row swallowed the resumed row
   crash mid-batch, SQLite: 16 rows, 16 distinct after resume (the torn batch rolled back)
   ```
   **What it means:** timings differ from the lesson's (0.176 / 22.841 / 3.980 / 0.058 s) on this slow shared mount; the ordering is the same. Per-row commits pay an fsync each; CSV is fast and *unsafe*.

3. **You run** `python scaling.py`.
   **What you see:**
   ```
   os.cpu_count() = 1
   workers 1 chunksize 1:   10.6 tasks/s  (speed-up x1.00)
   workers 4 chunksize 8:    4.7 tasks/s  (speed-up x0.44)
   Amdahl serial fraction estimate (chunksize 8): f = 1.00
   ```
   **What it means:** on one CPU workers only add overhead (lesson: 15.7 and 6.1 tasks/s). Multi-core machines speed up until cores run out.

ADR 0001 weighs:

- **A, streams by position + CSV append:** different resumed checksum and a torn line. Rejected.
- **B, identity-keyed streams + SQLite (WAL, PRIMARY KEY, INSERT OR IGNORE, batches of 8):** identical checksum; the interrupted batch rolled back. Chosen — at most 7 tasks redone after a crash.
- **C, identity streams + Parquet only:** a crash before the end loses everything. Export, not checkpoint.

It also records: one writer (the parent), and a local disk — WAL does not work over a network filesystem.

**The fitness function** `test_fitness.py` crashes the sweep at 0, 17 and 40 results on 1 and 2 workers and requires 48 rows and the clean checksum every time. **You run** `python -m unittest test_fitness -v` → **What you see:** `Ran 1 test in 190.527s` … `OK`.

## Common confusions

**Q:** Lesson 16's spawn fix makes resumes safe. — **A:** It ties streams to *positions*; after a resume the positions shift (20/[14]).

**Q:** Row count matches, so the resume is fine. — **A:** +72 rows either way; only the checksum differs.

**Q:** Commit every row is safest. — **A:** Slowest by far (28.286 s); batches of 8 redo at most 7 results.
