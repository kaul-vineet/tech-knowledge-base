# Performance and scale: vectorise, parallelise, keep streams independent — explained

## The intuition

When a simulation is too slow, there are two levers. **Vectorise**: replace the per-customer Python loop with whole-array numpy operations, so the work runs in compiled code. **Parallelise**: run independent replications in separate processes. The first is usually the bigger win on one machine; the second scales across cores — but brings a new risk: every worker needs its *own* random stream, and nothing warns you when they share one.

The vectorised trick is worth seeing once. Lindley's rule W(n+1) = max(0, W(n) + S(n) − A(n)) looks inherently sequential. But with the running sum S_n of (service − gap), the wait is W_n = S_n − min(0, min over k ≤ n of S_k): a cumulative sum and a running minimum, both available as numpy primitives (`cumsum`, `minimum.accumulate`).

For streams, NumPy's answer is `SeedSequence(root).spawn(n)`: children with distinct spawn keys that are statistically independent and reproducible. Pair child i with replication i in the parent, and the result no longer depends on how many workers you use or which worker gets which task.

Analogy: request IDs in a distributed system — generate them centrally (or derive them from identity), never let every node start counting from 1.
Where the analogy breaks: duplicate IDs usually cause loud collisions; duplicate random streams produce plausible numbers and an impossibly tight CI.

```
SeedSequence(16).spawn(40) ─> child i ─┐
replication i ─────────────────────────┴─> task (i, child_i) ─> spawn Pool(2) ─> one_replication()
                                                              └─> runs.jsonl {"rep","spawn_key","mean_wait","pid"}
shipped tasks_for(): (i, 16) for every i ─> every worker draws the same stream
```

The one thing to remember: parallel replications are only replications if each one has its own stream, assigned in the parent.

## Walkthrough: what actually happens when you run it

1. **You run** `python perf.py`.
   **What happens inside:** `main()` builds 40 serial replications from spawned children, times the Python loop, the numpy version and a 2-worker spawn pool fed by `tasks_for()`; the pool writes one JSON line per replication.
   **What you see:**
   ```
   largest difference loop vs numpy: 9.1e-14; numpy vs 2 workers: 7.7e-01
   TIMING (machine-dependent):
     python loop           2.746 s   speed-up x   1.0
     numpy vectorised      0.154 s   speed-up x  17.8
     2 spawn workers      22.608 s   speed-up x   0.1
   mean wait 4.240 +/- 0.000 min
   distinct replication results 1 of 40 (one line each in runs.jsonl)
   ```
   **What it means:** loop and numpy agree to round-off (9.1e-14), so vectorising is safe. On this 1-CPU sandbox the pool is *slower* — process start-up and re-imports dominate. Your speed-ups will differ; the lesson quotes 7–26x for numpy across runs here.

## Failure lab: one shared seed

1. **Inject.** Shipped `tasks_for()` returns `(rep, SEED)` — the integer 16 — for every task.
2. **Symptom.** The last two lines above: `4.240 +/- 0.000` and `1 of 40`. A CI of zero width looks like great precision.
3. **Diagnose.** **You run** `head -n 2 runs.jsonl`.
   **What you see:**
   ```
   {"rep": 0, "spawn_key": [], "mean_wait": 4.240082576236665, "pid": 6614}
   {"rep": 1, "spawn_key": [], "mean_wait": 4.240082576236665, "pid": 6614}
   ```
   **What it means:** identical results and an empty spawn key: every worker built `default_rng(16)`. Then `BUILD_TARGET=mine python -m unittest test_build_task -v` shows `AssertionError: 1 != 6` and `FAILED (failures=2)`; the 1-vs-2-worker test passes — both are equally wrong.
4. **Fix.** `tasks_for()` returns child i of `SeedSequence(16).spawn(reps)` with replication i.
5. **Proof.** **You run** `python solution/perf.py`.
   **What you see:**
   ```
   largest difference loop vs numpy: 9.1e-14; numpy vs 2 workers: 0.0e+00
     numpy vectorised      0.292 s   speed-up x  11.6
   mean wait 4.042 +/- 0.118 min
   distinct replication results 40 of 40 (one line each in runs.jsonl)
   ```
   **What it means:** serial and parallel are now bit-identical, and the CI has a real width that covers 4.0.

## Walkthrough continued

2. **You run** `python try_it.py`.
   **What you see:**
   ```
   1 vs 2 vs 3 workers bit-identical: True | mean wait 4.099 min
   root+id seeding: 7 of 8 replications of run B repeat run A
   SeedSequence(17).spawn(8): 0 of 8 repeat run A
   ```
   **What it means:** results do not depend on worker count. Seeding with root + worker_id is the pattern the NumPy docs warn about: "rerun with root + 1" silently reuses 7 of 8 streams.

## Common confusions

**Q:** Different PIDs mean different streams. — **A:** The log shows one PID and one value; even with many PIDs, `default_rng(16)` is the same stream.

**Q:** Parallel is always faster. — **A:** 22.608 s vs 0.154 s here: one CPU, spawn start-up costs.

**Q:** seed + i is independent enough. — **A:** try_it: 7 of 8 replications repeat across "different" runs.
