# Model governance and V&V: model cards checked against evidence — explained

## The intuition

When a model informs a staffing decision, someone asks "can I trust this, and for what?". A **model card** answers in a fixed structure: purpose, assumptions, the validity envelope (the range of inputs where it was shown to be accurate), accuracy, the most influential inputs, verification status, and the versions of code and data it was checked on.

A document can claim more than the evidence supports and nobody notices. So the card becomes data and the evidence a build artifact. `governance.py` regenerates the evidence — verification suite, validation against Erlang C at seven utilisations, elasticities, file hashes — and `check_card()` compares each claim with it. A claim may be *more conservative* than the evidence, never wider or better.

The validation requirement is fixed *in advance* (relative error and relative CI half-width ≤ 10%); the envelope is whatever passes.

Analogy: a type checker for documentation — the card's claims are type annotations, the evidence is the inferred type, and a mismatch blocks the build.
Where the analogy breaks: it only catches claims encoded as checkable; prose still needs a human.

```
governance.py ─> verification.py (7 Sargent-style tests)
             ─> validate: rho 0.50..0.95 × 10 reps ─> rel_err, rel_CI ≤ 10% ? ─> envelope
             ─> elasticities, sha256(code, data) ─> evidence.json
card.json ──┐
evidence ───┴─> check_card(): envelope, accuracy, key input, tests, hashes ─> findings [] ? PUBLISHABLE : BLOCKED
```

The one thing to remember: a model card is only as honest as the code that checks it against fresh evidence.

## Walkthrough: what actually happens when you run it

1. **You run** `python governance.py`.
   **What happens inside:** `verification.py` runs degenerate cases (1 desk = M/M/1), extreme conditions (overload refused) and internal validity (seeds, Little's law, pooling). Validation runs 10 replications of 20,000 patients per utilisation.
   **What you see:**
   ```
   verification: 7 tests, 0 failures
     0.85   1.573  1.623    3.1%   6.7%  True
     0.90   2.873  2.724    5.5%  11.9%  False
     0.95   6.127  6.047    1.3%  21.0%  False
   validity envelope: utilisation <= 0.85; max error inside 5.5%; busiest hour in arrivals.csv needs 0.8
   sensitivity (elasticity of Wq): {'lam': 6.01, 'mu': -7.02} -> most influential: mu
   ```
   **What it means:** at 0.95 the error is small (1.3%) but the CI is 21%: not shown accurate, just lucky. The envelope ends at 0.85, covering the busiest real hour (0.80).

## Failure lab: a draft that overclaims

1. **Inject.** Shipped `check_card()` only checks that the required headings exist.
2. **Symptom.** Same run, last block.
   **What you see:**
   ```
   draft_overclaiming.json: PUBLISHABLE; findings []
      [x] card claims match the evidence
   ```
   **What it means:** a card claiming utilisation ≤ 0.95, error 2.0%, key input λ and an old code hash passes — false assurance with a ticked box.
3. **Diagnose.** **You run** `BUILD_TARGET=mine python -m unittest test_build_task test_fitness -v` → **What you see:** four `FAIL` subtests (claim='envelope', 'error', 'influential', 'code_sha256'), `Ran 6 tests in 24.681s`, `FAILED (failures=4)`. The fitness tests pass: the *committed* card is honest; only the checker is blind.
4. **Fix.** `check_card()` compares envelope, accuracy, key input, verification count and both hashes.
5. **Proof.** **You run** `python solution/governance.py`.
   **What you see:**
   ```
   model_card.json: PUBLISHABLE; findings []
   draft_overclaiming.json: BLOCKED; findings ['envelope claims utilisation <= 0.95, evidence supports 0.85', 'claims max error 2.0%, evidence shows 5.5%', "claims most influential input 'lam', evidence says 'mu'", 'code_sha256 is stale: re-run the evidence and bump model_version']
   ```
   **What it means:** 4 of 4 caught; the honest card still publishes.

## The decision

ADR 0001 compares three ways to govern the model:

- **A, prose README checked by eye:** the shipped heading check passed the overclaiming draft — 0 of 4 caught. Rejected.
- **B, structured JSON card + machine-checked claims, evidence regenerated in CI:** 4 of 4 caught, and a data change stales the card (try_it below). Chosen.
- **C, full risk-informed credibility assessment** (NASA-STD-7009B, FDA 2023 / ASME V&V 40): human-scored, so not automated here; its factors become the review checklist. Kept for safety-relevant decisions.

**The fitness function** `test_fitness.py` re-runs the evidence and requires: verification failures 0, committed card findings [], envelope ≥ busiest hour (0.85 ≥ 0.80), every checklist item ticked. **You run** `python -m unittest test_fitness -v` → **What you see:** `Ran 4 tests in 31.106s` … `OK`.

3. **You run** `python agent_assist.py --fake`.
   **What you see:**
   ```
      OVERCLAIM envelope     'utilisation up to 0.95'
      OVERCLAIM accuracy     'within 2.0% of Erlang C'
      OK        key input    'most sensitive to the service rate'
   3. numbers not found in the evidence (UNVERIFIED): 3, 2.0
   4. code verdict: draft REJECTED - fix the claims, then re-run
   ```
   **What it means:** an agent may draft the prose; code checks every claim and number.

4. **You run** `python try_it.py`.
   **What you see:**
   ```
   accuracy requirement 5%: validated envelope utilisation <= 0.5
   one new row   : ['data_sha256 is stale: re-run the evidence and bump model_version']
   ```
   **What it means:** a 5% requirement shrinks the envelope to 0.5, below the busiest hour — the fitness test would fail. One appended data row blocks the card.

## Common confusions

**Q:** Small error at ρ 0.95 means it is valid there. — **A:** 1.3% error with a 21.0% CI: precision, not luck, is the requirement.

**Q:** A complete card is an honest card. — **A:** The overclaiming draft had every heading and ticked every box.

**Q:** Hashes are bureaucracy. — **A:** They turn one new data row into a blocking finding.
