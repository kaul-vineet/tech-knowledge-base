# Surrogate models and emulation: fast what-ifs that know where they stop — explained

## The intuition

Planners want "what if arrivals rise 10%?" answered in milliseconds; the clinic DES takes seconds per run. A **surrogate** (emulator) is a cheap model trained on a few dozen runs: (λ, μ) → mean wait.

Three questions decide whether to trust it. **Where were the training runs?** A Latin hypercube puts one run per stratum of each input. **How accurate is it?** Compare on 20 *fresh* holdout runs, and compare with the **noise floor**: the simulation itself scatters 0.033 min around the exact Erlang C answer, so no surrogate trained on noisy runs can honestly beat that. **Where does it stop?** Every surrogate interpolates; none knows what happens outside the training box. Queues are the worst case: wait time explodes as utilisation approaches 1, and that curve is exactly what a smooth fit cannot extrapolate.

A Gaussian process (GP) also reports a standard deviation, but under its own smoothness assumptions — outside the data it can be confidently wrong.

Analogy: a cache in front of a slow service — fast for keys near what it has seen.
Where the analogy breaks: a surrogate "miss" returns a plausible number; you must detect it yourself.

```
latin_hypercube(30) over λ 1.5–2.4, μ 0.95–1.10 ─> DES runs ─> fit poly / GP-lite / random features
holdout 20 uniform runs ─> RMSE vs noise floor 0.033 ; GP 95% coverage
what_if(λ, μ):  inside [LO, HI] and gp_sd <= 0.10 ? ─ yes ─> surrogate (ms)
                                                    └ no ──> 4 DES replications, labelled "*"
```

The one thing to remember: a surrogate is only valid inside the region it was trained on — make the code refuse outside it.

## Walkthrough: what actually happens when you run it

1. **You run** `python surrogate.py`.
   **What happens inside:** 30 LHS runs and 20 holdout runs of the M/M/3 DES; three surrogates fitted; then three what-ifs scored against exact Erlang C.
   **What you see:**
   ```
   polynomial              0.037     0.079
   gp-lite                 0.042     0.103
   random features         0.049     0.133
   (noise floor)           0.033   = holdout runs vs Erlang C
   gp-lite 95% intervals cover 85% of holdout runs; params {'length_scales': [0.4, 0.4], 'noise': 0.01}
   ```
   **What it means:** all within 0.016 of the noise floor — as good as the data. GP coverage of 85% (not 95%): its intervals are slightly too narrow even in-box.

## Failure lab: extrapolation

1. **Inject.** Shipped `what_if()` answers every question from the surrogate.
2. **Symptom.** The what-if rows from the same run:
   **What you see:**
   ```
     lam=2.00 mu=1.00 (rho 0.67): exact  0.444 | polynomial  0.466   gp-lite  0.447   random features  0.447  | gp sd 0.031
     lam=2.42 mu=1.00 (rho 0.81): exact  1.135 | polynomial  1.047   gp-lite  0.876   random features  0.833  | gp sd 0.052
     lam=2.70 mu=0.95 (rho 0.95): exact  6.015 | polynomial  1.930   gp-lite  0.877   random features  0.552  | gp sd 0.178
   ```
   **What it means:** in-box (λ 2.0) all are right. Just outside (λ 2.42, the box ends at 2.4) the GP is 23% low. At ρ 0.95 every surrogate is off by 3–11x, and the GP's sd of 0.178 would put the truth 29 sds away. Nothing flags it.
3. **Diagnose.** Check each query against the box and GP sd. **You run** `BUILD_TARGET=mine python -m unittest test_build_task test_fitness -v` → **What you see:** `Ran 6 tests in 48.086s` … `FAILED (failures=3)`; in-box tests pass.
4. **Fix.** Envelope guard: surrogate only inside [LO, HI] *and* sd ≤ 0.10; otherwise run 4 simulation replications and say so.
5. **Proof.** **You run** `python solution/surrogate.py`.
   **What you see:**
   ```
     lam=2.42 mu=1.00 (rho 0.81): exact  1.135 | polynomial  1.109*  gp-lite  1.109*  random features  1.109* | gp sd 0.052
     lam=2.70 mu=0.95 (rho 0.95): exact  6.015 | polynomial  6.240*  gp-lite  6.240*  random features  6.240* | gp sd 0.178
   ```
   **What it means:** out-of-box questions now take seconds, are marked `*`, and are right within simulation noise.

## The decision

ADR 0001 chose **GP-lite behind an envelope guard**:

- **A, quadratic polynomial:** best holdout (0.037) but no uncertainty, so it cannot express doubt. Kept as a cross-check.
- **B, GP-lite + guard:** 0.042, coverage 85%, guarded answers 1.109 and 6.240. Chosen — its sd gives a second tripwire besides the box.
- **C, random Fourier features:** 0.049, and fragile with little data (see try_it). Revisit with thousands of runs.

The ADR notes the guard's limit: a box is generous; in more dimensions the data's convex hull is far smaller than the box, so add a distance-to-nearest-run check before adding inputs.

**The fitness function** `test_fitness.py`: GP holdout RMSE ≤ 0.06, coverage ≥ 80%, in-box what-ifs within 10% of Erlang C, and zero out-of-box answers from the surrogate. **You run** `python -m unittest test_fitness -v` → **What you see:** `Ran 3 tests in 18.012s` … `OK`.

6. **You run** `python try_it.py`.
   **What you see:**
   ```
   n=10: polynomial 0.043  gp-lite 0.066  random features 0.181
   polynomial: raw 1.930, log-fit 2.583, exact 6.015
   gp-lite: raw 0.877, log-fit 0.929, exact 6.015
   ```
   **What it means:** with 10 runs random features collapse; the polynomial degrades least. A better-shaped output, log(Wq), still misses 6.015 by 2–6x.

## Common confusions

**Q:** The GP's sd tells me when it's wrong. — **A:** At ρ 0.95 the sd is 0.178 and the error 5.1 min.

**Q:** Beating the noise floor would be better. — **A:** It would mean fitting the simulation's noise, not the queue.

**Q:** Just widen the training box. — **A:** The guard is still needed at the new edges.
