# A supply-chain model: (s, S) inventory with common random numbers — explained

## The intuition

A bike shop sells inner tubes. When stock plus tubes on order falls to s, it orders up to S; deliveries take 1–4 days; customers who find no stock leave. Raising S costs holding but loses fewer sales. Which policy is cheaper?

The trap is comparison noise: if policy A sees a quiet year and B a busy one, the measured difference is mostly luck. Common random numbers (CRN) give both policies *the same years*: identical demand and lead times, so the difference reflects the policy. It works only if a number means the same thing in both runs — hence one random stream per purpose, drawn up front.

Analogy: an A/B test where both variants replay the same recorded traffic instead of splitting live users.
Where the analogy breaks: replayed traffic doesn't react to the variant; here lost sales and orders do — streams per purpose keep the *inputs* aligned while behaviour diverges.

```
streams(rep): rng([rep,0]) ─> weekly weather ─> demand[365]
              rng([rep,1]) ─> lead[365]   (lead time IF an order is placed on day t)
policy (30,80) ─┐ same demand, lead
policy (30,90) ─┴─> cost_b − cost_a per rep ─> CI of 30 differences
```

The one thing to remember: compare policies on the same random inputs and put a CI on the *difference*.

## Walkthrough: what actually happens when you run it

1. **You run** `python inventory.py`.
   **What happens inside:** `simulate(s, S, demand, lead)` loops 365 days: receive, sell `min(on_hand, d)`, count lost, compute position = on hand + on order, order up to S if position ≤ s, add holding cost. Order and lost-sale costs are added at the end.
   **What you see:**
   ```
     s=20 S=80:   8.71 +/- 0.30  orders/yr  40.6  lost tubes/yr  217.9
     s=30 S=80:   8.56 +/- 0.27  orders/yr  50.3  lost tubes/yr  111.3
     s=30 S=90:   8.30 +/- 0.22  orders/yr  42.7  lost tubes/yr   89.9
   ```
   **What it means:** the per-policy CIs overlap, so this table cannot rank (30,90) vs (30,80). Higher s halves lost tubes.

2. **You run** the same script; read the two comparison lines.
   **What happens inside:** `compare()` takes per-replication differences; with `crn=False` policy B uses `streams(r + 10_000)`.
   **What you see:**
   ```
   difference S=90 minus S=80, independent: +0.03 +/- 0.44 -> cannot tell
   difference S=90 minus S=80, CRN        : -0.25 +/- 0.12 -> S=90 is cheaper
   ```
   **What it means:** same 30 replications, a CI 3.7x narrower: shared busy and quiet years cancel.

3. **You run** `python try_it.py`.
   **What happens inside:** one generator draws weather, demand and lead times *as needed*; then lost-sale cost 2.00.
   **What you see:**
   ```
   same seeds, ONE shared stream: S=90 minus S=80 = -0.19 +/- 0.31
   same seeds, one stream per purpose (lab): -0.25 +/- 0.12
   lost sale costs 2.00: S=90 minus S=80 = -0.13 +/- 0.08 per day
   ```
   **What it means:** with one shared stream, the moment one policy places an order and draws a lead time, every later demand shifts — synchronisation is lost and most of the gain with it. The S=90 advantage survives cheaper lost sales.

4. **SimPy version.** Expected (not run here): `simpy_inventory.py` holds tubes in a `simpy.Container` and uses the same streams; the lesson expects identical cost per day in CI.

## Common confusions

**Q:** Same seed = CRN. — **A:** Step 3: same seeds, one shared stream, CI ±0.31 instead of ±0.12.

**Q:** CRN biases the comparison. — **A:** Each policy's mean is still unbiased; only the variance of the difference shrinks.

**Q:** Lead times should be drawn only when an order happens. — **A:** Drawing `lead[t]` for every day up front means order timing cannot shift the demand stream.

## Check your understanding

1. Why use `default_rng([rep, purpose])`?
<details><summary>Answer</summary>It gives independent, reproducible streams per replication and purpose, as in NumPy's parallel-streams docs.</details>

2. Why is "position" used instead of on-hand stock for the reorder test?
<details><summary>Answer</summary>Otherwise the shop reorders again while a delivery is already on its way.</details>

3. When would CRN not help?
<details><summary>Answer</summary>When the two outputs are not positively correlated — e.g. streams desynchronise or policies respond oppositely to the same inputs.</details>
