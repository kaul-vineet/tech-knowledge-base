# Co-simulation with FMI: master algorithm and communication step — explained

## The intuition

Big simulations are assembled from parts built in different tools. FMI (Functional Mock-up Interface) is the standard contract: each part, a Functional Mock-up Unit, exposes `instantiate`, `setup_experiment`, initialisation mode, `set_real` / `get_real` by value reference, `do_step(t, h)` and `terminate`. Each unit integrates its own equations internally. A **master algorithm** owns time: at every communication point it reads outputs, passes them as inputs, and tells every unit to advance by h.

Between communication points, inputs are frozen (zero-order hold). That is the price of modularity: the thermostat sees a temperature that is up to h seconds old, and the room sees a heater setting that was decided h seconds ago. A delay inside a feedback loop can make a perfectly good controller oscillate. For this loop — room time constant τ = 1 h, loop gain K = Kp × Q_max × R = 0.5 × 24 = 12 — a Jacobi master is stable only if (1 − e^(−h/τ))·K < 1, i.e. h < 313 s.

Analogy: two microservices syncing state by polling every h seconds — poll slowly enough and they chase each other's stale values.
Where the analogy breaks: here the instability threshold is computable from the physics before you run anything.

```
t ──> master (Jacobi):
        T  = room.get_real(T)        heater = ctrl.get_real(heater)
        ctrl.set_real(T)              room.set_real(heater)
        room.do_step(t, h)  [RK4, ≤ 60 s substeps]   ctrl.do_step(t, h)  [PI, anti-windup]
        log {"t_min","h_s","T_room","heater"} ──> cosim_log_<h>s.jsonl
      t += h
```

The one thing to remember: the communication step is part of the model — inside a feedback loop, it sets stability, not just speed.

## Walkthrough: what actually happens when you run it

1. **You run** `python cosim.py 60`.
   **What happens inside:** `run(60)` initialises both units, then performs 360 exchanges over 6 h. The room integrates with one RK4 substep per exchange; the PI controller updates its integral only while the heater is not saturated.
   **What you see:**
   ```
   {"h_s": 60, "last_hour_swing_C": 0.0, "last_hour_mean_error_C": 0.0, "heater_flips": 1}
     cosim_log_60s.jsonl: 360 lines; last 4:
       {"t_min": 359.0, "h_s": 60, "T_room": 21.0, "heater": 0.667}
   ```
   **What it means:** the room sits on the 21 C setpoint with the heater at 0.667 — exactly what balances losses to 5 C outside: (21 − 5)/24. One flip is the initial switch-on.

## Failure lab: a 15-minute communication step

1. **Inject.** The shipped `COMM_STEP_S = 900` "to run faster".
2. **Symptom.** **You run** `python cosim.py`.
   **What you see:**
   ```
   {"h_s": 900, "last_hour_swing_C": 6.78, "last_hour_mean_error_C": 2.72, "heater_flips": 9}
       {"t_min": 300.0, "h_s": 900, "T_room": 22.755, "heater": 0.049}
       {"t_min": 315.0, "h_s": 900, "T_room": 19.086, "heater": 0.0}
       {"t_min": 330.0, "h_s": 900, "T_room": 15.97, "heater": 0.996}
       {"t_min": 345.0, "h_s": 900, "T_room": 18.834, "heater": 1.0}
   ```
   **What it means:** the heater alternates ~0 / ~1 every 15 minutes — it looks broken, but both units are correct.
3. **Diagnose.** Read the log: the heater decision at t is based on T at t and held for 900 s, during which the room moves (1 − e^(−0.25))·12 ≈ 2.65 times the correction needed — every step overshoots. **You run** `BUILD_TARGET=mine python -m unittest test_build_task -v` → **What you see:** `FAILED (failures=2)` (step below the bound; default run settles).
4. **Fix.** Set `COMM_STEP_S` below 313 s (the solution uses 60).
5. **Proof.** **You run** `python try_it.py`.
   **What you see:**
   ```
   h=240 s: last-hour swing 0.01 C, heater flips 1
   h=300 s: last-hour swing 1.57 C, heater flips 1
   h=360 s: last-hour swing 2.42 C, heater flips 10
   Gauss-Seidel h=450 s: {'h_s': 450, 'last_hour_swing_C': 0.0, 'last_hour_mean_error_C': 0.0, 'heater_flips': 0}
   Gauss-Seidel h=900 s: {'h_s': 900, 'last_hour_swing_C': 2.81, 'last_hour_mean_error_C': 0.92, 'heater_flips': 14}
   ```
   **What it means:** the boundary is where theory puts it: 240 s settles, 300 s (close to 313) rings slowly, 360 s oscillates. Gauss–Seidel ordering — step the room first, give the thermostat the *fresh* temperature — removes one delay and is stable at 450 s, but not at 900 s.

2. **Real FMU.** Expected (not run here): export `RoomThermal.mo` with OpenModelica and run `python fmpy_cosim.py RoomThermal.fmu`; the lesson expects h = 60 to settle like the Python room. FMPy and OpenModelica are not installed here.

## Common confusions

**Q:** A bigger communication step only costs accuracy. — **A:** At 900 s it creates a 6.78 C oscillation.

**Q:** The oscillation means the PI gains are wrong. — **A:** Same gains at 60 s give swing 0.0.

**Q:** Gauss–Seidel fixes it for any step. — **A:** It moves the bound (stable at 450 s) but still fails at 900 s.

## Check your understanding

1. Why does the room substep at ≤ 60 s internally yet still oscillate at h = 900?
<details><summary>Answer</summary>Its internal accuracy is fine; the instability comes from the controller's input being frozen for 900 s.</details>

2. Where does 313 s come from?
<details><summary>Answer</summary>Solve (1 − e^(−h/3600))·12 = 1: h = 3600·ln(12/11) ≈ 313 s.</details>

3. Why log one JSON line per exchange?
<details><summary>Answer</summary>Swing, mean error and flips can be computed from the log, so a monitor can detect the fault without rerunning.</details>
