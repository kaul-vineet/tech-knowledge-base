# CRDTs for local-first collaboration: counters, OR-Set, LWW-Register and property tests — explained

## The intuition
A shopping list on a phone and a laptop is edited offline, then synced over a channel that loses, reorders and repeats messages; no server decides. In a CRDT, `merge(a, b)` computes the smallest state containing both — like a set union. If merge is commutative, associative and idempotent, replicas that saw the same updates end equal, however messages travelled.

Each type encodes a conflict policy. A G-Counter keeps one slot per replica merged with `max`, so concurrent increments survive. An OR-Set tags each add; a remove tombstones only tags it has *seen*, so a concurrent re-add wins. An LWW-Register keeps the highest timestamp — and needs a tie rule, or replicas disagree forever. A property-based tester finds that bug.

**Analogy:** two people tick items on paper copies of a list and later combine them by "union of everything either wrote"; it works whoever combines first or how often.
Where the analogy breaks: removals are not just crossing out — the OR-Set must remember *which* add was removed, so its state grows (tryIt 2).

```
replica r0 state ─┐
                  ├─ merge = join (commutative, associative, idempotent) ─▶ same state everywhere
replica r1 state ─┘
property tester: 500 seeded histories × (laws + convergence) ─▶ fail? ─▶ shrink to minimal steps
```

The one thing to remember: if merge is a join, replicas converge under any delivery order and duplicates — test the laws, not examples.

## Walkthrough: what actually happens when you run it
1. **You run** `python crdts.py`
   **What happens inside:** part 1 replays the phone/laptop story. Part 2 generates 500 seeded histories per type (3 replicas, 20% duplicated syncs), checks each law and convergence, and shrinks any failure step by step. Part 3 compares a last-writer-wins number with a PN-Counter.
   **What you see:**
   ```
   1) phone+laptop: ['eggs', 'milk'] == ['eggs', 'milk']: True
      OR-Set        {"commutative": "500/500", "associative": "500/500", "idempotent": "500/500", "converged": "500/500"}
      LWW-Register  {"commutative": "407/500", "associative": "500/500", "idempotent": "500/500", "converged": "386/500"}
                    shrunk counterexample: commutative fails after: r0.assign('r0', 'r0.9', 0); r1.assign('r1', 'r1.10', 0)
   3) like-counter, truth 140: LWW number [81, 81, 81] (concurrent adds lost), PN-Counter [140, 140, 140]; sync bytes LWW 15, PN 76
   ```
   **What it means:** milk survived the concurrent remove. Counters and OR-Set obey every law. LWW-Register fails commutativity in 93 histories, and the shrinker reduced the failure to two writes with the same timestamp. The plain number *converged* (81 everywhere) but to the wrong answer — convergence alone is not correctness. Matches the README.

2. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: G-Counter with sum-merge: {'commutative': '500/500', 'associative': '500/500', 'idempotent': '7/500'}, converged 0/500
            idempotent fails after: r0.inc('r0', 1)
   tryIt 2:   10 add/remove cycles -> value ['milk'], tombstones 10, state 311 bytes
   tryIt 2: 1000 add/remove cycles -> value ['milk'], tombstones 1000, state 31813 bytes
   ```
   **What it means:** summing instead of `max` double-counts every repeated sync; one increment is enough to show it. The OR-Set's value stays one item while its state grows ~100× — the price of add-wins.

### Failure lab: an LWW tie that never resolves
1. **Inject:** seeded histories where r0 and r1 assign concurrently at the same Lamport timestamp; duplicated syncs.
2. **Symptom:** step 1 — 407/500 commutative, 386/500 converged.
3. **Diagnose:** `merge` keeps *my* value when `other.ts == self.ts`, so r0 keeps r0's value and r1 keeps r1's — forever.
4. **Fix (build task):** compare `(ts, replica)` tuples so every replica breaks ties the same way.
5. **Proof** — **What you see** (`python solution_crdts.py`, then `test_fitness` on the unchanged file):
   ```
      LWW-Register  {"commutative": "500/500", "associative": "500/500", "idempotent": "500/500", "converged": "500/500"}
   FAILED (failures=3)
   ```

### The decision
- **Options and evidence:** plain values with last writer wins (15 bytes per sync, like-counter ends at 81 of 140); state-based CRDTs from this lab (all laws 500/500 after the tie-break, PN-Counter exact at 140 for 76 bytes); Automerge as a library — Expected (not run here): npm is unreachable in this sandbox; per the Automerge docs it converges and keeps both concurrent title values visible as conflicts.
- **Why ADR-018 chose what it did:** the constraints are "no lost increments", "add wins" and "converge after anti-entropy". Plain values fail the first; the OR-Set, PN-Counter and tie-broken LWW-Register meet all three with small payloads. Automerge is the upgrade path once the document grows beyond a few fields.
- **How the fitness function keeps it true:** `test_fitness.py` re-runs laws and convergence for the chosen types on seeds 18–20 and checks the cart session stays ≤ 4,096 bytes per sync. Reference: `OK`; the unchanged lesson file fails for LWW-Register on all three seeds. Anyone who reintroduces a one-sided comparison breaks the build.

## Common confusions
**Q:** All replicas agree, so the result is right. — **A:** The LWW number agreed on 81 while the truth was 140.

**Q:** Timestamps make LWW deterministic. — **A:** Equal timestamps happen with concurrent writes; without a tie-break, 114 of 500 histories diverged.

**Q:** Example tests are enough. — **A:** The bug needs two same-timestamp writes; random histories plus shrinking found it in seconds.
