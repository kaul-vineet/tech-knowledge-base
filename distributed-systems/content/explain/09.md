# Sharding with consistent hashing: virtual nodes, key movement, hot keys — explained

## The intuition
To spread keys over nodes, the obvious rule is `hash(key) % N`. It breaks when N changes: going from 4 to 5 nodes changes the remainder for most keys, so most data moves and caches go cold at once.

Consistent hashing asks "who is next on the circle?" instead. Nodes and keys hash onto one circle; a key belongs to the first node point clockwise. A new node takes over only the arcs just before its points. Give each node many points (virtual nodes) so arcs average out — and remember no hash spreads one very popular key.

**Analogy:** guests at a round table sit with the next host clockwise; a new host only takes the guests just before them.
Where the analogy breaks: the table has 2^64 seats and each host sits in 100 places at once.

```
key ─ h() = md5[:8] ─▶ position p
sorted points ... A#17  B#3  C#40 ...
bisect(points, p) % len ─▶ first point clockwise ─▶ owner = B
add("E"): E#0..E#99 inserted → only keys just before them move
```

The one thing to remember: a ring moves about 1/N of the keys on a membership change; modulo moves almost all.

## Walkthrough: what actually happens when you run it
1. **You run** `python ring.py`
   **What happens inside:** `add()` inserts 100 `node#i` positions per node (`bisect.insort`); `node_for()` binary-searches and wraps. `moved()` compares owners for 10,000 keys before and after; `imbalance()` = busiest / average.
   **What you see:**
   ```
   add E   : hash % N moves 80.3% of 10,000 keys; ring moves 18.9% (ideal 1/5 = 20.0%)
   remove D: ring moves 24.5%; only D's keys moved: True
   vnodes=1  : keys per node {'A': 309, 'B': 124, 'C': 4077, 'D': 5490} imbalance 2.20
   vnodes=100: keys per node {'A': 2577, 'B': 2466, 'C': 2509, 'D': 2448} imbalance 1.03
   hot key : user:42 lives on B; requests per node {'A': 20790, 'B': 39738, 'C': 19976, 'D': 19496} imbalance 1.59
   ```
   **What it means:** modulo moved ~4/5; the ring ~1/5. Removing D moved only D's keys. One point per node gives random, very unequal arcs; 100 points average them. The hot key adds 20% of all traffic to B. Matches the README.

2. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: vnodes=1   add E -> moves 17.0%, taken from {'D': 1695}
   tryIt 1: vnodes=100 add E -> moves 18.9%, taken from {'A': 488, 'B': 227, 'C': 540, 'D': 634}
   tryIt 2: hot key split 8 ways -> requests per node {'A': 25565, 'B': 27462, 'C': 24940, 'D': 22033} imbalance 1.10
   ```
   **What it means:** with 1 vnode a newcomer relieves one neighbour; with 100 it takes a little from everyone. Splitting `user:42` into 8 sub-keys spreads it: 1.59 → 1.10.

## Common confusions
**Q:** Python's `hash()` works. — **A:** It is salted per process, so clients would build different rings; `h()` uses md5.

**Q:** More nodes fix a hot key. — **A:** `user:42` still maps to one node; split or replicate it (tryIt 2).

**Q:** The ring moves exactly 1/N. — **A:** About 1/N (18.9% here), depending on where E's points land.
