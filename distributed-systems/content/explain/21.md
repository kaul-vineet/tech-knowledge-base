# Verifying correctness: model checking and linearizability checking — explained

## The intuition
Tests check the scenarios you thought of; distributed bugs live in interleavings you did not, like a restart between two messages. Two tools search them systematically.

A **model checker** explores a small *model* of the protocol breadth-first: every next step from every reachable state (3 nodes, terms ≤ 2), checking an invariant such as "at most one leader per term". Breadth-first means the first violation comes with the *shortest* trace — a replayable bug report. TLC does this for TLA+; `bfs()` is a small Python equivalent.

A **linearizability checker** works on the real implementation: record each operation's invoke and return time, then search for one order respecting real time and register semantics. Memoisation (as in Porcupine) keeps thousands of operations to milliseconds.

**Analogy:** a chess engine trying every line a few moves deep, and a referee checking whether any legal move order explains the recorded game.
Where the analogy breaks: a model is a simplification; a clean model proves nothing about details it leaves out.

```
model (states, next steps, invariants) ─▶ BFS queue ─▶ new state? check ElectionSafety, VoteOnce
                                                        violation ─▶ parent links ─▶ shortest trace
recorded history (invoke/ok + times) ─▶ lincheck: memoised search ─▶ True | False + op it cannot place
```

The one thing to remember: model-check the design for every interleaving within bounds, and history-check the implementation for what clients actually saw.

## Walkthrough: what actually happens when you run it
1. **You run** `python modelcheck.py`
   **What happens inside:** `PERSIST_VOTE = False` encodes the pull request's claim. `bfs()` pops states, generates every enabled action (timeout, vote, become leader, restart), deduplicates with `seen`, and checks `ElectionSafety`; `simulate()` takes random walks.
   **What you see:**
   ```
   BFS: 4519 distinct states explored, invariant ElectionSafety violated
     2. n1 votes for n0 in term 1
     3. n0 becomes leader of term 1
     5. n1 restarts (votedFor forgotten)
     6. n1 votes for n2 in term 1
     7. n2 becomes leader of term 1
   random simulation: bug hit in 16/1000 walks of <= 30 steps (shortest 8 steps)
   ```
   **What it means:** n1 voted twice in term 1 because it forgot its first vote: two majorities, two leaders. Three example tests passed; random walks found it 1.6% of the time; BFS found it every time, shortest first. Matches the README.

2. **You run** `python lincheck.py`
   **What you see:**
   ```
   1) Porcupine README histories: True, False (README says true, false)
   2) lab 17 R=2 W=2 write-back=False: 2273 ops, linearizable False, 48590 steps, 63 ms
      longest partial linearization 433 ops; cannot place r6 read -> 28 [1738.9, 1799.6] ms
   2) lab 17 R=2 W=2 write-back=True: 1947 ops, linearizable True, 2890 steps, 45 ms
   ```
   **What it means:** the checker reproduces Porcupine's documented examples, then pinpoints lesson 17's inversion — r6 read 28 after 29 was visible — in 63 ms over 2273 operations.

3. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1:  41 ops: memoised False in 4.49 ms, exhaustive (L300) False in 203.5 ms
   tryIt 2: MAX_TERM=2: 1853 distinct states, 59 ms, violation: none
   tryIt 2: MAX_TERM=3: 29221 distinct states, 946 ms, violation: none
   ```
   **What it means:** memoisation keeps history checks cheap as they grow; one more term multiplies the model's states ~16×. Bounds are a budget you choose. Times vary by machine (README differs slightly).

### Failure lab: a voting bug three tests miss
1. **Inject:** `PERSIST_VOTE = False`.
2. **Symptom:** example tests pass; BFS reports the 7-step trace above.
3. **Diagnose:** step 5 resets `votedFor`; step 6 grants a second vote in the same term.
4. **Fix (build task):** persist the vote, and add a `VoteOnce` invariant over a ghost log of (term, voter, candidate) — it catches the root cause earlier than the symptom.
5. **Proof** — **What you see** (`python solution_modelcheck.py`; the solution with the bug re-introduced; `test_fitness` on the unchanged file):
   ```
   BFS: 1853 distinct states explored, invariant none violated
   ('VoteOnce', ['n0 times out -> candidate, term 1', 'n1 times out -> candidate, term 1', 'n0 restarts (votedFor forgotten)', 'n0 votes for n1 in term 1'], 513, 3)
   FAILED (failures=1)
   ```
   With the stronger invariant the same bug surfaces in 4 steps after 513 states instead of 7.

TLA+ spec (`Election.tla`) — Expected (not run here): TLC needs Java and `tla2tools.jar`, not installed; per the TLA+ docs, TLC reports the invariant violation with an error trace of states, matching the BFS trace in shape.

### The decision
- **Options and evidence:** example tests (3 pass on the buggy protocol); random simulation (16 of 1,000 walks); exhaustive BFS + history checking (shortest trace after 4519 states; fixed model 1853 states clean; lab 17's bug pinpointed).
- **Why ADR-021 chose both checkers:** the brief asks for replayable counterexamples before merge (BFS), exhaustive coverage within bounds (BFS, not random), and fast checks on real implementation histories (memoised lincheck) — in the standard library on every OS.
- **How the fitness function keeps it true:** `test_fitness.py` requires `bfs()` to find no violation over > 1,000 states and `lincheck.check()` to pass lab 17's write-back histories on seeds 11–13. Reference: `OK`; the unchanged lesson model fails. A future "simplification" of vote persistence fails CI with a trace attached.

## Common confusions
**Q:** Random testing finds the same bugs. — **A:** 16 of 1,000 walks, never the shortest trace.

**Q:** A clean model check proves the code correct. — **A:** It proves the *model* within bounds; lincheck covers the implementation.

**Q:** History checking is too slow. — **A:** Memoised, 2273 operations took 63 ms.
