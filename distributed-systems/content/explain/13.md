# Network partitions and fault injection: proxy toxics, split brain, fencing and linearizability checking — explained

## The intuition
Networks rarely fail cleanly: a node reaches the database but not the lock service. To the caller that is just a timeout, and "up / down" code produces two leaders.

A proxy on each link can make it down, slow or lossy (Toxiproxy's vocabulary). The lab cuts n1 off from the lease store only; n1 treats renew timeouts as "still mine" while n2 takes over. Then it checks the recorded client history: could *one* copy of the data have produced these answers? That is linearizability checking, the core of Jepsen.

**Analogy:** two managers each think they run the shop because one missed the memo; only a log of who-said-what-when proves it.
Where the analogy breaks: a partitioned node cannot reach the one place that knows.

```
           lease store                       storage (register)
   n1 ──X── (partition t=2..9)   n1 ── slow 0.3 ──▶ write 3 (token 1)
   n2 ──────▶ acquires token 2   n2 ─────────────▶ write 2 (token 2)
client history ─▶ checker.check_register ─▶ linearizable: True | False + stale read
```

The one thing to remember: a timeout is not an answer; fencing and a history checker expose split brain.

## Walkthrough: what actually happens when you run it
1. **You run** `python partition.py` (happy path first, then the partition)
   **What happens inside:** `run(OPS, FAULTS)` replays scripted operations and proxy changes. `Proxy.call` raises `Timeout` on a down link; `Node.step` catches it and *keeps its token*. Reads come from the leader's local `self.cache`.
   **What you see:**
   ```
   happy path (no faults): leaders per tick n1 n1 n1 n1 n1 n1 n1 n1 n1 n1 n1
     linearizable: True
   t=2 fault: partition n1 | lease store; latency 0.3 n1->storage
   t=2 n1 renew timed out (n1->lease) -> still thinks it leads
   t=4 n2 acquired the lease, token 2, loaded value 1
   t=9 n1 renew refused -> steps down
   leaders per tick: 0:n1 1:n1 2:n1 3:n1 4:n1+n2 5:n1+n2 6:n1+n2 7:n1+n2 8:n1+n2 9:n2 10:n2
   ```
   **What it means:** n1's last good renewal was t=1, so n2 could acquire at t=4 (TTL 3). Five ticks with two leaders; only the refused renewal after the heal made n1 step down.

2. **You read** the history and verdict printed by the same run
   **What happens inside:** `check_register` searches orders of successful operations that respect real time and register semantics (a read returns the latest write).
   **What you see:**
   ```
     {"time": 7.8, "process": "c1", "type": "ok", "f": "write", "value": 3, "node": "n1"}
     {"time": 8.5, "process": "c2", "type": "ok", "f": "read", "value": 2, "node": "n2"}
   linearizable: False
     stale read: c2 read -> 2 via n2 [8, 8.5], but c1 write 3 via n1 [7, 7.8] had already finished
   ```
   **What it means:** write 3 ended before the read began, so it must come first — yet the read saw 2. Matches the README.

3. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: seed 13: n2 takes the lease at t=3, ticks with two leaders: 0
   tryIt 1: seed 14: n2 takes the lease at t=5, ticks with two leaders: 1
   tryIt 2: without fencing: c1 read via n1 -> 1, linearizable: False
   tryIt 2: with fencing: c1 read via n1 -> 1, linearizable: False
   ```
   **What it means:** partial loss causes split brain only sometimes. Fencing guards writes, not local reads.

### Failure lab: split brain writes, fixed with fencing
1. **Inject:** `FAULTS` at t=2 cuts n1 from the lease store and adds 0.3 latency to n1→storage; heal at t=9.
2. **Symptom:** two leaders for t=4–8 and `linearizable: False` with the stale read above.
3. **Diagnose:** `Storage.write(token, value)` ignores the token, so token 1 overwrites token 2's value.
4. **Fix (build task):** storage keeps `max_token` and returns `rejected: token X < Y`; `Node.handle` sets `token = None` and fails the client operation.
5. **Proof** — **What you see** (`python solution_partition.py`, then `BUILD_TARGET=mine` tests on the unchanged file):
   ```
   t=7 n1 write 3 rejected: token 1 < 2 -> steps down
   leaders per tick: 0:n1 1:n1 2:n1 3:n1 4:n1+n2 5:n1+n2 6:n1+n2 7:n1+n2 8:n2 9:n2 10:n2
   linearizable: True
   FAILED (failures=3)
   ```
   Fenced, n1 steps down at t=7 and the history is linearizable; the unchanged file fails all build-task tests.

Agent assist (`--fake`): the model blames `n2` and `c1 write 1`; `facts()` computes `n1` and `c1 write 3` and marks both WRONG.

## Common confusions
**Q:** Final state was fine, so the run was fine. — **A:** The *history* had a read no order explains.

**Q:** A renew timeout means "still leader". — **A:** It means "unknown"; n2 got token 2 at t=4.

**Q:** Fencing fixes split brain. — **A:** It fixes stale writes; tryIt 2 still reads 1 via n1 with fencing on.
