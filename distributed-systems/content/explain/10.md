# Caching and invalidation: cache-aside, TTL, stale reads, thundering herd — explained

## The intuition
A cache is a nearby copy so you do not pay for the slow original every time; the price is that the copy can be wrong. Two questions decide every design: how long may the copy be wrong, and what happens when there is no copy?

Cache-aside answers the first with a TTL (the copy dies after N seconds) plus invalidation (the writer deletes it). The TTL is the safety net: if a delete is lost or a race re-inserts an old value, the error still ends. The second question is the thundering herd: when a hot key is missing, every concurrent request misses and hits the database. Coalescing lets one request load while the rest wait.

**Analogy:** a sticky note copied from the master file; if fifty people find no note, all fifty walk to the cabinet.
Where the analogy breaks: people see each other walking; threads do not, unless you build that signal.

```
get_price: cache.get ── hit ──▶ value
              │ miss (absent or clock() >= expires)
              ▼
           db.read (0.2 s) ─▶ cache.set(value, now+TTL)
set_price: db.write ─▶ cache.delete(sku)
```

The one thing to remember: the TTL bounds staleness; invalidation and coalescing make the normal case fresh and cheap.

## Walkthrough: what actually happens when you run it
1. **You run** `python cache.py`
   **What happens inside:** `TTLCache.get` returns `None` once `clock() >= expires` — a check on read, no expiry thread. The service writes 7 without invalidation and reads at simulated t = 0, 10, 29, 30. Then it invalidates on write, deletes the key, and releases 50 threads through a `Barrier` so all check the cache before the first 0.2 s read returns.
   **What you see:**
   ```
   cache-aside  : [5, 5, 5] -> db reads 1 (1 miss, 2 hits)
   no invalidate: t=29s read 5 (STALE, db has 7)
   no invalidate: t=30s read 7 (fresh)
   invalidate   : t=100s write 9 -> read 9 (fresh)
   herd         : 50 concurrent reads of a cold key -> 50 db reads, values [9]
   ```
   **What it means:** the old price lived exactly one TTL. Delete-on-write made the next read fresh. The herd made 50 identical slow queries for one value. Matches the README.

2. **You run** `python try_it.py`
   **What happens inside:** tryIt 2 replays a race: reader A reads 5 and stalls, writer B writes 11 and deletes, A resumes and caches 5.
   **What you see:**
   ```
   tryIt 1: TTL 30 s -> 30 stale reads of 60, 2 db reads
   tryIt 1: TTL  5 s -> 5 stale reads of 60, 12 db reads
   tryIt 2: race -> db has 11, cache serves 5 until t=30 (TTL)
   ```
   **What it means:** TTL is a dial between staleness and load. Invalidation alone did not save tryIt 2; the TTL ends the error.

3. **You run** `herd()` against the reference `solution_cache.PriceService` (in-flight `Event` per key)
   **What you see:**
   ```
   coalesced herd: (1, [5])
   ```
   **What it means:** one database read served all 50 callers.

## Common confusions
**Q:** Update the cache on write instead of deleting. — **A:** Two writers can finish out of order and leave the older value; delete is idempotent.

**Q:** With invalidation, drop the TTL. — **A:** tryIt 2 re-inserted 5 after the delete.

**Q:** Herds only matter at huge scale. — **A:** 50 threads already made 50 db reads.
