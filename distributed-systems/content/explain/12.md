# Replicated log with Raft (simplified): terms, commit index, re-election, election restriction — explained

## The intuition
Three servers must keep one ordered log of writes, survive a crash, and never forget a confirmed write. Raft's leader appends each command and copies it; once a majority (2 of 3) stores an entry it is *committed*. If the leader goes silent, the first follower to time out starts an election for a higher *term*.

Safety rests on overlap: any two majorities share a server, so some voter for a new leader holds every committed entry. That helps only if voters refuse candidates with less up-to-date logs. Drop that check and a stale server can win and overwrite committed writes — the failure lab.

**Analogy:** a chair keeps minutes; a decision counts once most members copied it; a new chair must be as up to date as each voter.
Where the analogy breaks: members only learn through messages that may be late or lost.

```
term 1: n1 leader [1:x=1 1:x=2 1:x=3] ─AppendEntries(prev_index, prev_term)─▶ n2, n3
        stored on a majority + entry from current term ─▶ commit index 3
n1 crash ─▶ timers fire ─▶ RequestVote(term+1, last_term, last_index)
grant iff one vote per term AND (cand last_term, last_index) >= mine   ◀─ build task
```

The one thing to remember: majorities overlap, and the election restriction makes that overlap carry committed entries into every new leader.

## Walkthrough: what actually happens when you run it
1. **You run** `python raft.py`
   **What happens inside:** three `Node`s on a deterministic simulated network; `reset_timer()` draws seeded 10–19 tick timeouts. n1's fires first; n2's vote makes 2 of 3.
   **What you see:**
   ```
   t=17 n1 becomes leader for term 1 with votes ['n1', 'n2']
   1) happy path: 3 entries replicated and committed
      n2 term 1 follower  log [1:x=1 1:x=2 1:x=3] commit 3
   ```
   **What it means:** `1:x=2` is (term, command). The leader committed index 3 when `1 + sum(match >= 3)` reached a majority; followers learned it from the next AppendEntries.

2. **You keep reading** parts 2 and 3 (n1 crashed at t=23)
   **What happens inside:** both followers time out in the same tick and vote for themselves — a split vote; new random timeouts break the tie.
   **What you see:**
   ```
   t=40 n2 starts election for term 2 (log 1:x=1 1:x=2 1:x=3)
   t=40 n3 starts election for term 2 (log 1:x=1 1:x=2 1:x=3)
   t=57 n3 becomes leader for term 3 with votes ['n2', 'n3']
      n1 term 3 follower  log [1:x=1 1:x=2 1:x=3 3:x=4] commit 4
   safety violations: 0
   ```
   **What it means:** the split vote cost time (availability), not safety. Restarted n1 caught up. Matches the README.

3. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: followers down -> n1 log has 2 entries, commit index stays 1 (x=5 appended, never committed)
   tryIt 2: raft.py (no log check): committed entries lost in 11 of 20 seeds
   tryIt 2: solution_raft.py (log check): committed entries lost in 0 of 20 seeds
   ```
   **What it means:** no majority, no commit — clients see timeouts. The bug needs particular timing, so happy-path tests miss it.

### Failure lab: a stale follower wins and erases committed writes
1. **Inject:** `stale_leader_scenario()` keeps n3 down while x=1 and x=2 commit on n1+n2, crashes n1, restarts n3 empty and forces its timer first.
2. **Symptom** — **What you see** (part 4 of `python raft.py`):
   ```
   t=26 n3 becomes leader for term 2 with votes ['n2', 'n3']
      n2 term 2 follower  log [2:x=9] commit 2
   safety violations: 3
      t=27 LOST committed entry 1 (1:x=1): n2 now has 2:x=9 there
   ```
3. **Diagnose:** n2 voted on term alone (`granted = m['term'] == self.term and self.voted_for in (None, src)`), then deleted its entries to match n3. `SafetyChecker` flags any change to a committed index.
4. **Fix:** grant only if `(m['last_term'], m['last_index']) >= self.last()` — tuple order compares last term, then length (Raft paper, section 5.4.1).
5. **Proof** — **What you see** (`python solution_raft.py`, failure-lab part):
   ```
   t=25 n2 denies n3: candidate log (term, index) (0, 0) < mine (1, 2)
   t=35 n2 becomes leader for term 3 with votes ['n2', 'n3']
      n3 term 3 follower  log [1:x=1 1:x=2 3:x=9] commit 3
   safety violations: 0
   ```
   `BUILD_TARGET=mine` against unchanged `raft.py` gave `FAILED (failures=3)`; against the solution, `OK`.

## Common confusions
**Q:** A higher term means a more up-to-date candidate. — **A:** n3 asked for term 2 with log `(0, 0)`; a term is a clock, not data.

**Q:** Appended means committed. — **A:** tryIt 1: x=5 is in n1's log, commit index stays 1.

**Q:** Random timeouts make Raft safe. — **A:** They only make split votes rare; safety is the vote check.
