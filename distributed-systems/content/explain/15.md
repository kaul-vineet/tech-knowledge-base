# Distributed tracing with W3C traceparent: propagation, spans as JSON lines, critical path — explained

## The intuition
A slow checkout crosses three services, and each one's logs say "my part was fine". A trace joins one request's work into one timeline of *spans* (id, parent id, shared *trace id*). The context travels in `traceparent: 00-<trace id>-<parent span id>-<flags>`.

Each service keeps the incoming trace id and sends *its own* span id as the next parent. One call site that forgets splits the request into two traces, and the caller's span then looks slow because the callee's work is invisible. Hence: propagate in middleware.

**Analogy:** a tracking number every depot must copy onto the next label.
Where the analogy breaks: a request without a header silently starts a fresh trace.

```
gateway /checkout   trace 8575.., span 0942 (root)
  └─ orders /create        parent 0942, span e9bb
       └─ payments /authorize   parent e9bb   ◀─ raw call drops traceparent → new trace 0e11..
  └─ payments /receipt     parent 0942
spans (JSON lines) ─▶ analyze: group by trace id, link parents, walk the critical path
```

The one thing to remember: continue the incoming trace id, pass your own span id on, and do it in middleware so no hop can forget.

## Walkthrough: what actually happens when you run it
1. **You run** `python tracing.py`
   **What happens inside:** server middleware parses `traceparent` (valid → continue; missing/invalid → new trace); each request writes a JSON span line. Orders calls payments with a raw `call` and no header — the injected fault.
   **What you see:**
   ```
     {"trace_id": "0e11160004524a7c3d2bd371fc80be13", "span_id": "ce0c3f08e12656f1", "parent_id": null, "service": "payments", "name": "GET /authorize", "start": 26.7, "end": 86.9}
   trace 85750621..: 3 span(s): gateway GET /checkout, orders GET /create, payments GET /receipt
   trace 0e111600..: 1 span(s): payments GET /authorize
   critical path: gateway GET /checkout self 7 ms | orders GET /create self 82 ms | payments GET /receipt self 10 ms
   trace problems:
     2 trace ids for one request (a hop did not propagate traceparent)
   ```
   **What it means:** `/authorize` has `parent_id: null` — an orphan root. The critical path blames orders with 82 ms self time, though ~60 ms is the hidden payments call. Ids match the README (seeded); times vary per run (README: 88 ms).

2. **You run** `python try_it.py`
   **What happens inside:** tryIt 1 sends the W3C example header, the same in uppercase, and an all-zero trace id. tryIt 2 slows `/authorize` from 60 to 180 ms of work in the fixed version.
   **What you see:**
   ```
   tryIt 1: 00-4bf92f3577b34da6a... -> gateway trace 4bf92f3577b3.., parent 00f067aa0ba902b7 | traces: 1
   tryIt 1: 00-4BF92F3577B34DA6A... -> gateway trace 0e1116000452.., parent None | traces: 1
   tryIt 1: 00-00000000000000000... -> gateway trace 77616364568c.., parent None | traces: 1
   tryIt 2: authorize work 60 ms -> its span is 46% of the checkout, on the critical path: True
   tryIt 2: authorize work 180 ms -> its span is 78% of the checkout, on the critical path: True
   ```
   **What it means:** the spec requires lowercase hex and non-zero ids, so both bad headers restart the trace. Percentages vary by run (README: 55% and 76%).

### Failure lab: one hop drops the header
1. **Inject:** orders → payments uses `helpers.call` directly, without `traceparent`.
2. **Symptom:** step 1 — two trace ids, an orphan `/authorize`, inflated self time on orders.
3. **Diagnose:** `analyze` flags "extra root span: payments GET /authorize started a new trace"; the orphan's start/end (26.7–86.9) sit inside orders' span.
4. **Fix (build task):** wrap `helpers.call` as client middleware that injects `00-<trace id>-<current span id>-<flags>` whenever a span is current.
5. **Proof** — **What you see** (`python solution_tracing.py`, then `BUILD_TARGET=mine` tests on the unchanged file):
   ```
   trace 85750621..: 4 span(s): gateway GET /checkout, orders GET /create, payments GET /authorize, payments GET /receipt
   critical path: gateway GET /checkout self 16 ms | orders GET /create self 24 ms | payments GET /authorize self 63 ms | payments GET /receipt self 10 ms
   trace problems:
     none
   FAILED (failures=3)
   ```
   One trace; the payments time now sits on `/authorize`. The unchanged file still fails the build-task tests.

OpenTelemetry cross-check — Expected (not run here): the SDK is not installed; per the OpenTelemetry docs its default propagator writes the same W3C header, and `otel_equivalent.py` should print `otel equivalent OK` in CI.

## Common confusions
**Q:** Each service should start its own trace. — **A:** Then one request becomes several traces (step 1).

**Q:** The slowest-looking span is the culprit. — **A:** Only if propagation is complete; orders' 82 ms was mostly payments.

**Q:** Accept any header that looks close. — **A:** Uppercase and all-zero ids are invalid; restarting is correct (count it).
