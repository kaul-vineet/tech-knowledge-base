# At-least-once messaging: ack, visibility timeout, redelivery, dead letters — explained

## The intuition
If a broker deleted a message the instant a worker received it, a worker crash would lose it. So brokers lend messages instead: receiving hides the message for a while (visibility timeout); an ack deletes it; no ack and it reappears for someone else.

That never loses work, but it guarantees duplicates: the worker may have charged the card and crashed one line before the ack. The broker cannot tell "crashed before the work" from "after", so it redelivers either way. Hence consumers must be idempotent, and a message that crashes every worker must be parked in a dead-letter queue (DLQ).

**Analogy:** a library loan: the book leaves the shelf until the due date; overdue books return to the shelf; one damaged every time goes to the repair shelf.
Where the analogy breaks: the library knows who has the book; the broker only knows a timer ran out, and the borrower may still be working.

```
send ─▶ [queue] ── /receive ──▶ hidden until now+VISIBILITY, receipt id#n
           ▲                         │ /ack(receipt) ─▶ deleted
           └── visible again ◀───────┘ no ack
receives >= MAX_RECEIVES ─▶ DLQ
```

The one thing to remember: no ack means redelivery, so every effect before the ack can happen more than once.

## Walkthrough: what actually happens when you run it
1. **You run** `python broker.py`
   **What happens inside:** six orders plus `poison` are sent. Each simulated second, c1 and c2 call `/receive`; the broker skips messages whose `visible_at` is in the future, bumps `receives`, sets `visible_at = now + 3`, and issues receipt `m3#1`. `consume()` appends to `ledger` (the charge) *before* a seeded crash check, then acks.
   **What you see:**
   ```
   t=1 c1 m3=o3 receive #1: charged, CRASHED before ack
   t=2 c1 m5=o5 receive #1: charged, CRASHED before ack
   t=4 c1 m3=o3 receive #2: charged, acked
   t=5 c1 m5=o5 receive #2: charged, CRASHED before ack
   t=8 c1 m5=o5 receive #3: charged, acked
   t=9 c1 m7=poison receive #3: CRASHED while parsing
   ledger: 9 charges for 6 orders -> 3 duplicates
   dead-letter queue: ['poison']
   ```
   **What it means:** m3 crashed at t=1 and reappeared at 1 + 3 = t=4. o3 was charged twice, o5 three times: 3 duplicates, zero losses. The poison message used its 3 receives and moved to the DLQ. Matches the README.

2. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: VISIBILITY 3 s -> last delivery at t=9, 9 charges, DLQ ['poison']
   tryIt 1: VISIBILITY 10 s -> last delivery at t=23, 9 charges, DLQ ['poison']
   tryIt 2: MAX_RECEIVES 2 -> 12/30 runs dead-lettered a good order
   tryIt 2: MAX_RECEIVES 3 -> 5/30 runs dead-lettered a good order
   tryIt 2: MAX_RECEIVES 5 -> 2/30 runs dead-lettered a good order
   ```
   **What it means:** a longer timeout keeps the same duplicates and only delays recovery. A low DLQ limit parks unlucky good orders too.

3. **You run** `python -m unittest test_build_task` (reference: skip known ids, still ack)
   **What you see:**
   ```
   Ran 2 tests in 1.264s
   OK
   ```
   **What it means:** an id check before the charge leaves one ledger entry per order.

## Common confusions
**Q:** Ack first, then work. — **A:** Then a crash after the ack loses the order (at-most-once).

**Q:** A longer visibility timeout fixes duplicates. — **A:** tryIt 1: still 9 charges.

**Q:** The DLQ only holds bad payloads. — **A:** tryIt 2: good orders land there too; someone must watch it.
