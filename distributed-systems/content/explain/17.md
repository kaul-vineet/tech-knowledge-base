# Consistency models in practice: quorums (N, R, W), staleness and PACELC — explained

## The intuition
Three replicas hold each key. A write is done when W acknowledge; a read asks R and returns the newest version. Small R and W are fast but may miss the latest write; large ones wait for slow or distant replicas and stop answering when too many are unreachable. That is PACELC: during a **P**artition trade **A**vailability for **C**onsistency; **E**lse trade **L**atency for **C**onsistency, on every request.

R + W > N makes read and write quorums overlap, so a read cannot miss a *finished* write. But while a write is in flight, one read can see the new value and a later read the old one (an *inversion*) — not linearizable. The repair is a two-phase read (Attiya, Bar-Noy, Dolev): if replicas disagree, write the newest value back to W replicas before returning.

**Analogy:** asking two of three colleagues for the latest draft; if you hear "v29" and walk off, the next person may still hear "v28" unless you first hand v29 to a majority.
Where the analogy breaks: colleagues have no network tail; 5% of messages here take 20–80 ms extra, and that is where every anomaly lives.

```
client ─ write v ─▶ a@A  b@B  c@C(other region)   ack after W replies
client ─ read ────▶ ask all, wait for R replies ─▶ newest version
                        └─ write-back (build task): replies disagree and < W hold newest
                           ─▶ write newest to W replicas ─▶ then return it
measure per (R, W): p50/p99, stale%, read-your-writes, inversions, answered with C down
```

The one thing to remember: R + W > N stops stale reads of finished writes, not inversions; linearizability needs write-back (or a consensus log), and you pay for it in the tail.

### Failure lab: R + W > N is not linearizable
1. **Inject:** the seeded 5% slow-message tail delays some write messages while reads continue.
2. **Symptom:** 2 inversions at R=2 W=2; `decide()` finds nothing for config.
3. **Diagnose:** one read reached a replica with v29, a later read two with v28; quorums overlap *finished* writes only.
4. **Fix (build task):** in `finish_read`, if fewer than W replies hold the newest version, `self.write()` it to a quorum before answering.
5. **Proof** — **What you see** (`python solution_quorum.py`, then `test_fitness` on the unchanged file):
   ```
   3 2 2 +  True      12.7/124.5       67.5    0.0 (  0.0)         0          0  True          100.0%
   decide lock owner / config (linearizable): N=3 R=2 W=2 + read write-back
   FAILED (failures=8)
   ```

### The decision
- **Options and evidence:** R=1 W=1 (read p99 60.5 ms, 16.74% stale); R=2 W=2 (65.9 ms, 0% stale, 2 inversions); R=3 W=1 (linearizable, 0% answered with C down); R=2 W=2 + write-back (124.5 ms p99, 0 inversions, 100% answered).
- **Why ADR-017 chose what it did:** each use case takes the cheapest row meeting its numeric constraints. Cart badge tolerates 20% stale → R=1 W=1. Feature flags need ≤ 1% stale and read-your-writes → R=2 W=2. Lock owner/config needs linearizable *and* region-loss survival, which rules out R=3 W=1 → R=2 W=2 + write-back. The cost lands only in the tail: p50 stays at 12.7 ms because the extra round trip happens only when replicas disagree.
- **How the fitness function keeps it true:** `test_fitness.py` reruns config on seeds 11–20: 0 stale, 0 inversions, read p99 ≤ 150 ms, ≥ 99% answered with C down. Reference: `OK`; unchanged lesson file: 8 of 10 seeds had inversions. "Optimising" write-back away breaks the build.

## Common confusions
**Q:** R + W > N means strong consistency. — **A:** Row `3 2 2 -`: 0% stale, 2 inversions, linearizable False.

**Q:** Linearizability doubles latency. — **A:** p50 barely moved (12.5 → 12.7 ms); p99 paid (65.9 → 124.5 ms).

**Q:** One level per store. — **A:** The ADR picks three settings.
