# Foundations II: impossibility results and consensus - two generals, FLP, CAP, quorums and Paxos — explained

## The big picture
The applied labs kept making the same moves: retry and deduplicate instead of "exactly once" ("Idempotency keys: exactly-once effect over at-least-once delivery"), compensate instead of atomically commit ("Sagas with compensation: orchestration vs choreography, idempotent steps, saga log"), refuse requests during a partition ("Network partitions and fault injection: proxy toxics, split brain, fencing and linearizability checking"), and rely on majorities ("Replicated log with Raft (simplified): terms, commit index, re-election, election restriction"; "Consistency models in practice: quorums (N, R, W), staleness and PACELC"). These four results explain why those moves are forced: some goals are impossible, and the possible ones rest on one lemma — quorums intersect. ### T24.1 The two generals cannot coordinate over a lossy channel
**In plain words** If any message can be lost, no protocol guarantees that two parties both act or both refrain, while still acting when nothing is lost.

**Why it is true (intuition)** Look at the last message that mattered. Its sender cannot tell whether it arrived, so it decides the same either way — and its receiver decides differently.
1. Loss-free run: k messages, both attack. Run r_j: only the first j arrive.
2. r_0: nobody attacks; r_k: both. Take the smallest j where someone attacks.
3. r_{j-1} and r_j differ only in m_j; its sender hears nothing afterwards in both.
4. Deterministic ⇒ the sender decides the same; nobody attacked in r_{j-1}, so the sender waits and the receiver attacks.

**See it in numbers** `python consensus_proofs.py generals`
```
  protocols with a disagreeing or never-attacking run: 140; correct protocols: 0
  e.g. M=6, tA=3, tB=3: 5 delivered: A waits, B attacks
```
All 140 bounded protocols fail; the example is exactly move 4 — the last message is lost.

**Where it shows up in practice** "Sagas with compensation…": engineers make actions reversible (refund) or repeatable (idempotency keys) instead of pretending to agree.

### T24.2 FLP: no deterministic asynchronous consensus tolerates one crash (Fischer, Lynch & Paterson 1985, Theorem 1)
**In plain words** With unbounded delays and even one possible crash, any deterministic consensus protocol has a run that never decides. Safety survives; guaranteed termination does not.

**Why it is true (intuition)** Call a state *bivalent* if both outcomes are still reachable. An adversary scheduler can always keep the system bivalent.
1. Some initial state is bivalent (neighbouring inputs plus one silent process).
2. From any bivalent state, delaying the right message keeps it bivalent; a slow process is indistinguishable from a crashed one.
3. Repeat forever while every process still takes steps: a fair run that never decides.

**See it in numbers** `python consensus_proofs.py flp`
```
  ballots started 2000, accepts issued 2000, acceptances 0, values chosen 0 (safe, never live)
  with random backoff U[0, 4) after a clash (a timing assumption): 10,000 runs, all decided: True, mean attempts 4.35, max 37
```
Two proposers duel forever under the adversary — nothing wrong is chosen, nothing is chosen at all. Random backoff (giving up determinism plus a timing assumption) decided every run.

**Where it shows up in practice** "Replicated log with Raft…": randomized election timeouts and the split vote at t=40 — liveness from timing, safety from the vote rule.

### T24.3 CAP, precisely (Gilbert & Lynch 2002, Theorem 1 and Corollary 1.1)
**In plain words** During a partition, a register cannot be both linearizable and answer every request. It says nothing about the no-partition case.

**Why it is true (intuition)** The side that cannot hear the write cannot know about it.
1. Partition G1 | G2; write v1 in G1 completes (availability).
2. A later read in G2 must answer (availability) and has heard nothing: it returns v0.
3. The read started after the write finished: not linearizable.

**See it in numbers** `python consensus_proofs.py cap`
```
  AP-local               ok                               read -> v0                                   available=True linearizable=False
  CP-majority            no response (needs 2 of 3 acks)  read -> no response (needs 2 of 3 replies)   available=False linearizable=True
```
Each design gives up exactly one property in the partitioned run.

**Where it shows up in practice** "Network partitions and fault injection…": n2's read returned 2 after write 3 finished — the CAP execution, reproduced with a proxy.

### T24.4 Quorum intersection and the safety of single-decree Paxos
**In plain words** Read and write quorums overlap iff R + W > N. Paxos uses that overlap so a chosen value is carried into every later ballot: at most one value is ever chosen.

**Why it is true (intuition)** A new proposer must hear from a majority before proposing, and that majority shares an acceptor with whatever majority already chose.
1. Pigeonhole: |Q_R ∩ Q_W| ≥ R + W − N ≥ 1.
2. Suppose (m, v) was chosen by majority C; proposer n > m heard promises from majority S; some c is in both.
3. c accepted (m, v) before promising n, so it reported a proposal numbered ≥ m.
4. The proposer adopts the highest reported value; by induction that is v.

**See it in numbers** `python consensus_proofs.py paxos`
```
  R + W > N with a disjoint pair: 0; R + W <= N configurations with a disjoint pair: 56 of 56
  correct single-decree Paxos     : 3000 random runs (loss 15%, dup 10%, reorder), decided 3000, runs with 2 values chosen 0, runs violating P2b 0
  broken (ignores phase-1 values): 3000 random runs (loss 15%, dup 10%, reorder), decided 3000, runs with 2 values chosen 2296, runs violating P2b 2498
```
The lemma is exact in both directions. Skip move 4 (ignore phase-1 values) and two values get chosen in 2296 runs.

**Where it shows up in practice** "Replicated log with Raft…": the election restriction is Raft's version of move 4; removing it lost committed entries.

## Worked problems
**24-P1.** N = 7, R = 3. Smallest W so every read sees the latest write *and* any two writes overlap?
1. Read–write overlap: R + W > N ⇒ W ≥ 5. *Why:* the lemma.
2. Write–write overlap: 2W > N ⇒ W ≥ 4. *Why:* concurrent writes must meet to detect conflicts.
3. Both: W = 5. Check: 3 + 5 − 7 = 1 shared replica.

**24-P6.** A1 accepted (2, x), A2 accepted (3, y), A3 nothing. Proposer ballot 5: value with promises from {A1, A3}? From {A2, A3}?
1. {A1, A3} reports only (2, x) ⇒ propose x. *Why:* adopt the highest accepted value reported.
2. {A2, A3} reports (3, y) ⇒ propose y.
3. Neither is necessarily chosen yet: no value has a majority, so both are safe — the rule only constrains once something *might* be chosen.

## Common confusions
**Q:** FLP means Raft cannot work. — **A:** FLP forbids guaranteed termination; Raft keeps safety always and gets liveness from timing (backoff decided 10,000 of 10,000 runs).

**Q:** CAP says pick two of three. — **A:** Without a partition you can have both; it is a choice made *during* partitions.

**Q:** R + W > N makes reads linearizable. — **A:** It gives overlap; lesson 17 still measured 2 inversions without write-back.
