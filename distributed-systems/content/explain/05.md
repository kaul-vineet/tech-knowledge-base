# Idempotency keys: exactly-once effect over at-least-once delivery — explained

## The intuition
When a payment response is lost, the client cannot know whether the charge happened. It must retry, and the server may charge twice. The network cannot deliver exactly once, but the effect can happen once: the client names the operation with a key; the server remembers processed keys and replays the stored answer.

**Analogy:** a numbered ticket at a counter. If ticket #42 comes back, the cashier hands over a copy of the receipt instead of ringing it up again.
Where the analogy breaks: servers see concurrent retries, so key check and charge must be atomic.

```
pay(key=k1) ─▶ PaymentB: store[k1] = in-progress ─▶ charge ─▶ store[k1] = done + (201, ch_1)
   ✖ response lost (seeded 40%)
pay retry, SAME k1 ─▶ k1 done, same fingerprint ─▶ replay (201, ch_1), no new charge
```

The one thing to remember: at-least-once delivery plus deduplication by key gives an exactly-once effect.

## Walkthrough: what actually happens when you run it
1. **You run** `python idempotency.py`
   **What happens inside:** `PaymentB.do_POST` appends to `ledger`, then sometimes (seeded) drops the connection; `pay()` resends. With `enforce=True` it first checks `store` under a lock: other fingerprint → 422, running → 409, done → replay.
   **What you see:**
   ```
   --- Idempotency-Key OFF: 5 orders x 10 ---
   order 4: 201 {'charge_id': 'ch_8'} after 3 attempt(s)
   …
   ledger: 11 charges, total 110 (expected 50)
   --- Idempotency-Key ON: 5 orders x 10 ---
   order 1: 201 {'charge_id': 'ch_1'} after 2 attempt(s)
   …
   ledger: 5 charges, total 50 (expected 50)
   reuse key with amount 99 -> (422, {'title': 'Idempotency-Key is already used'})
   no key at all            -> (400, {'title': 'Idempotency-Key is missing or malformed'})
   ```
   **What it means:** order 4's lost responses left unseen charges. With keys, order 1's retry got the stored `ch_1`. Matches the README.

2. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: new key per attempt -> ledger 11 charges, total 110 (expected 50)
   tryIt 2: same key x3 -> [(201, {'charge_id': 'ch_1'}), (201, {'charge_id': 'ch_1'}), (201, {'charge_id': 'ch_1'})]; ledger 1 charge(s)
   ```
   **What it means:** a key made inside the retry loop equals no key; same-key repeats are free.

## Common confusions
**Q:** Just ignore duplicate amounts. — **A:** Two real €10 orders look identical; only the key tells "retry" from "new order".

**Q:** Store the key after charging. — **A:** A crash in between duplicates; the lab updates store and ledger under one lock.

**Q:** This is exactly-once delivery. — **A:** Requests still arrive several times (order 1: 2 attempts); only the effect is once.
