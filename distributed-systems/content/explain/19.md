# Multi-region design: latency budget, leader placement, follower reads, failover RTO/RPO — explained

## The intuition
Three regions survive a regional outage, but light is slow: us–eu 40 ms one way, us–ap 110 ms. Designs differ in *where writes go* (one leader, every region, a quorum near the client) and *when they are acknowledged* (async: after the leader's disk; sync: after a majority). Async is fast but loses in-flight writes when the leader's region dies — the RPO. Sync loses nothing but pays a round trip per write. Multi-leader never stops writing but creates conflicts.

Placement matters too. A majority-sync leader commits after its *nearest* follower, so a leader in the middle region (eu) is close to everyone. The deployed leader sat in ap because the team launched there — history, not measurement.

**Analogy:** placing a head office near the biggest customers and near a branch that countersigns every contract.
Where the analogy breaks: a head office does not vanish with its unsigned contracts; an async leader's region can.

```
user us/eu/ap ─ write ─▶ leader region ─┬─ async: ack now, replicate later   (RPO > 0)
                                        └─ sync-majority: ack after nearest follower (RPO 0)
region fails at t=10 s ─▶ election timeout ─▶ new leader ─▶ first successful write = RTO
multi-leader / leaderless: write locally, conflicts later
```

The one thing to remember: measure p99 per user region, RPO and RTO for each design *and* leader placement — the cheapest design that meets the brief wins, not the familiar one.

## Walkthrough: what actually happens when you run it
1. **You run** `python multiregion.py`
   **What happens inside:** a seeded simulation sends 100 writes/s from us (50%), eu (35%), ap (15%). Each design runs calm and with the leader's region failing at 10 s (RPO = acknowledged writes lost; RTO = time to the next successful write).
   **What you see:**
   ```
   design               write p99 us / eu / ap ms   lag p99  conflicts  RPO lost  RTO ms  rejected
   async@ap                346.0 /  265.3 /  102.3     266.6          0        16    1129       108
   sync-majority@us        310.9 /  354.9 /  445.8      95.9          0         0    1209        74
   sync-majority@eu        304.6 /  267.8 /  341.7      67.9          0         0    1313        73
   sync-majority@ap        497.2 /  450.1 /  354.5      38.4          0         0    1009       102
   multi-leader            140.6 /  127.1 /  112.8     197.4        434         2      65         0
   leaderless              203.9 /  147.1 /  221.9      34.2        409         0      65         0
   deployed {'replication': 'async', 'leader': 'ap'}: violations ['RPO: 16 acknowledged writes lost']
   place_leader('sync-majority') -> ap
   ```
   **What it means:** async@ap acknowledged 16 orders that died with ap. Every sync-majority row has RPO 0 and RTO near 1 s (the 1–2 s election timeout). Only eu keeps both us and eu users under 350 ms. Multi-leader is fastest and never stops, at the cost of 434 conflicts. Matches the README.

2. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: ap follower read: ~2 ms, stale by up to 103.6 ms (p99 lag); leader read: ~140 ms + jitter, current if the leader confirms it still leads (Raft section 8)
   tryIt 2: election timeout 1000-2000 ms -> RTO 1313 ms, 73 writes rejected during failover, RPO 0
   tryIt 2: election timeout 150-300 ms -> RTO 278 ms, 21 writes rejected during failover, RPO 0
   ```
   **What it means:** follower reads trade staleness for a local answer. A LAN-style election timeout cuts RTO, but WAN jitter would cause false elections (not modelled), so 278 ms is optimistic.

### Failure lab: the deployed design loses orders
1. **Inject:** ap fails at t=10 s while 100 writes/s flow (seed 19).
2. **Symptom:** step 1's last lines — 16 acknowledged writes lost; `place_leader` returns the historical `ap`.
3. **Diagnose:** async commits at the leader's arrival time, so anything not yet shipped dies with the region.
4. **Fix (build task):** `place_leader()` simulates each leader region and returns the lowest traffic-weighted p99; `DESIGN` becomes majority-sync with that leader.
5. **Proof** — **What you see** (`python solution_multiregion.py`, then `test_fitness` on the unchanged file):
   ```
   deployed {'replication': 'sync-majority', 'leader': 'eu'}: violations none
   place_leader('sync-majority') -> eu
   FAILED (failures=10)
   ```

### The decision
- **Options and evidence:** async (fast, RPO 16–17); sync-majority at us/eu/ap (RPO 0 everywhere, eu the only placement with us 304.6 ms and eu 267.8 ms both ≤ 350); multi-leader and leaderless (no failover gap, 434 and 409 conflicts).
- **Why ADR-019 chose sync-majority in eu:** the brief demands RPO 0 (rules out async), no conflicts on order rows (rules out multi-leader and leaderless), and p99 ≤ 350 ms for us and eu (rules out leaders in us — eu at 354.9 — and ap). RTO 1313 ms is well inside 5,000. The extra cost lands on ap users (341.7 ms), who are 15% of traffic and outside the p99 constraint.
- **How the fitness function keeps it true:** `test_fitness.py` replays the brief on seeds 19–28 and asserts `place_leader()` still returns the configured leader on seeds 19–21. Reference: `OK`; the unchanged lesson file failed on all 10 seeds. If traffic shifts toward ap, the placement test fails first and tells you to re-decide.

## Common confusions
**Q:** Synchronous replication means every region acknowledges. — **A:** Majority-sync waits for the *nearest* follower; that is why lag p99 is 67.9 ms at eu, not the full ap round trip.

**Q:** RTO is the failover's whole cost. — **A:** RPO is separate: async@ap recovered in 1129 ms *and* lost 16 orders.

**Q:** Multi-leader is strictly better. — **A:** 434 conflicts on order rows violate the brief; fine for CRDT carts (lesson 18).
