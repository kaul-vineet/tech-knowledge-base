# Leader election with leases and fencing tokens — explained

## The intuition
Some work must run on exactly one replica, and the replicas must pick a new owner automatically when it dies. A lease does both: a key in a shared store that one node creates atomically (compare-and-swap) and keeps renewing. Stop renewing and the key expires; the next node's CAS wins.

The hard case is a holder that is paused, not dead (GC pause, frozen VM). It wakes believing it still leads and writes once more; it cannot notice the expiry, because noticing needs code that was not running. So protection must live in the resource: each new lease gets a larger number (fencing token), and the resource refuses tokens older than the largest it has seen.

**Analogy:** a parking permit with an expiry date and a serial number; the attendant refuses permits older than the newest serial.
Where the analogy breaks: a driver can read the date; a paused process does not see time pass.

```
Node.step ──/get──▶ KVStore (CAS + TTL, one revision counter)
   │ 404 → /cas expect=0 → 200 {rev, created}   token = created
   │ leader → FencedStorage.write(token) → accepted | REJECTED
   └ leader → /cas expect=self.rev (renew) → 200 | 409 → step down
```

The one thing to remember: a lease decides who should lead; only a fencing check in the resource stops a stale leader.

## Walkthrough: what actually happens when you run it
1. **You run** `python election.py`
   **What happens inside:** `KVStore` applies `/cas` under one lock, so exactly one create wins; every successful write takes the next store-wide revision. A simulated clock advances 1 s per tick. n1 wins at t=0 (`created=1` is its token), then each tick writes and renews with `expect: self.rev`. n1 pauses at t=3, resumes at t=7.
   **What you see:**
   ```
   t=0 n1 acquired the lease, fencing token 1
   t=3 n1 pause
   t=5 n2 acquired the lease, fencing token 4
   t=7 n1 resume
   t=7 n1 writes with token 1: REJECTED (token 1 < 4)
   t=7 n1 renew failed (rev 3 != 5) -> steps down
   …
   lease holder per tick: 0:n1 1:n1 2:n1 3:n1 4:n1 5:n2 6:n2 7:n2 8:n2
   ```
   **What it means:** n1 used revisions 1–3 (create + two renewals). Last renewal t=2 + TTL 3 s = expiry at t=5; nobody detected the pause, the TTL did. At t=7 n1 writes *before* renewing (`step()` order) — the realistic gap — and storage rejects 1 < 4. Matches the README.

2. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: fencing off -> accepted | n1's stale write landed after n2's write at t=6
   tryIt 2: TTL 3 s -> holder per tick 111112222 | n2 takes over at t=5
   tryIt 2: TTL 6 s -> holder per tick 111111111 | no failover: n1 renewed in time after its pause
   ```
   **What it means:** without fencing, two leaders wrote. A 6 s TTL rode out the pause but would take 6 s to replace a truly dead leader.

3. **You run** `python -m unittest test_build_task` (reference `resign()`: CAS-delete with your own revision)
   **What you see:**
   ```
   Ran 3 tests in 0.855s
   OK
   ```
   **What it means:** a clean hand-over skips the TTL wait. Use `BUILD_TARGET=mine` for your version.

Optional etcd step — Expected (not run here): per the etcd docs, a lease plus a transaction comparing the key's create revision with 0 plays the role of `/cas expect=0`, and the create revision serves as the token.

## Common confusions
**Q:** Check "am I still leader?" before writing. — **A:** The pause can follow the check; at t=7 n1 believed it led.

**Q:** Any unique value works as a token. — **A:** It must grow per holder; `created` comes from one counter, so 4 > 1.

**Q:** Shorter TTL is better. — **A:** Faster failover, but pauses become false failovers (tryIt 2).
