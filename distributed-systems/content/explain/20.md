# Chaos engineering: hypotheses, steady state, blast radius and seeded fault campaigns — explained

## The intuition
Chaos engineering is an experiment, not vandalism. You state a *steady state* you can measure from the system's own data ("harmed orders = 0": nobody paid without shipping), write a *hypothesis* ("during a courier outage, harmed orders stay 0"), inject a realistic fault, and compare. If the hypothesis holds, you gained confidence; if it is refuted, you found a weakness before customers did.

The catch is that a refuted hypothesis *is* customer harm when the experiment runs on real traffic. So a good experiment limits the damage it can do while still finding the weakness: inject into a small, stable cohort (10%), keep the rest as a control group to prove the fault caused the harm, and abort the moment the steady state breaks. And the campaign must contain the *right* faults: random crashes are easy and comfortable; a fast rolling restart is the realistic operational event that exposed the Raft bug from lesson 12.

**Analogy:** a fire drill in one wing, stopped the moment someone gets hurt.
Where the analogy breaks: a drill fakes the fire; here the fault is real.

```
hypothesis + steady state (from service data)
   ─▶ cohort(sagas, 10%)  ─▶ inject fault ─▶ harmed(...) after each order ─▶ abort after 1
   └▶ control group (90%) ─▶ no fault ─────▶ control_harmed must be 0
campaign: saga {shipping-outage, crash-after-charge} × Raft {random-crash, rolling-restart} × seeds
```

The one thing to remember: keep the finding, bound the damage — a stable cohort, a control group and an abort rule turn "60 customers hurt" into one.

## Walkthrough: what actually happens when you run it
1. **You run** `python chaos.py` (the lesson harness)
   **What happens inside:** `run_saga_experiment` replays 60 orders (seed 14) through the L300 lesson saga and the hardened one, injecting the fault into *every* order. The Raft experiments crash nodes at random or restart them one by one with 0–4 ticks between, over 20 seeds, and use lesson 12's safety checker as the steady state.
   **What you see:**
   ```
   {"aborted": false, "blast_radius_pct": 100.0, "control_harmed": null, "customers_hurt": 60, "experiment": "saga/shipping-outage", "experiment_harmed": 60, "held": false, "seed": 14, "steady_state": "harmed orders = 0", "target": "L300 lesson"}
   experiment              target          hypothesis held   customers hurt by the experiment
   saga/shipping-outage    L300 lesson       0/1   runs           60
   saga/shipping-outage    L300 hardened     1/1   runs            0
   raft/random-crash       L300 lesson      20/20  runs            0
   raft/rolling-restart    L300 lesson      19/20  runs            0
   raft/rolling-restart    L300 hardened    20/20  runs            0
   ```
   **What it means:** the harness *works* — it refutes the hypothesis on the unhardened saga and confirms the hardened one — but it hurt all 60 customers to learn that. Random crashes never found the Raft bug; the rolling restart did, in 1 of 20 seeds. Matches the README.

2. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: blast 10%, abort after 1 harmed order: customers hurt 1, hypothesis held False
   tryIt 1: blast 10%, abort after never: customers hurt 6, hypothesis held False
   tryIt 1: blast 50%, abort after never: customers hurt 30, hypothesis held False
   tryIt 2: rolling restart, wait 0-4 ticks between nodes: L300 lesson Raft refuted in 1/20 seeds
   tryIt 2: rolling restart, wait 20-30 ticks between nodes: L300 lesson Raft refuted in 0/20 seeds
   ```
   **What it means:** every protection keeps the same verdict and cuts the harm: 30 → 6 → 1. A patient rolling restart hides the Raft bug without fixing it — an operational workaround, not a code fix.

### Failure lab: an experiment that hurts everyone
1. **Inject:** courier outage and crash-after-charge on all 60 orders.
2. **Symptom:** `customers_hurt: 60`, `blast_radius_pct: 100.0`, `control_harmed: null` (no control group, so no proof of cause).
3. **Diagnose:** the harness has no cohort, no control and no stopping rule.
4. **Fix (build task):** `harness.cohort(sagas, BLAST_PCT, ...)` picks a stable 10%; check `harmed(...)` after each faulty order; stop after `ABORT_AFTER = 1`.
5. **Proof** — **What you see** (`python solution_chaos.py`, then `test_fitness` on the unchanged file):
   ```
   {"aborted": true, "blast_radius_pct": 10.0, "control_harmed": 0, "customers_hurt": 1, "experiment": "saga/shipping-outage", "experiment_harmed": 1, "held": false, "seed": 14, "steady_state": "harmed orders = 0", "target": "L300 lesson"}
   FAILED (failures=4)
   ```
   Same finding (`held: false`), one customer hurt, control group clean.

### The decision
- **Options and evidence:** fault everything (finds weaknesses, 60 hurt per experiment); bounded campaign (same verdicts, 1 hurt, control 0); manual game days only (random crashes passed 20/20 on buggy Raft; only the scripted rolling restart found it).
- **Why ADR-020 chose the bounded campaign:** the constraints say ≤ 1 customer hurt per refuted hypothesis, ≤ 10% of orders faulted, and one Raft node at a time. Only the bounded harness meets them without losing a finding. Game days stay as a complement because people invent faults a script would not.
- **How the fitness function keeps it true:** `test_fitness.py` asserts every saga experiment has blast radius ≤ 10% and hurt ≤ 1, and that the hardened saga and Raft hold every hypothesis on seeds 14–16. Reference: `OK`; the unbounded lesson harness fails 4 checks. Someone widening the cohort "to find bugs faster" breaks the build.

## Common confusions
**Q:** Chaos means random faults. — **A:** Random crashes found nothing in 20/20 runs; the targeted rolling restart found the bug.

**Q:** Bounding the experiment hides problems. — **A:** The verdict stayed `held: false`; only the damage shrank.

**Q:** A passing patient restart proves the cluster is safe. — **A:** tryIt 2: 0/20 with slow restarts, yet the election-restriction bug is still in the code.
