# Sagas with compensation: orchestration vs choreography, idempotent steps, saga log — explained

## The intuition
An order touches three services that each own their database: orders, payments, shipping. No transaction spans them, so when shipping fails, the order and the charge already exist. You cannot roll back; you can only *compensate*: cancel the order, refund the charge — newest first.

Two things make this harder than it sounds. First, the coordinator can crash between steps, so it writes a saga log (one JSON line per step status) and a new coordinator rebuilds every unfinished saga from it. Second, recovery cannot always know whether the last call happened: the step is "in doubt". The only safe move is to run the compensation anyway — which is safe only if compensations are idempotent (one refund per saga id, no-op if nothing was charged).

**Analogy:** a travel agent books flight, hotel and car; if the car fails they cancel the hotel then the flight, ticking each in a notebook so a colleague can finish the job.
Where the analogy breaks: a phone cancellation is confirmed on the spot; here the "cancelled?" answer can be lost, so the colleague may cancel twice.

```
Orchestrator.run(saga): create ─▶ charge ─▶ ship ✖ (no courier slot)
                              ◀─ refund ◀─ cancel     (reverse order; build task)
every status ─▶ SagaLog (JSON lines) ─▶ recover(): finish sagas with no final entry
choreography: PaymentCharged ─▶ ShippingFailed ─▶ PaymentRefunded on a bus
```

The one thing to remember: undo completed steps in reverse order with idempotent compensations, driven by a durable log.

## Walkthrough: what actually happens when you run it
1. **You run** `python saga.py`
   **What happens inside:** `Orchestrator.steps` lists (name, action, compensation); shipping has none — it is the irreversible last step. `Shipping` fails 30% (seed 14). On `StepFailed` the lesson orchestrator logs `failed` and returns. `audit()` checks the invariant from the services' own data: money kept equals the amount if shipped, else 0.
   **What you see:**
   ```
   fault (30% of shipments fail, seed 14): {'o1': 'failed', 'o2': 'completed', 'o3': 'completed', 'o4': 'completed', 'o5': 'failed', 'o6': 'failed'}
     {"saga": "o1", "step": "charge", "status": "done"}
     {"saga": "o1", "step": "ship", "status": "failed", "error": "no courier slot"}
   audit:
     o1: FAILED, shipped=False, money kept=10 of 10
   ```
   **What it means:** three customers paid for parcels that never ship, and the log shows nobody tried to fix it. Matches the README.

2. **You run** `python choreography.py`
   **What happens inside:** no coordinator; each service reacts to events on a bus, and Payments' `ShippingFailed` handler refunds.
   **What you see:**
   ```
   choreography: 21 events delivered, audit: OK
   ```
   **What it means:** the flow works, but it is spread over handlers — and the bus is at-least-once (tryIt 2).

3. **You run** `python try_it.py`
   **What happens inside:** tryIt 1 crashes the solution orchestrator right after the refund call, before it logs `compensated`; a new orchestrator runs `recover()`. tryIt 2 duplicates ~20% of bus events.
   **What you see:**
   ```
   tryIt 1: idempotent refund=False: refunds [-10, -10], audit: ['o1: CANCELLED, shipped=False, money kept=-10 of 10']
   tryIt 1: idempotent refund=True: refunds [-10], audit: OK
   tryIt 2: lesson Payments: 32 deliveries, audit: | o6: CANCELLED, shipped=False, money kept=-60 of 60
   tryIt 2: solution Payments: 32 deliveries, audit: | OK
   ```
   **What it means:** recovery and duplicates re-run compensations; only idempotent ones stay correct.

### Failure lab: failed shipments keep the customer's money
1. **Inject:** `Shipping(fail_rate=0.3)`, seed 14 (o1, o5, o6), plus `crash_once_after` to kill the orchestrator after a call.
2. **Symptom:** step 1's audit — `money kept=10 of 10`, 50 and 60; no compensation lines in the log.
3. **Diagnose:** the `StepFailed` branch sets FAILED and returns; `refund` is not keyed by saga, so a retried refund pays twice.
4. **Fix (build task):** compensate completed steps with `reversed(self.steps)`, skipping ones already logged `compensated`; make `refund` once-per-saga; add `recover()` that compensates the in-doubt step too.
5. **Proof** — **What you see** (`python solution_saga.py`, then `BUILD_TARGET=mine` tests on the unchanged file):
   ```
     {"saga": "o1", "step": "ship", "status": "failed", "error": "no courier slot"}
     {"saga": "o1", "step": "charge", "status": "compensated"}
     {"saga": "o1", "step": "create", "status": "compensated"}
     {"saga": "o1", "step": "saga", "status": "compensated"}
   audit:
     OK
   FAILED (failures=3, errors=1)
   ```
   The solution compensates newest first; the lesson file fails until fixed.

## Common confusions
**Q:** Compensation is a rollback. — **A:** It is a semantic undo: `refund` appends −10; the charge stays in the ledger, and others may have seen it.

**Q:** Log "done" before calling, to be safe. — **A:** Then recovery skips work that never happened; log after the call and treat the next step as in doubt.

**Q:** Choreography avoids these problems. — **A:** tryIt 2: duplicated events refunded o6 twice without idempotency.
