# An order pipeline that survives chaos and proves it — explained

## The intuition
Earlier labs fixed one failure each; a real pipeline meets them together — retries, bursts, courier outages, crashes after charging, relay crashes, duplicates, a config-leader crash. The capstone composes the fixes and attacks the whole with a bounded chaos campaign judged by deterministic checks.

The new piece is the **outbox**: each step writes its state change and its event in *one* local transaction; a relay publishes unsent rows at least once. Otherwise a crash between "update database" and "publish" loses or invents events.

**Analogy:** each kitchen station writes the order slip in the same motion as plating; a runner may carry a slip twice; the cashier ignores slips already rung up.
Where the analogy breaks: software needs the processed-id check written down, or duplicates become double charges.

```
client(key, trace) ─▶ gateway: admit ≤ max_queue (Raft config) else 503 + Retry-After
   ─▶ saga: create ─▶ charge ─▶ ship   (reverse compensation, recover())
        each step: OutboxDB.transact(state change + event)
   ─▶ Relay (at-least-once) ─▶ Bus (may duplicate) ─▶ IdempotentConsumer(email, revenue)
checks.py reads services' own data ─▶ run_capstone.py: 27 runs ─▶ 10 criteria ─▶ exit 0|1
```

The one thing to remember: compose idempotent pieces around one atomic write per step, then let code — not people or models — judge the result under every fault.

## Walkthrough: what actually happens when you run it
1. **You run** `python pipeline.py`
   **What happens inside:** 60 orders flow through all mechanisms with no faults; the config value is proposed through the lesson 12 Raft log and applied only once committed.
   **What you see:**
   ```
   ticks 33, sagas {'completed': 60}, events published 180, delivered 360, spans 660, config {'version': 2, 'max_queue': 12}, audit: OK
   ```
   **What it means:** 3 events per order; 360 deliveries because two consumers subscribe; 11 spans per order in one trace. Matches the README.

2. **You run** `python run_capstone.py`
   **What happens inside:** 9 experiments × 3 seeds; order faults hit a 10% cohort; `checks.py` runs 8 checks per run from the services' own data.
   **What you see:**
   ```
   {"blast_radius_pct": 10.0, "compensated": 6, "duplicates_absorbed": 108, "experiment": "everything", "failed": [], …, "harmed_orders": 0, "held": true, …, "seed": 22, "ticks": 48}
   {"criterion": "exactly-once effects", "measure": "passes in 27/27 runs (baseline: max emails per event 1, revenue mismatches 0)", "pass": true}
   {"criterion": "bounded queue", "measure": "passes in 27/27 runs (baseline: over bound 0, p99 wait 2 ticks)", "pass": true}
   {"scorecard": "10/10", "pass": true}
   ```
   **What it means:** all faults at once: 6 compensated, 0 harmed. The exit code is the release gate.

3. **You run** `python try_it.py` (switch one mechanism off)
   **What you see:**
   ```
   tryIt 1: consumers without dedupe, bus-duplicates: failed checks {'exactly-once effects': 'max emails per event 2, revenue mismatches 14'}
   tryIt 2: gateway without idempotency keys, lost-acks: failed checks {'one order and one charge per key': 'max created 2, max charges 1', 'exactly-once effects': 'max emails per event 2, revenue mismatches 0'}
   ```
   **What it means:** remove a mechanism and exactly its criteria fail.

4. **You run** `python run_capstone.py --explain --fake`
   **What you see:**
   ```
   agent check relay-crash         agent: ('no', 0) code: ('yes', 0) WRONG
   agent check burst               agent: ('yes', 3) code: ('yes', 0) WRONG
   agent verdict IGNORED (code decides): PASS - safe to release
   ```
   **What it means:** the model only explains; wrong claims are flagged and its release verdict is ignored.

### The decision
- **Options:** distributed transaction across database and bus vs outbox + idempotent consumers (ADR-022-1); choreography vs orchestrated saga (ADR-022-2); config file vs Raft-committed config (ADR-022-3); queue everything vs shed at admission (ADR-022-4).
- **What the measurements showed:** effects exactly once in 27/27 runs (14 revenue mismatches without dedupe); 0 harmed orders; config at committed version 2 through a leader crash; queue within bound.
- **Why the ADRs chose them:** each is the cheapest option meeting a hard constraint of the brief, built from parts proven in lessons 12–21.
- **How the fitness functions keep it true:** each ADR names its scorecard criterion; `run_capstone.py` exits non-zero if any fails, and `test_m1`…`test_m6` guard each piece.

## Common confusions
**Q:** Dedupe gives exactly-once delivery. — **A:** Deliveries still repeat (108 absorbed); only effects are once.

**Q:** 10/10 means correct. — **A:** Only for these faults, seeds and checks.

**Q:** A good model could approve releases. — **A:** The fake model got 2 of 9 lines wrong; code decides.
