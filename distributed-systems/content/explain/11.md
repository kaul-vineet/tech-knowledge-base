# Rate limiting: token bucket, per-client limits, 429 and Retry-After — explained

## The intuition
Without limits, the client with the busiest loop takes all of an API's capacity. A rate limiter gives each client an allowance and, when it is used up, answers `429 Too Many Requests` plus `Retry-After: <seconds>`.

A token bucket holds at most `burst` tokens and refills at `rate` per second; a request spends one. Long-run, a client gets at most `rate` requests per second, but after a quiet spell it may burst. The lab refills lazily — `tokens += elapsed × rate` when a request arrives — so no timer thread is needed.

**Analogy:** a phone allowance that tops up continuously, with a cap on rollover.
Where the analogy breaks: a phone company bills overage; a limiter refuses and says when to return.

```
GET /data  X-Client-Id: alice ─▶ limiters["alice"] (rate 2/s, burst 5)
   allow(): tokens = min(5, tokens + (now - last) * 2)
     tokens >= 1 ─▶ 200, tokens -= 1
     else        ─▶ 429, Retry-After = max(1, ceil((1 - tokens) / 2))
```

The one thing to remember: a token bucket caps each client's average rate with bounded bursts; 429 + Retry-After says when to come back.

## Walkthrough: what actually happens when you run it
1. **You run** `python ratelimit.py`
   **What happens inside:** `run()` is an event loop on a simulated clock serving whichever client's next request is earliest. Alice honours `Retry-After`; bob retries after 0.1 s; carol wants 3 requests. `limiters` is keyed by `X-Client-Id`.
   **What you see:**
   ```
   alice trace: 200 200 200 200 200 429(wait 1) 200 200 429(wait 1) 200 200 429(wait 1) 200 200 429(wait 1) 200
   alice (honors Retry-After): 12 ok, 4 x 429, done at t=4s
   bob   (retries every 0.1 s): 12 ok, 35 x 429, done at t=3.5s
   carol (honors Retry-After): 3 ok, 0 x 429, done at t=0s
   ```
   **What it means:** alice spent her burst at t=0; the next token was 0.5 s away, rounded *up* to `Retry-After: 1`. One second later 2 tokens had refilled: two 200s, then 429 — the steady 2/s. Bob finished half a second sooner at the cost of 35 rejected requests. Carol never noticed: per-client isolation. Matches the README.

2. **You run** `python try_it.py`
   **What you see:**
   ```
   tryIt 1: 10 requests within 10 ms across a second boundary -> fixed window allows 10, token bucket allows 5
   tryIt 2: BURST 5 -> alice 12 ok, 4 x 429, done at t=4s
   tryIt 2: BURST 1 -> alice 12 ok, 11 x 429, done at t=11s
   ```
   **What it means:** a fixed window resets at the boundary, so "5 per second" let 10 through in 10 ms. With burst 1, each 0.5 s wait is sent as a whole second, so alice wastes half of every wait.

3. **You run** `python -m unittest test_build_task` (reference `SlidingWindowLog`)
   **What you see:**
   ```
   Ran 3 tests in 0.159s
   OK
   ```
   **What it means:** counting accepted timestamps in the last window avoids the boundary double burst.

## Common confusions
**Q:** Hammering gets served faster. — **A:** Bob saved 0.5 s with 35 rejected requests; at scale those are the overload.

**Q:** A per-second counter equals a bucket. — **A:** tryIt 1: 10 vs 5 at the boundary.

**Q:** Key limits on any header. — **A:** Clients choose `X-Client-Id` here; production keys on an authenticated identity.
