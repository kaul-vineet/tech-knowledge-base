## The big picture
Every lab so far assumed something about time and failure. "Ordering events with Lamport clocks" assumed messages carry counters; "Timeouts: fail fast instead of hanging" assumed a slow reply probably means a dead peer; "Leader election with leases and fencing tokens" kept safety in a token and liveness in a timer. ### T23.1 Lamport's clock condition and total order (Lamport 1978)
**In plain words** If a can have influenced b, a's Lamport number is smaller. Sorting by (number, process id) gives one global order that never puts an effect before its cause — but a smaller number does not mean "caused".

**Why it is true (intuition)** Happened-before is built from only two kinds of links: "earlier on the same process" and "send before its receive". Each link forces the counter up, and chains of links keep going up.
1. Program order: IR1 ticks between successive events, so the later one is larger.
2. Messages: IR2 sets the receiver above the stamp, so the receive is larger than the send.
3. `<` on integers is transitive, so any chain of links keeps increasing.
4. Distinct (C, pid) keys make the lexicographic order total; it contains every causal pair.
5. The converse fails: two silent processes number events independently.

**See it in numbers** `python clocks_proofs.py clock`
```
  pairs with a->b: 13,599; violations of L(a) < L(b): 0
  converse fails: 11,063 of 27,402 concurrent pairs still have L(a) < L(b)
  broken receive rule (tick only, no max): 990 violations
```
Zero violations over every causal pair; about 40% of *unrelated* pairs still look ordered; and dropping `max` on receive breaks the condition 990 times — the same bug as lesson 6's tryIt 1.

**Where it shows up in practice** "Ordering events with Lamport clocks": sorting by (L, node) fixed the skewed wall-clock order, while the two L=8 events were concurrent.

### T23.2 Vector clocks characterise happened-before
**In plain words** Give each event a vector with one counter per process. Then a happened before b exactly when a's vector is ≤ b's in every slot and different; incomparable vectors mean concurrent.

**Why it is true (intuition)** Slot k of V(e) counts how many of P_k's events are in e's causal past. Pasts are prefixes, so "contains" becomes "≤".
1. Lemma by induction: local events add themselves; a receive merges two pasts, and the union of two prefixes has the size of the larger, which is the element-wise max.
2. (⇒) a → b means past(a) ⊆ past(b), so V(a) ≤ V(b); b's own slot is strictly larger.
3. (⇐) if V(b)[i] ≥ V(a)[i] = c, b's past holds P_i's first c events, including a.
4. Cost: n integers per message.

**See it in numbers** `python clocks_proofs.py vector`
```
  mismatches between a->b and V(a) < V(b): 0
  concurrent pairs 27,402; incomparable vectors 27,402
  broken receive rule (no element-wise max): 4,546 mismatches
```
Exactness in both directions: every concurrent pair is incomparable. Lamport's single integer wrongly "ordered" 11,063 of those.

**Where it shows up in practice** "CRDTs for local-first collaboration: counters, OR-Set, LWW-Register and property tests": a merge must know when writes were concurrent — the LWW tie bug lives exactly there.

### T23.3 Safety and liveness (Alpern & Schneider 1985)
**In plain words** Safety: "nothing bad happens" — a violation shows up at a finite moment and cannot be undone. Liveness: "something good eventually happens" — any finite run can still be completed. Every requirement is one of each, intersected.

**Why it is true (intuition)** Take the closure of a property: every run whose prefixes could all still succeed.
1. The closure is safety: a prefix that cannot be extended into P cannot be extended into the closure.
2. P ∪ (not closure) is liveness: any prefix either extends into P or already lies outside the closure.
3. Their intersection is P.

**See it in numbers** `python clocks_proofs.py safety`
```
  safety S = 'never more responses than requests': 3,292 good traces, 6,549 bad
  bad traces repaired by any extension up to length 3: 0
  liveness L = 'every request eventually answered': good prefixes that cannot be completed = 0
```
No bad trace was ever repaired — that is what makes S safety. No prefix was ever hopeless for L — that is liveness.

**Where it shows up in practice** "Leader election with leases and fencing tokens": fencing protects safety (a token never goes backwards); the lease timeout provides liveness (someone eventually leads).

### T23.4 Failure detection depends on the timing model
**In plain words** With known delay bounds, a timeout of 2Δ + π is a perfect detector. Without bounds, every timeout sometimes suspects a live peer. With bounds that hold only eventually, an adaptive timeout makes finitely many mistakes.

**Why it is true (intuition)** The prober only sees "no reply yet".
1. Synchronous: a live reply arrives within Δ + π + Δ, so silence means crashed.
2. Asynchronous: a live peer whose reply is delayed past T is indistinguishable, up to T, from a crashed one.
3. A deterministic prober must decide the same in both: wrong in one.
4. Partial synchrony: doubling T after each false suspicion eventually exceeds the real bound.

**See it in numbers** `python clocks_proofs.py detector`
```
        5 ms -> 17,960 (8.9800%); theory 8.9443%
      100 ms ->    194 (0.0970%); theory 0.1000%
     1000 ms ->      5 (0.0025%); theory 0.0032%
  synchronous model (one-way <= 50 ms, processing <= 5 ms): timeout 105 ms -> 0 false suspicions; max observed 104.4 ms
```
With unbounded (Pareto) delays the false rate falls as T^-1.5 and matches theory, but never reaches 0. With bounded delays 105 ms is exactly enough.

**Where it shows up in practice** "Timeouts: fail fast instead of hanging": its p99.9 timeout accepts 0.1% false timeouts — a probability, not a guarantee.

## Worked problems
**23-P1.** P1: a, b (send m1), c. P2: d, e (recv m1), f (send m2). P3: g, h, i (recv m2). Find L(i), V(i); relate c and i.
1. Lamport, P1: a=1, b=2, c=3. *Why:* IR1 ticks each event.
2. P2: d=1, e=max(1, 2)+1=3, f=4. *Why:* IR2 jumps past the stamp 2.
3. P3: g=1, h=2, i=max(2, 4)+1=5. So L(i)=5.
4. Vectors: b=(2,0,0), c=(3,0,0); e=max((0,1,0),(2,0,0))+tick=(2,2,0), f=(2,3,0); i=max((0,0,2),(2,3,0))+tick=(2,3,3). *Why:* merge before ticking.
5. Compare V(c)=(3,0,0) and V(i)=(2,3,3): 3 > 2 in slot 1, 0 < 3 in slot 2 — incomparable, so concurrent, although L(c)=3 < L(i)=5 (T23.1's converse failing).

**23-P7.** Two clocks drift ≤ 50 ppm, resynchronised every 60 s with ≤ 1 ms error. Worst gap before resync?
1. Relative drift ≤ 2 × 50 ppm = 1e-4. *Why:* they can drift in opposite directions.
2. Over 60,000 ms: 6 ms. Add the 1 ms sync error: 7 ms.
3. Consequence: events 2 ms apart on two machines can be stamped in the wrong order — lesson 6's skew. *Why it matters:* use logical clocks for causality.

## Common confusions
**Q:** L(a) < L(b) means a caused b. — **A:** 11,063 concurrent pairs had L(a) < L(b).

**Q:** "Respond within 200 ms" is liveness. — **A:** It is safety: a late reply is a finite, irreparable violation.

**Q:** A long enough timeout is always correct. — **A:** Asynchronously, 1000 ms still gave 5 false suspicions.
